# 07.03 - Domain-Driven Design

**Project:** GsmUi
**Architecture:** Domain-Driven Design (DDD) on Modular Monolith
**Framework:** Laravel 13 + Livewire 4
**Version:** 1.0.0

---

> See also: `05.05-module-boundaries.md` (module ownership, dependency matrix, communication mechanisms), `06.01-design-principles.md` (domain-driven table ownership, §1). This document specifies the *implementation contract* for mapping DDD concepts onto `app/Domains/*` — it does not re-document the module list or the dependency rules.

# Purpose

Domain-Driven Design gives GsmUi a vocabulary and structure that mirrors the business. This document is the implementation contract that binds DDD concepts (bounded context, ubiquitous language, entity, value object, aggregate, domain event, repository) to concrete PHP namespaces and files. It ensures that every developer places code in the right domain and expresses domain rules in domain terms, keeping the codebase aligned with `05.05-module-boundaries.md` and `06.01-design-principles.md`.

The contract is prescriptive: each DDD building block has a fixed home, a naming rule, and a dependency direction. Deviations require an architectural review.

---

## 1. Bounded Contexts

A **bounded context** is one business capability that owns its language and its data. GsmUi's bounded contexts are the modules listed in `05.05-module-boundaries.md`. Each context:

- Owns its tables (per `06.01-design-principles.md` §1).
- Owns its Eloquent models, services, events, jobs, policies, routes, tests.
- May NOT mutate another context's tables directly.
- Communicates outward only through services, events, query services, or shared contracts (per `05.05-module-boundaries.md` "Module Communication").

```text
Bounded Context = Domain folder under app/Domains/<Name>/
        │
        ├── Models/        (Entities + Aggregates)
        ├── ValueObjects/  (immutable concepts)
        ├── Enums/         (constrained vocabularies)
        ├── Services/      (business rules)
        ├── Repositories/  (aggregate persistence)
        ├── Events/        (facts that happened)
        └── Actions/       (use-case orchestration)
```

## 2. Ubiquitous Language

Terms used in code, database, and docs MUST match. The mapping is enforced by naming conventions:

| Domain term | Code artifact | DB artifact |
| --- | --- | --- |
| Component | `App\Domains\Components\Models\Component` | `components` |
| Theme Token | `App\Domains\Themes\ValueObjects\ThemeToken` | `theme_tokens` |
| Subscription | `App\Domains\Billing\Models\Subscription` | `subscriptions` |
| Product | `App\Domains\Marketplace\Models\Product` | `products` |
| Component Released (event) | `App\Domains\Components\Events\ComponentReleased` | `activity_log` row |

Rules:

- No synonym drift: if the domain says "Product", the class is `Product`, not `Item` or `Good`.
- ENUM values are the canonical vocabulary for constrained states (see `07.11-enums.md`).
- Translations are presentation only; the internal term stays English and stable.

## 3. Entities, Aggregates, and Value Objects

- **Entity**: a model with identity (`id`). Lives in `Models/`.
- **Aggregate**: a cluster rooted at one entity; the repository loads/saves the whole aggregate (see `07.07-repository-layer.md`).
- **Value Object**: identity-less, immutable, validated in constructor (see `07.10-value-objects.md`). Lives in `ValueObjects/`.

```php
// Entity (aggregate root)
namespace App\Domains\Billing\Models;

use Illuminate\Database\Eloquent\Model;

final class Subscription extends Model
{
    protected $table = 'subscriptions';
}
```

```php
// Value Object (no identity, immutable)
namespace App\Domains\Themes\ValueObjects;

final readonly class ThemeToken
{
    public function __construct(
        public string $name,
        public string $value,
    ) {
        if (! str_starts_with($value, '#') && ! str_starts_with($value, 'rgb')) {
            throw new \InvalidArgumentException("Invalid color token: {$value}");
        }
    }
}
```

## 4. Mapping DDD to `app/Domains/*`

The physical layout is the standard domain layout from `05.06-folder-structure.md`. The implementation contract fixes the mapping:

| DDD concept | Directory | Notes |
| --- | --- | --- |
| Bounded context | `app/Domains/<Name>/` | One per module in `05.05` |
| Entity / Aggregate root | `app/Domains/<Name>/Models/` | Eloquent models |
| Value Object | `app/Domains/<Name>/ValueObjects/` | `readonly` classes |
| Enum / vocabulary | `app/Domains/<Name>/Enums/` | Backed enums |
| Domain Service | `app/Domains/<Name>/Services/` | Business rules |
| Repository | `app/Domains/<Name>/Repositories/` | Aggregate persistence |
| Domain Event | `app/Domains/<Name>/Events/` | Extends `App\Shared\Events\DomainEvent` |
| Application Service / Action | `app/Domains/<Name>/Actions/` | Use-case orchestration |
| Cross-context contract | `app/Shared/Contracts/` | Shared interfaces only |

The Shared Kernel (`app/Shared/`) holds only generic, reusable DDD primitives (base `AggregateRoot`, `DomainEvent`, `ValueObject` traits). It contains **no** business logic and **no** module ownership (per `05.05-module-boundaries.md` "Shared Kernel" and `05.06-folder-structure.md` rules).

## 5. Anti-Corruption Layer

When a domain must consume an external provider (Stripe, Paddle, Meilisearch), the adapter lives in `app/Infrastructure/<Provider>/` and translates the provider's model into the domain's vocabulary. The domain service depends on a `Shared\Contracts` interface, never on the provider SDK directly.

```text
BillingService
     │ depends on
     ▼
App\Shared\Contracts\PaymentGateway   (interface)
     │ implemented by
     ▼
App\Infrastructure\Stripe\StripeGateway
```

## 6. Domain Events

Domain events are facts that happened in the domain. They are named in past tense, are immutable, and carry only the data needed by listeners.

### 6.1 Event Structure

```php
namespace App\Domains\Components\Events;

use App\Shared\Events\DomainEvent;
use Illuminate\Broadcasting\Channel;
use Illuminate\Broadcasting\InteractsWithSockets;
use Illuminate\Contracts\Broadcasting\ShouldBroadcast;

final class ComponentReleased extends DomainEvent
{
    use InteractsWithSockets;

    public function __construct(
        public readonly int $componentId,
        public readonly string $slug,
        public readonly int $version,
        public readonly int $releasedBy,
    ) {
        parent::__construct();
    }

    public function broadcastOn(): array
    {
        return [new Channel('components')];
    }

    public function broadcastAs(): string
    {
        return 'component.released';
    }
}
```

### 6.2 Event Naming Rules

| Rule | Pattern | Example |
| --- | --- | --- |
| Past tense | `{Entity}{PastVerb}` | `ComponentReleased` |
| No "was" prefix | `{Entity}{PastVerb}` | `ComponentReleased` (not `WasComponentReleased`) |
| No "on" prefix | `{Entity}{PastVerb}` | `ComponentPublished` (not `OnComponentPublished`) |
| State change only | Only fire when state actually changes | `ComponentPublished` (not `ComponentSaved`) |
| Cross-module events | Include minimal entity data (ID + slug) | `ComponentReleased(componentId, slug)` |

### 6.3 Event Dispatch Rules

| When | Where | Method |
| --- | --- | --- |
| After DB commit | Action or Service | `dispatchAfterCommit(new Event(...))` |
| Synchronous side-effect | Service | `event(new Event(...))` |
| Cross-module notification | Action | `dispatchAfterCommit(new Event(...))` |
| Outside transaction | Service (for external calls) | `event(new Event(...))` after transaction |

### 6.4 Event Listener Pattern

```php
namespace App\Domains\Components\Listeners;

use App\Domains\Components\Events\ComponentReleased;
use App\Domains\Search\Services\SearchIndexService;
use App\Domains\Notifications\Services\NotificationService;

final class ComponentReleasedListener
{
    public function __construct(
        private SearchIndexService $search,
        private NotificationService $notifications,
    ) {}

    public function handle(ComponentReleased $event): void
    {
        // Index the component in search
        $this->search->indexComponent($event->componentId);

        // Notify followers
        $this->notifications->notifyFollowers(
            entityType: 'component',
            entityId: $event->componentId,
            event: 'released',
        );
    }
}
```

### 6.5 Event Subscriber Pattern

```php
namespace App\Domains\Components\Listeners;

use App\Domains\Components\Events\{
    ComponentCreated,
    ComponentUpdated,
    ComponentDeleted,
    ComponentReleased,
};

final class ComponentEventSubscriber
{
    public function __construct(
        private SearchIndexService $search,
        private CacheService $cache,
    ) {}

    public function subscribe(): array
    {
        return [
            ComponentCreated::class => 'onCreated',
            ComponentUpdated::class => 'onUpdated',
            ComponentReleased::class => 'onReleased',
            ComponentDeleted::class => 'onDeleted',
        ];
    }

    public function onCreated(ComponentCreated $event): void
    {
        $this->search->indexComponent($event->componentId);
    }

    public function onUpdated(ComponentUpdated $event): void
    {
        $this->search->reindexComponent($event->componentId);
        $this->cache->forget("component:{$event->slug}");
    }

    public function onReleased(ComponentReleased $event): void
    {
        $this->cache->forget("component:{$event->slug}");
        $this->cache->forget("components:published");
    }

    public function onDeleted(ComponentDeleted $event): void
    {
        $this->search->removeComponent($event->componentId);
        $this->cache->forget("component:{$event->slug}");
        $this->cache->forget("components:published");
    }
}
```

## 7. Aggregates

An aggregate is a cluster of domain objects that can be treated as a single unit for data changes. The aggregate root is the only entity accessed from outside.

### 7.1 Aggregate Structure

```text
Component (Aggregate Root)
    ├── ComponentVersion (Entity)
    │       ├── version_number
    │       ├── changelog
    │       └── published_at
    ├── ComponentExample (Entity)
    │       ├── title
    │       ├── code_snippet
    │       └── sort_order
    ├── ComponentFile (Entity)
    │       ├── file_path
    │       ├── file_type
    │       └── size_bytes
    └── ComponentTag (Value Object)
            ├── tag_name
            └── tag_slug
```

### 7.2 Aggregate Rules

| Rule | Description | Enforcement |
| --- | --- | --- |
| One aggregate root | External code only accesses the root entity | Repository returns root only |
| Invariant boundary | All invariants enforced at the root level | Root validates before mutation |
| Reference by ID | Other aggregates reference by ID, not object | Foreign key, not relation |
| Single transaction | All changes in one aggregate in one transaction | Repository saves entire aggregate |
| Consistency | Strong consistency within aggregate boundary | Repository enforces |

### 7.3 Aggregate Root Implementation

```php
namespace App\Domains\Components\Models;

use App\Domains\Components\Events\{ComponentReleased, ComponentVersionAdded};
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\HasMany;
use Illuminate\Database\Eloquent\SoftDeletes;

final class Component extends Model
{
    use SoftDeletes;

    protected $table = 'components';

    protected $fillable = [
        'name', 'slug', 'description', 'status',
        'author_id', 'category_id', 'version',
    ];

    protected $casts = [
        'status' => \App\Domains\Components\Enums\ComponentStatus::class,
    ];

    // --- Relationships (read side) ---

    public function versions(): HasMany
    {
        return $this->hasMany(ComponentVersion::class);
    }

    public function examples(): HasMany
    {
        return $this->hasMany(ComponentExample::class);
    }

    // --- Aggregate behavior (write side) ---

    public function release(int $userId): void
    {
        if ($this->status !== ComponentStatus::Draft) {
            throw new \App\Domains\Components\Exceptions\ComponentAlreadyPublishedException(
                $this->slug
            );
        }

        $this->update([
            'status' => ComponentStatus::Published,
            'version' => $this->version + 1,
            'published_at' => now(),
        ]);

        event(new ComponentReleased(
            componentId: $this->id,
            slug: $this->slug,
            version: $this->version,
            releasedBy: $userId,
        ));
    }

    public function addVersion(string $changelog): void
    {
        $this->versions()->create([
            'version_number' => $this->version + 1,
            'changelog' => $changelog,
            'published_at' => now(),
        ]);

        $this->increment('version');

        event(new ComponentVersionAdded(
            componentId: $this->id,
            version: $this->version,
        ));
    }
}
```

### 7.4 Aggregate Loading Strategy

| Strategy | When to use | Implementation |
| --- | --- | --- |
| Eager load all | Small aggregates (< 5 relations) | `with(['versions', 'examples', 'files'])` |
| Lazy load (on demand) | Large aggregates with rarely-used relations | `->relation` access |
| Read model projection | Read-heavy views (dashboards, lists) | Dedicated `ComponentReadModel` |
| Partial load | Only need specific fields | `select(['id', 'name', 'slug'])` |

## 8. Domain Services

A domain service encapsulates business logic that doesn't naturally belong to a single entity or value object. It operates on multiple entities or coordinates between aggregates.

### 8.1 Domain Service vs Application Service

| Aspect | Domain Service | Application Service |
| --- | --- |--- |
| Purpose | Business rule evaluation | Use-case orchestration |
| Layer | Domain | Application |
| Transaction | Does NOT own transaction | Owns transaction boundary |
| Event dispatch | Does NOT dispatch events | Dispatches events after commit |
| Example | `PricingService::calculateDiscount()` | `CreateOrderAction::run()` |
| Dependencies | Other domain services, repositories | Domain services, actions |

### 8.2 Domain Service Pattern

```php
namespace App\Domains\Billing\Services;

use App\Domains\Billing\Models\{Subscription, Invoice};
use App\Domains\Billing\ValueObjects\{Money, TaxRate};

final class PricingService
{
    public function __construct(
        private readonly TaxService $tax,
    ) {}

    /**
     * Calculate the total price for a subscription plan
     * considering discounts, taxes, and billing period.
     */
    public function calculateTotal(
        Money $basePrice,
        float $discountPercent,
        string $country,
    ): Money {
        $discounted = $basePrice->multiply(1 - $discountPercent / 100);
        $tax = $this->tax->calculate($discounted, $country);

        return $discounted->add($tax);
    }

    /**
     * Determine the prorated amount for a mid-cycle plan change.
     */
    public function prorate(
        Subscription $subscription,
        Money $newPlanPrice,
    ): Money {
        $daysRemaining = $subscription->ends_at->diffInDays(now());
        $daysInPeriod = $subscription->started_at->diffInDays($subscription->ends_at);

        return $newPlanPrice->multiply($daysRemaining / $daysInPeriod);
    }
}
```

## 9. Domain Exceptions

Domain exceptions represent business rule violations. They carry a user-safe message and are thrown from services and actions.

### 9.1 Exception Naming Rules

| Rule | Pattern | Example |
| --- | --- | --- |
| Descriptive | `{Entity}{Violation}Exception` | `ComponentAlreadyExistsException` |
| Past tense (state) | `{Entity}{State}Exception` | `ComponentAlreadyPublishedException` |
| No generic names | Avoid `DomainException` alone | Use specific subtypes |
| User message | Constructor accepts user-friendly message | `new ComponentAlreadyExistsException($slug)` |

### 9.2 Exception Hierarchy

```text
App\Shared\Exceptions\DomainException (abstract base)
├── ComponentAlreadyExistsException
├── ComponentNotPublishedException
├── ComponentAlreadyPublishedException
├── ThemeNotPublishedException
├── ThemeAlreadyPublishedException
├── SubscriptionRequiredException
├── SubscriptionExpiredException
├── LicenseExpiredException
├── InsufficientBalanceException
├── PaymentFailedException
└── MarketplaceProductNotFoundException
```

### 9.3 Exception Implementation

```php
namespace App\Domains\Components\Exceptions;

use App\Shared\Exceptions\DomainException;

final class ComponentAlreadyExistsException extends DomainException
{
    public function __construct(string $slug)
    {
        parent::__construct(
            message: "A component with slug '{$slug}' already exists.",
            code: 409,
            previous: null,
        );
    }

    public function render($request)
    {
        if ($request->expectsJson()) {
            return response()->json([
                'type' => 'https://gsmui.dev/errors/component-exists',
                'title' => 'Component Already Exists',
                'status' => 409,
                'detail' => $this->getMessage(),
            ], 409);
        }

        return back()->withErrors(['slug' => $this->getMessage()]);
    }
}
```

## 10. Repositories and Domain Boundaries

### 10.1 Repository Responsibilities

| Responsibility | Description |
| --- | --- |
| Aggregate persistence | Load and save entire aggregates |
| Query isolation | Encapsulate all query logic |
| Eager loading | Prevent N+1 by loading relations |
| Criteria application | Apply reusable query constraints |
| Read/write separation | Separate read queries from write operations |

### 10.2 Repository Contract Pattern

```php
namespace App\Domains\Components\Repositories\Contracts;

use App\Domains\Components\Models\Component;
use Illuminate\Contracts\Pagination\LengthAwarePaginator;
use Illuminate\Database\Eloquent\Collection;

interface ComponentRepositoryInterface
{
    // Read operations
    public function find(int $id): ?Component;
    public function findOrFail(int $id): Component;
    public function findBySlug(string $slug): ?Component;
    public function all(): Collection;
    public function paginatePublished(int $perPage = 15): LengthAwarePaginator;
    public function search(string $query): Collection;
    public function slugExists(string $slug): bool;
    public function countByStatus(ComponentStatus $status): int;

    // Write operations
    public function create(array $attributes): Component;
    public function update(Component $component, array $attributes): Component;
    public function delete(Component $component): void;
    public function restore(Component $component): void;
}
```

### 10.3 Forbidden Repository Patterns

| Anti-pattern | Why | Correct approach |
| --- | --- | --- |
| Business logic in repository | Repositories are persistence adapters | Move logic to service |
| Event dispatch in repository | Events are dispatched after commit | Dispatch in action/service |
| Transaction in repository | Transactions are managed by action/service | Remove transaction |
| Validation in repository | Validation is a service concern | Move to service/DTO |
| Direct model query from Livewire | Violates dependency rules | Use action/service |

## 11. Cross-Context Communication

### 11.1 Communication Mechanisms

```text
┌─────────────────────────────────────────────────────────────┐
│              Cross-Context Communication                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. Service Contract (synchronous)                          │
│     Components → Billing (check subscription status)        │
│     Components → Users (get author information)             │
│                                                             │
│  2. Domain Event (asynchronous)                             │
│     Components → Search (re-index after publish)            │
│     Billing → Notifications (send invoice email)            │
│                                                             │
│  3. Query Service (read-only projection)                    │
│     Components → Marketplace (component data for listing)   │
│     Themes → CMS (theme data for content pages)             │
│                                                             │
│  4. Shared Contract (interface in Shared/)                  │
│     ComponentServiceContract ← used by Billing, Search      │
│     UserServiceContract ← used by all contexts              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 11.2 Event-Based Communication

```php
// In Components domain — fire event
$component->release($userId);
// Event: ComponentReleased dispatched

// In Search domain — listen and react
class ReindexComponentListener
{

    }
}

// In Notifications domain — listen and react
class NotifyFollowersListener
{
    public function handle(ComponentReleased $event): void
    {
        $this->notify->notifyFollowers('component', $event->componentId);
    }
}
```

### 11.3 Service Contract Communication

```php
            throw new ComponentNotFoundException($data->componentId);
```

## 12. Anti-Corruption Layer (Detailed)

### 12.1 When to Use ACL

| Situation | ACL needed | Example |
| --- |--- | --- |
| External API (Stripe, Paddle) | Yes | Payment gateway adapter |
| Internal third-party package | Yes | Search engine client |
| Another domain's repository | No (use contract) | Components → Users |
| Database driver | No (Laravel handles) | MySQL, PostgreSQL |
| File storage driver | No (Laravel handles) | S3, local |

### 12.2 ACL Pattern

```php
// Interface (domain vocabulary)
namespace App\Shared\Contracts;

interface PaymentGatewayInterface
{
    public function charge(Money $amount, string $customerId): PaymentResult;
    public function refund(string $chargeId, ?Money $amount = null): RefundResult;
    public function createCustomer(string $email, string $name): string;
}

// Adapter (translates to provider SDK)
namespace App\Infrastructure\Stripe;

use App\Shared\Contracts\PaymentGatewayInterface;

final class StripeGateway implements PaymentGatewayInterface
{
    public function __construct(
        private StripeClient $stripe,
    ) {}

    public function charge(Money $amount, string $customerId): PaymentResult
    {
        $result = $this->stripe->paymentIntents->create([
            'amount' => $amount->toCents(),
            'currency' => $amount->currency(),
            'customer' => $customerId,
        ]);

        return new PaymentResult(
            transactionId: $result->id,
            status: $result->status,
            amount: $amount,
        );
    }
}
```

## 13. Ubiquitous Language Enforcement

### 13.1 Language Mapping Rules

| Rule | Enforcement | Example |
| --- |--- |--- |
| No synonyms | Class names match domain terms exactly | `Component`, not `Item` or `Widget` |
| No abbreviations | Full words in class/method names | `ComponentService`, not `CompSvc` |
| Past tense events | Events named as facts that happened | `ComponentReleased` |
| Consistent verbs | Use same verb for same operation | `publish()` everywhere, not `activate()` or `launch()` |
| DB column names | Match domain terminology in snake_case | `published_at`, not `pub_date` or `release_time` |

### 13.2 Language Consistency Audit

```php
// Correct: consistent language
class ComponentService {
    public function publish(Component $component): void { /* ... */ }
    public function unpublish(Component $component): void { /* ... */ }
    public function findBySlug(string $slug): ?Component { /* ... */ }
}

// Wrong: mixed language
class ComponentService {
    public function activate(Component $component): void { /* ... */ }
    public function unpublish(Component $component): void { /* ... */ }
    public function getBySlug(string $slug): ?Component { /* ... */ }
}
```

## 14. Domain Modeling Patterns

### 14.1 Entity vs Value Object Decision

| Characteristic | Entity | Value Object |
| --- | ---| --- |
| Has identity (ID) | Yes | No |
| Mutable | Yes (state changes) | No (immutable) |
| Equality based on | ID | All properties |
| Persistence | Own database row | Embedded or serialized |
| Example | `Component` (has ID, status changes) | `ThemeToken` (name + value, immutable) |

### 14.2 Value Object Implementation

```php
namespace App\Domains\Themes\ValueObjects;

final readonly class ThemeToken
{
    public function __construct(
        public string $name,
        public string $category,
        public string $value,
        public string $type,
    ) {
        if ($this->type === 'color' && ! $this->isValidColor($value)) {
            throw new \InvalidArgumentException("Invalid color value: {$value}");
        }

        if ($this->type === 'spacing' && ! preg_match('/^\d+(\.\d+)?(rem|px|em)$/', $value)) {
            throw new \InvalidArgumentException("Invalid spacing value: {$value}");
        }
    }

    public static function color(string $name, string $category, string $value): self
    {
        return new self($name, $category, $value, 'color');
    }

    public static function spacing(string $name, string $category, string $value): self
    {
        return new self($name, $category, $value, 'spacing');
    }

    public function toArray(): array
    {
        return [
            'name' => $this->name,
            'category' => $this->category,
            'value' => $this->value,
            'type' => $this->type,
        ];
    }

    private function isValidColor(string $value): bool
    {
        return preg_match('/^#([0-9a-f]{3}|[0-9a-f]{6})$/i', $value)
            || preg_match('/^rgb\(\d+,\s*\d+,\s*\d+\)$/', $value)
            || preg_match('/^rgba\(\d+,\s*\d+,\s*\d+,\s*[\d.]+\)$/', $value);
    }
}
```

## 15. Domain Layer Testing Strategy

### 15.1 Test Categories for DDD Artifacts

| Artifact | Test type | What to test |
| --- |--- |---|
| Entity | Unit test | State transitions, business rules |
| Value Object | Unit test | Construction validation, immutability |
| Domain Service | Unit test | Business logic, edge cases |
| Domain Event | Unit test | Event data, serialization |
| Repository | Feature test | Query correctness, eager loading |
| Aggregate | Unit test | Invariant enforcement |

### 15.2 Entity Test Pattern

```php
namespace Tests\Unit\Domains\Components;

use App\Domains\Components\Models\Component;
use App\Domains\Components\Enums\ComponentStatus;
use PHPUnit\Framework\TestCase;

class ComponentTest extends TestCase
{
    /** @test */
    public function release_transitions_from_draft_to_published(): void
    {
        $component = Component::factory()->draft()->create();

        $component->release(userId: 1);

        $this->assertEquals(ComponentStatus::Published, $component->status);
        $this->assertNotNull($component->published_at);
    }

    /** @test */
    public function release_throws_when_already_published(): void
    {
        $component = Component::factory()->published()->create();

        $this->expectException(ComponentAlreadyPublishedException::class);

        $component->release(userId: 1);
    }
```

## 16. DDD Anti-Patterns to Avoid

| Anti-pattern | Description | Correct approach |
| --- | --- | --- |
| Anemic domain model | Entities with only getters/setters, no behavior | Put business logic in entity methods |
| Domain logic in controllers | Business rules in controller methods | Move to service/action layer |
| Database-driven design | Starting with tables, not domain concepts | Start with bounded contexts |
| God aggregate | One aggregate with too many entities | Split into smaller aggregates |
| Cross-aggregate references | Direct object references between aggregates | Reference by ID |
| Event storms everywhere | Firing events for every minor change | Only fire for meaningful state changes |
| Shared database | Multiple domains owning the same table | Each domain owns its tables |
| Service chaining | Service A calls Service B calls Service C | Use events for cross-domain communication |

## 17. DDD Refactoring Guidelines

### 17.1 When to Refactor

| Trigger | Action |
| --- |---|
| New business capability | Create new bounded context |
| Two contexts sharing a table | Split table ownership |
| Business rule duplicated in services | Move to domain entity or service |
| Cross-context coupling increasing | Introduce event-based communication |
| Aggregate growing too large | Split into smaller aggregates |
| Repository method growing complex | Extract query service |

### 17.2 Migration Path

```text
Monolith (no DDD)
    │
    ├── Step 1: Identify bounded contexts (group by business capability)
    ├── Step 2: Create app/Domains/<Name>/ directories
    ├── Step 3: Move models to respective domains
    ├── Step 4: Extract services from controllers
    ├── Step 5: Add repository interfaces
    ├── Step 6: Introduce DTOs for cross-layer data
    ├── Step 7: Add domain events for cross-context communication
    └── Step 8: Enforce dependency rules via architecture tests
```

## 19. Domain Event Storming

### 19.1 Event Storming Workshop Format

Event storming is a collaborative technique for discovering domain events, commands, aggregates, and bounded contexts. The GsmUi team uses this format for new module design.

```text
Step 1: Brainstorm Domain Events (orange sticky notes)
    │
    ├── "ComponentCreated"
    ├── "ComponentPublished"
    ├── "ThemeDeployed"
    ├── "SubscriptionActivated"
    ├── "PaymentProcessed"
    ├── "OrderCompleted"
    ├── "LicenseGenerated"
    └── "SearchIndexUpdated"
    │
    ▼
Step 2: Identify Commands (blue sticky notes)
    │
    ├── "CreateComponent" → ComponentCreated
    ├── "PublishComponent" → ComponentPublished
    ├── "DeployTheme" → ThemeDeployed
    ├── "ActivateSubscription" → SubscriptionActivated
    ├── "ProcessPayment" → PaymentProcessed
    ├── "CompleteOrder" → OrderCompleted
    └── "GenerateLicense" → LicenseGenerated
    │
    ▼
Step 3: Identify Aggregates (yellow sticky notes)
    │
    ├── Component (handles Create/Publish commands)
    ├── Theme (handles Deploy command)
    ├── Subscription (handles Activate command)
    ├── Payment (handles Process command)
    ├── Order (handles Complete command)
    └── License (handles Generate command)
    │
    ▼
Step 4: Identify Bounded Contexts (big pink areas)
    │
    ├── Components Context: Component, ComponentVersion, ComponentExample
    ├── Themes Context: Theme, ThemeToken, ThemeVariant
    ├── Billing Context: Subscription, Plan, Invoice, Payment
    ├── Marketplace Context: Product, Order, OrderItem, License
    └── Search Context: SearchIndex, SearchQuery
    │
    ▼
Step 5: Identify Read Models (green sticky notes)
    │
    ├── ComponentList (for browse page)
    ├── ComponentDetail (for detail page)
    ├── ThemeGallery (for theme listing)
    ├── SubscriptionDashboard (for billing page)
    └── MarketplaceGrid (for marketplace page)
```

### 19.2 Event Storm to Code Mapping

| Event Storm artifact | Code artifact | Location |
| --- | --- | --- |
| Domain Event (orange) | `{Entity}{PastVerb}.php` | `app/Domains/{Context}/Events/` |
| Command (blue) | `{Verb}{Entity}Action.php` | `app/Domains/{Context}/Actions/` |
| Aggregate (yellow) | `{Entity}.php` | `app/Domains/{Context}/Models/` |
| Bounded Context (pink) | `app/Domains/{Context}/` | Domain directory |
| Read Model (green) | `{Entity}Resource.php` or `{Entity}ReadModel.php` | `Resources/` or `Models/` |
| Policy (red) | `{Entity}Policy.php` | `app/Domains/{Context}/Policies/` |
| External System (lilac) | Adapter in `app/Infrastructure/{Provider}/` | Infrastructure layer |

### 19.3 Event Storming Checklist

| Check | Description |
| --- | --- |
| All events are past tense | `ComponentCreated`, not `CreateComponent` |
| All events are domain-specific | No technical events (`DatabaseSaved`) |
| Each event has a clear producer | One command or trigger per event |
| Each event has at least one consumer | At least one listener/job reacts to it |
| No orphan events | Every event is produced somewhere |
| No orphan commands | Every command has a handler |
| Aggregates enforce invariants | Business rules validated at aggregate root |
| Bounded contexts are independent | No direct database access across contexts |

```php
namespace App\Domains\Components\Models;

use App\Domains\Components\Enums\ComponentStatus;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\{BelongsTo, HasMany};

final class Component extends Model
{
    protected $table = 'components';

    protected $fillable = [
        'name', 'slug', 'description', 'status',
        'author_id', 'category_id', 'version',
        'is_featured', 'published_at',
    ];

    protected $casts = [
        'status' => ComponentStatus::class,
        'is_featured' => 'boolean',
        'published_at' => 'datetime',
    ];

    // --- Relationships ---

    public function author(): BelongsTo
    {
        return $this->belongsTo(User::class, 'author_id');
    }

    public function category(): BelongsTo
    {
        return $this->belongsTo(Category::class);
    }

    public function versions(): HasMany
    {
        return $this->hasMany(ComponentVersion::class);
    }

    public function examples(): HasMany
    {
        return $this->hasMany(ComponentExample::class);
    }

    public function files(): HasMany
    {
        return $this->hasMany(ComponentFile::class);
    }

    // --- Business Rules ---

    public function isPublished(): bool
    {
        return $this->status === ComponentStatus::Published;
    }

    public function isDraft(): bool
    {
        return $this->status === ComponentStatus::Draft;
    }

    public function latestVersion(): int
    {
        return $this->version;
    }

    public function canBePublished(): bool
    {
        return $this->status === ComponentStatus::Draft
            && $this->versions()->count() > 0;
    }

    public function canBeDeleted(): bool
    {
        return $this->status === ComponentStatus::Draft
            || $this->status === ComponentStatus::Archived;
    }
}
```

### 20.2 Value Object Pattern

```php
namespace App\Domains\Billing\ValueObjects;

final readonly class Money
{
    public function __construct(
        public int $amount,
        public string $currency,
    ) {
        if ($amount < 0) {
            throw new \InvalidArgumentException('Amount cannot be negative');
        }

        if (strlen($currency) !== 3) {
            throw new \InvalidArgumentException('Currency must be 3-letter ISO code');
        }
    }

    public static function usd(int $cents): self
    {
        return new self($cents, 'USD');
    }

    public static function eur(int $cents): self
    {
        return new self($cents, 'EUR');
    }

    public function add(self $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new \InvalidArgumentException('Cannot add different currencies');
        }

        return new self($this->amount + $other->amount, $this->currency);
    }

    public function multiply(float $factor): self
    {
        return new self((int) round($this->amount * $factor), $this->currency);
    }

    public function format(): string
    {
        $formatted = number_format($this->amount / 100, 2);

        return match ($this->currency) {
            'USD' => "\${$formatted}",
            'EUR' => "€{$formatted}",
            'GBP' => "£{$formatted}",
            default => "{$formatted} {$this->currency}",
        };
    }

    public function toCents(): int
    {
        return $this->amount;
    }

    public function toArray(): array
    {
        return [
            'amount' => $this->amount,
            'currency' => $this->currency,
            'formatted' => $this->format(),
        ];
    }
}
```

### 20.4 Domain Service Pattern

```php
namespace App\Domains\Billing\Services;

use App\Domains\Billing\ValueObjects\Money;

final readonly class PricingService
{
    public function calculateDiscount(
        Money $basePrice,
        float $discountPercent,
    ): Money {
        if ($discountPercent < 0 || $discountPercent > 100) {
            throw new \InvalidArgumentException('Discount must be between 0 and 100');
        }

        return $basePrice->multiply(1 - $discountPercent / 100);
    }

    public function calculateTax(
        Money $amount,
        float $taxRate,
    ): Money {
        return $amount->multiply($taxRate);
    }

    public function prorateAmount(
        Money $fullPrice,
        int $daysRemaining,
        int $daysInPeriod,
    ): Money {
        return $fullPrice->multiply($daysRemaining / $daysInPeriod);
    }
}
```

## 26. Domain Model Invariants Reference

### 26.1 Invariant Definition Pattern

```php
// Invariant enforced at entity level
final class Component extends Model
{
    public function release(int $userId): void
    {
        // Invariant: must be draft to publish
        if ($this->status !== ComponentStatus::Draft) {
            throw new ComponentAlreadyPublishedException($this->slug);
        }

        // Invariant: must have at least one version
        if ($this->versions()->count() === 0) {
            throw new ComponentWithoutVersionsException($this->slug);
        }

        $this->update([
            'status' => ComponentStatus::Published,
            'published_at' => now(),
        ]);
    }
}

// Invariant enforced at service level
final class ComponentService extends AbstractService
{
    public function create(ComponentData $data): Component
    {
        // Invariant: slug must be unique
        if ($this->components->slugExists($data->slug)) {
            throw new ComponentAlreadyExistsException($data->slug);
        }

        return $this->components->create($data->toArray());
    }
}

// Invariant enforced at repository level
final class ComponentRepository extends BaseRepository
{
    public function create(array $attributes): Component
    {
        // Invariant: slug must be lowercase
        $attributes['slug'] = strtolower($attributes['slug']);

        return $this->query()->create($attributes);
    }
}
```

## 29. DDD Anti-Patterns and Fixes

| Anti-Pattern | Symptom | Fix |
|---|---|---|
| Anemic domain model | Services set public properties directly on entities | Move behavior into entity methods; make properties private |
| God aggregate | Aggregate with 20+ methods touching 10+ tables | Split into smaller aggregates; use domain events for cross-aggregate coordination |
| Transaction script | Service is a single 200-line method | Extract value objects, domain services, and entity behavior |
| Shared database | Two modules query the same table | Define a repository interface per module; enforce ownership |
| Domain events everywhere | Every tiny action fires an event | Limit events to cross-module boundaries and audit-critical actions |
| Value object abuse | Creating a value object for a single string | Use a value object only when you need validation, comparison, or multiple properties |
| Repository per model | One repository for every Eloquent model | One repository per aggregate root; child entities go through the root |
| Missing ubiquitous language | Code uses `item_id` but the domain calls it "component" | Rename to match the business term |

### 29.1 Anti-Pattern Detection Checklist

```
Does the entity have public mutable properties?
  → YES → Anemic domain model — encapsulate
Does the aggregate touch more than 3 tables?
  → YES → Split into smaller aggregates
Does the service layer contain business rules?
  → YES → Move rules into domain entities or value objects
Do two repositories query the same table?
  → YES → Shared database — define per-module ownership
Does every method fire a domain event?
  → YES → Over-dispatching — limit to cross-module boundaries
```

## 30. Aggregate Design Cheat Sheet

### 30.1 Design Questions

Before finalizing an aggregate, ask:

1. **What is the consistency boundary?** Which invariants must be enforced in a single transaction?
2. **What is the loading strategy?** Will you always need the full aggregate, or can you lazy-load children?
3. **What is the write pattern?** Is the aggregate mostly-created-then-rarely-modified, or frequently-updated?
4. **What is the collision risk?** How often will two users modify the same aggregate simultaneously?

### 30.2 Aggregate Size Guidelines

| Size | Tables | Invariants | Transaction cost | Example |
|---|---|---|---|---|
| Small | 1–2 | Simple | Low | `User` + `UserProfile` |
| Medium | 2–4 | Moderate | Medium | `Order` + `OrderItem` + `ShippingAddress` |
| Large | 4–6 | Complex | High | `Product` + `Variant` + `Inventory` + `Price` |
| Too large | 6+ | Unmanageable | Unacceptable | Split into multiple aggregates |

### 30.3 Cross-Aggregate Communication

```
┌─────────────────┐       Domain Event       ┌─────────────────┐
│  Order Aggregate │ ───────────────────────▶ │ Inventory Agg.   │
│                  │                          │                  │
│  createOrder()   │  OrderCreated            │  reserveStock()  │
│  → fires event   │  (async listener)        │  → adjusts qty   │
└─────────────────┘                          └─────────────────┘
         │
         │  Domain Event
         ▼
┌─────────────────┐
│  Billing Agg.    │
│                  │
│  generateInvoice()│
│  → creates invoice│
└─────────────────┘
```

Rules:
- Aggregates never hold direct references to each other
- Use IDs for cross-aggregate references
- Use domain events for eventual consistency
- Accept that two aggregates may be momentarily inconsistent

## 31. Bounded Context Mapping Patterns

### 31.1 Mapping Patterns Reference

| Pattern | When to use | GsmUi example |
|---|---|---|
| **Shared Kernel** | Two contexts share a small, stable model | `User` identity shared between Auth and Billing |
| **Customer/Supplier** | One context provides; another consumes | Search consumes Components (supplier/customer) |
| **Conformist** | Consumer must adapt to provider's model | Third-party payment gateway API |
| **Anti-Corruption Layer** | Translate foreign model into local domain | Stripe/Paddle adapter translating external events |
| **Open Host Service** | Provider offers a well-defined API | Module API routes consumed by other modules |
| **Published Language** | Shared data format between contexts | JSON-LD for search index, ActivityPub for social |
| **Separate Ways** | No integration needed | Admin dashboard (standalone) |

### 31.2 ACL (Anti-Corruption Layer) Example

```php
namespace App\Domains\Billing\Infrastructure\Gateways;

use App\Domains\Billing\Domain\ValueObjects\Money;
use App\Domains\Billing\Domain\ValueObjects\Currency;
use App\Domains\Billing\Domain\Events\PaymentReceived;

final class StripeGatewayAdapter
{
    public function __construct(
        private \Stripe\StripeClient $stripe,
    ) {}

    /**
     * Translate Stripe webhook event into domain event.
     */
    public function translateWebhook(array $payload): ?PaymentReceived
    {
        $type = $payload['type'] ?? null;

        if ($type !== 'payment_intent.succeeded') {
            return null;
        }

        $intent = $payload['data']['object'];

        return new PaymentReceived(
            transactionId: $intent['id'],
            amount: new Money(
                amount: $intent['amount'],
                currency: Currency::from($intent['currency']),
            ),
            customerId: $intent['metadata']['customer_id'] ?? null,
            occurredAt: Carbon::createFromTimestamp($intent['created']),
        );
    }
}
```
