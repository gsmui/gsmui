# 07.05 - Folder Structure

**Project:** GsmUi
**Architecture:** Modular Monolith (implementation contract)
**Framework:** Laravel 13 + Livewire 4
**Version:** 1.0.0

---

> See also: `05.06-folder-structure.md` (full physical directory layout, naming conventions, dependency rules). This document is the *implementation contract*: the concrete tree with a one-line purpose per directory, expressed for builders rather than re-stating rationale.

# Purpose

This document is the authoritative on-disk layout implementers use to place every new file. It is the implementation-level counterpart to `05.06-folder-structure.md`: where that document explains *why* the structure looks the way it does, this document states *exactly what goes where*. Every directory below has a single, non-overlapping responsibility, and the standard domain layout recurs under each `app/Domains/<Name>/`.

Adherence is mandatory — misplaced files break the module ownership rules in `05.05-module-boundaries.md` and the dependency rules in `05.06-folder-structure.md`.

---

## 1. Root Tree

```text
gsmui/
├── app/                  Laravel application code (domains, core, shared, infra)
├── src/                  Reusable package code / published stubs (per gsmui-pro layout)
├── bootstrap/            App bootstrap (app.php, cache)
├── config/               Configuration files (per-domain config/*.php)
├── database/             Migrations, factories, seeders, schema
├── public/               Web root (images, fonts, downloads, index.php)
├── resources/            Frontend assets, Blade views, emails, layouts
├── routes/               Route files (web, api, console, channels, domains/*)
├── storage/              Logs, framework cache, media, exports, imports
├── tests/                Test suites (Unit, Feature, Architecture, Browser)
├── artisan               Artisan CLI entrypoint
├── composer.json         PHP dependencies and autoload
└── vite.config.js        Frontend build config
```

| Directory | Purpose |
| --- | --- |
| `app/` | All backend PHP: domains, core bootstrap, shared kernel, infrastructure |
| `src/` | Self-contained package/stub code shipped or consumed by the app |
| `bootstrap/` | Framework bootstrap and cached config/routes/services |
| `config/` | Declarative configuration (one file per domain where applicable) |
| `database/` | Schema migrations, model factories, seeders |
| `public/` | The only web-served directory; static assets and entry script |
| `resources/` | Source frontend assets and Blade templates (not directly web-served) |
| `routes/` | HTTP/API/console/channel route definitions |
| `storage/` | Writable runtime data: logs, cache, uploaded media, exports |
| `tests/` | Automated test suites across all layers |

## 2. `app/` Tree

```text
app/
├── Core/                 Application-wide bootstrap (Kernel, Exceptions, Middleware, Routing)
├── Domains/              Business modules (one folder per bounded context)
├── Shared/               Generic reusable primitives (Contracts, DTOs, Enums, Exceptions, Traits)
├── Infrastructure/       Framework/provider implementations (Cache, Payments, Search, Storage)
├── Providers/            App-level service providers (App, Auth, Event, Route, Domain)
├── Console/              Artisan commands and schedules
└── Support/              App-wide helpers and macros
```

| Directory | Purpose |
| --- | --- |
| `app/Core/` | HTTP/Console kernels, global middleware, exception handler, route registration |
| `app/Domains/` | Per-business-capability modules (see §3) |
| `app/Shared/` | Cross-cutting, business-agnostic primitives; no module ownership |
| `app/Infrastructure/` | Concrete implementations of external/provider integrations |
| `app/Providers/` | Top-level service providers that boot the app and discover domains |
| `app/Console/` | Artisan commands and scheduled tasks |
| `app/Support/` | Small framework-agnostic helpers and macros |

## 3. Standard Domain Layout (`app/Domains/<Name>/`)

Every domain folder follows this identical structure (recurs for each module):

```text
app/Domains/Components/
├── Module.php            Module manifest (see 07.04-module-architecture.md)
├── ComponentsServiceProvider.php
├── Actions/              Single-use-case orchestration (transaction + events)
├── Services/             Business logic (see 07.06-service-layer.md)
├── Repositories/         Persistence (see 07.07-repository-layer.md)
├── Models/               Eloquent entities / aggregates
├── DTOs/                 Data transfer objects (see 07.09-dto-layer.md)
├── ValueObjects/        Immutable domain concepts (see 07.10-value-objects.md)
├── Enums/                Backed enums (see 07.11-enums.md)
├── Events/               Domain events (see 07.12-events.md)
├── Listeners/            Event handlers (see 07.13-listeners.md)
├── Jobs/                 Queue jobs (see 07.14-jobs.md)
├── Policies/             Authorization policies (see 07.15-policies.md)
├── Rules/                Custom validation rules (see 07.17-validation.md)
├── Exceptions/           Domain-specific exceptions
├── Http/                 Controllers + Form Requests (see 07.18-form-requests.md)
├── Livewire/             Livewire components (see 07.19-livewire-architecture.md)
├── Mail/                 Mailable classes (see 07.28-mail.md)
├── Notifications/        Notification classes (see 07.27-notifications.md)
├── Observers/            Model observers (see 07.47-observers.md)
├── Contracts/            Public interfaces consumed by other modules
├── Resources/            API/JSON resource transformers
├── Views/                Blade views owned by the module
├── Database/             Domain migrations, factories, seeders
└── Tests/                Module-local tests
```

| Subdirectory | Purpose |
| --- | --- |
| `Actions/` | One class per use case; owns transaction + event dispatch |
| `Services/` | Reusable business logic invoked by actions/controllers/jobs |
| `Repositories/` | Only layer that touches Eloquent/models for persistence |
| `Models/` | Eloquent entities and aggregate roots |
| `DTOs/` | Immutable input/output carriers between layers |
| `ValueObjects/` | Identity-less validated domain concepts |
| `Enums/` | Constrained vocabularies mapped to DB columns |
| `Events/` | Facts that occurred; consumed by listeners |
| `Listeners/` | React to events; may enqueue jobs |
| `Jobs/` | Async/queued work |
| `Policies/` | Resource authorization |
| `Http/` | Thin controllers + Form Requests only |
| `Livewire/` | Stateful UI components (delegate to actions/services) |
| `Contracts/` | The module's public API surface |

## 18. File Placement Rules

### 18.1 Decision Tree

```text
New file to create
    │
    ├── Is it a business capability? → app/Domains/<Name>/
    │       ├── Model → Models/
    │       ├── Business logic → Services/
    │       ├── Use case → Actions/
    │       ├── Data carrier → DTOs/
    │       ├── Immutable concept → ValueObjects/
    │       ├── State vocabulary → Enums/
    │       ├── Something happened → Events/
    │       ├── React to event → Listeners/
    │       ├── Async work → Jobs/
    │       ├── Authorization → Policies/
    │       ├── Validation → Rules/
    │       ├── HTTP endpoint → Http/Controllers/
    │       ├── Form validation → Http/Requests/
    │       ├── Livewire UI → Livewire/
    │       ├── Email template → Mail/
    │       ├── Notification → Notifications/
    │       ├── Model observer → Observers/
    │       ├── Public interface → Contracts/
    │       ├── API resource → Resources/
    │       ├── Blade view → Views/
    │       ├── Database change → Database/Migrations/
    │       ├── Test → Tests/
    │       └── Documentation → README.md
    │
    ├── Is it cross-cutting? → app/Shared/
    │       ├── Interface → Contracts/
    │       ├── Base class → Support/
    │       ├── Exception → Exceptions/
    │       ├── Event → Events/
    │       ├── Enum → Enums/
    │       └── Trait → Traits/
    │
    ├── Is it an external adapter? → app/Infrastructure/<Provider>/
    │       ├── Payment gateway → Stripe/ or Paddle/
    │       ├── Search engine → Meilisearch/ or Algolia/
    │       ├── File storage → S3/
    │       └── Email driver → Mail/
    │
    ├── Is it a provider? → app/Providers/
    │       └── Service provider for registration
    │
    ├── Is it a command? → app/Console/Commands/
    │       └── Artisan command
    │
    ├── Is it a route? → routes/
    │       └── Route definition
    │
    ├── Is it a migration? → database/migrations/{domain}/
    │       └── Schema change
    │
    ├── Is it a view? → resources/views/{domain}/
    │       └── Blade template
    │
    ├── Is it a config? → config/
    │       └── Configuration file
    │
    └── Is it a test? → tests/{Unit|Feature|Integration|Architecture|Browser}/
            └── Test file
```

## 25. Folder Structure Anti-Patterns

### 25.1 Common Mistakes

| Mistake | Symptom | Fix |
| --- |---| --- |
| Flat app/ directory | All classes in `app/` root | Organize into Domains, Core, Shared |
| God module | One module with > 100 files | Split into smaller modules |
| Shared models | Models in `app/Models/` | Move to `app/Domains/{Name}/Models/` |
| Shared services | Services in `app/Services/` | Move to `app/Domains/{Name}/Services/` |
| Mixed concerns | Controller with business logic | Extract to Action/Service |
| Missing contracts | Direct class references cross-module | Add Contracts/ interfaces |
| No tests directory | Missing `Tests/` in module | Add module-scoped tests |
| Config in wrong place | Config in `config/app.php` | Move to `config/{module}.php` |

### 25.2 Directory Audit Commands

```bash
# Find files in wrong location
find app/ -maxdepth 2 -name "*.php" -not -path "app/Core/*" -not -path "app/Domains/*" -not -path "app/Shared/*" -not -path "app/Infrastructure/*" -not -path "app/Providers/*" -not -path "app/Console/*" -not -path "app/Support/*"

# Find modules without Module.php
find app/Domains/ -mindepth 1 -maxdepth 1 -type d | while read dir; do
    if [ ! -f "$dir/Module.php" ]; then
        echo "Missing Module.php: $dir"
    fi
done

# Find modules without ServiceProvider
```

### 26.1 Automated Migration Script

```php
// database/migrations/migrate_to_domain_structure.php
// Run once to migrate from flat to domain structure

$domainMap = [
    'Component' => 'Components',
    'ComponentVersion' => 'Components',
    'Theme' => 'Themes',
    'ThemeToken' => 'Themes',
    'Subscription' => 'Billing',
    'Invoice' => 'Billing',
    'Payment' => 'Billing',
    'Product' => 'Marketplace',
    'Order' => 'Marketplace',
    'License' => 'Marketplace',
];

foreach ($domainMap as $model => $domain) {
    $source = app_path("Models/{$model}.php");
    $dest = app_path("Domains/{$domain}/Models/{$model}.php");

    if (file_exists($source)) {
        // Create directory if needed
        $dir = dirname($dest);
        if (! is_dir($dir)) {
            mkdir($dir, 0755, true);
        }

        // Move file
        rename($source, $dest);

        // Update namespace
        $content = file_get_contents($dest);
        $content = str_replace(
            "namespace App\\Models;",
            "namespace App\\Domains\\{$domain}\\Models;",
            $content
        );
        file_put_contents($dest, $content);

        echo "Moved {$model} to {$domain}\n";
    }
}
```

```php
final class DomainServiceProvider
```

## 32. Common Folder Structure Mistakes

### 32.1 Mistake Reference Table

| Mistake | Consequence | Fix |
|---|---|---|
| Models in `app/Models/` root | Violates domain ownership | Move to `app/Domains/{Domain}/Models/` |
| Services in `app/Services/` root | Cross-domain coupling | Move to `app/Domains/{Domain}/Services/` |
| Putting controllers in domain dirs | Leaky architecture | Controllers stay in `app/Http/Controllers/` |
| Mixing admin and user code | Hard to split later | Separate `Domains/Admin/` module |
| Flat namespace without domains | No boundary enforcement | Refactor to domain-organized namespaces |
| Shared repositories | Hidden coupling | One repository per aggregate root per domain |
| No Contracts directory | Tight coupling | Create `Contracts/` with interfaces |
| Putting views in domain dirs | Blade discovery issues | Views stay in `resources/views/domains/` |

### 32.2 Structural Smells Detection

```php
// Detect structural smells automatically

// Check for Models in root

    $smells[] = 'Services found in app/Services/ root — should be in domains';

foreach ($domains as $domain) {
    $name = basename($domain);
    if (!is_dir("{$domain}/Contracts")) {

    }
}

// Check for non-final models
$models = glob(app_path('Domains/*/Models/*.php'));

    $content = file_get_contents($model);
    if (!str_contains($content, 'final class')) {
        $smells[] = "Model " . basename($model) . " is not final";
    }
}
```

```php
use Illuminate\Console\Command;

class MakeDomainCommand extends Command
{
    protected $signature = 'make:domain {name} {--with-tests} {--with-factory}';

    protected $description = 'Create a new domain module with full directory structure';

    public function handle(): int
    {
        $name = $this->argument('name');
        $path = app_path("Domains/{$name}");

        if (is_dir($path)) {
            $this->error("Domain '{$name}' already exists.");
            return 1;
        }

        $directories = [
            "{$path}/Domain/Entities",
            "{$path}/Domain/ValueObjects",
            "{$path}/Domain/Events",
            "{$path}/Domain/Exceptions",
            "{$path}/Contracts",
            "{$path}/Services",
            "{$path}/Repositories",
            "{$path}/Actions",
            "{$path}/DTOs",
            "{$path}/Http/Livewire",
            "{$path}/Database/Migrations",
            "{$path}/Database/Factories",
            "{$path}/Database/Seeders",
            "{$path}/Config",
        ];

        foreach ($directories as $dir) {
            if (!is_dir($dir)) {
                mkdir($dir, 0755, true);
            }
        }

        // Create service provider
        file_put_contents(
            "{$path}/{$name}ServiceProvider.php",
            $this->stub('ServiceProvider', $name)
        );

        // Create module manifest
        file_put_contents(
            "{$path}/Module.php",
            $this->stub('Module', $name)

        $this->info("Domain '{$name}' created successfully.");
        $this->newLine();
        $this->info("Directory structure:");
        $this->info("{$path}/");

        return 0;
    }

    private function stub(string $type, string $name): string
    {
        return file_get_contents(
            resource_path("stubs/{$type}.stub")
        );
    }
}
```

## 39. Documentation Directory Patterns

### 39.1 Documentation Structure

| Directory | Purpose | Content |
|---|---|---|
| `docs/architecture/` | Architecture decision records | ADRs, diagrams |
| `docs/domains/` | Domain-specific documentation | Business rules, workflows |
| `docs/api/` | API documentation | Endpoint specs, examples |
| `docs/deployment/` | Deployment guides | CI/CD, Docker, hosting |
| `docs/testing/` | Testing documentation | Test strategies, fixtures |
| `docs/security/` | Security documentation | CSP, auth, permissions |

### 39.2 README Organization

Each module directory should contain a `README.md` with:

1. Module purpose and responsibility
2. Key entities and their relationships
3. Public API (contracts)
4. Domain events dispatched
5. External dependencies
6. Testing instructions
