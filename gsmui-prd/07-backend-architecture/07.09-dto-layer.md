# 07.09 - DTO Layer

**Project:** GsmUi
**Architecture:** Data Transfer Object Pattern
**Framework:** Laravel 13 + Livewire 4
**Version:** 1.0.0

---

# Purpose

> See also: `05.07-service-layer.md` §"DTO Usage" for the role of DTOs in the service layer. This document specifies the **implementation contract** — the `Data` base class, the `FromRequest`/`ToArray` conventions, immutability rules, and the mapping strategy from Eloquent models to DTOs consumed by Actions (see `07.08-action-layer.md`).

DTOs are immutable, typed value carriers that cross the application-layer boundary. Actions receive a DTO instead of a raw request array, which gives compile-time type safety, a single validation boundary, and clear method signatures. DTOs carry no behavior beyond construction and serialization; they never touch the database and never contain business rules.

Every complex write operation in GsmUi is described by a DTO named for the operation it feeds (`CreateComponentData`, `PublishThemeData`, `PurchaseTemplateData`). Read operations may return a DTO or a projection, but never a hydrated Eloquent model when a lean payload is sufficient.

# 1A. Architecture Overview

The DTO layer sits between the HTTP/controller boundary and the domain service layer. It is the last validation gate before data enters the business domain.

```text
┌─────────────────────────────────────────────────────────────────┐
│                        REQUEST LIFECYCLE                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────────┐  │
│  │  HTTP Request │───▶│ Form Request  │───▶│  DTO Factory     │  │
│  │  (raw input)  │    │ (validation)  │    │  (fromRequest)   │  │
│  └──────────────┘    └──────────────┘    └────────┬─────────┘  │
│                                                    │             │
│                                          ┌─────────▼──────────┐ │
│                                          │   DTO (readonly)    │ │
│                                          │   (typed payload)   │ │
│                                          └─────────┬──────────┘ │
│                                                    │             │
│                                          ┌─────────▼──────────┐ │
│                                          │   Action::run($dto) │ │
│                                          │   (business logic)  │ │
│                                          └────────────────────┘ │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

Key properties of every DTO:

| Property | Contract |
| --- | --- |
| Immutability | `final readonly` — no post-construction mutation |
| Type safety | Every property has an explicit PHP type |
| No identity | Two DTOs with the same values are equal |
| No behavior | Beyond `fromRequest()`, `fromModel()`, `toArray()` |
| No persistence | Never touches the database directly |
| No side effects | Pure data carrier — no service calls, no events |

# 1A3. DTO Contract Rules

These rules are enforced by code review and CI:

| Rule | Enforcement | Rationale |
| --- | --- | --- |
| DTOs are `final readonly` | PHPStan level 8 | Prevents inheritance bugs and mutation |
| DTOs have no `public` methods beyond factories/serialization | CI lint | Behavior belongs in Services/Actions |
| DTOs do not import Eloquent models | PHPStan | DTOs are persistence-agnostic |
| DTOs do not import `Request` | CI lint (except `fromRequest()`) | DTOs are HTTP-agnostic |
| DTOs do not call `cache()`, `DB::`, or any facade | PHPStan | No side effects in DTOs |
| Write DTOs have matching Action classes | CI test | Every write DTO must be consumable |
| Read DTOs have `fromModel()` factory | CI test | Every read DTO must be constructable from a model |
| DTOs are serializable (no closures, no resources) | CI test | Must survive queue/cache/Livewire round-trips |

# 1B. Why DTOs Over Arrays

Raw arrays are the default in Laravel (form requests return `$request->validated()`). DTOs add compile-time safety, IDE autocompletion, and explicit contracts.

```text
┌─────────────────────────────────────────────────────────────────┐
│                   ARRAY vs DTO COMPARISON                       │
├───────────────────────────────┬─────────────────────────────────┤
│  Raw Array                    │  DTO                           │
├───────────────────────────────┼─────────────────────────────────┤
│  No type hints                │  Full type hints on every prop  │
│  Typos silently ignored       │  Compile-time error on typo     │
│  No IDE autocompletion        │  Full IDE support               │
│  Shape is implicit            │  Shape is declared              │
│  Easy to pass wrong shape     │  Constructor enforces shape     │
│  Hard to refactor             │  Find references works          │
│  No validation at boundary    │  VO construction validates      │
│  Works everywhere             │  Requires a class per shape     │
└───────────────────────────────┴─────────────────────────────────┘
```

Anti-pattern: Using DTOs everywhere. Simple CRUD reads where `$request->only(...)` suffices do not need a DTO. DTOs are for **write operations** and **cross-boundary reads** where type safety matters.

# 1C. DTO Naming Conventions

GsmUi uses operation-specific DTO names following these patterns:

| Pattern | Purpose | Example |
| --- | --- | --- |
| `Create{Entity}Data` | Input for creation | `CreateComponentData` |
| `Update{Entity}Data` | Input for update | `UpdateComponentData` |
| `{Entity}Data` | Read projection | `ComponentData` |
| `Publish{Entity}Data` | Specialized write | `PublishThemeData` |
| `Import{Entity}Data` | Bulk/batch input | `ImportProductsData` |
| `Search{Entity}Data` | Query parameters | `SearchComponentsData` |

The suffix `Data` is used (not `DTO`, `Payload`, or `Command`) to maintain consistency with the Spatie `laravel-data` package convention already familiar in the Laravel ecosystem.

# 2. Base Data Class

```php
namespace App\Data;

use Illuminate\Http\Request;

abstract class Data
{
    /**
     * Build the DTO from a validated HTTP request.
     * Subclasses override and type-hint the concrete Request.
     */
    public static function fromRequest(Request $request): static
    {
        return new static(...$request->validated());
    }

    /**
     * Build the DTO from a plain array (commands, jobs, tests).
     */
    public static function fromArray(array $data): static
    {
        return new static(...$data);
    }

    /**
     * Serialize to a plain array for persistence or transport.
     */
    public function toArray(): array
    {
        return get_object_vars($this);
    }
}
```

# 2A. Extended Base Data Class

The base `Data` class provides common factories and serialization. An enhanced version adds serialization support for queues, Livewire, and caching:

```php
namespace App\Data;

use Illuminate\Http\Request;
use Illuminate\Support\Collection;

abstract class Data
{
    /**
     * Build the DTO from a validated HTTP request.
     * Subclasses override and type-hint the concrete Request.
     */
    public static function fromRequest(Request $request): static
    {
        return new static(...$request->validated());
    }

    /**
     * Build the DTO from a plain array (commands, jobs, tests).
     */
    public static function fromArray(array $data): static
    {
        return new static(...$data);
    }

    /**
     * Build a Collection of DTOs from a query builder result.
     */
    public static function fromCollection(Collection $items): \Illuminate\Support\Collection
    {
        return $items->map(fn ($item) => static::fromModel($item));
    }

    /**
     * Serialize to a plain array for persistence or transport.
     */
    public function toArray(): array
    {
        return get_object_vars($this);
    }

    /**
     * Serialize to JSON-safe array (handles value objects recursively).
     */
    public function jsonSerialize(): array
    {
        return collect($this->toArray())->mapWithKeys(function ($value, $key) {
            if ($value instanceof \App\Data\Data) {
                return [$key => $value->jsonSerialize()];
            }
            if (is_object($value) && method_exists($value, 'toString')) {
                return [$key => $value->toString()];
            }
            return [$key => $value];
        })->toArray();
    }

    /**
     * Create a new DTO with one or more properties replaced.
     * Useful for partial updates without breaking immutability.
     */
    public function merge(array $overrides): static
    {
        return new static(...array_merge($this->toArray(), $overrides));
    }

    /**
     * Check if two DTOs have identical values.
     */
    public function equals(self $other): bool
    {
        return $this->toArray() === $other->toArray();
    }

    /**
     * Return only the specified keys from the DTO.
     */
    public function only(array $keys): array
    {
        return collect($this->toArray())->only($keys)->toArray();
    }

    /**
     * Return all keys except the specified ones.
     */
    public function except(array $keys): array
    {
        return collect($this->toArray())->except($keys)->toArray();
    }
}
```

# 2B. Base Data Class Decision Table

| Method | When to use | When to avoid |
| --- | --- | --- |
| `fromRequest()` | Controller/Livewire receiving validated input | CLI commands, seeding, tests |
| `fromArray()` | Tests, jobs, seeders, programmatic construction | When `fromRequest()` is available |
| `fromModel()` | Read-side DTOs projecting from Eloquent | Write-side DTOs (they receive input, not models) |
| `fromCollection()` | Paginated listings, bulk reads | Single-item reads |
| `toArray()` | Passing to repository `create()`/`update()` | Never needed when VO handles serialization |
| `jsonSerialize()` | API responses, Livewire round-trips | Internal-only DTOs |
| `merge()` | Partial updates, cloning with overrides | Full construction (use constructor directly) |
| `equals()` | Testing DTO equality | Performance-critical hot paths |
| `only()` / `except()` | Selective field exposure | When full DTO is needed |

# 2C. Abstract vs Concrete Base Class

GsmUi uses an abstract `Data` class (not an interface) for these reasons:

| Decision | Rationale |
| --- | --- |
| Abstract class over interface | Default method implementations reduce boilerplate in every DTO |
| `static` return type | Late static binding allows `CreateComponentData::fromRequest()` to return the correct type |
| No `readonly` on base | Child classes declare `readonly` individually (some DTOs need mutability for Livewire) |
| `jsonSerialize()` on base | Every DTO may be serialized; no reason to opt-in per DTO |
| `merge()` on base | Common pattern for partial updates; saves repetition |

Anti-pattern: Making `Data` an interface with `toArray()`. This forces every DTO to re-implement common logic.

# 3. Immutable DTO Example

DTOs are declared `final readonly` so they cannot be mutated after construction. Validation occurs in the constructor (or is guaranteed by the upstream Form Request, see `07.18-form-requests.md`).

```php
namespace App\Domains\Components\DTOs;

use App\Data\Data;
use App\Domains\Components\ValueObjects\ComponentSlug;
use Illuminate\Http\Request;

final readonly class CreateComponentData extends Data
{
    public function __construct(
        public string $name,
        public ComponentSlug $slug,
        public string $description,
        public int $categoryId,
        public int $userId,
        public array $tags = [],
    ) {}

    public static function fromRequest(Request $request): static
    {
        return new self(
            name: $request->input('name'),
            slug: ComponentSlug::fromString($request->input('slug')),
            description: $request->input('description'),
            categoryId: (int) $request->input('category_id'),
            userId: $request->user()->id,
            tags: $request->input('tags', []),
        );
    }
}
```

# 4. `FromRequest` Contract

The `fromRequest()` factory is the canonical bridge between validated HTTP input and the application layer. It must accept a fully-validated `Request` (after a Form Request has run) and never re-validate. Value objects (see `07.10-value-objects.md`) are constructed here from raw strings.

```php
// In a controller or Livewire component:
$data = CreateComponentData::fromRequest($request);
$component = app(CreateComponentAction::class)->run($data);
```

# 3B. Multi-Step Write DTOs

Some operations require multi-step confirmation (e.g., publishing a theme). The DTO carries a `confirmationToken` that an Action validates before proceeding:

```php
final readonly class PublishThemeData extends Data implements Wireable
{
    public function __construct(
        public int $themeId,
        public int $userId,
        public string $version,
        public ?string $confirmationToken = null,
    ) {}

    public static function fromRequest(Request $request): static
    {
        return new self(
            themeId: (int) $request->input('theme_id'),
            userId: $request->user()->id,
            version: $request->input('version', '1.0.0'),
            confirmationToken: $request->input('confirmation_token'),
        );
    }

    /**
     * First step: validate the theme is ready.
     * Returns true if theme can be published.
     */
    public function requiresConfirmation(): bool
    {
        return $this->confirmationToken === null;
    }
}
```

The Action checks `requiresConfirmation()` and either returns a preview or executes the publish.

# 3C. DTO Inheritance Patterns

GsmUi avoids DTO inheritance hierarchies in favor of composition. When two DTOs share most properties, extract the common subset into a child DTO:

```php
// COMPOSITION over inheritance
final readonly class ComponentData extends Data
{
    public function __construct(
        public int $id,
        public string $name,
        public string $slug,
        public string $status,
        public int $categoryId,
        public \DateTimeImmutable $createdAt,
        public \DateTimeImmutable $updatedAt,
    ) {}
}

// Summary variant — fewer fields, not a subclass
final readonly class ComponentSummaryData extends Data
{
    public function __construct(
        public int $id,
        public string $name,
        public string $slug,
        public string $status,
    ) {}
}
```

Anti-pattern: `class ComponentSummaryData extends ComponentData`. This creates fragile base class problems and breaks the readonly contract when the child needs different constructor parameters.

# 5. `ToArray` Contract

`toArray()` produces the attribute array passed to the repository's `create()`/`update()`. Read models may expose a `toArray()` consumed by API Resources (see `07.21-api-architecture.md`).

```php
$attributes = $data->toArray();
// ['name' => '...', 'slug' => '...', 'description' => '...', ...]
$component = $this->components->create($attributes);
```

# 5A. `toArray()` Value Object Handling

When a DTO contains value objects, `toArray()` must serialize them to their scalar form. The base class `toArray()` returns raw objects; the `jsonSerialize()` method handles recursive serialization:

```php
// Write DTO with a value object:
$dto = new CreateComponentData(
    name: 'Button',
    slug: ComponentSlug::fromString('button-primary'),
    description: 'A button component',
    categoryId: 1,
    userId: 5,
);

$dto->toArray();
// ['name' => 'Button', 'slug' => ComponentSlug object, ...]

$dto->jsonSerialize();
// ['name' => 'Button', 'slug' => 'button-primary', ...]
```

For repository `create()` calls, the DTO's `toArray()` is wrapped with a helper that handles VOs:

```php
// In a Repository:
public function create(CreateComponentData $data): Component
{
    return $this->model->create($data->jsonSerialize());
}

// Or more explicitly, using an AttributeCaster helper:
public function create(CreateComponentData $data): Component
{
    return $this->model->create(
        AttributesCaster::cast($data->toArray(), [
            'slug' => ComponentSlugCast::class,
        ])
    );
}
```

---

# 5B. `toArray()` Decision Matrix

| Scenario | Method to use | Why |
| --- | --- | ---|
| Repository `create()` / `update()` | `$dto->toArray()` + cast helpers | Eloquent expects scalar attributes |
| API Resource serialization | `$dto->jsonSerialize()` | Recursively handles VOs |
| Livewire state | `$dto->toLivewire()` (Wireable) | Livewire needs arrays/strings |
| Event payload | `$dto->toArray()` + manual casting | Events carry scalars only |
| Cache storage | `$dto->jsonSerialize()` | Redis needs strings |
| Testing assertion | `$dto->toArray()` | Direct property access |

# 5C. DTO with Nullable Fields and Defaults

Read-side DTOs often need nullable fields for optional relationships. Use constructor promotion with defaults:

```php
final readonly class ComponentData extends Data
{
    public function __construct(
        public int $id,
        public string $name,
        public string $slug,
        public string $status,
        public int $categoryId,
        public ?string $description = null,
        public ?string $categoryName = null,
        public array $tags = [],
        public ?int $latestVersionId = null,
        public ?\DateTimeImmutable $publishedAt = null,
    ) {}

    public static function fromModel(Component $component): self
    {
        return new self(
            id: $component->id,
            name: $component->name,
            slug: $component->slug,
            status: $component->status->value,
            categoryId: $component->category_id,
            description: $component->description,
            categoryName: $component->category?->name,
            tags: $component->tags->pluck('name')->toArray(),
            latestVersionId: $component->latestVersion?->id,
            publishedAt: $component->published_at
                ? \DateTimeImmutable::createFromMutable($component->published_at)
                : null,
        );
    }
}
```

Note: `fromModel()` eagerly loads relationships inline to prevent lazy-loading in the API layer (see `07.07-repositories.md`).

# 6. Mapping From Models

Read-side DTOs are projected from Eloquent models via a static `fromModel()` factory. This keeps presentation and API layers free of model internals and prevents accidental lazy-loading.

```php
namespace App\Domains\Components\DTOs;

use App\Models\Component;

final readonly class ComponentData extends Data
{
    public function __construct(
        public int $id,
        public string $name,
        public string $slug,
        public string $status,
        public int $categoryId,
    ) {}

    public static function fromModel(Component $component): self
    {
        return new self(
            id: $component->id,
            name: $component->name,
            slug: $component->slug,
            status: $component->status,
            categoryId: $component->category_id,
        );
    }
}

// Usage in a query service:
return $components->paginatePublished()
    ->through(fn (Component $c) => ComponentData::fromModel($c));
```

# 6B. Eager Loading in `fromModel()`

The `fromModel()` factory is responsible for eager loading relationships to prevent N+1 queries in the API layer:

```php
final readonly class ComponentData extends Data
{
    public function __construct(
        public int $id,
        public string $name,
        public string $slug,
        public string $status,
        public int $categoryId,
        public string $categoryName,
        public array $tags,
        public ?string $authorName,
        public int $downloads,
    ) {}

    public static function fromModel(Component $component): self
    {
        // Caller must eager-load: ->with(['category', 'tags', 'author'])
        return new self(
            id: $component->id,
            name: $component->name,
            slug: $component->slug,
            status: $component->status->value,
            categoryId: $component->category_id,
            categoryName: $component->category->name,
            tags: $component->tags->pluck('name')->toArray(),
            authorName: $component->author?->name,
            downloads: $component->downloads_count,
        );
    }
}

// In the repository or controller:
$components = Component::with(['category', 'tags', 'author'])
    ->where('status', 'published')
    ->paginate();

return $components->through(fn ($c) => ComponentData::fromModel($c));
```

Anti-pattern: Calling `$component->category->name` without eager loading. This causes N+1 queries and is caught by Laravel Debugbar in development and Scout in CI.

# 7. Validation Boundary

DTO construction is the last validation gate before the domain. The layered contract is:

```text
Form Request (input shape)        ── 07.18
        │
        ▼
DTO construction (value objects)  ── 07.09 / 07.10
        │
        ▼
Service business rules           ── 07.06
```

A DTO must refuse to construct when a value object throws (e.g., an invalid `ComponentSlug`). This keeps invalid state out of the domain without duplicating rule logic.

# 7A. Validation Boundary Deep Dive

The validation boundary is a three-layer defense:

```text
┌─────────────────────────────────────────────────────────────────┐
│                    VALIDATION LAYERS                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Layer 1: Form Request (HTTP shape validation)                  │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  - Required fields present                              │    │
│  │  - Types match (string, int, array)                     │    │
│  │  - Formats valid (email, URL, date)                     │    │
│  │  - Business rule basics (unique, exists)                │    │
│  │  - Custom rule objects for complex validation           │    │
│  └─────────────────────────────────────────────────────────┘    │
│                          │                                      │
│                          ▼                                      │
│  Layer 2: DTO Construction (value object validation)            │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  - VOs constructed from raw scalars                     │    │
│  │  - Each VO validates in its constructor                 │    │
│  │  - ComponentSlug rejects invalid patterns               │    │
│  │  - Money rejects negative amounts                       │    │
│  │  - Email rejects malformed addresses                    │    │
│  │  - InvalidArgumentException on failure                  │    │
│  └─────────────────────────────────────────────────────────┘    │
│                          │                                      │
│                          ▼                                      │
│  Layer 3: Service Business Rules                                │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  - Domain-specific validation (slug uniqueness)         │    │
│  │  - State machine transitions (draft → published)        │    │
│  │  - Cross-field rules (category + tags compatible)       │    │
│  │  - External API validation (payment processor)          │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

The key insight: **Form Requests handle shape, DTOs handle value, Services handle rules**. This separation prevents duplication and makes each layer independently testable.

# 7B. DTO Construction Error Handling

When a DTO refuses to construct (e.g., invalid slug), the `InvalidArgumentException` bubbles up through the Action. The controller/Livewire component catches it:

```php
// In a Livewire component:
public function createComponent(): void
{
    try {
        $data = CreateComponentData::fromRequest($this->formRequest);
        $component = app(CreateComponentAction::class)->run($data);
        $this->notify('Component created successfully.');
    } catch (\InvalidArgumentException $e) {
        $this->addError('form', $e->getMessage());
    }
}

// In a controller (FormRequest handles validation, but VO errors still possible):
public function store(CreateComponentRequest $request): RedirectResponse
{
    try {
        $data = CreateComponentData::fromRequest($request);
        $component = app(CreateComponentAction::class)->run($data);
        return redirect()->route('components.show', $component);
    } catch (\InvalidArgumentException $e) {
        return back()->withErrors(['slug' => $e->getMessage()]);
    }
}
```

```php
use Livewire\Wireable;

final readonly class PublishThemeData extends Data implements Wireable
```

```php
        public int $themeId,
        public int $userId,
        public string $version,
```

# 8B. Livewire Form DTOs

For complex Livewire forms, create DTOs that represent the form state:

```php
final readonly class ComponentFormData extends Data implements Wireable
{
    public function __construct(
        public string $name = '',
        public string $slug = '',
        public string $description = '',
        public ?int $categoryId = null,
        public array $selectedTags = [],
        public ?string $templateId = null,
    ) {}

    public function toLivewire(): array
    {
        return $this->toArray();
    }

    public static function fromLivewire($value): static
    {
        return self::fromArray($value);
    }

    /**
     * Convert form data to a write DTO for submission.
     */
    public function toCreateData(int $userId): CreateComponentData
    {
        return new CreateComponentData(
            name: $this->name,
            slug: ComponentSlug::fromString($this->slug),
            description: $this->description,
            categoryId: $this->categoryId,
            userId: $userId,
            tags: $this->selectedTags,
        );
    }

    /**
     * Validate the form data before submission.
     */
    public function validate(): array
    {
        $errors = [];

        if (empty($this->name)) {
            $errors['name'] = 'Name is required.';
        }

        if (empty($this->slug)) {
            $errors['slug'] = 'Slug is required.';
        }

        if ($this->categoryId === null) {
            $errors['categoryId'] = 'Category is required.';
        }

        return $errors;
    }
}
```

Usage in a Livewire component:

```php
class CreateComponentForm extends Component
{
    public ComponentFormData $form;

    public function mount(): void
    {
        $this->form = new ComponentFormData();
    }

    public function submit(): void
    {
        $errors = $this->form->validate();
        if (!empty($errors)) {
            $this->withErrors($errors);
            return;
        }

        $data = $this->form->toCreateData($this->user()->id);
        app(CreateComponentAction::class)->run($data);
    }
}
```

# 10C. DTO Anti-Patterns

| Anti-pattern | Why it's bad | Correct approach |
| --- | --- | --- |
| DTO with `public` mutable properties | Breaks immutability; any code can mutate | Use `final readonly` |
| DTO with business logic | Violates single responsibility | Move logic to Service/Action |
| DTO that references an Eloquent model | Ties DTO to persistence; breaks serialization | Pass scalar IDs |
| DTO that references `Request` | Ties DTO to HTTP layer | Use `fromRequest()` factory |
| DTO with `validate()` method | Duplicates Form Request logic | Use Form Request for validation |
| DTO that dispatches events | Side effects in a data carrier | Events dispatched by Action |
| DTO with static factory `fromRequest()` on read DTOs | Read DTOs come from models, not requests | Use `fromModel()` instead |
| DTO with computed properties | Computed values should be on API Resources | Compute in Resource, not DTO |
| DTO with `\DateTime` instead of `\DateTimeImmutable` | Mutable dates can be accidentally changed | Use `DateTimeImmutable` |

# 10D. DTO Performance Considerations

DTOs are lightweight, but bulk operations (thousands of models) can create overhead:

```php
// SLOW: Creates 10,000 DTO objects
$components = Component::paginate(10000);
$dtoCollection = $components->through(fn ($c) => ComponentData::fromModel($c));

// FAST: Lazy generation via generator
$components = Component::cursor();
$dtoGenerator = function () use ($components) {
    foreach ($components as $component) {
        yield ComponentData::fromModel($component);
    }
};
```

For most use cases (paginated results of 20-50 items), the overhead is negligible. Optimize only when profiling shows DTO construction as a bottleneck.

# 10I. DTO Best Practices Summary

| Practice | Benefit |
| --- | ---|
| Use `final readonly` | Prevents mutation and inheritance bugs |
| One DTO per operation | Clear, focused contracts |
| VOs for domain primitives | Self-validating, type-safe values |
| `fromRequest()` for writes | Clean bridge from HTTP to domain |
| `fromModel()` for reads | Clean bridge from persistence to API |
| No business logic in DTOs | Single responsibility, easy to test |
| No Eloquent models in DTOs | Persistence-agnostic, serializable |
| Immutable dates (`DateTimeImmutable`) | No accidental mutation |
| Nullable fields with defaults | Handles optional data gracefully |
| `toArray()` for Eloquent, `jsonSerialize()` for API | Correct serialization per context |
| Test construction, factories, and serialization | Catch regressions early |
| CI checks for dependencies and immutability | Enforce architectural rules |

# 10J. DTO Common Pitfalls and Solutions

| Pitfall | Symptom | Solution |
| --- | ---| --- |
| DTO has `public` mutable property | Any code can change the value | Use `final readonly` |
| DTO references `Request` object | Ties DTO to HTTP layer | Use `fromRequest()` factory |
| DTO references Eloquent model | Breaks serialization, ties to DB | Pass scalar IDs only |
| DTO has computed properties | Business logic leaks into data layer | Move to API Resource |
| DTO stores `DateTime` instead of `DateTimeImmutable` | Accidental mutation | Use `DateTimeImmutable` |
| DTO has nullable VO fields | VO `fromString(null)` throws | Use `?VO` type, check null first |
| DTO `toArray()` returns VO objects | Eloquent can't save them | Use `jsonSerialize()` or cast |
| DTO tested with real DB | Slow tests, fragile | Mock models, test DTO in isolation |
| DTO created in a loop | Performance overhead | Use cursor/generator pattern |
| DTO stored in session/cache without serialization | Unserialization fails | Implement `__serialize()` |

# 10L. DTO Evolution Strategy

When a DTO needs new fields, add them with defaults to maintain backward compatibility:

```php
// Before:
final readonly class CreateComponentData extends Data
{
    public function __construct(
        public string $name,
        public ComponentSlug $slug,
        public string $description,
        public int $categoryId,
        public int $userId,
    ) {}
}

// After (backward compatible):
final readonly class CreateComponentData extends Data
{
    public function __construct(
        public string $name,
        public ComponentSlug $slug,
        public string $description,
        public int $categoryId,
        public int $userId,
        public array $tags = [],           // NEW — optional
        public ?string $templateId = null, // NEW — nullable
    ) {}
}
```

The old callers continue to work unchanged. New callers can pass the additional fields.

# 10Q. DTO Common Code Patterns

**Pattern: DTO with optional nested DTO:**

```php
final readonly class CreateOrderData extends Data
{
    public function __construct(
        public int $userId,
        public array $items, // array of OrderItemData
        public ?ShippingData $shipping = null,
        public ?string $couponCode = null,
    ) {}

    public static function fromRequest(Request $request): static
    {
        return new self(
            userId: $request->user()->id,
            items: collect($request->input('items', []))
                ->map(fn ($item) => OrderItemData::fromArray($item))
                ->toArray(),
            shipping: $request->has('shipping')
                ? ShippingData::fromArray($request->input('shipping'))
                : null,
            couponCode: $request->input('coupon_code'),
        );
    }
}
```

**Pattern: Read DTO with computed display values:**

```php
final readonly class ComponentSummaryData extends Data
{
    public function __construct(
        public int $id,
        public string $name,
        public string $slug,
        public string $status,
        public string $statusLabel,  // computed from enum
        public string $authorName,   // from relationship
        public string $categoryName, // from relationship
        public int $downloadCount,
        public string $publishedAtFormatted, // formatted date
    ) {}

    public static function fromModel(Component $component): self
    {
        return new self(
            id: $component->id,
            name: $component->name,
            slug: $component->slug,
            status: $component->status->value,
            statusLabel: $component->status->label(),
            authorName: $component->author->name,
            categoryName: $component->category->name,
            downloadCount: $component->downloads_count,
            publishedAtFormatted: $component->published_at
                ? $component->published_at->diffForHumans()
                : 'Not published',
        );
    }
}
```

**Pattern: DTO with validation callback:**

```php
final readonly class SearchComponentsData extends Data
{
    public function __construct(
        public string $query = '',
        public ?int $categoryId = null,
        public ?string $status = null,
        public string $sortBy = 'name',
        public string $sortDirection = 'asc',
        public int $perPage = 20,
    ) {
        if (!in_array($this->sortBy, ['name', 'created_at', 'downloads'])) {
            throw new \InvalidArgumentException("Invalid sort field: {$this->sortBy}");
        }

        if (!in_array($this->sortDirection, ['asc', 'desc'])) {
            throw new \InvalidArgumentException("Invalid sort direction: {$this->sortDirection}");
        }

        if ($this->perPage < 1 || $this->perPage > 100) {
            throw new \InvalidArgumentException("Per page must be between 1 and 100.");
        }
    }
}
```

# 10R. DTO for Bulk Operations

When processing bulk operations (import/export), use a specialized DTO that carries batch metadata:

```php
final readonly class ImportProductsData extends Data
{
    public function __construct(
        public int $userId,
        public string $source,         // 'csv', 'api', 'json'
        public array $items,           // array of ProductItemData
        public ?int $categoryId = null,
        public bool $skipDuplicates = true,
        public bool $sendNotifications = false,
    ) {
        if (count($this->items) > 1000) {
            throw new \InvalidArgumentException('Bulk import limited to 1000 items.');
        }
    }

    /**
     * Split into chunks for memory-efficient processing.
     */
    public function chunk(int $size): \Generator
    {
        foreach (array_chunk($this->items, $size) as $chunk) {
            yield new self(
                userId: $this->userId,
                source: $this->source,
                items: $chunk,
                categoryId: $this->categoryId,
                skipDuplicates: $this->skipDuplicates,
                sendNotifications: false,
            );
        }
    }

    /**
     * Get unique item count (for progress tracking).
     */
    public function itemCount(): int
    {
        return count($this->items);
    }
}
```

# 10S. DTO for API Responses

Read-side DTOs for API responses should be structured for JSON serialization:

```php
final readonly class ComponentApiData extends Data
{
    public function __construct(
        public int $id,
        public string $name,
        public string $slug,
        public string $status,
        public string $description,
        public array $tags,
        public object $author,      // { id, name, avatar }
        public object $category,    // { id, name, slug }
        public ?string $publishedAt,
        public string $createdAt,
        public string $updatedAt,
        public object $links,       // { self, edit, download }
    ) {}

    public static function fromModel(Component $component): self
    {
        return new self(
            id: $component->id,
            name: $component->name,
            slug: $component->slug,
            status: $component->status->value,
            description: $component->description,
            tags: $component->tags->pluck('name')->toArray(),
            author: (object) [
                'id' => $component->author->id,
                'name' => $component->author->name,
                'avatar' => $component->author->avatar_url,
            ],
            category: (object) [
                'id' => $component->category->id,
                'name' => $component->category->name,
                'slug' => $component->category->slug,
            ],
            publishedAt: $component->published_at?->toIso8601String(),
            createdAt: $component->created_at->toIso8601String(),
            updatedAt: $component->updated_at->toIso8601String(),
            links: (object) [
                'self' => route('api.components.show', $component),
                'edit' => route('api.components.update', $component),
                'download' => route('api.components.download', $component),
            ],
        );
    }
}
```

# 10T. DTO Error Handling Patterns

| Error Type | Where Thrown | How Handled |
| --- | --- | --- |
| `InvalidArgumentException` | VO construction (invalid slug, negative money) | Caught by Action/Controller, returned as 422 |
| `TypeError` | Wrong types passed to constructor | Caught by PHPStan, never reaches production |
| `ValueError` | Invalid enum case | Caught by Form Request validation |
| Domain exception | Service rejects the operation | Caught by Action, returned as 422/409 |

The DTO itself should only throw `InvalidArgumentException` for invalid construction. All other errors belong in the Service layer.

# 10U. DTO Field Naming Conventions

| Convention | Example | Rationale |
| --- | --- | --- |
| camelCase for properties | `$categoryId`, `$userId` | PHP standard |
| snake_case in `toArray()` output | `category_id`, `user_id` | Database/Eloquent convention |
| Prefix with entity for FKs | `categoryId` not `id` | Clarity in DTO context |
| Boolean flags end with verb | `$skipDuplicates`, `$sendNotifications` | Readable as `if ($dto->skipDuplicates)` |
| Nullable for optional values | `?string $templateId = null` | Explicit nullability |
| Array for collections | `array $tags = []` | PHP standard |

# 10V. DTO and Action Pairing

Every write DTO must have a corresponding Action. The Action's `run()` method signature references the DTO type:

| DTO | Action | Queue |
| --- | --- | --- |
| `CreateComponentData` | `CreateComponentAction` | Sync |
| `UpdateComponentData` | `UpdateComponentAction` | Sync |
| `PublishComponentData` | `PublishComponentAction` | Sync |
| `CreateThemeData` | `CreateThemeAction` | Sync |
| `PublishThemeData` | `PublishThemeAction` | Sync |
| `PurchaseTemplateData` | `PurchaseTemplateAction` | Sync |
| `GenerateInvoicePdf` | `GenerateInvoicePdfJob` | Queued |
| `ImportProductsData` | `ImportProductsAction` | Queued |

The Action is the consumer of the DTO. The DTO is never used outside the Action context for write operations.

# 10W. DTO Security Considerations

| Risk | Mitigation |
| --- | ---|
| Mass assignment | DTO constructor controls which fields are accepted |
| Hidden field injection | `fromRequest()` only reads validated fields |
| IDOR | Action checks authorization before using DTO |
| Sensitive data in logs | DTO `__debugInfo()` can redact sensitive fields |
| Serialization leakage | `toArray()` excludes internal fields |
| Session/cache poisoning | DTOs are immutable; no mutable state to corrupt |

# 10X. DTO and Horizon Integration

When DTOs are used in queued jobs (via `ShouldQueue` listeners), the DTO must be serializable:

```php
// In a queued listener:
final class SendComponentNotification implements ShouldQueue
{
    public function handle(ComponentPublished $event): void
    {
        // Event carries scalar IDs, not DTOs
        $component = Component::find($event->componentId);
        $user = User::find($event->userId);

        // Construct DTO inside the job for freshness
        $notificationData = new NotificationData(
            recipientId: $user->id,
            subject: "Component {$component->name} published",
            body: "Your component has been published.",
        );

        app(NotificationService::class)->send($notificationData);
    }
}
```

Rule: Queued jobs should construct DTOs internally from scalar IDs, not receive pre-built DTOs as constructor arguments (which may become stale).
