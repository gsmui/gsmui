# 07.13 - Listeners

**Project:** GsmUi
**Architecture:** Event-Driven Architecture (EDA) – Listener Implementation
**Framework:** Laravel 13 + Livewire 4
**Version:** 1.0.0

---

# Purpose

Listeners are the subscribers in GsmUi's event-driven architecture. They react to domain events dispatched by Actions (see `05.10-events.md`) and perform follow-up work such as indexing search, sending notifications, invalidating caches, or dispatching downstream jobs. Listeners keep cross-domain coupling low because they depend only on the event payload, never on the dispatching domain's internals.

A listener is a single-responsibility class with one `handle()` method. Expensive work must implement `ShouldQueue` so it runs on a Horizon worker instead of blocking the HTTP request. All listeners must be idempotent: an event may be delivered more than once under retry or at-least-once queue semantics, and a listener must not create duplicate side effects.

> See also: `05.10-events.md` (the conceptual event/listener contract, event lifecycle, naming, and event matrix). This document specifies the *implementation contract* — the concrete base classes, registration, and idempotency pattern.

---

# 1. Listener Rules

1. **One responsibility per listener.** Prefer `UpdateSearchIndex` over a catch-all `HandleComponentEvents`.
2. **No business rules inside listeners.** Delegate domain logic to Services and Actions (see `05.09-actions.md`).
3. **Queue expensive listeners.** Anything touching I/O, external services, or media must implement `ShouldQueue`.
4. **Idempotent by design.** Use unique constraints, idempotency keys, or status checks (see `06.01` §15).
5. **Handle only the payload.** Never accept the full request or an Eloquent model the event did not serialize.

# 3. Synchronous Listener (lightweight)

Use only for cheap, in-process work such as cache invalidation or audit logging.

```php
<?php

declare(strict_types=1);

namespace App\Domains\Components\Listeners;

use App\Domains\Components\Events\ComponentPublished;

final class ClearComponentCache
{
    public function handle(ComponentPublished $event): void
    {
        cache()->forget("component:{$event->componentId}");
    }
}
```

# 4. Queued Listener

Expensive listeners implement `ShouldQueue` and declare their queue explicitly (matching the topology in `05.11-jobs.md`).

```php
<?php

declare(strict_types=1);

namespace App\Domains\Components\Listeners;

use App\Domains\Components\Events\ComponentPublished;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Queue\InteractsWithQueue;

final class UpdateComponentSearchIndex implements ShouldQueue
{
    use InteractsWithQueue;

    public string $queue = 'search';

    public int $tries = 3;

    public int $timeout = 60;

    public function handle(ComponentPublished $event): void
    {
        $service = app(\App\Domains\Search\Services\SearchService::class);

        $service->upsert('components', $event->componentId);
    }
}
```

# 5. Registration

Prefer automatic discovery. Enable it in `EventServiceProvider`:

```php
protected function shouldDiscoverEvents(): bool
{
    return true;
}

protected function discoversEventsWithin(): array
{
    return [
        app_path('Domains'),
    ];
}
```

When explicit registration is required (e.g. conditional listeners), map them in `boot()`:

```php
public function boot(): void
{
    Event::listen(
        \App\Domains\Components\Events\ComponentPublished::class,
        \App\Domains\Components\Listeners\UpdateComponentSearchIndex::class,
    );

    Event::listen(
        \App\Domains\Themes\Events\ThemeGenerated::class,
        \App\Domains\Themes\Listeners\ExportThemeAssets::class,
    );
}
```

# 6. Idempotent Handling

A listener must tolerate duplicate delivery. Use a processed-event marker or a unique DB constraint.

```php
public function handle(ComponentPublished $event): void
{
    if (cache()->has("processed:component-published:{$event->componentId}")) {
        return;
    }

    $this->generateDocs($event->componentId);

    cache()->forever("processed:component-published:{$event->componentId}", true);
}
```

For financial or webhook-driven events, persist an `idempotency_key` row (see `06.01` §15) and rely on the unique index rather than cache.

# 7. Retry & Backoff

Define retry behavior on queued listeners to survive transient failures.

```php
public int $tries = 3;

public array $backoff = [10, 30, 60];

public function failed(ComponentPublished $event, \Throwable $exception): void
{
    report($exception);

    logger()->error('component.search_index.failed', [
        'component_id' => $event->componentId,
        'error'       => $exception->getMessage(),
    ]);
}
```

# 8. Testing

Listeners are tested without the queue by calling `handle()` directly, and with the queue via `assertPushed`.

```php
public function test_search_index_listener_upserts_record(): void

    (new UpdateComponentSearchIndex())->handle($event);

    Queue::assertPushedOn('search', UpdateComponentSearchIndex::class);
```

# 10. Listener Security Considerations

| Risk | Mitigation |
| --- | --- |
| Listener performs unauthorized action | Check authorization in listener |
| Listener exposes sensitive data | Only use event payload data |
| Listener calls external service without auth | Use proper API keys from config |
| Listener modifies state without validation | Validate before processing |
| Listener runs in wrong context | Use proper queue connection |

# 15. Listener Best Practices Summary

| Practice | Description |
| --- | --- |
| One responsibility | One listener per follow-up action |
| Idempotent handling | Safe for duplicate delivery |
| Queue expensive work | I/O, external services, media |
| Handle failures gracefully | Implement `failed()` method |
| Use proper queue | Match queue to work type |
| Set timeout | Prevent hanging jobs |
| Set tries and backoff | Handle transient failures |
| Test thoroughly | Unit, integration, queue tests |
| Document clearly | Queue, timeout, tries in PHPDoc |
| Monitor with Horizon | Dashboard, alerts, dead letters |

# 16. Listener Anti-Patterns Complete List

| Anti-pattern | Why it's bad | Correct approach |
| --- | --- | --- |
| Business logic in listener | Violates SRP | Delegate to Service |
| Non-idempotent listener | Duplicate side effects | Use unique constraints |
| Missing failure handling | Silent failures | Implement `failed()` method |
| Sync listener for expensive work | Blocks HTTP request | Use `ShouldQueue` |
| Listener with too many responsibilities | Hard to maintain | Split into multiple listeners |
| Missing queue configuration | Default queue may be wrong | Set `$queue` explicitly |
| Missing timeout | Jobs may hang forever | Set `$timeout` |
| Missing tries | No retry on failure | Set `$tries` and `$backoff` |
| Listener accessing request | Ties to HTTP context | Use event payload only |
| Listener with database queries | Performance impact | Batch or optimize queries |

# 18. Listener and Event Coupling

Listeners should depend only on the event payload, not on the dispatching domain's internals:

```php
// BAD: Listener depends on Component model directly
class BadListener implements ShouldQueue
{
    public function handle(ComponentPublished $event): void
    {
        $component = Component::find($event->componentId);
        // Direct model dependency
    }
}

// GOOD: Listener uses only event payload
class GoodListener implements ShouldQueue
{
    public function handle(ComponentPublished $event): void
    {
        $this->search->upsert('components', $event->componentId);
        // No model dependency
    }
}
```

# 29. Listener Idempotency Patterns

| Pattern | Use Case | Implementation |
| --- | --- | --- |
| Unique constraint | Database writes | `unique('table', 'column')` |
| Cache marker | Temporary dedup | `cache()->has("processed:{$id}")` |
| Idempotency key | External APIs | `Idempotency-Key` header |
| Status check | State transitions | Check if already processed |
| Upsert | Search indexing | `upsert()` instead of `insert()` |
| Conditional insert | Once-only operations | `insertOrIgnore()` |

# 30. Listener Idempotency Implementation

```php
// Pattern 1: Cache marker
class GenerateDocsListener implements ShouldQueue
{
    public function handle(ComponentPublished $event): void
    {
        $key = "docs:generated:{$event->componentId}";

        if (cache()->has($key)) {
            return;
        }

        $this->generateDocs($event->componentId);

        cache()->forever($key, true);
    }
}

// Pattern 2: Unique constraint
class GrantLicenseListener implements ShouldQueue
{
    public function handle(ProductPurchased $event): void
    {
        try {
            DB::table('licenses')->insert([
                'user_id' => $event->userId,
                'product_id' => $event->productId,
                'order_id' => $event->orderId,
                'created_at' => now(),
            ]);
        } catch (\Illuminate\Database\QueryException $e) {
            // Duplicate key = already granted
            if (str_contains($e->getMessage(), 'Duplicate entry')) {
                return;
            }
            throw $e;
        }
    }
}

// Pattern 3: Upsert
```

# 31. Listener Failure Recovery

```php
class UpdateSearchIndexListener implements ShouldQueue
{
    use InteractsWithQueue;

    public int $tries = 3;

    public array $backoff = [10, 30, 60];

    public function handle(ComponentPublished $event): void
    {
        $this->search->upsert('components', $event->componentId);
    }

    public function failed(ComponentPublished $event, \Throwable $exception): void
    {
        report($exception);

        logger()->error('search_index.failed', [
            'component_id' => $event->componentId,
            'error' => $exception->getMessage(),
            'tries' => $this->attempts(),
        ]);

        // Notify admin after max retries
        if ($this->attempts() >= $this->tries) {
            Notification::send(
                User::where('is_admin', true)->get(),
                new SearchIndexFailedNotification($event, $exception)
            );
        }
    }

    public function retryUntil(): \DateTime
    {
        return now()->addMinutes(30);
    }
}
```

# 39. Listener Anti-Patterns Complete List

| Anti-pattern | Why it's bad | Correct approach |
| --- | --- | --- |
| Business logic in listener | Violates SRP | Delegate to Service |
| Non-idempotent listener | Duplicate side effects | Use unique constraints |
| Missing failure handling | Silent failures | Implement `failed()` method |
| Sync listener for expensive work | Blocks HTTP request | Use `ShouldQueue` |
| Listener with too many responsibilities | Hard to maintain | Split into multiple listeners |
| Missing queue configuration | Default queue may be wrong | Set `$queue` explicitly |
| Missing timeout | Jobs may hang forever | Set `$timeout` |
| Missing tries | No retry on failure | Set `$tries` and `$backoff` |
| Listener accessing request | Ties to HTTP context | Use event payload only |
| Listener with database queries | Performance impact | Batch or optimize queries |
| Missing `failed()` method | No error handling | Implement `failed()` |
| Listener without middleware | No rate limiting | Add `RateLimited` middleware |
| Listener without logging | No observability | Add structured logging |

# 68. Listener and Job Batching

```php
class BatchProcessListener implements ShouldQueue
{
    public function handle(object $event): void
    {
        $batch = Bus::batch([
            new ProcessItem1($event->id),
            new ProcessItem2($event->id),
            new ProcessItem3($event->id),
        ])->then(function (Batch $batch) {
            // All jobs completed successfully
            logger()->info('batch.completed', ['batch_id' => $batch->id]);
        })->catch(function (Batch $batch, \Throwable $e) {
            // First batch job failure
            logger()->error('batch.failed', [
                'batch_id' => $batch->id,
                'error' => $e->getMessage(),
            ]);
        })->finally(function (Batch $batch) {
            // All jobs have completed or failed
            logger()->info('batch.finished', ['batch_id' => $batch->id]);
        })->onConnection('redis')->onQueue('default')->dispatch();
    }
}
```

# 70. Listener Best Practices Complete

| Practice | Description | Example |
| --- | --- | --- |
| One responsibility | One listener per action | `UpdateSearchIndex`, not `HandleAllEvents` |
| Idempotent | Safe for duplicate delivery | Use `upsert()` or unique constraints |
| Queue expensive work | I/O, external services | `implements ShouldQueue` |
| Handle failures | Implement `failed()` method | Log error, notify admin |
| Use proper queue | Match queue to work type | `search` queue for indexing |
| Set timeout | Prevent hanging jobs | `$timeout = 60` |
| Set tries and backoff | Handle transient failures | `$tries = 3, $backoff = [10, 30, 60]` |
| Test thoroughly | Unit, integration, queue tests | `handle()` direct call, `Queue::fake()` |
| Document clearly | Queue, timeout, tries in PHPDoc | PHPDoc block above class |
| Monitor with Horizon | Dashboard, alerts, dead letters | Horizon dashboard |
| Use middleware | Rate limiting, overlapping prevention | `RateLimited('search')` |
| Log structured data | Facilitate debugging | `logger()->info('event', [...])` |
