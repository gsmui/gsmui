# Purpose

This document specifies the **implementation-level deployment contract** for GsmUi: how code moves from a merged commit to a running, zero-downtime production environment, and the exact commands, ordering, and safeguards involved.

It covers:

* Build and asset compilation
* Environment configuration and secret injection
* Database migrations and seeders
* Config/route/view caching
* Queue worker (Horizon) and scheduler (cron) lifecycle
* Atomic, zero-downtime releases
* Rollback procedure

> See also: `05.38-deployment-architecture.md` (infrastructure targets), `05.39-devops-ci-cd.md` (CI/CD pipeline), `05.44-production-infrastructure.md` (production topology), and `33-devops.md` for the operational runbook. This document specifies the *how*, not the *where*.

---

# 1. Deployment Principles

1. **Immutable releases** — every deploy is a tagged, versioned artifact; never patch a running release in place.
2. **Zero-downtime** — new code is built alongside the old; traffic switches only after health checks pass.
3. **Migrations are forward-only and reversible** — every migration must have a working `down()` for rollback.
4. **One command** — a single `deploy` entrypoint orchestrates all steps; no manual sequencing.
5. **Fail safe** — if any step fails, the previous release keeps serving traffic.

---

# 2. Release Topology

```text
Git Tag (vX.Y.Z)
        │
        ▼
CI Build (compile assets, run tests)
        │
        ▼
Release Artifact (tarball / image)
        │
        ▼
Provision Release Dir  /releases/2026-07-15T09-00-00/
        │  (symlink current → release after health check)
        ▼
Run Migrations (isolated, --force)
        │
        ▼
Cache Warm (config/route/view)
        │
        ▼
Health Check  ──pass──▶  atomically swap `current` symlink
        │
        ▼
Restart Horizon + Scheduler (graceful)
```

# 3. The Deploy Script Contract

A single Artisan command (`php artisan gsmui:deploy`) implements the orchestration. It is **idempotent** — re-running it on a completed release is a no-op.

```php
// app/Console/Commands/DeployCommand.php
final class DeployCommand extends Command
{
    protected $signature = 'gsmui:deploy
        {--release= : release tag or timestamp}
        {--dry-run : validate without mutating}
        {--skip-migrations : do not run migrations}';

    public function handle(Deployer $deployer): int
    {
        $plan = $deployer->plan(
            release: $this->option('release') ?? now()->format('Y-m-d\TH-i-s'),
            skipMigrations: (bool) $this->option('skip-migrations'),
        );

        if ($this->option('dry-run')) {
            $this->table(['Step', 'Action'], $plan->rows());
            return self::SUCCESS;
        }

        $deployer->run($plan, output: $this->getOutput());

        return $plan->succeeded() ? self::SUCCESS : self::FAILURE;
    }
}
```

The `Deployer` service encapsulates each step so it can be unit-tested in isolation:

```php
// app/Domains/Deployment/Deployer.php
final class Deployer
{
    public function __construct(
        private MigrationRunner $migrations,
        private CacheWarmer $cache,
        private HealthProbe $health,
        private ReleaseSwapper $swapper,
        private WorkerSupervisor $workers,
    ) {}

    public function run(DeployPlan $plan, OutputInterface $output): void
    {
        $plan->provisionRelease();
        $this->cache->warm($plan->releasePath());

        if (! $plan->skipsMigrations()) {
            $this->migrations->up(release: $plan->release());
        }

        if (! $this->health->passes($plan->releasePath())) {
            $plan->markFailed('health check failed');
            return; // previous `current` symlink untouched
        }

        $this->swapper->atomicSwap($plan->releasePath());
        $this->workers->gracefulRestart(); // Horizon + scheduler
        $plan->markSucceeded();
    }
}
```

# 4. Migration Strategy

Migrations run **before** the symlink swap, against the new release, using `--force`:

```bash
php artisan migrate --force
```

Rules:

* `up()` must be backward-compatible with the *currently running* old code (expand, then contract).
* Long-running migrations use `Schema::table(...)->lazyById()` to avoid table locks.
* Data backfills run as queued jobs, never inline in a migration.
* Rollback uses `php artisan migrate:rollback --step=1 --force`.

---

# 5. Caching & Optimization

After a release is provisioned, warm the framework caches in the *new* release directory:

```bash
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan event:cache
```

> Caches are written into the release directory, so a rollback to the previous release also reverts its caches. Never run `config:cache` against a symlinked `current` during a swap.

---

# 6. Queue & Scheduler Lifecycle

Horizon and the scheduler must be restarted **after** the symlink swap, gracefully:

```bash
php artisan horizon:terminate   # drains active jobs, then exits
php artisan horizon             # supervisord respawns
php artisan schedule:work &     # or systemd timer invoking `schedule:run`
```

`WorkerSupervisor::gracefulRestart()` sends `horizon:terminate`, waits for the drain window, then signals Supervisor to respawn against the new `current` path. This prevents jobs from running against stale code mid-deploy.

# 7. Health Check Gate

The atomic swap is blocked until `HealthProbe` passes against the new release:

```php
// app/Domains/Deployment/HealthProbe.php
final class HealthProbe
{
    public function __construct(private Health $spatieHealth) {}

    public function passes(string $releasePath): bool
    {
        // Boot the new release in isolation to read its compiled config.
        return (bool) $this->spatieHealth
            ->registerUsing(fn () => null)
            ->check()->status; // DB, Redis, Horizon, Meilisearch, disk
    }
}
```

The HTTP `GET /up` endpoint (registered by Spatie Health, see `07.52-health-checks.md`) is the external load-balancer gate during the swap.

# 8. Rollback Procedure

Rollback is a single, atomic operation — repoint the `current` symlink to the previous release and restart workers:

```bash
php artisan gsmui:rollback --to=previous
```

```php
// app/Domains/Deployment/ReleaseSwapper.php
public function rollbackTo(string $previousReleasePath): void
{
    $this->atomicSwap($previousReleasePath);
    $this->workers->gracefulRestart();
    // NOTE: migrations are NOT auto-rolled-back; use `migrate:rollback` only
    // when the migration itself was the cause of failure.
}
```

Data migrations are treated as immutable (per `06.01-design-principles.md` §2); rollbacks prefer redeploying a fixed forward migration over reversing data.

# 11. Environment Configuration Management

## 11.1 Environment Variable Categories

GsmUi divides environment variables into three categories based on sensitivity and deployment timing:

| Category | Injection Time | Example | Storage |
| --- | --- | --- | --- |
| Build-time | CI build step | `APP_VERSION`, `NODE_ENV` | CI variables |
| Deploy-time | Before migrations | `APP_KEY`, `DB_HOST`, `REDIS_HOST` | Vault/secret manager |
| Runtime | Each request | `APP_DEBUG`, `LOG_LEVEL` | `.env` file |

## 11.2 Environment Validation

The deployer validates all required environment variables before running any steps:

```php
namespace App\Domains\Deployment;

final class EnvironmentValidator
{
    private const REQUIRED = [
        'APP_NAME',
        'APP_ENV',
        'APP_KEY',
        'APP_DEBUG',
        'APP_URL',
        'DB_CONNECTION',
        'DB_HOST',
        'DB_PORT',
        'DB_DATABASE',
        'DB_USERNAME',
        'DB_PASSWORD',
        'REDIS_HOST',
        'REDIS_PORT',
        'CACHE_DRIVER',
        'QUEUE_CONNECTION',
        'SESSION_DRIVER',
        'MAIL_MAILER',
        'MAIL_HOST',
        'MAIL_PORT',
    ];

    private const PRODUCTION_REQUIRED = [
        'SENTRY_DSN',
        'STRIPE_SECRET',
        'STRIPE_WEBHOOK_SECRET',
        'MEILISEARCH_HOST',
        'MEILISEARCH_KEY',
    ];

    public function validate(string $environment): array
    {
        $missing = [];

        foreach (self::REQUIRED as $key) {
            if (!env($key)) {
                $missing[] = $key;
            }
        }

        if ($environment === 'production') {
            foreach (self::PRODUCTION_REQUIRED as $key) {
                if (!env($key)) {
                    $missing[] = $key;
                }
            }
        }

        return $missing;
    }
}
```

# 12. Asset Compilation

## 12.1 Build Process

Assets are compiled during the CI build step, not during deployment. The compiled assets are included in the release artifact.

```bash
# CI build step
npm ci
npm run build
php artisan icons:cache
```

## 12.2 Asset Manifest

The Vite manifest (`public/build/manifest.json`) maps source paths to compiled paths:

```json
{
  "resources/css/app.css": {
    "file": "assets/app-4f8b2c1d.css",
    "isEntry": true
  },
  "resources/js/app.js": {
    "file": "assets/app-9a3b4c5d.js",
    "isEntry": true,
    "css": ["assets/app-4f8b2c1d.css"]
  },
  "resources/js/editor.js": {
    "file": "assets/editor-1b2c3d4e.js",
    "isEntry": true
  }
}
```

## 12.3 Asset Integrity

Compiled assets include content hashes in filenames for cache-busting. The deployment process verifies asset integrity:

```php
namespace App\Domains\Deployment;

final class AssetVerifier
{
    public function verify(string $releasePath): bool
    {
        $manifestPath = $releasePath . '/public/build/manifest.json';

        if (!file_exists($manifestPath)) {
            return false;
        }

        $manifest = json_decode(file_get_contents($manifestPath), true);

        foreach ($manifest as $source => $compiled) {
            $compiledPath = $releasePath . '/public/build/' . $compiled['file'];

            if (!file_exists($compiledPath)) {
                return false;
            }
        }

        return true;
    }
}
```

## 12.4 Asset Caching Strategy

Assets are served with long-lived cache headers (1 year) because filenames include content hashes:

```
Cache-Control: public, max-age=31536000, immutable
ETag: "4f8b2c1d"
```

The HTML response includes `<link rel="preload">` for critical CSS:

```html
<link rel="preload" href="/build/assets/app-4f8b2c1d.css" as="style">
<link rel="stylesheet" href="/build/assets/app-4f8b2c1d.css">
<script type="module" src="/build/assets/app-9a3b4c5d.js"></script>
```

# 13. Database Migration Strategy

## 13.1 Migration Ordering

Migrations run in a specific order to prevent conflicts:

1. **Schema changes** (add column, add index) — backward-compatible with current code
2. **Data backfills** — queued jobs, not inline in migrations
3. **Column drops** — after code is deployed and no longer reads the column
4. **Index drops** — after column drops are deployed

## 13.2 Migration Safety Rules

```php
namespace App\Database\Rules;

final class MigrationSafetyRules
{
    public const RULES = [
        'never_drop_columns_in_production' => true,
        'always_provide_down_migration' => true,
        'use_lazy_by_id_for_large_tables' => true,
        'never_lock_tables_exclusively' => true,
        'backfill_data_via_jobs_not_migrations' => true,
        'test_migrations_on_copy_of_production_data' => true,
        'validate_migration_backward_compatibility' => true,
    ];
}
```

## 13.3 Large Table Migrations

For tables with millions of rows, migrations use `lazyById()` to process in batches:

```php
use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;
use Illuminate\Support\Facades\DB;

return new class extends Migration
{
    public function up(): void
    {
        Schema::table('components', function (Blueprint $table) {
            $table->string('search_vector')->nullable()->after('description');
        });

        // Backfill in batches via queued job
        dispatch(new BackfillSearchVectorJob());
    }

    public function down(): void
    {
        Schema::table('components', function (Blueprint $table) {
            $table->dropColumn('search_vector');
        });
    }
};
```

## 13.4 Migration Testing

Before deploying, migrations are tested against a copy of production data:

```bash
# Test migration against production snapshot
php artisan migrate:fresh --seed --database=testing
php artisan migrate --database=testing
```

## 13.5 Zero-Downtime Migration Checklist

| Step | Action | Rollback |
| --- | --- | --- |
| 1 | Add nullable column | `dropColumn()` |
| 2 | Deploy code that reads/writes new column | N/A |
| 3 | Backfill column via job | Delete backfilled rows |
| 4 | Add NOT NULL constraint with default | `dropColumn()` |
| 5 | Remove default | Add default back |
| 6 | Drop old column (if replacing) | Add column back |

# 14. Cache Warming Strategy

## 14.1 Cache Warming Steps

After a release is provisioned, the following caches are warmed:

```bash
# 1. Config cache (must be first — other commands depend on it)
php artisan config:cache

# 2. Route cache (speeds up route resolution)
php artisan route:cache

# 3. View cache (compiles Blade templates)
php artisan view:cache

# 4. Event cache (compiles event listeners)
php artisan event:cache

# 5. Icon cache (compiles Blade icons)
php artisan icons:cache

# 6. Application cache (warms frequently accessed data)
php artisan cache:warm
```

## 14.2 Cache Warming Order Dependencies

```text
config:cache
    │
    ├──▶ route:cache (depends on config for route prefixes)
    │
    ├──▶ view:cache (depends on config for view paths)
    │
    ├──▶ event:cache (depends on config for event listeners)
    │
    └──▶ icons:cache (depends on config for icon paths)
            │
            └──▶ cache:warm (depends on all of the above)
```

## 14.3 Cache Warming Failure Handling

If any cache warming step fails, the deployment is aborted:

```php
namespace App\Domains\Deployment;

final class CacheWarmer
{
    public function warm(string $releasePath): bool
    {
        $steps = [
            'config:cache',
            'route:cache',
            'view:cache',
            'event:cache',
            'icons:cache',
        ];

        foreach ($steps as $step) {
            $exitCode = $this->runCommand($step, $releasePath);

            if ($exitCode !== 0) {
                Log::error('deploy.cache_warm_failed', [
                    'step' => $step,
                    'exit_code' => $exitCode,
                ]);

                return false;
            }
        }

        return true;
    }
}
```

# 15. Queue Worker Lifecycle

## 15.1 Worker Restart Sequence

```text
Deployer detects new release
    │
    ▼
Send SIGTERM to Horizon master process
    │
    ├──▶ Horizon sends SIGTERM to all worker processes
    │    ├──▶ Workers finish current job (up to 30s timeout)
    │    └──▶ Workers exit gracefully
    │
    ├──▶ Horizon master process exits
    │
    ▼
Supervisor detects Horizon process exited
    │
    ├──▶ Restarts Horizon against new `current` symlink
    │    ├──▶ Horizon starts new worker pool
    │    └──▶ Workers begin processing jobs from new code
    │
    ▼
Deployer verifies Horizon is running
    │
    └──▶ Continue deployment
```

## 15.2 Worker Drain Timeout

The drain timeout is configurable:

```php
// config/horizon.php
'environments' => [
    'production' => [
        'drain' => env('HORIZON_DRAIN_TIMEOUT', 30),
        'minProcesses' => 1,
        'maxProcesses' => 10,
        'balanceMaxShift' => 1,
        'balanceCooldown' => 3,
    ],
],
```

## 15.3 Worker Health Check

After restart, the deployer verifies workers are processing jobs:

```php
namespace App\Domains\Deployment;

final class WorkerHealthCheck
{
    public function verify(): bool
    {
        $status = Artisan::call('horizon:status');

        return str_contains(Artisan::output(), 'running');
    }
}
```

# 16. Scheduler Lifecycle

## 16.1 Scheduler Restart Sequence

The scheduler is restarted after the symlink swap:

```bash
# Stop the current scheduler
pkill -f "schedule:run" || true

# Start the new scheduler
php artisan schedule:work &
```

## 16.2 Scheduler vs Cron

GsmUi uses `schedule:work` instead of cron for the scheduler:

| Method | Pros | Cons |
| --- | --- | --- |
| Cron + `schedule:run` | Simple, reliable | One-minute granularity |
| `schedule:work` | Sub-minute, self-managing | Requires process manager |
| Systemd timer | Precise, restartable | More configuration |

## 16.3 Scheduler Health Monitoring

```php
namespace App\Jobs;

use Illuminate\Support\Facades\Log;

final class MonitorSchedulerHealth
{
    public function handle(): void
    {
        $lastRun = cache()->get('scheduler:last_run');

        if (!$lastRun || now()->diffInMinutes(now()->parse($lastRun)) > 2) {
            Log::warning('scheduler.missed_run', [
                'last_run' => $lastRun,
                'minutes_since' => $lastRun ? now()->diffInMinutes(now()->parse($lastRun)) : null,
            ]);

            // Restart scheduler
            Artisan::call('schedule:work');
        }

        cache()->put('scheduler:last_run', now()->toIso8601String());
    }
}
```

# 18. Blue-Green Deployment

## 18.1 Blue-Green Strategy

GsmUi supports blue-green deployments for zero-downtime:

```text
Blue (current) ──── serving traffic
Green (new)    ──── deploying, not serving traffic
    │
    ▼
Green passes health check
    │
    ▼
Atomic symlink swap
    │
    ├──▶ Green ──── serving traffic
    └──▶ Blue  ──── standby (previous release)
```

## 18.2 Blue-Green Implementation

```php
namespace App\Domains\Deployment;

final class BlueGreenDeployer
{
    public function deploy(string $releasePath): void
    {
        // 1. Provision green release
        $this->provisioner->provision($releasePath);

        // 2. Run migrations on green
        $this->migrations->up($releasePath);

        // 3. Warm caches on green
        $this->cacheWarmer->warm($releasePath);

        // 4. Health check green
        if (!$this->healthProbe->passes($releasePath)) {
            throw new DeploymentFailedException('health', 'Green release failed health check');
        }

        // 5. Atomic swap symlink
        $this->swapper->atomicSwap($releasePath);

        // 6. Restart workers against green
        $this->workers->gracefulRestart();

        // 7. Verify green is serving
        if (!$this->healthProbe->passes()) {
            // Rollback to blue
            $this->rollback();
            throw new DeploymentFailedException('health', 'Post-swap health check failed');
        }
    }
}
```

## 18.3 Blue-Green Rollback

```php
public function rollback(): void
{
    $previousRelease = $this->releaseManager->previous();

    if (!$previousRelease) {
        throw new ReleaseNotFoundException('previous');
    }

    $this->swapper->atomicSwap($previousRelease->path());
    $this->workers->gracefulRestart();

    Log::warning('deploy.rollback.completed', [
        'from_release' => $this->releaseManager->current()->tag(),
        'to_release' => $previousRelease->tag(),
    ]);
}
```

# 19. Canary Deployment

## 19.1 Canary Strategy

For high-risk changes, GsmUi supports canary deployments:

```text
Current release ──── serving 90% traffic
Canary release  ──── serving 10% traffic
    │
    ▼
Canary metrics pass threshold
    │
    ├──▶ Promote canary to 100%
    └──▶ Rollback canary if metrics degrade
```

## 19.2 Canary Implementation

```php
namespace App\Domains\Deployment;

final class CanaryDeployer
{
    public function deploy(
        string $releasePath,
        float $canaryPercentage = 10.0,
    ): void {
        // Deploy canary alongside current release
        $this->provisioner->provision($releasePath);

        // Configure load balancer to route percentage of traffic
        $this->loadBalancer->setCanaryWeight($canaryPercentage);

        // Monitor canary for configurable period
        $this->monitorCanary($releasePath, duration: 300); // 5 minutes
    }

    private function monitorCanary(string $releasePath, int $durationSeconds): void
    {
        $start = time();

        while (time() - $start < $durationSeconds) {
            $metrics = $this->metricsCollector->getCanaryMetrics();

            if ($this->shouldRollback($metrics)) {
                $this->loadBalancer->removeCanary();
                throw new DeploymentFailedException('canary', 'Canary metrics degraded');
            }

            sleep(10);
        }

        // Canary passed, promote to 100%
        $this->loadBalancer->promoteCanary();
    }

    private function shouldRollback(array $metrics): bool
    {
        return $metrics['error_rate'] > 0.01  // > 1% errors
            || $metrics['p99_latency_ms'] > 500  // > 500ms p99
            || $metrics['cpu_usage'] > 80;  // > 80% CPU
    }
}
```

# 20. Deployment Rollback Strategy

## 20.1 Rollback Types

| Type | Trigger | Speed | Risk |
| --- | --- | --- | --- |
| Symlink rollback | Manual command | Instant | Low (code only) |
| Migration rollback | Failed migration | Minutes | Medium (data risk) |
| Full rollback | Catastrophic failure | Minutes | Low (restore from backup) |
| Canary rollback | Metrics degrade | Instant | Low (traffic shift) |

## 20.2 Rollback Decision Tree

```text
Issue detected
    │
    ├──▶ Is it a code issue?
    │    ├──▶ Yes: Symlink rollback to previous release
    │    └──▶ No: Continue investigation
    │
    ├──▶ Is it a migration issue?
    │    ├──▶ Yes: Migration rollback + symlink rollback
    │    └──▶ No: Continue investigation
    │
    ├──▶ Is it a data issue?
    │    ├──▶ Yes: Restore from backup + symlink rollback
    │    └──▶ No: Continue investigation
```

# 29. Deployment Rollback Procedures

## 29.1 Automated Rollback

When a deployment fails health checks, the deployer automatically rolls back:

```php
namespace App\Domains\Deployment;

final class AutomaticRollback
{
    public function execute(DeployPlan $plan): void
    {
        $previousRelease = $this->releaseManager->previous();

        if (!$previousRelease) {
            Log::emergency('deploy.no_previous_release', [
                'current_release' => $plan->release(),
            ]);
            return;
        }

        Log::warning('deploy.auto_rollback_started', [
            'from_release' => $plan->release(),
            'to_release' => $previousRelease->tag(),
        ]);

        $this->swapper->atomicSwap($previousRelease->path());
        $this->workers->gracefulRestart();

        Log::warning('deploy.auto_rollback_completed', [
            'from_release' => $plan->release(),
            'to_release' => $previousRelease->tag(),
        ]);
    }
}
```

## 29.2 Manual Rollback

```bash
# List available releases
php artisan gsmui:releases

# Rollback to specific release
php artisan gsmui:rollback --to=v1.2.3

# Rollback to previous release
php artisan gsmui:rollback --to=previous

# Dry run rollback
php artisan gsmui:rollback --to=previous --dry-run
```

## 29.3 Rollback with Migration

When a rollback requires reverting a migration:

```bash
# 1. Rollback the migration
php artisan migrate:rollback --step=1 --force

# 2. Symlink rollback
php artisan gsmui:rollback --to=previous

# 3. Restart workers
php artisan horizon:terminate

# 4. Verify health
php artisan gsmui:health:check
```

## 29.4 Rollback Verification

After rollback, verify:

1. Health check passes
2. Workers are processing jobs
3. Scheduler is running
4. No errors in logs
5. Critical paths work

```php
            ['start' => '2026-12-24', 'end' => '2026-12-26'],
            ['start' => '2026-12-31', 'end' => '2027-01-01'],
            ['start' => '2026-11-27', 'end' => '2026-12-01'],
        ];

        $now = now()->toDateString();

        foreach ($freezePeriods as $period) {
            if ($now >= $period['start'] && $now <= $period['end']) {
                return true;
            }
        }

        return false;
    }
}
```

## 35.3 Emergency Deployment During Freeze

Emergency deployments during freeze require:

1. Approval from two senior developers
2. Incident ticket number
3. Rollback plan documented
4. Post-incident review scheduled

# 37. Deployment Rollback Decision Tree

```text
Issue detected in production
    │
    ├── Is it a code issue?
    │   ├── Yes → Symlink rollback to previous release
    │   └── No  → Continue investigation
    │
    ├── Is it a migration issue?
    │   ├── Yes → Migration rollback + symlink rollback
    │   └── No  → Continue investigation
    │
    ├── Is it a data issue?
    │   ├── Yes → Restore from backup + symlink rollback
    │   └── No  → Continue investigation
    │
    ├── Is it an infrastructure issue?
    │   ├── Yes → Scale/restart infrastructure
    │   └── No  → Continue investigation
    │
    ├── Is it a cache issue?
    │   ├── Yes → Flush cache + verify
    │   └── No  → Continue investigation
    │
    └── Is it an external dependency issue?
        ├── Yes → Enable circuit breaker / fallback
        └── No  → Page on-call engineer
```

# 38. Deployment Verification Script

```bash
#!/bin/bash
# scripts/post-deploy-verify.sh

set -euo pipefail

ENVIRONMENT=${1:-production}
BASE_URL="https://${ENVIRONMENT}.gsmui.dev"

echo "=== Post-Deploy Verification for $ENVIRONMENT ==="

# 1. Health check
echo "[1/6] Health check..."
HTTP_STATUS=$(curl -s -o /dev/null -w "%{http_code}" "$BASE_URL/up")
if [ "$HTTP_STATUS" != "200" ]; then
    echo "FAIL: Health check returned $HTTP_STATUS"
    exit 1
fi
echo "PASS"

# 2. Horizon status
echo "[2/6] Horizon status..."
php artisan horizon:status
echo "PASS"

# 3. Scheduler status
echo "[3/6] Scheduler status..."
php artisan schedule:list --no-interaction
echo "PASS"

# 4. Database connectivity
echo "[4/6] Database connectivity..."
php artisan tinker --execute="DB::connection()->getPdo(); echo 'OK';"
echo "PASS"

# 5. Redis connectivity
echo "[5/6] Redis connectivity..."
php artisan tinker --execute="Redis::ping(); echo 'OK';"
echo "PASS"

# 6. Critical page loads
echo "[6/6] Critical page loads..."
for path in "/" "/docs" "/components" "/marketplace"; do
    HTTP_STATUS=$(curl -s -o /dev/null -w "%{http_code}" "$BASE_URL$path")
    if [ "$HTTP_STATUS" != "200" ] && [ "$HTTP_STATUS" != "302" ]; then
        echo "FAIL: $path returned $HTTP_STATUS"
        exit 1
    fi
done
echo "PASS"

echo "=== All verifications passed ==="
```

# 39. Deployment Error Recovery

## 39.1 Recovery Procedures

| Failure | Recovery Action | Timeout |
| --- | --- | --- |
| Migration failure | `migrate:rollback` + symlink rollback | 5 min |
| Cache warm failure | Skip cache, deploy without optimization | 1 min |
| Health check failure | Auto-rollback to previous release | 2 min |
| Worker restart failure | Force kill + restart | 3 min |
| Symlink swap failure | Manual intervention required | — |

## 39.2 Recovery Logging

Every recovery action is logged:

```php
namespace App\Domains\Deployment;

final class RecoveryLogger
{
    public static function logRecovery(
        string $trigger,
        string $action,
        bool $success,
    ): void {
        Log::channel('stack')->warning('deploy.recovery', [
            'trigger' => $trigger,
            'action' => $action,
            'success' => $success,
        ]);

        Log::channel('audit')->info('deploy.recovery', [
            'trigger' => $trigger,
            'action' => $action,
            'success' => $success,
        ]);
    }
}
```

# 40. Operational Rules (Complete Final)

1. Immutable releases — every deploy is a tagged, versioned artifact.
2. Zero-downtime — new code is built alongside the old; traffic switches only after health checks pass.
3. Migrations are forward-only and reversible — every migration must have a working `down()`.
4. One command — `php artisan gsmui:deploy` orchestrates all steps.
5. Fail safe — if any step fails, the previous release keeps serving traffic.
6. Environment validation — all required env vars are checked before deployment.
7. Asset integrity — compiled assets are verified after provisioning.
8. Cache warming — all framework caches are warmed before traffic switch.
9. Worker lifecycle — Horizon is gracefully restarted after symlink swap.
10. Scheduler lifecycle — the scheduler is restarted after symlink swap.
11. Health check gate — atomic swap is blocked until health check passes.
12. Rollback procedure — `php artisan gsmui:rollback --to=previous` repoints symlink.
13. Deployment audit — every deployment action is logged in the audit channel.
14. Deployment monitoring — metrics are collected and alerted on.
15. Blue-green deployment — supported for zero-downtime releases.
16. Canary deployment — supported for high-risk changes.
17. Deployment testing — pre-deploy and post-deploy tests verify correctness.
18. Deployment security — access control and secrets management.
19. Deployment documentation — runbook, changelog, and architecture diagrams.
20. Deployment automation — CI/CD pipeline handles build, test, and deploy.
21. Container deployment — Docker-based for consistent environments.
22. Cloud deployment — AWS ECS/Fargate for production.
23. Automated rollback — triggered on health check failure.
24. Manual rollback — available for operator intervention.
25. Environment promotion — code moves Local → CI → Staging → Production.
26. Pre-deploy checklist — verified before every deployment.
27. Post-deploy verification — health, workers, scheduler, logs checked.
28. Deployment rollback verification — health, workers, scheduler checked after rollback.
29. Deployment secrets — injected from Vault at deploy time, never baked into artifacts.
30. Deployment audit trail — every action logged in the audit channel.
31. Deployment secrets rotation — secrets rotated quarterly via Vault.
32. Deployment health gate — health check must pass before traffic switch.
33. Deployment worker drain — Horizon workers drain before restart.
34. Deployment cache warm — all caches warmed before traffic switch.
35. Deployment asset verification — compiled assets verified after provisioning.
36. Deployment migration safety — expand/contract pattern for zero-downtime migrations.

39. Deployment documentation — runbook, changelog, and architecture diagrams maintained.
