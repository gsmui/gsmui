# Purpose

> See also: `07.01-overview.md` for the layer recap and `07.02-request-lifecycle.md` for the generic HTTP/Livewire flow. This document is the **synthesis** of Section 07 — it walks two real, end-to-end requests through every layer so the contracts defined in `07.02`–`07.59` can be seen working together rather than in isolation.

The earlier 07 files each specify a single layer's contract in isolation: `07.06-service-layer.md` defines services, `07.07-repository-layer.md` defines repositories, `07.08-action-layer.md` defines actions, and so on. This document ties them together. By the end you should be able to answer "when a user buys a template, which file owns authorization, which file owns the charge, and which file owns the receipt email?" and "when a doc page is rendered, where does caching happen and where does Markdown get parsed?".

Two scenarios are traced:

1. **A write request** — a marketplace template purchase (the hardest path: validation → auth → action → service → repository → model → event → queued job → listener, touching billing and payment webhooks).
2. **A read request** — a documentation page render (a read-mostly path that leans on caching, the Documentation Engine, and Blade rendering).

Every step links to the exact `07.*` file that defines its contract, so this document doubles as a navigable index across Section 07.

# 1. Scenario A — Marketplace Template Purchase (Write)

A signed-in user clicks **Buy** on a premium template in the marketplace. This is a classic write use case: money moves, a license is provisioned, an email is sent, and the work must be atomic and idempotent.

## 1.3 Notes Tied to Real Contracts

- **Validation before authorization.** The Form Request (`07.18`) runs first and rejects malformed input cheaply. Authorization (`07.15` / `07.23`) runs only on valid input — the controller delegates both to Laravel's request lifecycle, never hand-rolling checks.
- **One transaction per use case.** `PurchaseTemplateAction::run()` (see `07.08-action-layer.md` §2–§4) opens the transaction. `MarketplaceService`, `OrderRepository`, and `BillingService::charge()` all execute *inside* that open transaction. A failed capture throws and the whole order write rolls back — no orphaned `orders` rows.
- **Events fire only after commit.** `dispatchAfterCommit(new OrderPlaced(...))` (see `07.08` §5 and `07.12-events.md`) guarantees listeners never observe rolled-back state. If the capture throws, `OrderPlaced` is never emitted and no receipt is sent.
- **Idempotency lives in two places.** The action scopes a cache key via `markProcessed()` (`07.08` §6) and the `orders.idempotency_key` unique constraint (per `06.01-design-principles.md` §15). The payment webhook (`07.29-webhooks.md`) is independently idempotent so a retried provider callback never double-provisions a license.
- **Billing is a service, not a controller concern.** `BillingService::charge()` (`07.30-billing.md`) owns the gateway call, invoice creation, and subscription entitlement checks. The action never talks to Stripe/Paddle directly.
- **Listeners stay thin and queued.** Each listener in `07.13-listeners.md` does one thing and pushes the heavy lifting to a queued job (`07.14-jobs.md`) running on Horizon. The HTTP response returns before the receipt email is sent.
- **Webhooks reconcile, they don't lead.** The synchronous purchase path is the source of truth. The webhook (`07.29`) only *reconciles* provider state (e.g. a late `succeeded` callback) and is safe to call multiple times.

## 2.3 Notes Tied to Real Contracts

- **Reads skip actions and transactions.** Unlike the purchase path, there is no `Action` (`07.08`) and no `DB::transaction`. Reads go Controller → Service → Repository (`07.06` / `07.07`) directly. Actions are reserved for writes, per `07.01-overview.md` §2.
- **Caching is at the repository boundary.** `DocumentationPageRepository::findCached()` (`07.07` + `07.25-cache.md`) wraps the model load in a tagged `Cache::remember`. Invalidating a doc version bumps the `docs:{version}` cache tag, so a republish flushes every page at once without per-page key management.
- **The Documentation Engine owns parsing.** Raw Markdown is never rendered in Blade. `DocumentationEngine::compile()` (`07.35-documentation-engine.md`) produces safe HTML, the nav tree, and TOC anchors. Blade (`07.20`) only lays out the engine's output through `<x-docs.*>` components.
- **Search is for in-page navigation, not full-text here.** The Scout/Meilisearch layer (`07.24-search.md`) supplies heading anchors for the "on this page" TOC. Full-text doc search is a separate controller that queries the same index.
- **Storage is pluggable.** Markdown sources live behind the storage abstraction (`07.26-storage.md`) — local disk in dev, object storage in production — so the engine never hard-codes a path.
- **Anonymous responses are cacheable at the edge.** `07.25-cache.md` drives `Cache-Control`/`Surrogate-Key` headers for signed-out visitors; authenticated responses skip public caching and rely on the tagged Redis layer instead.

# 4. Dependency Rule Reaffirmed

Both scenarios obey the strict dependency rule stated in `07.01-overview.md` §2 and enforced in `07.07-repository-layer.md`:

```text
Controller / Livewire ──▶ Action ──▶ Service ──▶ Repository ──▶ Model
```

- Controllers and Livewire components (`07.19`) never touch repositories or models directly.
- Writes always pass through an Action (`07.08`); reads may call a Service (`07.06`) directly.
- Repositories (`07.07`) are the only layer that touches Eloquent models (`07.48`).
- Events (`07.12`) are the only sanctioned way to cross into async work (`07.13` listeners, `07.14` jobs).

Any implementation that violates this spine (e.g. a controller calling `Order::create()`) fails the contract in `07.07-repository-layer.md` and should be rejected in review.

# 6. Scenario C — Livewire Component Update (Hybrid)

A user interacts with a Livewire component on a page—for example, updating a component's status from "draft" to "published" via a toggle. This is a hybrid path: it uses Livewire's update cycle (XHR) instead of a full HTTP request.

## 6.1 Flow Diagram

```text
[ Browser ]
    │  Livewire XHR POST /livewire/update
    │  XSRF token + Livewire snapshot
    ▼
[ Laravel HTTP Kernel ]  ───────────────────────────── 07.02-request-lifecycle.md
    │  ├─ TrustProxies / EncryptCookies
    │  ├─ VerifyCsrfToken                              ── 07.57-security.md
    │  └─ AssignCorrelationId                          ── 07.54-logging.md
    ▼
[ Livewire Manager ]
    │  Decrypts snapshot, resolves component
    ▼
[ ComponentController::update() ]  ─────────────────── 07.19-livewire-architecture.md
    │  Hydrates state from snapshot
    ▼
[ Component::toggleStatus() ]  ─────────────────────── 07.19-livewire-architecture.md
    │  Calls action method
    ▼
[ PublishComponentAction::run() ]  ─────────────────── 07.08-action-layer.md
    │  DB::transaction begins
    ▼
    ├─ [ ComponentService::publish() ]  ────────────── 07.06-service-layer.md
    │     ├─ checks status transition validity
    │     └─ calls repository inside open txn
    │
    ├─ [ ComponentRepository::updateStatus() ]  ────── 07.07-repository-layer.md
    │     └─ updates component row
    │
    └─ dispatchAfterCommit(new ComponentPublishedEvent($component))  ── 07.12-events.md
    │
    ▼
[ DB::transaction commits ]
    │
    ▼
[ Listeners (queued) ]
    ├─ SearchIndexListener       → reindex component in Meilisearch
    └─ NotifySubscribersListener → email subscribers
    │
    ▼
[ Livewire returns updated snapshot + DOM diff ]
    │
    ▼
[ Browser ]  applies partial DOM update
```

| # | Step | Owning layer | Defining `07.*` file |
| --- | --- | --- | --- |

| 2 | CSRF + correlation ID | Security/logging | `07.57-security.md`, `07.54-logging.md` |
| 3 | Livewire snapshot decryption, component hydration | Livewire | `07.19-livewire-architecture.md` |

| 11 | Browser applies partial update | Frontend | `08-frontend-architecture.md` |

## 6.3 Notes Tied to Real Contracts

- **Livewire follows the same dependency spine.** Even though Livewire components are hydrated from snapshots, the action/service/repository chain is identical to a controller flow (see `07.08-action-layer.md`). The Livewire component plays the role of the controller.
- **Livewire updates are XHR, not full page reloads.** The response is a JSON payload containing the updated snapshot and a DOM diff. The browser applies the diff without a full page refresh.
- **CSRF protection applies.** Livewire sends the XSRF token with every XHR request, and the `VerifyCsrfToken` middleware validates it (see `07.57-security.md`).
- **Correlation IDs are threaded.** The `AssignCorrelationId` middleware runs for Livewire XHR requests, so every log line during the update has the same correlation ID.
- **Actions open transactions.** The `PublishComponentAction::run()` opens a transaction, ensuring that the status update and any side effects are atomic (see `07.08-action-layer.md` §4).
- **Events fire after commit.** `ComponentPublishedEvent` is dispatched only after the transaction commits, so listeners never observe rolled-back state.
- **Listeners are queued.** The search reindex and subscriber notification happen asynchronously, keeping the Livewire response fast.

# 11. Dependency Rule Across All Scenarios

All six scenarios obey the strict dependency rule:


Exceptions:

# 16. Operational Rules (Complete)

1. All six scenarios follow the dependency spine: Controller → Action → Service → Repository → Model.
2. Reads skip the Action layer; writes always use Actions.
3. Transactions are opened in Actions, never in Services or Repositories.
4. Events are dispatched after commit via `dispatchAfterCommit()`.

6. Webhooks are idempotent and skip CSRF.

9. Scheduled tasks bypass the HTTP kernel entirely.
10. Every scenario produces structured log entries with correlation IDs.
11. Cache strategy is read-through for reads, write-through for writes.
12. Security middleware runs for all HTTP scenarios.
13. Failure modes are documented and caught at the correct layer.
14. The dependency rule is the single source of truth for architecture.
15. Any violation of the spine is rejected in code review.

| Webhook | HTTP 4xx/5xx | application/problem+json |

| Password Reset | Redirect with flash | text/html |
| File Upload | problem+json | application/problem+json |
| Search | problem+json | application/problem+json |
| Queue Job | Log entry + job marked failed | N/A |
| Observer | Exception bubbles to caller | Depends on caller |
| Feature Flag | None (flag defaults to false) | N/A |

## 26.2 Error Handling in Actions

Actions catch and re-throw domain exceptions:

```php
public function run(ComponentData $data): Component
{
    try {
        return DB::transaction(function () use ($data) {
            $existing = $this->repository->findBySlug($data->slug);

            if ($existing) {
                throw ComponentExceptionFactory::alreadyExists($data->slug);
            }

            return $this->service->create($data);
        });
    } catch (ComponentAlreadyExistsException $e) {
        Log::warning('action.create_component.conflict', [
            'slug' => $data->slug,
            'exception' => $e->getMessage(),
        ]);
        throw $e;
    }
}
```

## 26.3 Error Handling in Services

Services catch infrastructure failures and wrap them in domain exceptions:

```php
public function search(string $query): Collection
{
    try {
        return $this->searchClient->search($query);
    } catch (\MeiliSearch\Exceptions\ApiException $e) {
        Log::error('search.engine.error', [
            'query' => $query,
            'exception' => $e->getMessage(),
        ]);
        throw new SearchEngineUnavailableException('Meilisearch', $e);
    }
}
```

## 26.4 Error Handling in Listeners

Listeners catch exceptions and log them, but do not re-throw:

```php
public function handle(OrderPlaced $event): void
{
    try {
        SendPurchaseReceiptJob::dispatch(orderId: $event->order->id);
    } catch (\Exception $e) {
        Log::error('listener.send_receipt.failed', [
            'order_id' => $event->order->id,
            'exception' => $e->getMessage(),
        ]);
    }
}
```

## 26.5 Error Handling in Jobs

Jobs implement `failed()` for error logging:

```php
public function handle(): void
{
    $order = Order::findOrFail($this->orderId);

    $this->billingService->sendReceipt($order);
}

public function failed(\Throwable $exception): void
{
    Log::channel('queue')->error('job.send_receipt.failed', [
        'order_id' => $this->orderId,
        'exception' => get_class($exception) . ': ' . $exception->getMessage(),
        'attempt' => $this->attempts(),
    ]);
}
```

| Observer | Caller's transaction | Varies |

## 27.2 Transaction Safety Rules

1. **One transaction per use case.** Each write scenario opens exactly one transaction in its action.
2. **Services execute inside the open transaction.** Services never open their own transactions.
3. **Repositories execute inside the open transaction.** Repositories never open their own transactions.
4. **Events fire after commit.** `dispatchAfterCommit()` ensures listeners never observe rolled-back state.
5. **Rollback on exception.** If any step throws, the entire transaction rolls back.
6. **No nested transactions.** Savepoints are used only when absolutely necessary.

## 27.3 Transaction Failure Scenarios

| Failure | Where Caught | Recovery |
| --- | --- | --- |
| Payment declined | BillingService throws | Transaction rolls back, 402 returned |
| Duplicate order | Unique constraint violation | Transaction rolls back, 409 returned |
| Search engine down | SearchService throws | Transaction rolls back, 503 returned |
| Database timeout | DB::transaction callback | Transaction rolls back, 500 returned |
| Queue worker crash | Horizon supervisor | Job retried |

# 40. Cross-Scenario Data Flow Summary

## 40.1 Data Flow for Template Purchase (Write)

```
User clicks "Buy"
  → Browser sends POST /marketplace/templates/{slug}/purchase
  → Kernel: TrustProxies, EncryptCookies, VerifyCsrfToken, Authenticate
  → Route resolves to MarketplaceController@purchase
  → PurchaseTemplateRequest validates: template_slug, payment_method_id, idempotency_key
  → TemplatePolicy@purchase checks: user is authenticated, not already purchased
  → Controller builds PurchaseTemplateData DTO
  → PurchaseTemplateAction::run($dto) opens DB transaction
    → MarketplaceService resolves template + price (incl. region tax)
    → MarketplaceService checks active Subscription (entitlement)
    → OrderRepository::create() persists order row (unique idempotency_key)
    → TemplateRepository::markPurchased() updates template
    → BillingService::charge() calls PaymentGateway::authorizeAndCapture
    → dispatchAfterCommit(new OrderPlaced($order))
  → DB transaction commits
  → Controller redirects to /library with flash message
  → Listeners fire: SendPurchaseReceiptListener, ProvisionLicenseListener
    → SendPurchaseReceiptJob dispatched on Horizon
    → ProvisionLicenseJob dispatched on Horizon
  → Payment provider webhook arrives: POST /webhooks/payments
    → PaymentSucceededWebhook verifies signature
    → WebhookIdempotency::check() returns false (first time)
    → ProcessPaymentSucceededAction::run() opens DB transaction
      → OrderRepository::findByIdempotencyKey() finds order
      → OrderRepository::markPaid() updates order status
      → dispatchAfterCommit(new PaymentSucceeded($order))
    → DB transaction commits
    → WebhookIdempotency::markProcessed() caches event_id
    → HTTP 200 OK response
```

## 40.2 Data Flow for Documentation Page (Read)

```
User navigates to /docs/2.x/installation
  → Browser sends GET /docs/{version}/{page}
  → Kernel: TrimStrings, ConvertEmptyStringsToNull, EncryptCookies
  → Route resolves to DocsController@show
  → Controller builds DocumentationRequest DTO (version, slug)
  → DocumentationService::render() orchestrates
    → DocumentationPageRepository::findCached() wraps in Cache::remember
      → Cache::tags(['docs:2.x'])->remember('page:installation', 3600, fn)
        → Cache miss: DocumentationPage model loads from DB
        → Cache hit: return cached model
    → DocumentationEngine::compile() parses Markdown source
      → Reads Markdown from storage (pluggable disk)
      → Parses front-matter + AST
      → Builds sidebar/nav tree (cached)
      → Extracts code-fence metadata for highlighting
    → SearchIndex lookup for "on this page" TOC
      → Scout/Meilisearch returns heading anchors
  → Blade renders: <x-docs.layout> → <x-docs.sidebar> → <x-docs.prose>
  → Response with public cache headers for anonymous
  → Browser renders docs page
```
