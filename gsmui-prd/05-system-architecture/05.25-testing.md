# Purpose

This document outlines the testing strategy for the GsmUi platform, including test types, coverage targets, execution strategy, and quality gates. It serves as the authoritative reference for how quality is assured across the entire platform.

---

# Architecture Overview

The testing strategy follows the testing pyramid model with a foundation of unit tests, a middle layer of feature and integration tests, and a cap of end-to-end browser tests. Each layer provides different tradeoffs between speed, coverage, and confidence.

Unit tests run fast and in isolation, providing rapid feedback during development. Feature tests validate component behavior and HTTP interactions with real database operations. Browser tests verify complete user flows in a real browser environment.

Static analysis and code style checks run before tests to catch issues early. The entire test suite executes in the CI pipeline with quality gates that prevent merging of code that doesn't meet coverage and passing thresholds.

The testing infrastructure uses the same software stack as production (MySQL, Redis, Nginx) to ensure tests validate real-world behavior. Test databases are isolated per run and seeded with known data states for reproducible results.

# Test Types

## Unit Tests

Unit tests validate individual classes and methods in isolation. External dependencies like databases, caches, and HTTP services are mocked to ensure tests focus purely on business logic.

### Scope

- Service class methods
- Repository query logic
- Model relationships and scopes
- Validation rules
- Helper functions
- Policy authorization logic
- Event listener behavior

### Conventions

```php
class UserServiceTest extends TestCase
{
    public function test_user_can_be_suspended(): void
    {
        $user = User::factory()->create(['status' => 'active']);
        $service = new UserService(
            users: Mockery::mock(UserRepository::class),
            logger: Mockery::mock(ActivityLogger::class),
        );

        $service->suspendUser($user, 'Terms violation');

        $this->assertEquals('suspended', $user->fresh()->status);
    }
}
```

### Coverage Target

90% coverage for business logic classes.

## Feature Tests

Feature tests validate HTTP endpoints, Livewire component behavior, and integration between multiple classes. They use the actual database and cache but mock external services.

### Scope

- HTTP endpoint responses and status codes
- Livewire component rendering and interaction
- Form validation and error handling
- Authorization and authentication
- Database operations and state changes
- Event dispatching and listener execution
- Queue job dispatching

### Conventions

```php
class UserManagementTest extends TestCase
{
    public function test_admin_can_view_user_list(): void
    {
        $admin = User::factory()->create();
        $admin->assignRole('admin');

        $this->actingAs($admin)
            ->get('/admin/users')
            ->assertOk()
            ->assertSee('User Management');
    }

    public function test_non_admin_cannot_view_user_list(): void
    {
        $user = User::factory()->create();

        $this->actingAs($user)
            ->get('/admin/users')
            ->assertForbidden();
    }
}
```

### Coverage Target

80% coverage for controllers and Livewire components.

## Browser Tests

Browser tests validate complete user flows in a real browser using Playwright. They run against a fully seeded application with realistic data.

### Scope

- User registration and onboarding
- Component browsing and preview
- Playground interactions
- Download process
- Subscription management
- Admin panel operations
- Mobile responsive behavior
- Accessibility compliance

### Conventions

```javascript
// tests/Browser/UserFlow.spec.js
test('user can browse and download components', async ({ page }) => {
    await page.goto('/components');
    await page.click('[data-component="card"]');
    await page.waitForSelector('[data-testid="component-detail"]');

    expect(await page.textContent('h1')).toContain('Component Name');

    await page.click('button:has-text("Download")');
    await expect(page.locator('.success-message')).toBeVisible();
});
```

### Coverage Target

100% coverage for critical user flows (registration, purchase, download).

## Static Analysis

### PHPStan / Larastan

Static analysis runs at level 6 by default, catching type errors, undefined methods, and potential bugs without executing code.

```bash
vendor/bin/phpstan analyse --level=6 --memory-limit=512M
```

### Laravel Pint

Code style enforcement using Laravel's opinionated code formatter. Runs automatically on commit and in CI.

```bash
vendor/bin/pint --test
```

### JavaScript ESLint

Frontend code is linted with ESLint using the project's configuration. Catches unused variables, undefined references, and style inconsistencies.

```bash
npm run lint
```

## Coverage Enforcement

Coverage is measured using PHPUnit's built-in code coverage with Xdebug or PCOV. The CI pipeline enforces coverage thresholds:

```yaml
- name: Check Coverage
  run: |
    COVERAGE=$(vendor/bin/phpunit --coverage-text | grep "Lines:" | awk '{print $2}')
    if (( $(echo "$COVERAGE < 85" | bc -l) )); then
      echo "Coverage $COVERAGE% is below 85% threshold"
      exit 1
    fi
```

## Coverage Exclusions

The following are excluded from coverage requirements:
- Generated code (factories, migrations)
- Configuration files
- View templates (covered by browser tests)
- Third-party integrations (covered by integration tests)

# CI Test Execution

## GitHub Actions Workflow

```yaml
name: Test Suite

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: PHP Lint
        run: find app -name "*.php" -exec php -l {} \;
      - name: Code Style
        run: vendor/bin/pint --test
      - name: Static Analysis
        run: vendor/bin/phpstan analyse --memory-limit=512M

  test:
    needs: lint
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: testing
          MYSQL_DATABASE: gsmui_testing
        ports:
          - 3306:3306
      redis:
        image: redis:7
        ports:
          - 6379:6379
    steps:
      - uses: actions/checkout@v4
      - name: Setup PHP
        uses: shivammathur/setup-php@v2
        with:
          php-version: 8.4
          extensions: mbstring, xml, ctype, json, bcmath, pdo_mysql
          coverage: pcov
      - name: Install Dependencies
        run: composer install --no-progress
      - name: Run Migrations
        run: php artisan migrate --force
      - name: Seed Database
        run: php artisan db:seed --force
      - name: Unit Tests
        run: vendor/bin/phpunit --testsuite=Unit --coverage-cobertura=coverage.xml
      - name: Feature Tests
        run: vendor/bin/phpunit --testsuite=Feature
      - name: Upload Coverage
        uses: codecov/codecov-action@v3
        with:
          file: coverage.xml

  browser:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Start Server
        run: |
          php artisan serve --port=8000 &
          sleep 5
      - name: Install Playwright
        run: npx playwright install --with-deps chromium
      - name: Run Browser Tests
        run: npx playwright test
```

## Pipeline Stages

1. **Lint** - Code style and static analysis (fastest feedback)
2. **Unit Tests** - Isolated business logic tests
3. **Feature Tests** - Integration and component tests
4. **Browser Tests** - End-to-end user flows (main branch only)

# Performance Testing

## Load Testing

Load tests use Artillery to simulate realistic traffic patterns:

```yaml
# artillery-config.yml
config:
  target: "http://localhost:8000"
  phases:
    - duration: 60
      arrivalRate: 10
    - duration: 120
      arrivalRate: 50
    - duration: 60
      arrivalRate: 100

scenarios:
  - name: "Browse Components"
    flow:
      - get:
          url: "/components"
      - think: 2
      - get:
          url: "/components/{{ $randomComponentId }}"

  - name: "User Registration"
    flow:
      - post:
          url: "/register"
          json:
            name: "{{ $randomString }}"
            email: "{{ $randomEmail }}"
            password: "Test1234!"
```

## Stress Testing

Stress tests identify breaking points by gradually increasing load until the system fails. This helps capacity planning and identifies bottlenecks.

## Database Query Profiling

Slow query logging and profiling ensure database performance stays within acceptable bounds. Queries exceeding 100ms are flagged for optimization.

```php
// Enable slow query logging
DB::listen(function ($query) {
    if ($query->time > 100) {
        Log::warning('Slow query', [
            'sql' => $query->sql,
            'time' => $query->time,
            'bindings' => $query->bindings,
        ]);
    }
});
```

## Cache Effectiveness

Cache hit rates are monitored to ensure caching strategies are effective. Hit rates below 90% trigger investigation into cache invalidation patterns and TTL settings.

# Testing Best Practices

## Test Isolation

Every test runs in a database transaction that is rolled back after completion. This ensures tests don't affect each other and can run in parallel.

```php
use RefreshDatabase;

class ExampleTest extends TestCase
{
    use RefreshDatabase;

    // Database state is reset after each test
}
```

## Test Data

Factories generate test data with sensible defaults. Seeders provide known data states for feature and browser tests. Test data never contains real PII.

## Mocking Strategy

- External services (payment, email, search) are always mocked
- Database operations use real queries with test database
- Cache operations use real Redis with test database
- HTTP calls to third-party APIs are mocked with HTTP fixtures

## CI Optimization

- Tests run in parallel where possible
- Browser tests only run on main branch
- Failed tests are retried once before failing
- Test results are cached between runs

# Risk

## Risk Register

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| Flaky browser tests causing false failures | High | Medium | Retry logic, stable selectors, test isolation |
| Insufficient test coverage for critical flows | Medium | Critical | Coverage gates, browser test requirement for merges |
| Slow CI pipeline deterring developers | Medium | High | Parallel execution, test splitting, caching |
| Test data leaks containing PII | Low | Critical | Factory-generated data, no real user data in tests |
| Third-party test service outage | Low | Medium | Local fallback, retry with backoff |
| Test maintenance burden exceeds capacity | Medium | High | Page Object Model, shared fixtures, test documentation |

## Contingency Plans

- **Flaky tests**: Quarantine flaky tests, investigate root cause, restore to suite within 1 week
- **Coverage drop**: Block merges until coverage restored, add tests in same PR
- **CI slowdown**: Identify bottleneck stage, optimize or parallelize further
- **Service outage**: Run tests locally, report to service provider, schedule re-run

## Risk Monitoring

- Daily: CI pipeline pass rate tracking
- Weekly: Flaky test identification and quarantine review
- Monthly: Coverage trend analysis
- Quarterly: Test suite performance benchmark

## Unit Test Specifications

### Service Layer Tests

```php
// tests/Unit/Services/SubscriptionServiceTest.php
class SubscriptionServiceTest extends TestCase
{
    private SubscriptionService $service;
    private MockInterface $stripeMock;

    protected function setUp(): void
    {
        parent::setUp();
        
        $this->stripeMock = Mockery::mock(StripeClient::class);
        $this->service = new SubscriptionService(
            stripe: $this->stripeMock,
            logger: app(ActivityLogger::class),
        );
    }

    public function test_can_create_subscription(): void
    {
        $user = User::factory()->create();
        $plan = Plan::factory()->create(['price' => 2900]);

        $this->stripeMock
            ->shouldReceive('subscriptions->create')
            ->once()
            ->andReturn((object) ['id' => 'sub_123', 'status' => 'active']);

        $subscription = $this->service->createSubscription($user, $plan);

        $this->assertEquals('active', $subscription->status);
        $this->assertEquals($plan->id, $subscription->plan_id);
    }

    public function test_can_cancel_subscription(): void
    {
        $user = User::factory()->create();
        $subscription = Subscription::factory()->create([
            'user_id' => $user->id,
            'stripe_id' => 'sub_123',
            'status' => 'active',
        ]);

        $this->stripeMock
            ->shouldReceive('subscriptions->cancel')
            ->once();

        $this->service->cancelSubscription($subscription);

        $this->assertEquals('cancelled', $subscription->fresh()->status);
    }

    public function test_cannot_cancel_already_cancelled_subscription(): void
    {
        $subscription = Subscription::factory()->create([
            'status' => 'cancelled',
        ]);

        $this->expectException(InvalidOperationException::class);
        $this->service->cancelSubscription($subscription);
    }
}
```

```javascript
// tests/Browser/Pages/MarketplacePage.js
class MarketplacePage {
  constructor(page) {
    this.page = page;
    this.productGrid = page.locator('[data-component="product-grid"]');
    this.searchInput = page.locator('input[placeholder="Search components..."]');
    this.filterSidebar = page.locator('[data-component="filter-sidebar"]');
  }

  async goto() {
    await this.page.goto('/marketplace/products');
    await this.page.waitForSelector('[data-component="product-grid"]');
  }

  async search(query) {
    await this.searchInput.fill(query);
    await this.page.waitForTimeout(500); // Wait for debounce
  }

  async filterByType(type) {
    await this.filterSidebar.click(`text=${type}`);
    await this.page.waitForTimeout(300);
  }

  async getProductCount() {
    return this.page.locator('[data-component="product-card"]').count();
  }

  async clickProduct(index) {
    await this.page.locator('[data-component="product-card"]').nth(index).click();
    await this.page.waitForSelector('[data-component="product-detail"]');
  }
}

module.exports = { MarketplacePage };
```

|--------|--------|-------------|

| Flaky Test Rate | < 1% | Flaky tests / total tests |

## Test Smells

| Smell | Description | Fix |
|-------|-------------|-----|
| Test too long | > 100 lines | Break into smaller tests |
| Test depends on other tests | Shared state | Use factories, isolated data |
| Test has magic numbers | Hardcoded values | Use constants or variables |
| Test tests too much | Multiple assertions | Split into focused tests |
| Test name unclear | Doesn't describe behavior | Rename to describe behavior |
