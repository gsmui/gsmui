# Purpose

This document details the architecture of the Admin Platform, including its modules, components, and integration points. It serves as the authoritative reference for how the administrative interface is structured, how data flows through the system, and how security and performance constraints are enforced.

---

# Architecture Overview

The Admin Platform is a server-rendered single-page application experience built on Laravel Livewire. It provides a comprehensive interface for platform administrators to manage users, content, products, and system configuration. The architecture follows a layered approach where Blade templates define the visual structure, Livewire components manage state and interaction, and backend services encapsulate business logic.

The admin panel is isolated from the public-facing application through separate route groups, middleware stacks, and authentication guards. All admin routes are prefixed with `/admin` and protected by dedicated authorization middleware that verifies the authenticated user holds an administrative role before any controller or Livewire component is instantiated.

The system leverages the GsmUi component library for all UI elements, ensuring visual consistency with the rest of the platform while providing admin-specific variants where needed. Charts, data tables, modals, and form elements all come from the core component set, extended with admin-specific behaviors like bulk actions, inline editing, and real-time validation.

## User Management

The user management module provides a full lifecycle view of every platform user. The `UserTable` component renders a paginated, filterable, and sortable data table with support for column-based filtering on status, role, registration date, and last activity. Bulk actions allow administrators to suspend, activate, export, or delete multiple users in a single operation.

The `UserDetail` component presents a comprehensive profile view including activity timeline, subscription history, download records, and support tickets. It integrates with the notification system to allow direct messaging to individual users and with the billing module to display payment history.

Profile editing is handled through a dedicated form component that validates input server-side using Laravel validation rules and provides real-time feedback through Livewire updates. Sensitive operations like password resets and role changes require re-authentication.

## Role and Permission System

The role and permission system implements a hierarchical RBAC model. Roles can inherit permissions from parent roles, and individual permissions can be overridden at the user level for exceptional cases. The `PermissionMatrix` component provides a visual grid showing all roles against all permissions, with checkmarks indicating granted access.

Every permission change is logged with the actor, timestamp, old value, and new value. The system supports both additive and restrictive permissions, allowing administrators to grant broad access through roles and then revoke specific capabilities for individual users.

## Content Management

The content management module handles the lifecycle of all platform content including components, documentation, themes, and templates. The approval workflow moves content through states: draft, submitted, under review, approved, and published. Each state transition triggers notifications to relevant stakeholders.

The documentation editor supports Markdown with live preview, version history, and collaborative editing through operational transformation. Theme management provides a visual editor for customizing platform appearance with real-time preview across different device sizes.

## Marketplace Administration

The marketplace admin provides tools for managing the product catalog, processing orders, and moderating reviews. Product management includes bulk import/export, variant configuration, pricing rules, and promotional pricing. Order management integrates with payment processors for refund handling and dispute resolution.

Review moderation uses a combination of automated content filtering and manual review queues. Suspicious reviews are flagged automatically based on patterns like rapid posting, identical content, or accounts with no purchase history.

```text
    |- Query Builder
    |- Eloquent ORM
    |

```

## Real-Time Updates

Livewire components use polling and broadcast channels to provide real-time updates for critical data. The dashboard metrics poll every 30 seconds, order notifications use WebSocket broadcast, and audit log entries appear in real-time through event streaming.

## State Management

Each Livewire component manages its own state through public properties that are synchronized with the browser. Complex components use the `Controllable` pattern to separate internal state from externally-bound values, preventing sync loops and ensuring predictable updates.

# Security Framework

## Authentication and Authorization

All admin users must authenticate using the standard authentication flow plus an additional admin verification step. The system checks that the authenticated user has an active admin role before granting access to any admin route. Session management enforces absolute timeouts of 4 hours and idle timeouts of 30 minutes for admin sessions.

Two-factor authentication is mandatory for all admin accounts. The system supports TOTP-based authenticators and backup recovery codes. Backup codes are generated in sets of 10 and are single-use with cryptographic hashing.

## Authorization Model

The RBAC system defines permissions at the module level with granularity down to individual actions. Permission checks occur at multiple layers: route middleware validates access to admin sections, Livewire component mounting checks specific component access, and service methods verify operation-level permissions.

```php
// Permission naming convention
'module.action' // e.g., 'users.view', 'users.edit', 'roles.manage'

// Hierarchical check
Role::find($roleId)->hasPermissionTo('users.edit');
```

## Audit Trail

Every administrative action generates an audit log entry capturing:
- Actor (user ID, email, IP address)
- Action performed
- Target resource (type, ID)
- Before/after state for modifications
- Timestamp with timezone
- User agent string

Audit logs are immutable and stored in a dedicated table with append-only semantics. Retention is configured for 1 year with quarterly archival to cold storage.

## CSRF Protection

All forms and Livewire component interactions include CSRF tokens. The token is refreshed on every page load and validated on every state mutation. Cross-origin requests are blocked by the SameSite cookie policy and additional origin header verification.

## Rate Limiting

Admin API endpoints are rate-limited at 60 requests per minute per user. Livewire component updates are limited at 30 requests per minute per component. Login attempts are limited to 5 per minute per IP address with exponential backoff.

## Data Protection

Sensitive fields like passwords, API tokens, and payment information are encrypted at rest using AES-256. Database backups are encrypted before storage. PII is masked in logs and error reports. Admin access to user data is logged and auditable.

# Performance Optimization

## Caching Strategy

- Dashboard metrics cached for 60 seconds with automatic invalidation on data changes
- Role and permission matrices cached for the session duration
- User list filters cached in Redis with 5-minute TTL
- Report data cached for 15 minutes with background refresh

## Database Optimization

- All list queries use indexed columns for filtering and sorting
- Eager loading prevents N+1 queries on relationship data
- Cursor-based pagination for large datasets instead of offset pagination
- Read replicas for analytics queries that don't require real-time consistency

## Frontend Performance

- Livewire partial rendering updates only changed DOM elements
- Alpine.js handles client-side interactivity without full page reloads
- Asset compilation through Vite with code splitting and tree shaking
- Lazy loading for images and non-critical components
- Service worker for offline admin dashboard access

## Queue Processing

Heavy operations like report generation, bulk exports, and data migrations are dispatched to queued jobs. The Horizon dashboard provides visibility into queue depth, worker status, and failed jobs. Priority queues ensure critical operations like user suspension are processed before background tasks.

# Testing Strategy

## Unit Tests

Service layer classes are tested with isolated unit tests that mock repository dependencies. Authorization logic is tested with role and permission combinations. Event handlers are tested for correct side effects.

## Feature Tests

Livewire components are tested using the built-in Livewire testing utilities. Tests verify rendering, interaction, authorization, and validation. HTTP tests cover all admin API endpoints for correct responses and error handling.

## Browser Tests

Critical admin flows are automated with Playwright: user management CRUD, role assignment, content approval workflow, and dashboard navigation. Tests run against a seeded database with known data states.

## Security Tests

Authorization bypass attempts are tested for every admin endpoint. SQL injection and XSS vectors are validated through automated scanning. CSRF protection is verified for all state-changing operations.

# Risk

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Admin account compromise leads to platform-wide breach | Low | Critical | Mandatory 2FA for all admin accounts. Session timeout at 30 minutes idle. IP allowlisting for production admin access. Audit every privileged action. |
| Privilege escalation through RBAC misconfiguration | Medium | High | Automated permission matrix validation in CI. Quarterly RBAC audit by security team. Principle of least privilege enforced by default for new roles. |
| Bulk operations (user deletion, content purge) cause data loss | Medium | High | Soft-delete with 30-day recovery window. Confirmation modals with typed confirmation for destructive operations. Batch size limits (max 100 per operation). |
| Admin panel becomes attack surface for CSRF/XSS | Medium | High | CSRF tokens on every form. Content Security Policy headers. Input sanitization on all admin-managed content. Automated security scanning in CI. |
| Audit log tampering undermines compliance | Low | Critical | Append-only audit table. Cryptographic hash chain for log integrity. Regular integrity checks. Separate storage from main database. |
| Real-time dashboard polling degrades database performance | Medium | Medium | Dedicated read replica for analytics queries. Polling interval increased to 30 seconds. Redis caching for dashboard metrics. |
| Admin session hijacking through shared computers | Medium | Medium | Force logout on password change. Session listing with device/IP info. One-click "revoke all sessions" button. |
| Feature flag misconfiguration causes platform outage | Medium | High | Feature flags default to safe state. Rollback capability within 1 click. Staging environment testing required before production toggle. |
| Content moderation backlog delays product publishing | Medium | Low | Automated pre-screening reduces manual review volume. Priority queue for verified creators. SLA of 48 hours for moderation response. |

**Audit Log Integrity:**

Each audit log entry includes a cryptographic hash chain:

```php
class AuditLog extends Model
{
    public function computeHash(): string
    {
        $payload = json_encode([
            'id' => $this->id,
            'trace_id' => $this->trace_id,
            'actor_id' => $this->actor_id,
            'action' => $this->action,
            'target_type' => $this->target_type,
            'target_id' => $this->target_id,
            'created_at' => $this->created_at->toIso8601String(),
            'previous_hash' => $this->previousHash?->hash,
        ]);

        return hash('sha256', $payload);
    }
}
```

```php
public function handle($request, Closure $next)
```

## Input Sanitization

All admin-managed content is sanitized to prevent XSS:

```php
class AdminContentSanitizer
{
    public function sanitize(string $content): string
    {
        $html = strip_tags($content, [
            'p', 'br', 'strong', 'em', 'u', 'ol', 'ul', 'li',
            'h1', 'h2', 'h3', 'h4', 'h5', 'h6',
            'a', 'img', 'blockquote', 'code', 'pre',
            'table', 'thead', 'tbody', 'tr', 'th', 'td',
        ]);

        // Remove event handlers
        $html = preg_replace('/on\w+="[^"]*"/i', '', $html);
        $html = preg_replace("/on\w+='[^']*'/i", '', $html);

        // Remove javascript: URLs
        $html = preg_replace('/javascript:/i', '', $html);

        return $html;
    }
}
```

- Actor identification (user ID, email, IP)
- Action performed
- Target resource
- Before/after state for modifications
- Timestamp with timezone
- Request metadata (user agent, request ID)

Logs are immutable, stored in append-only tables, and protected against tampering with cryptographic hash chains.

# Admin Accessibility

## WCAG 2.1 AA Compliance

All admin components must meet WCAG 2.1 AA standards:

### Color Contrast

| Element Type | Minimum Ratio |
|--------------|---------------|
| Normal text | 4.5:1 |
| Large text | 3:1 |
| UI components | 3:1 |
| Focus indicators | 3:1 |

### Keyboard Navigation

- All interactive elements must be keyboard accessible
- Focus order must follow logical reading order
- Focus must be visible on all focusable elements
- Skip navigation link provided

### Screen Reader Support

- All images have descriptive alt text
- Form inputs have associated labels
- ARIA landmarks used for page structure
- Status messages announced via ARIA live regions

### Testing

```javascript
// tests/Browser/Admin/Accessibility.spec.js
const { test, expect } = require('@playwright/test');
const AxeBuilder = require('@axe-core/playwright').default;

test('admin dashboard has no accessibility violations', async ({ page }) => {
    await page.goto('/admin/dashboard');
    
    const accessibilityScanResults = await new AxeBuilder({ page })
        .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'])
        .analyze();

    expect(accessibilityScanResults.violations).toEqual([]);
});

test('admin user table is keyboard navigable', async ({ page }) => {
    await page.goto('/admin/users');
    
    // Tab to first interactive element
    await page.keyboard.press('Tab');
    await expect(page.locator(':focus')).toBeVisible();
    
    // Navigate through table
    await page.keyboard.press('ArrowDown');
    await page.keyboard.press('ArrowDown');
    
    // Verify focus management
    const focused = await page.evaluate(() => document.activeElement.tagName);
    expect(['INPUT', 'BUTTON', 'A', 'SELECT']).toContain(focused);
});
```

# Admin Backup & Recovery

## Backup Schedule

| Data Type | Frequency | Retention | Storage |
|-----------|-----------|-----------|---------|
| Database | Every 6 hours | 30 days | S3 + Local |
| Audit logs | Daily | 1 year | S3 |
| Configuration | On change | 90 days | Git + S3 |
| Media assets | Weekly | 90 days | S3 |
| User uploads | Daily | 30 days | S3 |

## Recovery Procedures

### Database Recovery

```bash
# Restore from backup
mysql -u root -p gsmui < backup_2024_01_15.sql

# Verify integrity
php artisan db:verify

# Rebuild caches
php artisan cache:clear
php artisan config:cache
php artisan route:cache
```

### Configuration Recovery

```bash
# Restore from Git
git checkout HEAD~1 -- config/

# Restore from S3
aws s3 cp s3://gsmui-backups/config/latest/ config/

# Clear and rebuild
php artisan config:clear
php artisan config:cache
```

### Full Recovery

```bash
# Estimated time: 1 hour

# 1. Stop traffic (5 minutes)
sudo systemctl stop nginx

# 2. Restore database (15 minutes)
mysql -u root -p gsmui < latest_backup.sql

# 3. Restore application code (5 minutes)
git checkout main
composer install --no-dev --optimize-autoloader

# 4. Restore configuration (5 minutes)
cp .env.backup .env
php artisan config:cache

# 5. Restore media (10 minutes)
aws s3 sync s3://gsmui-backups/media/ storage/app/public/

# 6. Clear and warm caches (5 minutes)
php artisan cache:clear
php artisan view:cache
php artisan route:cache

# 7. Restart services (5 minutes)
sudo systemctl restart php8.4-fpm
sudo systemctl restart nginx
sudo systemctl restart redis

# 8. Verify (10 minutes)
php artisan health:check
curl -I https://gsmui.com
```

# Admin API Versioning

## Version Strategy

The admin API follows semantic versioning with the following rules:

- **Major version**: Breaking changes to response format or authentication
- **Minor version**: New endpoints or features
- **Patch version**: Bug fixes or performance improvements

## Version Header

```text
X-API-Version: 1.0
X-API-Supported: 1.0-2.0
X-API-Deprecated: < 1.0
```

## Version Lifecycle

| Version | Status | Support |
|---------|--------|---------|
| 2.0 | Current | Full support |
| 1.0 | Supported | Security fixes only |
| < 1.0 | Deprecated | Removed in 6 months |

## Migration Guide

When a new major version is released:

1. Deprecation notice sent 6 months in advance
2. Migration guide published in documentation
3. Compatibility layer provided for 12 months
4. Old version removed after deprecation period
