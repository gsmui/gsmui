# Chapter 2: Order Model

## 2.1 Order Fields

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `number` | string | yes | Human-readable |
| `customer_id` | ulid | yes | Buyer |
| `status` | enum | yes | Lifecycle |
| `currency` | char(3) | yes | ISO 4217 |
| `subtotal_cents` | int | yes | Before tax |
| `tax_cents` | int | yes | Tax amount |
| `total_cents` | int | yes | Grand total |
| `placed_at` | timestamp | yes | Creation time |
| `paid_at` | timestamp | no | Set on capture |

## 2.2 Order Statuses

```
created -> pending -> paid -> fulfilled -> closed
                   \-> cancelled
paid -> refunded
paid -> partially_refunded
```

## 2.3 Order Numbers

Order numbers are sequential per year: `GSM-2026-000123`. Sequence gaps are acceptable and never reused.

## 2.4 Order Lines

| Field | Notes |
|-------|-------|
| `variant_id` | Purchased variant |
| `description` | Snapshot of title |
| `quantity` | Units |
| `unit_cents` | Snapshot price |
| `tax_cents` | Line tax |
| `total_cents` | Line total |

Line prices are snapshotted at placement. Later catalogue price changes never alter historical orders.

## 2.5 Immutability

Financial fields (`subtotal`, `tax`, `total`) are immutable after payment. Corrections are made through credit notes, never by editing an order.

# Chapter 3: Subscription Model

## 3.1 Plans

| Field | Notes |
|-------|-------|
| `code` | Stable identifier |
| `name` | Display name |
| `interval` | month, year |
| `price_ref` | Marketplace price |
| `features` | Feature entitlements |
| `trial_days` | Optional |

## 3.2 Subscription Fields

| Field | Notes |
|-------|-------|
| `customer_id` | Subscriber |
| `plan_code` | Current plan |
| `status` | Lifecycle |
| `current_period_start` | Period start |
| `current_period_end` | Period end |
| `cancel_at_period_end` | Boolean |

## 3.3 Subscription Statuses

```
trialing -> active -> past_due -> cancelled
                   \-> paused
active -> cancelled
```

## 3.4 Period Semantics

- Periods are half-open intervals `[start, end)`.
- Renewal occurs at `period_end`.
- Proration applies on plan changes mid-period.

## 3.5 Trials

Trials grant full access for `trial_days`. Trials convert automatically on the first successful charge. Trials without a payment method expire into `cancelled`.

## 3.6 Dunning

| Attempt | Timing | Action |
|---------|--------|--------|
| 1 | At due date | Charge |
| 2 | +3 days | Retry |
| 3 | +5 days | Retry + email |
| 4 | +7 days | Retry + warning |
| 5 | +7 days | Cancel or downgrade |

`past_due` state begins at the first failure and resolves on success or cancellation.

---

# Chapter 4: Plan Changes and Proration

## 4.1 Upgrade

Upgrades take effect immediately. The customer is charged the prorated difference for the remainder of the period.

## 4.2 Downgrade

Downgrades take effect at the next renewal by default. Immediate downgrade requires explicit confirmation and may trigger a credit.

## 4.3 Proration Formula

```
prorated = round(plan_price * remaining_days / period_days)
```

Proration uses whole days and rounds half-up to the nearest cent.

## 4.4 Credits

Credits are issued as `credit_note` records and applied to the next invoice. Credits never expire while the subscription is active.

## 4.5 Quantity Changes

Seat-based plans prorate on quantity change using the same formula applied to the per-seat price.

# Chapter 5: Invoice Generation

## 5.1 Invoice Triggers

| Trigger | Timing |
|---------|--------|
| Order paid | Immediately |
| Subscription renewal | At period start |
| Manual | On demand |
| Credit note | On issuance |

## 5.2 Invoice Fields

| Field | Notes |
|-------|-------|
| `number` | Sequential per year |
| `order_id` | Source order |
| `customer_id` | Billed party |
| `issued_at` | Issue timestamp |
| `due_at` | Due timestamp |
| `currency` | ISO 4217 |
| `total_cents` | Amount due |
| `status` | Lifecycle |

## 5.3 Invoice Statuses

```
draft -> issued -> paid
                \-> void
issued -> overdue
```

## 5.4 Invoice Numbering

Invoices are numbered `INV-2026-000456`. Numbers are assigned at issue and never reused. A voided invoice retains its number.

## 5.5 PDF Rendering

Invoices render to PDF with a stable template. The PDF embeds a QR code linking to a verification page. PDFs are stored in the media library and linked from the invoice record.

## 5.6 Delivery

Invoices are emailed on issue and available in the admin panel. Customers may download any historical invoice.

# Chapter 6: Tax Handling

## 6.1 Tax Classes

| Class | Applies To |
|-------|------------|
| `digital_service` | Downloads, themes, packs |
| `physical_goods` | Swag items |
| `professional_service` | Consulting |

## 6.2 Tax Configuration

| Field | Notes |
|-------|-------|
| `country` | ISO 3166-1 alpha-2 |
| `region` | Optional subdivision |
| `class` | Tax class |
| `rate_bps` | Basis points |
| `inclusive` | Price includes tax |
| `effective_from` | Start date |

## 6.3 Rate Resolution

Resolution order:

1. Exact country and region match.
2. Country-only match.
3. Destination default.
4. Zero rate with a warning if unconfigured.

## 6.4 Reverse Charge

B2B customers with a valid VAT id in a different jurisdiction receive reverse-charge treatment. The invoice notes the reverse-charge condition and charges zero tax.

## 6.5 Rounding

Tax is computed per line and summed. Line tax rounds half-up to the cent.

## 6.6 Tax Reporting

Tax summaries group by country, class, and period. The summary feeds the financial reporting export.

# Chapter 7: Credit Notes and Refunds

## 7.1 Credit Note Fields

| Field | Notes |
|-------|-------|
| `number` | Sequential |
| `invoice_id` | Related invoice |
| `reason` | Code |
| `amount_cents` | Credited amount |
| `tax_cents` | Tax reversed |
| `issued_at` | Timestamp |

## 7.2 When to Issue

| Situation | Record |
|-----------|--------|
| Refund | Credit note plus refund |
| Billing error | Credit note |
| Goodwill | Credit note |
| Downgrade | Credit note (if immediate) |

## 7.3 Relationship to Refunds

The marketplace issues refunds. The billing module issues credit notes to keep financial records consistent. A refund without a credit note is a reconciliation exception.

## 7.4 Totals

The sum of credit notes against an invoice never exceeds the invoice total.

# Chapter 8: Revenue Recognition

## 8.1 Recognition Rules

| Product | Recognition |
|---------|-------------|
| Digital one-off | At delivery |
| Physical | At shipment |
| Subscription | Ratably over the period |

## 8.2 Deferred Revenue

Subscriptions create deferred revenue at period start and recognise it daily. The deferred balance is available in reports.

## 8.3 Refund Impact

Refunds reverse recognised revenue in the current period. If the refund spans periods, the reversal is split proportionally.

## 8.4 Reporting Periods

Reporting periods are monthly. Adjustments after period close are recorded in the following period with a reference to the original.

---

# Chapter 9: Multi-Currency

## 9.1 Currency Handling

Prices are stored per currency by the marketplace. Orders snapshot the currency and amounts at placement.

## 9.2 Exchange Rates

Reporting converts to a base currency using the period-end rate. The rate source and date are recorded with each conversion.

## 9.3 Display

Customers see prices in their currency. Invoices always show the invoiced currency.

## 9.4 Rounding

Currency conversion rounds to the currency's minor unit. JPY has zero decimals; most currencies have two.

# Chapter 11: Payment Synchronisation

## 11.1 Source of Truth

The payment processor is the source of truth for captured funds. The billing module mirrors captures into its records and reconciles any divergence.

## 11.2 Capture Mirroring

On `PaymentCaptured`, the order transitions to `paid` and `paid_at` is set. The invoice is issued. Mirroring is idempotent by payment id.

## 11.3 Failures

If mirroring fails, a reconciliation task retries. Persistent failures are surfaced as exceptions and block period close.

## 11.4 Refund Mirroring

On `RefundIssued`, a credit note is created automatically. The credit note references the refund id for traceability.

## 11.5 Chargebacks

A lost dispute creates a credit note with reason `chargeback`. Won disputes generate no record.

2. Compare against billing records.
3. Identify unmatched entries.
4. Create credit notes or corrections.
5. Block period close until resolved.

# Appendix Q: Worked Walkthroughs

## Q.1 First Purchase

1. Customer places an order.
2. Order is `pending` with snapshotted prices.
3. Payment is captured by the marketplace.
4. `OrderPaid` mirrors to billing; order becomes `paid`.
5. Invoice is issued and emailed.
6. Product fulfilment proceeds independently.
7. Order closes after fulfilment.

## Q.2 Failed Renewal

1. Renewal job runs at period end.
2. Charge fails; subscription becomes `past_due`.
3. Dunning step 1 email sent.
4. Retry succeeds on step 2.
5. Subscription returns to `active`.
6. Invoice remains paid; dunning closes.

## Q.3 Immediate Downgrade

1. Customer requests immediate downgrade.
2. Proration credit is computed.
3. Credit note is issued.
4. Plan changes immediately.
5. Next invoice reflects the new plan.
6. Credit is applied to the next invoice.

## Q.4 Refund with Credit Note

1. Marketplace issues a refund.
2. `RefundIssued` mirrors to billing.
3. Credit note is created and linked to the refund.
4. Invoice status becomes `partially_refunded`.
5. Revenue recognition reverses proportionally.

# Appendix R: Extended FAQ

**Why can't I edit an order total?** Financial fields are immutable after payment to preserve audit integrity. Use a credit note instead.

**What happens if an invoice is unpaid?** It becomes overdue, reminders are sent, and the subscription enters dunning.

**Can I have two invoices for one order?** No. One order produces one invoice; corrections use credit notes.

**How is tax calculated for B2B?** With a valid cross-border VAT id, reverse charge applies and tax is zero with a note on the invoice.

**When is revenue recognised for a yearly plan?** Daily, ratably over the year.

**Can a cancelled subscription be resumed?** Yes, before the period ends, if the plan is still available.

**What if a customer disputes a charge?** A lost dispute produces a credit note with reason `chargeback`.

# Appendix Z: Proration Reference

| Scenario | Formula | Example |
|----------|---------|---------|
| Upgrade | `(new - old) * remaining / period` | 29 days left of 30, +10 → +9.67 |
| Downgrade immediate | `(old - new) * remaining / period` (credit) | 29 days left, −10 → credit 9.67 |
| Seat increase | `seat_price * added_seats * remaining / period` | 3 seats, 29/30 → ~2.9 seat units |
| Cancellation | No charge; access until period end | — |

## Z.1 Rounding Example

At 29/30 of a 10.00 difference, the prorated amount is 9.666… which rounds to 9.67. Rounding always occurs once, at the final amount, never per intermediate step.

# Appendix AB: Invoice Verification

Each invoice PDF embeds a QR code pointing to a verification URL. The URL displays the invoice number, issue date, total, and a signature hash.

## AB.1 Signature

```
signature = hmac_sha256(invoice_number|issued_at|total_cents, secret)
```

Verification recomputes the signature and compares. Mismatch indicates tampering or a key rotation issue.

## AB.2 Key Rotation

Keys rotate annually. Old keys remain available for verification of historical invoices for ten years.

## AG.2 Concurrency Control

## AG.3 Duplicate Protection

Unique constraints protect order numbers, invoice numbers, credit numbers, and idempotency keys. Violations are treated as duplicate deliveries and handled without error.

A refund in June reverses recognised revenue for June and defers the remainder reversal across the remaining months proportionally.
