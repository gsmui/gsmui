```
draft -> review -> published -> archived
```

Archiving hides a product from the catalogue but preserves order history.

## 3.4 Invariants

- Every physical product has at least one variant.
- Every published product has at least one media item.
- Digital products have exactly one active file bundle per version.
- SKUs are unique across the catalogue.
- Archived products cannot be added to new carts.

# Chapter 4: Variants and Options

## 4.1 Option Model

A product defines one or more options, each with ordered values.

| Option | Values |
|--------|--------|
| Size | S, M, L, XL |
| Colour | Black, White, Sand |

## 4.2 Variant Generation

The variant matrix is the Cartesian product of option values. The editor allows pruning invalid combinations.

## 4.3 Variant Fields

| Field | Notes |
|-------|-------|
| `sku` | Unique, uppercase |
| `price_ref` | Marketplace price reference |
| `weight_grams` | Physical only |
| `barcode` | Optional |
| `active` | Disable without deleting |

## 4.4 SKU Convention

```
{CLASS}-{PRODUCT}-{SIZE}-{COLOUR}
```

Example: `APP-HOODIE-L-BLK`.

## 4.5 Limits

- Maximum four options per product.
- Maximum 60 variants per product.
- Option value count maximum 12 per option.

# Chapter 5: Digital Delivery

## 5.1 Bundle Structure

A digital product ships one bundle per version. The bundle is a zip archive stored in the media library.

## 5.2 Delivery Flow

1. Buyer completes purchase (marketplace).
2. Entitlement is created.
3. Buyer opens the download page.
4. A short-lived signed URL is issued.
5. The bundle is downloaded.

## 5.3 Signed URL Rules

| Rule | Value |
|------|-------|
| TTL | 10 minutes |
| Single use | No (re-request allowed) |
| Scope | Entitlement-bound |
| Rate limit | 10 downloads per hour |

## 5.4 Versioning

Publishing a new bundle version updates the entitlement's available version. Buyers receive updates for the licence term.

## 5.5 Integrity

Bundles are checksummed. The download page displays the checksum so buyers can verify integrity.

## 5.6 Licence Metadata

Each bundle embeds a `LICENSE.txt` generated from the product licence. The licence is also shown on the product page.

# Chapter 6: Inventory Management

## 6.1 Inventory Fields

| Field | Meaning |
|-------|---------|
| `on_hand` | Physically present units |
| `reserved` | Units allocated to open orders |
| `available` | `on_hand - reserved` |
| `incoming` | Units on order from supplier |
| `safety_stock` | Minimum buffer |

## 6.2 Movement Types

| Type | Effect |
|------|--------|
| `receive` | Increase on_hand |
| `reserve` | Increase reserved |
| `release` | Decrease reserved |
| `ship` | Decrease on_hand and reserved |
| `adjust` | Set on_hand with reason |
| `return` | Increase on_hand |

## 6.3 Reservation Rules

- Reservations occur at order placement.
- Reservations expire after 30 minutes for unpaid orders.
- Shipping consumes the reservation.

## 6.4 Adjustments

Adjustments require a reason code and are audited. Negative on_hand is not permitted; the adjustment is rejected instead.

## 6.5 Cycle Counts

| Frequency | Scope |
|-----------|-------|
| Weekly | Top 20 SKUs by velocity |
| Monthly | Full count |
| Quarterly | Supplier reconciliation |

## 6.6 Low Stock Alerts

Alerts fire when `available` falls below `safety_stock`. Alerts route to the operations channel with a reorder suggestion.

# Chapter 8: Shipping and Fulfilment

## 8.1 Shipping Zones

| Zone | Coverage | Carrier Options |
|------|----------|-----------------|
| Domestic | Home country | Standard, Express |
| Regional | Neighbouring countries | Standard |
| International | Rest of world | Tracked |

## 8.2 Rate Selection

Rates are quoted at checkout through the carrier integration. Flat-rate fallback applies if quoting fails.

## 8.3 Fulfilment Steps

1. Order paid and reservation confirmed.
2. Pick list generated.
3. Units picked and packed.
4. Label generated.
5. Parcel handed to carrier.
6. Tracking number recorded.
7. Buyer notified.

## 8.4 Packing Slips

Packing slips include order id, items, and return instructions. Marketing inserts are optional and configurable.

## 8.5 Tracking

Tracking events are polled from the carrier and stored against the shipment. Buyer notifications fire on key transitions.

## 8.6 Exceptions

| Exception | Handling |
|-----------|----------|
| Address invalid | Hold and contact buyer |
| Carrier rejection | Re-quote or refund |
| Lost parcel | Carrier claim after 10 days |
| Damaged in transit | Replacement or refund |

# Chapter 9: Pricing References

## 9.1 Separation of Concerns

Products store a `price_ref`; the actual price lives in the marketplace price snapshot. This avoids divergent pricing between modules.

## 9.2 Price Display

Catalogue pages display the price resolved from the marketplace. If no price exists, the product cannot be published.

## 9.3 Discounts

Discounts are owned by the marketplace (coupons and campaigns). The products module never applies discounts directly.

## 9.4 Currency

Prices are stored per currency by the marketplace. The products module is currency-agnostic and displays the resolved value.

# Chapter 11: Order Integration

## 11.1 Order Handoff

The marketplace creates orders and emits `OrderPaid`. The products module consumes this event to trigger fulfilment.

## 11.2 Fulfilment Queue

| Item Type | Queue | SLA |
|-----------|-------|-----|
| Digital | Immediate grant | Under 1 minute |
| Physical | Pick and pack | Ship within 2 days |

## 11.3 Idempotency

Fulfilment handlers key on `order_id`. Replayed events do not create duplicate shipments or duplicate entitlements.

## 11.4 Partial Fulfilment

An order may contain both digital and physical items. Digital items fulfil immediately; physical items fulfil on shipment.

## 11.5 Cancellation

Cancellation before shipment releases reservations and cancels the pick list. Cancellation after shipment becomes a return.

## 11.6 Address Changes

Addresses may be changed while the order is in `paid` state and before label generation. After label generation, changes require carrier intercept or return.

# Chapter 12: Returns and Restocking

## 12.1 Return Eligibility

| Condition | Eligible |
|-----------|----------|
| Within 30 days | yes |
| Unworn, tags attached | yes |
| Customised item | no |

## 12.2 Return Flow

1. Buyer requests a return.
2. Operations approves and issues a return label.
3. Buyer ships the item back.

5. Refund is issued by the marketplace.
6. Inventory is restocked or quarantined.

## 12.3 Disposition

| Disposition | Effect |

## 12.4 Restocking Fees

# Chapter 18: Security

## 18.1 Access Control

All mutations require a specific ability. Inventory adjustments additionally require `inventory.manage` and are audited with reason codes.

## 18.2 Asset Protection

Digital bundles are never served from public URLs. Downloads always go through signed, entitlement-bound routes.

## 18.3 Threat Model

| Threat | Mitigation |
|--------|------------|
| Bundle leakage | Signed URLs, entitlement check |
| Price tampering | Price owned by marketplace |
| Inventory manipulation | Audited adjustments |
| SKU collision | Unique constraint |
| Fake returns | Inspection and disposition |
| Label fraud | Carrier account controls |

## 18.4 Audit

| Action | Audited |

# Appendix N: Worked Scenario Walkthroughs

## N.1 Digital Purchase to Download

1. Buyer purchases a theme on the marketplace.
2. Marketplace captures payment and emits `OrderPaid`.
3. Products module grants an entitlement for the theme version.
4. Buyer receives a download link email.
5. Buyer opens the download page.
6. The page issues a signed URL valid for 10 minutes.
7. Buyer downloads and verifies the checksum.

Failure points: entitlement service down, bundle missing, checksum mismatch. Each has a specific error surfaced to the buyer and a runbook for operations.

## N.2 Swag Purchase to Delivery

1. Buyer purchases a hoodie.
2. Marketplace captures payment and emits `OrderPaid`.
3. Products module reserves one unit of the purchased variant.
4. Pick list is generated for the warehouse.
5. Warehouse picks and packs; label is generated.
6. Tracking number is recorded and the buyer is notified.
7. Carrier delivers; delivery event updates the shipment.
8. Reservation is consumed; on_hand decreases.

Failure points: stock exhaustion at reserve time, invalid address, carrier rejection. Each triggers a specific exception path.

## N.3 Return and Restock

1. Buyer requests a return within 30 days.
2. Operations approves and issues a return label.
3. Buyer ships the item.
4. Warehouse receives and inspects.
5. Disposition is `restock`, `quarantine`, or `write_off`.
6. Marketplace issues the refund.
7. Inventory reflects the disposition.

Failure points: item not received, item damaged beyond restock, refund policy conflict.

## N.4 Purchase Order Cycle

1. Operations creates a draft PO for low-stock SKUs.
2. PO is sent to the supplier.
3. Supplier confirms with a delivery date.
4. Goods arrive; receiving matches lines.
5. Discrepancies are recorded and resolved.
6. Inventory `on_hand` and `incoming` are updated.
7. PO is closed.

# Appendix U: Inventory Mathematics

## U.1 Available Stock

```
available = on_hand - reserved
```

`reserved` includes all open unpaid and paid-but-unshipped orders.

## U.2 Projected Stock

```
projected = on_hand + incoming - reserved
```

Projection is used for reorder decisions.

## U.3 Reorder Point

```
reorder_point = safety_stock + (avg_daily_sales * lead_time_days)
```

Reorder is triggered when `projected` falls below `reorder_point`.

## U.4 Example Calculation

| Input | Value |
|-------|-------|
| on_hand | 40 |
| reserved | 12 |
| incoming | 30 |
| safety_stock | 15 |
| avg_daily_sales | 3 |
| lead_time_days | 14 |

```
reorder_point = 15 + (3 * 14) = 57
projected = 40 + 30 - 12 = 58
```

`projected` (58) is above `reorder_point` (57), so no reorder is needed yet. The margin is thin, so the next weekly review will likely trigger a reorder.

## U.5 Reservation Expiry

Unpaid reservations expire after 30 minutes:

```
if order.status == pending_payment and now - order.created_at > 30m:
    release_reservation(order)
```

Expiry releases stock back to `available` and cancels the pick list.

# Appendix AB: Operational FAQ Extension

**What is the difference between reserved and on hand?** On hand is the physical count. Reserved is allocated to open orders. Available is the difference.

**Why did my download link expire?** Links are valid for ten minutes to limit sharing. Reopen the download page for a fresh link.

**Can I edit a published product?** Yes, but publishing changes again after editing. Major changes should be reviewed.

**What happens to archived products in existing orders?** Existing orders are unaffected. Archiving only blocks new purchases.

**How do I handle a lost parcel?** Wait ten days after the last tracking update, then file a carrier claim per the runbook.

**Are digital products refundable?** Refunds follow the marketplace policy; typically eligible within 14 days if not downloaded.

**Can inventory be negative?** No. Adjustments that would go negative are rejected.

The products and swag module is deliberately split from the marketplace. Products own what is sold and how it is fulfilled; the marketplace owns money. That separation keeps inventory logic auditable and allows the catalogue to grow to hundreds of items without entangling payment concerns. Implementers should preserve the boundary: never compute prices here, never capture payments here, and never serve bundles without an entitlement check.

End of 05.03.03.13.

# Appendix AE: Fulfilment Queue Contract

## AE.1 Job Payload

```json
{
  "job": "fulfil_order",
  "order_id": "01J9Z3K8YQ4T7M2N5P6R8S0V1W",
  "items": [
    { "variant_id": "01J9...V21", "type": "digital" },
    { "variant_id": "01J9...V22", "type": "physical", "qty": 2 }
  ],
  "attempt": 1
}
```

## AE.2 Retry Policy

| Attempt | Delay | Notes |
|---------|-------|-------|
| 1 | immediate | Initial |
| 2 | 30 s | Transient errors |
| 3 | 5 min | Transient errors |
| 4 | 30 min | Final retry |
| — | DLQ | Manual intervention |

## AE.3 Dead Letter Handling

Jobs in the DLQ surface on an operations dashboard. Each job requires a resolution note before it can be discarded. Requeueing preserves the original `order_id` for idempotency.

## AE.4 Idempotency Keys

| Job | Key |
|-----|-----|
| `fulfil_order` | `order:{order_id}` |
| `reserve_stock` | `reserve:{order_id}:{variant_id}` |
| `release_stock` | `release:{order_id}:{variant_id}` |
| `create_shipment` | `ship:{order_id}` |

## AE.5 Ordering Guarantees

Reservation always precedes shipment creation. Release always precedes cancellation completion. Violating this ordering is a bug, not a recoverable state.

- Labels expire after 14 days.

# Appendix AG: Supplier Scorecard

| Metric | Weight | Target |
|--------|--------|--------|
| On-time delivery | 40% | above 95% |
| Quality acceptance | 30% | above 98% |
| Lead time variance | 20% | under 3 days |
| Responsiveness | 10% | under 24 hours |

## AG.1 Scoring

Each metric is normalised to 0–100 and weighted. A score below 70 triggers a supplier review. Two consecutive quarters below 70 triggers replacement planning.

## AG.2 Quality Acceptance

Acceptance is measured as accepted units divided by received units. Rejected units are returned to the supplier and excluded from `on_hand`.
