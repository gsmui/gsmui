| Variant | Purpose | Size |
|---------|---------|------|
| `thumb` | Lists and pickers | 160×160 cover |
| `small` | Cards | 480 wide |
| `medium` | Detail | 960 wide |
| `large` | Lightbox | 1600 wide |
| `og` | Social preview | 1200×630 |

## 2.4 Invariants

- An asset has at least one variant when an image.
- Checksums are unique per asset content.
- Deletion is blocked while usages exist.
- MIME type is determined by content sniffing, never by extension.

# Chapter 3: Upload Pipeline

## 3.1 Flow

1. Client requests an upload session.
2. Server returns a signed upload target.
3. Client uploads directly to storage.
4. Server verifies the object exists and matches the declared size.
5. Server computes the checksum and sniffs the MIME type.
6. Asset record is created.
7. Variants are queued for generation.

## 3.2 Direct Upload

Direct-to-storage upload avoids proxying large files through the application server. The signed target expires after 15 minutes.

## 3.3 Chunked Uploads

Files above 20 MB use chunked uploads with resumable sessions. Chunk size is 5 MB.

## 3.4 Validation

| Check | Rule |
|-------|------|
| Size | Max 25 MB default, configurable |
| MIME allowlist | Images, PDFs, plain text, zip |
| Image dimensions | Max 12000×12000 |
| Malware scan | Required before publish |
| Checksum | Recomputed server-side |

## 3.5 Rejections

Rejected uploads return a specific code and never create an asset record. Partial uploads are cleaned up after 24 hours.

# Chapter 4: Storage Abstraction

## 4.1 Drivers

| Driver | Use |
|--------|-----|
| `local` | Development |
| `s3` | Production object storage |
| `gcs` | Alternative cloud |
| `custom` | Pluggable |

## 4.2 Driver Contract

| Operation | Semantics |
|-----------|-----------|
| `put` | Write object, return path |
| `get` | Read object stream |
| `exists` | Boolean |
| `delete` | Remove object |
| `url` | Public or signed URL |
| `size` | Object size |

## 4.3 Path Layout

```
media/{yyyy}/{mm}/{uuid}/{variant}.{ext}
```

Paths are opaque. Consumers never construct paths; they resolve via the asset id and variant name.

## 4.4 Portability

Assets are addressed by uuid, not by path. Switching drivers requires migrating objects but no application changes.

# Chapter 5: Image Processing

## 5.1 Processing Steps

1. Decode and validate.
2. Strip metadata (EXIF) except orientation.
3. Apply orientation transform.
4. Generate variants.
5. Encode to modern formats.

## 5.2 Formats

| Source | Output |
|--------|--------|
| JPEG | AVIF, WebP, JPEG fallback |
| PNG | WebP, PNG fallback |
| GIF | WebP (animated preserved where supported) |
| SVG | Served as-is with sanitisation |

## 5.3 Quality

Default quality is 82 for lossy formats. Quality is tuned per variant so that thumbnails remain crisp.

## 5.4 Metadata Stripping

EXIF is stripped after applying orientation to protect privacy. GPS coordinates are never retained.

## 5.5 SVG Sanitisation

SVGs are sanitised to remove scripts, external references, and event handlers. Unsafe SVGs are rejected.

## 5.6 Animated Images

Animated images are converted only when the animated format is supported; otherwise the first frame is used and a warning is recorded.

# Chapter 6: Delivery

## 6.1 URL Strategy

| Visibility | URL |
|------------|-----|
| Public | CDN URL with immutable hash |
| Private | Signed URL with TTL |

## 6.2 Immutable Caching

Public URLs include a content hash so that caches never serve stale bytes. Changing an asset creates a new hash.

## 6.3 Responsive Delivery

Templates emit `srcset` with multiple variants. Browsers select the appropriate size.

## 6.4 Signed URLs

Private assets use signed URLs valid for 10 minutes. Signatures are bound to the asset id and variant.

## 6.5 Range Requests

Large files support range requests for PDFs and archives.

## 6.6 CSP

Delivery domains are allowlisted in the platform CSP. Inline data URIs are not used for media.

# Chapter 7: Organisation

## 7.1 Folders

Folders form a tree with a maximum depth of five. Moving a folder moves its descendants logically; paths are not stored.

## 7.2 Tags

Tags are flat and shared across the library. Tags power filtering and bulk selection.

## 7.3 Search

| Field | Searchable |
|-------|------------|
| Filename | yes |
| Alt text | yes |
| Tags | yes |
| Folder | filter only |

## 7.4 Bulk Operations

- Move to folder.
- Add or remove tags.
- Delete (blocked by usages).
- Download as zip.

Bulk operations are limited to 200 assets and are audited.

---

# Chapter 8: Usage Tracking

## 8.1 Reference Model

`MediaUsage` records owner type and id. Owners register usage when they attach an asset.

## 8.2 Blocking Deletes

Deleting an asset with usages is blocked. The UI lists usages with links to the owning records.

## 8.3 Orphan Detection

A nightly job compares usages against assets. Assets without usages older than 30 days are candidates for cleanup.

## 8.4 Broken References

If a referenced asset is missing, the owning record shows a placeholder and an alert is raised. Broken references block publish for content that requires media.

---

# Chapter 9: Lifecycle and Retention

## 9.1 States

```
uploading -> processing -> ready -> archived -> deleted
                       \-> rejected
```

## 9.2 Soft Delete

Deletion is soft for 30 days. During that window the asset can be restored. After 30 days objects are purged.

## 9.3 Archival

Archived assets remain accessible by id but are excluded from pickers. Archival is used for superseded assets.

## 9.4 Retention Policy

| Asset Type | Retention |
|------------|-----------|
| Content images | While referenced |
| Product bundles | While product exists |
| Temporary uploads | 24 hours |
| Deleted assets | 30 days |

## 9.5 Legal Hold

Assets under legal hold cannot be deleted until the hold is released by an administrator.

# Chapter 11: Security

## 11.1 Threat Model

| Threat | Vector | Mitigation |
|--------|--------|------------|
| Malicious file | Upload of executable | MIME sniffing + scan |
| SVG XSS | Inline script in SVG | Sanitisation |
| Path traversal | Crafted filename | Opaque paths |
| Private asset leak | Guessing URLs | Signed URLs |
| Metadata leak | EXIF GPS | Stripping |
| Zip bomb | Compressed upload | Size and ratio limits |
| Decompression attack | Image bombs | Dimension limits |

## 11.2 MIME Sniffing

The server determines MIME from content, never the extension. A mismatch with the declared type rejects the upload.

## 11.3 Scanning

Files are scanned for malware before becoming `ready`. Scanned-clean is required before an asset can be attached to published content.

# Chapter 21: Deduplication

## 21.1 Content Addressing

Uploads with an identical checksum resolve to the existing asset. The new upload session is discarded and the existing asset id is returned.

## 21.2 Reference Counting

Deduplication does not duplicate storage. Usages are recorded per owner, so deleting one owner's reference does not remove the asset while others remain.

## 21.3 Limits

Deduplication applies across visibility scopes only when the existing asset is public. Private assets are never returned for a public upload.

## 21.4 Audit

Deduplicated uploads record a `deduplicated` note against the upload session for traceability.

# Appendix K: Variant Generation Internals

## K.1 Pipeline

```
request(variant) -> cache lookup -> hit: serve
                                   -> miss: enqueue
enqueue -> decode -> transform -> encode -> store -> serve
```

## K.2 Concurrency

Generation uses a per-asset lock so that concurrent requests for the same variant generate once.

## K.3 Failure Handling

| Failure | Behaviour |
|---------|-----------|
| Decode error | Mark asset `unprocessable`, serve original |
| Encode error | Retry once, then serve original |
| Storage error | Retry with backoff |
| Timeout | Serve original, log |

## K.4 Cache Headers

Variant responses set long-lived cache headers because variant bytes are immutable for a given asset uuid and variant name.

## K.5 Regeneration

Replacing an asset creates a new uuid, so variants are regenerated naturally. In-place variant regeneration is not supported.

# Appendix M: Image Security Deep Dive

## M.1 Decoder Hardening

Decoding runs in a sandboxed process with memory and time limits. Decoder crashes are contained and do not affect the application.

## M.2 Decompression Bombs

Limits on pixel count and decoded size prevent decompression bombs from exhausting memory.

## M.3 Format-Specific Risks

| Format | Risk | Mitigation |
|--------|------|------------|
| JPEG | Parser exploits | Sandboxed decode |
| PNG | Large IDAT | Size limits |
| GIF | Frame bombs | Frame limits |
| SVG | Script injection | Sanitisation |
| AVIF | Decoder bugs | Sandbox + version pinning |

## M.4 Output Encoding

All outputs are re-encoded, which normalises malformed inputs and strips embedded payloads.

## M.5 Scanning

Antivirus scanning runs on the original bytes before processing. Failed scans quarantine the asset.
