# Part II: Settings Specification

This part specifies how platform settings are modelled, validated, stored, changed, and audited. Settings are the highest-leverage surface in the admin panel: a single misconfigured value can affect every tenant, so the module prioritises explicit validation, safe change propagation, and strong auditability over convenience.

---

# Chapter 1: Scope and Objectives

## 1.1 Objectives

| Objective | Measure | Target |
|-----------|---------|--------|
| Change safety | Invalid settings accepted | zero |
| Propagation | Setting to all nodes | under 60 s |
| Auditability | Mutations recorded | 100% |
| Recovery | Rollback time | under 5 min |
| Secrecy | Secret values exposed in logs | zero |

## 1.2 In Scope

- Platform-wide general settings.
- Appearance and branding.
- Integration credentials and endpoints.
- Security policy configuration.
- Email template customisation.
- Change history and rollback.

## 1.3 Out of Scope

- Per-user preferences (users module 05.03.03.04).
- Tenant-level overrides beyond documented keys.
- Infrastructure secrets managed by the deployment platform.
- Feature flags (feature flags module 05.03.03.20).

## 1.4 Consumers

| Consumer | Settings Used |
|----------|---------------|
| Web application | General, appearance, security |
| Billing | Payment gateway credentials |
| Notifications | Email provider, templates |
| Media | Storage and CDN |
| Search | Search engine credentials |
| Blog | Base URL, timezone |

# Chapter 2: Settings Model

## 2.1 Entities

| Entity | Purpose | Key Fields |
|--------|---------|------------|
| `SettingGroup` | Logical grouping | `key`, `name`, `order` |
| `Setting` | Individual value | `key`, `group`, `type`, `value` |
| `SettingVersion` | Immutable snapshot | `setting_key`, `version`, `value_hash` |
| `SettingSecret` | Encrypted secret | `key`, `ciphertext`, `rotated_at` |
| `SettingChange` | Change record | `key`, `old`, `new`, `actor_id` |
| `SettingSchema` | Validation schema | `key`, `rules` |

## 2.2 Setting Types

| Type | Storage | Example |
|------|---------|---------|
| `string` | text | Platform name |
| `text` | long text | Email footer |
| `integer` | int | Session timeout |
| `boolean` | bool | 2FA required |
| `enum` | varchar | Timezone mode |
| `json` | jsonb | IP allowlist |
| `secret` | encrypted | API key |
| `url` | text | Base URL |
| `email` | text | From address |

## 2.3 Key Convention

Keys use dot notation: `general.platform_name`, `mail.from_address`, `storage.driver`. Keys are permanent; renaming requires a migration.

## 2.4 Values

Values are typed at the boundary. A boolean stored as the string "true" is invalid. Type coercion is explicit and tested.

## 2.5 Defaults

Every setting declares a default in code. The database stores only overrides, so a fresh install behaves predictably even with an empty settings table.

# Chapter 3: Validation

## 3.1 Validation Rules

| Rule | Applies To |
|------|------------|
| Required | All settings without defaults |
| Type check | All settings |
| Range | integer |
| Format | url, email |
| Enum membership | enum |
| Regex | string where declared |
| Reachability | url settings (optional probe) |

## 3.2 Validation Timing

Validation runs on save and again on read for critical settings. A stored value that no longer validates is surfaced as a warning banner rather than silently used.

## 3.3 Cross-Field Validation

Some settings depend on others:

- Choosing `s3` storage requires bucket and region.
- Enabling a payment gateway requires its keys.
- Requiring 2FA requires at least one MFA method enabled.

Cross-field rules are declared centrally so the UI and the API agree.

## 3.4 Failure Behaviour

Invalid saves are rejected atomically. Partial application is never allowed: either every changed setting in the request validates, or none are written.

## 3.5 Probing

URL and credential settings may be probed with a test call. Probes are optional, rate limited, and never block saving unless the operator opts into strict mode.

# Chapter 4: Secret Handling

## 4.1 Storage

Secrets are encrypted at rest with the platform key. They are never stored in plaintext and never returned by the API in full.

## 4.2 Display

Secrets are masked as `••••••••` with only the last four characters shown. Revealing a secret requires an explicit action and is audited.

## 4.3 Rotation

Rotating a secret writes a new ciphertext and keeps the previous version for a grace period. Consumers read the current version.

## 4.4 Logging

Secrets are redacted from logs, error reports, and analytics automatically. A regression test asserts redaction.

## 4.5 Export

Settings exports exclude secrets by default. Including them requires an explicit flag and produces an encrypted archive.

# Chapter 5: Change Propagation

## 5.1 Propagation Path

```
save -> validate -> persist -> emit SettingChanged -> consumers refresh
```

## 5.2 Consumers

| Consumer | Refresh Strategy |
|----------|------------------|
| Web application | Cache invalidation |
| Queue workers | Restart on critical keys |
| Scheduled jobs | Read at next run |
| Edge cache | Purge affected keys |

## 5.3 Critical Keys

Some keys require worker restart rather than refresh, for example mail transport. These keys are marked critical and trigger a controlled restart.

## 5.4 Propagation Guarantee

Changes propagate to all nodes within 60 seconds. Propagations are recorded with timestamps and node acknowledgements where available.

## 5.5 Failure Handling

If a consumer fails to refresh, it continues with the previous value and reports a warning. Persistent failures raise an alert.

---

# Chapter 6: Change History and Rollback

## 6.1 Recording

Every change records the key, previous value hash, new value hash, actor, timestamp, and request id. Secret values are recorded as hashes only.

## 6.2 History View

The history view lists changes by group and key, with filters by actor and date. Each entry links to the diff where the value is non-secret.

## 6.3 Rollback

Rolling back restores the previous value, which itself creates a new change record. History is append-only; rollback never deletes entries.

## 6.4 Bulk Rollback

Bulk rollback restores a group to a prior snapshot. It requires a second approver when the group contains critical keys.

## 6.5 Retention

Change records are retained for seven years, consistent with platform audit policy.

# Chapter 7: Appearance and Branding

## 7.1 Brand Settings

| Setting | Type | Notes |
|---------|------|-------|
| `brand.name` | string | Display name |
| `brand.logo` | media id | Light logo |
| `brand.logo_dark` | media id | Dark logo |
| `brand.favicon` | media id | 32×32 minimum |
| `brand.accent` | color | Hex value |

## 7.2 Validation

Logos must resolve to media assets. Colors must parse as valid CSS colors. Favicon dimensions are checked on upload.

## 7.3 Application

Branding applies to the admin panel, transactional emails, and public pages. Application is immediate on save.

## 7.4 Fallbacks

Missing logos fall back to the platform name rendered as text. Missing accent falls back to the default theme accent.

# Chapter 8: General Settings

## 8.1 General Keys

| Key | Type | Default |
|-----|------|---------|
| `general.platform_name` | string | GsmUi |
| `general.base_url` | url | empty |
| `general.timezone` | enum | UTC |
| `general.date_format` | enum | Y-m-d |
| `general.locale` | enum | en |
| `general.support_email` | email | empty |

## 8.2 Constraints

- `base_url` must be absolute and https in production.
- `timezone` must be a valid IANA identifier.
- `locale` must be a supported locale.
- `support_email` must be a reachable address.

## 8.3 Impact

Changing `base_url` invalidates absolute links in cached content and triggers regeneration of sitemaps and emails.

# Chapter 10: Security Settings

## 10.1 Security Keys

| Key | Type | Default |
|-----|------|---------|
| `security.mfa_required` | boolean | false |
| `security.password_min_length` | integer | 12 |
| `security.password_require_symbols` | boolean | true |
| `security.session_timeout_minutes` | integer | 120 |
| `security.ip_allowlist` | json | [] |
| `security.audit_retention_days` | integer | 2555 |

## 10.2 Constraints

- Password minimum length is between 8 and 128.
- Session timeout is between 15 minutes and 30 days.
- IP allowlist entries must be valid CIDR blocks.
- Enabling MFA requires at least one MFA method configured.

## 10.3 Lockout Risk

Changing IP allowlist or session timeout can lock out administrators. The UI requires confirmation and offers a 15-minute grace window where the old policy remains valid.

## 10.4 Emergency Access

A break-glass procedure exists outside this module for recovery when security settings lock everyone out. It is documented in the security runbook (05.03.03.22).
