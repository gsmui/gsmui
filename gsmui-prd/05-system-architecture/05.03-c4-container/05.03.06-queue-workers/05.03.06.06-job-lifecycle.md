# 05.03.06.06 - Job Lifecycle

**Project:** GsmUi
**Architecture:** C4 Model – Level 2 (Container)
**Container:** Queue Workers
**Framework:** Laravel 13 + Horizon
**Version:** 1.0.0

---

# Purpose

This document traces a job through its entire lifecycle in the GsmUi queue system — from the moment it is dispatched by application code, through Redis queue storage, worker processing, and eventual completion, retry, or failure. Understanding the job lifecycle is essential for debugging, monitoring, and designing resilient background operations.

---

# Responsibilities

The job lifecycle involves:

* Job creation and dispatch
* Serialization and queue storage
* Reservation by worker
* Processing execution
* Success acknowledgment
* Failure handling
* Retry scheduling
* Dead-letter queue storage

# Lifecycle States

## 1. Dispatched

Application code creates and dispatches a job:

```php
ProcessMedia::dispatch($file)->onQueue('media');
```

At this stage:

* Job class is instantiated (or resolved from container)
* Properties are serialized
* Dispatch event is fired
* Job is pushed to Redis

---

## 2. Queued

The job payload is stored in a Redis list:

```text
Key: redis:queues:media
Value: Serialized job payload with:
  - display_name
  - job
  - data (serialized payload)
  - attempts (0)
  - timeout (300)
  - retry_until (null)
```

The job waits until a worker is available.

---

## 3. Reserved

A worker pops the job from the Redis list using `BRPOP`:

```text
Worker calls:
BRPOP redis:queues:media 0

Redis returns:
[job payload]

Worker increments attempt count
Worker moves job to reserved list:
LPUSH redis:queues:media:reserved {payload_with_attempt_1}
```

At this point, the job is no longer visible to other workers.

---

## 4. Processing

The worker deserializes the job and calls `handle()`:

```php
public function handle(MediaProcessor $processor): void
{
    $processor->convert($this->file);
}
```

During processing:

* Job timeout timer is active
* Memory usage is monitored
* Progress may be tracked via events
* Database connections are held

---

## 5. Completed

On successful completion:

```php
public function handle(): void
{
    // Business logic succeeds
}

// Worker calls:
$this->delete(); // Removes from reserved list
```

The job is removed from Redis and marked as processed in metrics.

---

## 6. Failed

If the job throws an exception:

```php
public function handle(): void
{
    throw new \Exception('Processing failed');
}

// Worker calls:
$this->fail($exception);
```

The job is:

* Moved from reserved list
* Added to failed jobs list in Redis
* Optionally persisted to MySQL `failed_jobs` table
* Exception and payload are recorded

---

## 7. Retrying

If retry attempts remain:

```php
// config/horizon.php
'tries' => 3,
'backoff' => [10, 30, 60],
```

The job is:

* Requeued to the same queue
* Delayed by the backoff period
* Attempt count incremented

```text
Attempt 1 fails → wait 10 seconds → retry
Attempt 2 fails → wait 30 seconds → retry
Attempt 3 fails → move to DLQ
```

---

## 8. Dead (DLQ)

When max attempts are exhausted:

```text
Job moved to redis:failed:jobs
Job persisted to failed_jobs table
Exception and payload preserved
Admin notified
```

Administrators can:

* Inspect the failure reason
* Retry manually
* Delete permanently

# Timing and Timeouts

Each job has two timeout values:

| Timeout | Source | Purpose |
|---------|--------|---------|
| `timeout` | Job class or config | Worker process hard limit |
| `retry_until` | Optional, per-job | Absolute deadline for retries |

Worker enforces `timeout` by killing the process if `handle()` does not complete within the limit.

# Job Chaining

Jobs can be chained to execute sequentially:

```php
ProcessMedia::withChain([
    new GenerateThumbnails($file),
    new UpdateSearchIndex($file),
])->dispatch();
```

If any job in the chain fails, subsequent jobs are not dispatched.

---

# Job Batching

Jobs can be batched for parallel processing with cancellation:

```php
$batch = Bus::batch([
    new ProcessItem($item1),
    new ProcessItem($item2),
    new ProcessItem($item3),
])->onQueue('media')
  ->then(function (Batch $batch) {
      // All jobs completed
  })
  ->catch(function (Batch $batch, Throwable $e) {
      // Batch failed
  })
  ->finally(function (Batch $batch) {
      // Batch cleanup
  })
  ->dispatch();
```

Batch jobs share a batch ID and can be cancelled, tracked, and reported collectively.

---

# Rate Limiting

Jobs can be rate-limited to prevent overwhelming downstream systems:

```php
use Illuminate\Support\Facades\RateLimiter;

// In handle()
RateLimiter::for('api', function (Request $request) {
    return Limit::perMinute(60)->by($request->user()?->id);
});
```

Rate limiting is enforced at dispatch time, not worker time.

---

# Job Cancellation

Jobs can be cancelled before processing:

```php
// From application
Queue::delete($jobId);

// From Horizon dashboard
// Jobs in the queue can be deleted before reservation
```

Once a job is reserved by a worker, cancellation requires worker cooperation (e.g., checking a cancellation flag).

# Failure Analysis

When a job fails, investigate:

1. Exception type and message
2. Job payload (input data)
3. Attempt count and backoff history
4. Worker logs at failure time
5. Downstream system state

Common failure patterns:

| Pattern | Cause | Resolution |
|---------|-------|------------|
| Timeout | Job too slow | Increase timeout, optimize job |
| Memory | Job too large | Reduce batch size, stream data |
| Downstream error | External service down | Retry with backoff, circuit breaker |
| Data error | Invalid input | Validate before dispatch |

# Advanced Lifecycle Patterns

## Job Middleware

Job middleware executes code before and after the job handler:

```php
class ProcessMedia implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public function middleware(): array
    {
        return [
            new WithoutOverlapping('media-processing'),
            new ThrottlesExceptions(10, 60),
        ];
    }

    public function handle(): void
    {
        // Processing logic
    }
}
```

### WithoutOverlapping Middleware

Prevents concurrent execution of the same job type:

```php
new WithoutOverlapping('media-processing')
```

This middleware:

* Acquires a lock in Redis
* If lock is held, releases the job back to the queue
* Processes the job if lock is available
* Releases lock after job completes

---

### ThrottlesExceptions Middleware

Limits the rate of exceptions:

```php
new ThrottlesExceptions(10, 60) // 10 exceptions per 60 seconds
```

This middleware:

* Tracks exception count in Redis
* If limit exceeded, delays the job
* Prevents cascading failures

---

### EnsureIdempotent Middleware

Ensures jobs are not processed twice:

```php
class EnsureIdempotent
{
    public function handle(object $job, Closure $next): void
    {
        $lockKey = 'job:idempotent:' . $job->uuid();
        
        if (Redis::set($lockKey, 1, 'EX', 3600, 'NX')) {
            $next($job);
        } else {
            $job->delete(); // Already processed
        }
    }
}
```

## Job Batching Lifecycle

Batch jobs have additional lifecycle states:

```text
Batch Created → Jobs Dispatched → Jobs Processing → Batch Complete
                    │                  │
                    │                  ├── Some jobs fail
                    │                  │   └── catch() callback
                    │                  │
                    │                  └── All jobs complete
                    │                      └── then() callback
                    │
                    └── Batch cancelled
                        └── finally() callback
```

### Batch State Machine

```text
pending → processing → completed
                → cancelled
                → failed

Transitions:
  pending → processing: first job starts
  processing → completed: all jobs finish
  processing → cancelled: cancel() called
  processing → failed: catch() callback triggered
```

---

## Job Chain Lifecycle

Chains execute jobs sequentially with dependency tracking:

```text
Job 1 (Processing) → Job 2 (Pending) → Job 3 (Pending)
     │
     ├── Success → Job 2 starts
     │
     └── Failure → Chain stops, remaining jobs not dispatched
```

### Chain State Tracking

```php
$chain = ProcessMedia::withChain([
    new GenerateThumbnails($file),
    new UpdateSearchIndex($file),
    new NotifyUser($user),
])->dispatch();

// Track chain progress
$chainId = $chain->chainId();
$jobs = DB::table('jobs')
    ->where('chain_id', $chainId)
    ->get();
```

## Serialization Security

Jobs must not serialize sensitive data:

```php
class ProcessPayment implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    // BAD: Card number is serialized
    public function __construct(
        public string $cardNumber, // Exposed in Redis!
        public float $amount,
    ) {}

    // GOOD: Only reference IDs are serialized
    public function __construct(
        public int $paymentId,
        public float $amount,
    ) {}

    public function handle(): void
    {
        $payment = Payment::find($this->paymentId);
        // Load sensitive data at processing time
        $this->processPayment($payment->card_number, $this->amount);
    }
}
```

---

## Model Serialization

Eloquent models are serialized as references:

```json
{
  "command": "O:26:\"App\\Jobs\\ProcessMedia\":1:{s:4:\"file\";s:45:\"App\\Models\\Media:123:{...}\"}}"
}
```

When the job is processed:

1. Worker deserializes the payload
2. Model reference is resolved from database
3. Fresh model instance is loaded
4. Handler receives the fresh model

This ensures workers always operate on current data.

# Job Timing Deep Dive

## Dispatch to Queue

Time from `dispatch()` to Redis storage:

```php
$start = microtime(true);
ProcessMedia::dispatch($file);
$elapsed = microtime(true) - $start;

// Expected: <50ms
```

Factors affecting this time:

* Redis connection latency
* Serialization complexity
* Network overhead

---

## Queue to Worker

Time from Redis storage to worker pickup:

```text
Job dispatched → Waiting in Redis → Worker picks up job
                                    │
                                    ├── Worker idle: <1 second
                                    ├── Worker busy: until current job finishes
                                    └── No workers: waits indefinitely
```

Factors affecting this time:

* Worker availability
* Current job duration
* Queue depth

---

## Processing Time

Time from worker pickup to job completion:

| Job Type | Expected Time | Timeout |
|----------|---------------|---------|
| Email send | 2-5 seconds | 120 seconds |
| Image resize | 5-30 seconds | 300 seconds |
| Search index | 10-60 seconds | 300 seconds |
| Data export | 30-300 seconds | 600 seconds |
| Analytics | 60-600 seconds | 600 seconds |
| Backup | 300-1800 seconds | 1800 seconds |

---

## Total Lifecycle Time

```text
Dispatch → Queue → Pickup → Processing → Complete

Target: <10 seconds for high priority jobs
Target: <60 seconds for default jobs
Target: <5 minutes for media jobs
Target: <10 minutes for export jobs
```

# Job Failure Patterns

## Transient Failures

Temporary issues that resolve with retry:

```php
class CallExternalApi implements ShouldQueue
{
    public int $tries = 3;

    public function backoff(): array
    {
        return [10, 30, 60]; // Exponential backoff
    }

    public function handle(): void
    {
        $response = Http::timeout(10)->get($this->url);
        
        if ($response->failed()) {
            throw new \Exception('API unavailable');
        }
    }
}
```

---

## Data Failures

Invalid input data that cannot be retried:

```php
class ProcessUpload implements ShouldQueue
{
    public function handle(): void
    {
        $file = File::find($this->fileId);
        
        if (!$file) {
            // File was deleted — no point retrying
            Log::warning('File not found', ['file_id' => $this->fileId]);
            return; // Silently skip
        }

        if (!$file->isValid()) {
            // Invalid file — cannot process
            throw new InvalidFileException('File is corrupted');
        }

        // Process valid file
    }
}
```

---

## Code Failures

Bugs in job logic:

```php
class BuggyJob implements ShouldQueue
{
    public function handle(): void
    {
        // BUG: Undefined variable
        $result = $undefinedVariable + 1;
    }
}

// Fix: Deploy corrected code, then retry failed job
```

---

## Resource Failures

Insufficient resources:

```php
class LargeExport implements ShouldQueue
{
    public int $timeout = 600;
    public int $memory = 1024; // MB

    public function handle(): void
    {
        $data = $this->loadLargeDataset(); // Uses lots of memory
        $this->generateExport($data);
    }
}
```

Resource failures require configuration changes, not code changes.

# Job Idempotency Patterns

## Database Check Pattern

```php
class ProcessPayment implements ShouldQueue
{
    public function handle(): void
    {
        $payment = Payment::find($this->paymentId);
        
        if ($payment->status === 'completed') {
            return; // Already processed
        }

        // Process payment
        $this->gateway->charge($payment);
        $payment->update(['status' => 'completed']);
    }
}
```

## Lock Pattern

```php
class UpdateSearchIndex implements ShouldQueue
{
    public function handle(): void
    {
        $lock = Cache::lock('search:index:' . $this->documentId, 60);
        
        if ($lock->get()) {
            try {
                $this->indexer->update($this->documentId);
            } finally {
                $lock->release();
            }
        }
        // If lock not acquired, another worker is processing this document
    }
}
```

---

## UUID Pattern

```php
class ProcessEvent implements ShouldQueue
{
    public function __construct(
        public string $eventId,
        public array $eventData,
    ) {}

    public function handle(): void
    {
        $processed = Cache::has('event:processed:' . $this->eventId);
        
        if ($processed) {
            return; // Already processed
        }

        // Process event
        $this->processEvent($this->eventData);
        
        // Mark as processed
        Cache::put('event:processed:' . $this->eventId, true, now()->addDays(7));
    }
}
```

# Job Cancellation Patterns

## Pre-Processing Cancellation

```php
class LongRunningJob implements ShouldQueue
{
    public function handle(): void
    {
        $steps = [/* ... */];
        
        foreach ($steps as $step) {
            // Check cancellation flag
            if ($this->isCancelled()) {
                Log::info('Job cancelled', ['job_id' => $this->uuid()]);
                return;
            }
            
            $this->processStep($step);
        }
    }

    private function isCancelled(): bool
    {
        return Cache::has('job:cancelled:' . $this->uuid());
    }
}
```

# Job Lifecycle Best Practices

1. **Design for idempotency** — Jobs may be processed more than once
2. **Set appropriate timeouts** — Prevent zombie jobs from holding workers
3. **Use meaningful job names** — Help operators understand job purpose
4. **Document queue selection** — Explain why jobs are on specific queues
5. **Log key events** — Enable debugging and monitoring
6. **Handle exceptions gracefully** — Don't let exceptions crash workers
7. **Test failure scenarios** — Verify retry and DLQ behavior
8. **Monitor lifecycle metrics** — Track dispatch, processing, and completion rates
9. **Use job middleware** — Add cross-cutting concerns without modifying job code
10. **Keep payloads small** — Serialize only necessary data

### Without Overlapping Middleware

```php
class ProcessMedia implements ShouldQueue
{
```

# Job Lifecycle Best Practices

## Design Principles

1. **Idempotency** — Jobs may be processed more than once. Design jobs to be safe to retry.

2. **Atomicity** — Jobs should complete entirely or not at all. Use database transactions.

3. **Timeout Awareness** — Set appropriate timeouts to prevent zombie jobs.

4. **Resource Cleanup** — Release connections and resources between jobs.

5. **Meaningful Logging** — Log key events for debugging and monitoring.

6. **Error Handling** — Handle exceptions gracefully. Don't let exceptions crash workers.

7. **Payload Minimization** — Serialize only necessary data. Use references for large objects.

8. **Queue Selection** — Choose the right queue based on urgency and resource needs.

9. **Retry Strategy** — Use exponential backoff for transient failures.

10. **Monitoring** — Track job metrics for performance and reliability.

---

## Common Pitfalls

| Pitfall | Problem | Solution |
|---------|---------|----------|
| Large payloads | Redis memory exhaustion | Use references instead of full objects |
| No timeout | Zombie jobs hold workers | Set appropriate timeouts |
| No retry | Transient failures become permanent | Use retry with backoff |
| Shared state | Race conditions | Use locks and idempotency keys |
| No monitoring | Silent failures | Track job metrics and failures |
| Tight coupling | Jobs depend on specific state | Design for independence |
