# 06.01 - Database Design Principles

**Project:** GsmUi
**Architecture:** Domain-Driven Database Design
**Database:** MySQL 8.4 LTS (InnoDB)
**Framework:** Laravel 13 + Eloquent ORM
**Version:** 1.0.0

---

# Purpose

This document defines the database design principles that govern every schema, table, relationship, index, and migration within GsmUi.

The objective is to create a database that is:

* Maintainable
* Performant
* Scalable
* Secure
* Consistent
* Easy to evolve

These principles apply across all business domains, including Components, Themes, Marketplace, Billing, Documentation, CMS, Blog, Playground, AI, MCP, and Administration.

---

# Core Principles

## 1. Domain-Driven Design (DDD)

The database is organized by **business domains**, not technical features.

Example:

```text id="ddd01"
Identity

Marketplace

Billing

Themes

Components

Documentation

CMS

Blog

Playground

Analytics

AI

MCP
```

Each domain owns its tables and relationships.

---

## 2. Modular Monolith

All domains share a single relational database during the MVP while maintaining clear ownership boundaries.

Rules:

* No shared "miscellaneous" tables
* Domain-specific migrations
* Domain-specific repositories
* Domain-specific services

Future extraction into separate databases should require minimal changes.

---

## 3. Single Source of Truth

MySQL is the authoritative source for business data.

Other systems are derived from it:

```text id="ddd02"
MySQL

↓

Redis

↓

Meilisearch

↓

Analytics

↓

Exports
```

Never treat cache or search indexes as canonical.

---

## 4. ACID Transactions

Critical business operations must preserve:

* Atomicity
* Consistency
* Isolation
* Durability

Examples:

* Purchases
* Subscription changes
* License generation
* Theme publication

Transactions are coordinated in the Action layer.

---

## 5. Normalization

Target:

**Third Normal Form (3NF)**

Benefits:

* Reduced duplication
* Easier maintenance
* Better consistency

Intentional denormalization is allowed only for measured performance improvements.

---

## 6. Clear Domain Ownership

Each table belongs to exactly one domain.

Example:

```text id="ddd03"
Themes Domain

themes

theme_versions

theme_tokens

theme_exports
```

Other domains access data through Services or Repositories—not by assuming ownership.

---

## 7. Business-Meaningful Tables

Table names should reflect business concepts.

Good:

```text id="ddd04"
subscriptions

orders

licenses

components

themes
```

Avoid vague names such as:

```text id="ddd05"
data

records

items

objects

misc
```

---

## 8. Explicit Relationships

Every relationship must be clearly defined.

Supported:

* One-to-One
* One-to-Many
* Many-to-Many
* Polymorphic (only when appropriate)

Use foreign keys wherever possible.

---

## 9. Consistent Naming

Follow Laravel conventions.

Examples:

```text id="ddd06"
users

theme_tokens

component_examples

marketplace_products
```

Rules:

* snake_case
* plural table names
* singular foreign keys

---

## 10. Immutable History

Historical business data should not be overwritten.

Examples:

* Orders
* Invoices
* Payments
* Licenses
* Activity Logs

Create new records instead of modifying historical facts.

# Table Design Principles

Every table should have:

* Single responsibility
* Clear ownership
* Stable primary key
* Foreign keys
* Audit timestamps
* Appropriate indexes

Avoid mixing unrelated concepts.

---

# Primary Keys

Standard:

```text id="ddd08"
BIGINT UNSIGNED AUTO_INCREMENT
```

Advantages:

* Fast joins
* Small indexes
* Laravel compatibility

Public identifiers may additionally use UUID or ULID where appropriate.

---

# Public Identifiers

Expose UUID/ULID for:

* Public APIs
* Shared URLs
* Download links
* Webhooks

Internal joins continue to use integer keys.

---

# Foreign Keys

Use foreign keys for referential integrity.

Example:

```text id="ddd09"
order.user_id

license.order_id

theme.author_id
```

Apply cascading rules deliberately:

* `CASCADE`
* `RESTRICT`
* `SET NULL`

Choose the behavior that matches the business requirement.

---

# Soft Deletes

Use `deleted_at` only when recovery is valuable.

Recommended:

* Users
* Components
* Themes
* Templates
* Blog posts

Avoid soft deletes for immutable transactional records such as invoices.

---

# Audit Columns

Standard columns:

```text id="ddd10"
created_at

updated_at

deleted_at
```

Optional ownership:

```text id="ddd11"
created_by

updated_by
```

---

# Data Integrity

Enforce integrity through:

* Foreign keys
* Unique constraints
* Check constraints (where supported)
* Database defaults
* Application validation

Never rely solely on frontend validation.

---

# Indexing Strategy

Index:

* Foreign keys
* Slugs
* Status
* Publication dates
* Frequently filtered columns

Review indexes using production query metrics.

---

# Unique Constraints

Examples:

```text id="ddd12"
users.email

themes.slug

components.slug

roles.name

permissions.name
```

Use composite unique indexes where required.

---

# Composite Indexes

Examples:

```text id="ddd13"
(status, published_at)

(user_id, created_at)

(product_id, version)
```

Optimize for real query patterns.

---

# JSON Columns

Use JSON only for:

* Flexible metadata
* User preferences
* Theme settings
* Temporary configuration

Do not store core relational data inside JSON.

---

# Enum Strategy

Prefer lookup tables or constrained string values over database ENUM types when future extensibility is expected.

Suitable examples:

* Order status
* Subscription status
* Theme visibility

Represent these as well-defined application constants.

---

# Timestamps

Always use UTC.

Application layer handles timezone conversion for display.

Never store local time in the database.

---

# Monetary Values

Never use floating-point types.

Use:

```text id="ddd14"
DECIMAL(12,2)
```

or integer minor units (cents) when precision requirements dictate.

Store currency separately.

---

# Versioning

Entities that evolve over time should have dedicated version tables.

Examples:

```text id="ddd15"
theme_versions

template_versions

component_versions

documentation_versions
```

Do not overwrite published artifacts.

---

# Event Sourcing

Not required for MVP.

Future candidates:

* Billing
* Subscription lifecycle
* License management

Current design remains compatible with event sourcing if adopted later.

---

# Multi-Tenancy

MVP:

* Single tenant

Future:

* Team workspaces
* Organizations
* Enterprise tenants

Schema should avoid assumptions that prevent tenant isolation.

---

# Read vs Write

Write model:

* Normalized
* Transactional

Read model:

* Cached
* Search indexed
* Aggregated

Repositories abstract persistence details.

---

# Migration Strategy

Rules:

* One concern per migration
* Forward-only
* Version controlled
* Repeatable deployments

Never edit previously executed production migrations.

---

# Seeding Strategy

Seed only deterministic data.

Examples:

* Roles
* Permissions
* Default settings
* Theme presets
* Categories

Avoid environment-specific business records.

---

# Performance Principles

* Normalize first
* Measure before optimizing
* Prefer indexes over duplicated data
* Paginate large datasets
* Use eager loading
* Archive historical records when appropriate

---

# Security Principles

Protect:

* Credentials
* Tokens
* Recovery codes
* API secrets

Hash passwords with Argon2id.

Encrypt sensitive fields using Laravel's encryption services.

---

# Backup Principles

Backups must be:

* Automated
* Encrypted
* Verified
* Tested regularly

Recovery procedures are part of operational readiness.

---

# Testing Principles

Every schema change should include:

* Migration tests
* Constraint verification
* Foreign key validation
* Performance review
* Repository integration tests

Database integrity is verified continuously.

---

# Scalability Principles

Design for future:

* Read replicas
* Partitioning
* Archiving
* Search offloading
* Queue processing
* Domain extraction

The schema should evolve incrementally without breaking existing contracts.

---

# Anti-Patterns

Avoid:

* Generic tables
* EAV models for core entities
* Circular foreign keys
* Unbounded JSON storage
* Missing indexes
* Soft deleting immutable records
* Business logic in database triggers

Keep the database focused on persistence and integrity.

---

# Summary

The GsmUi database is designed around business domains, strong relational modeling, explicit ownership, and long-term maintainability. By following these principles—consistent naming, normalized schemas, clear relationships, audited changes, and performance-conscious indexing—the platform establishes a robust foundation capable of supporting both the MVP and future enterprise-scale growth.

# Security

Database security principles:

* Passwords hashed with Argon2id (never plaintext)
* Sensitive fields encrypted via Laravel
* API secrets stored in environment variables
* Database users follow least-privilege
* No business logic in database triggers
* Audit columns track data modifications
* Backup encryption at rest
* Network-level access restrictions
* No raw SQL in application code
* Foreign keys enforce referential integrity

---

# Testing

Testing principles for database changes:

| Test Type | Scope |
|-----------|-------|
| Migration tests | Forward/backward compatibility |
| Constraint verification | Unique, FK, check constraints |
| Foreign key validation | Cascade rules, nullable behavior |
| Performance review | Query plan analysis |
| Repository integration | All repositories against test DB |
| Seed idempotency | All seeders run cleanly |
| Schema diff | CI detects unexpected changes |

Every schema change must include corresponding tests.

---

# Performance

Performance principles:

* Normalize first, measure before optimizing
* Prefer indexes over duplicated data
* Paginate large datasets (cursor preferred)
* Use eager loading (prevent N+1)
* Archive historical records quarterly
* Review query plans for new indexes
* Monitor slow query log
* Target p95 <20ms for simple queries
* Target p95 <100ms for complex queries

# API

Database serves the API through:

| API Consumer | Access Pattern |
|-------------|----------------|
| REST API | Repository → Eloquent → API Resource |
| Livewire | Service → Repository → Model |
| MCP Clients | Same REST API, token auth |
| CLI Tools | Artisan → Service → Repository |
| Webhooks | Event → Service → Repository |
| Analytics | Read replica queries |
| Search | Meilisearch async indexing |

Rules:

* No raw SQL in controllers
* Eloquent models never exposed directly
* API Resources serialize all responses
* Query scopes enforce consumer boundaries
