# 06.02 - Database Naming Conventions

**Project:** GsmUi
**Architecture:** Database Standards
**Database:** MySQL 8.4 LTS
**Framework:** Laravel 13 + Eloquent ORM
**Version:** 1.0.0

---

# Purpose

This document establishes the official naming conventions for the GsmUi database. Consistent naming improves readability, maintainability, onboarding, tooling compatibility, and long-term scalability.

These standards apply to:

* Tables
* Columns
* Primary Keys
* Foreign Keys
* Indexes
* Constraints
* Pivot Tables
* Migrations
* Eloquent Models
* Relationships
* Enums
* JSON Fields

Every new database object must follow these conventions.

---

# General Principles

Names should be:

* Clear
* Predictable
* Business-oriented
* Consistent
* Laravel-friendly
* Database-friendly

Avoid abbreviations unless universally understood.

---

# Character Rules

Allowed:

* Lowercase letters
* Numbers
* Underscores (`_`)

Never use:

* Spaces
* Hyphens
* Dots
* Special characters
* Mixed casing

Correct:

```text id="name01"
marketplace_products

theme_tokens

component_examples
```

Incorrect:

```text id="name02"
MarketPlaceProducts

theme-Tokens

ComponentExamples

product data
```

---

# Table Names

Rules:

* snake_case
* plural nouns
* Business terminology

Examples:

```text id="name03"
users

roles

permissions

components

component_versions

themes

theme_tokens

templates

orders

licenses

subscriptions

blog_posts

cms_pages

notifications
```

Avoid:

```text id="name04"
tbl_users

data

records

objects

misc
```

---

# Domain Prefixes

Large domains should use prefixes for clarity.

Examples:

```text id="name05"
theme_tokens

theme_versions

component_examples

component_categories

marketplace_products

marketplace_reviews

billing_invoices

billing_payments
```

This prevents collisions across domains.

---

# Singular vs Plural

| Object              | Convention                             |
| ------------------- | -------------------------------------- |
| Table               | Plural                                 |
| Model               | Singular                               |
| Foreign Key         | Singular                               |
| Relationship Method | Plural (hasMany), Singular (belongsTo) |

Example:

```text id="name06"
Table: users

Model: User

Foreign Key: user_id

Relation: orders()
```

---

# Primary Keys

Standard primary key:

```text id="name07"
id
```

Type:

```text id="name08"
BIGINT UNSIGNED
```

Avoid:

```text id="name09"
userId

userID

userid
```

---

# Foreign Keys

Convention:

```text id="name10"
{table_singular}_id
```

Examples:

```text id="name11"
user_id

theme_id

component_id

order_id

license_id
```

Self-referencing:

```text id="name12"
parent_id
```

---

# Pivot Tables

Convention:

* Alphabetical order
* Singular names

Examples:

```text id="name13"
permission_role

role_user

component_tag

product_category

theme_template
```

Composite primary keys are optional; unique composite indexes are recommended.

---

# Timestamp Columns

Standard:

```text id="name14"
created_at

updated_at

deleted_at
```

Ownership:

```text id="name15"
created_by

updated_by
```

Publication:

```text id="name16"
published_at
```

---

# Boolean Columns

Prefix with verbs.

Examples:

```text id="name17"
is_active

is_public

is_featured

is_verified

has_access

can_download
```

Avoid ambiguous names like:

```text id="name18"
active

public

verified
```

---

# Status Columns

Use:

```text id="name19"
status
```

Examples:

* draft
* published
* archived
* active
* suspended

Prefer application constants or lookup tables for values.

---

# Date Columns

Suffix with `_at` for timestamps.

Examples:

```text id="name20"
expires_at

starts_at

ends_at

processed_at

completed_at
```

For date-only values:

```text id="name21"
birth_date

invoice_date
```

---

# Monetary Columns

Use descriptive names.

Examples:

```text id="name22"
price

subtotal

discount_amount

tax_amount

total_amount

refund_amount
```

Currency:

```text id="name23"
currency
```

Store values as `DECIMAL` or integer minor units.

---

# Slug Columns

Always use:

```text id="name24"
slug
```

Example:

```text id="name25"
button

corporate-theme

admin-dashboard
```

Unique index required where public routing depends on slugs.

---

# JSON Columns

Suffix with `_data` or use descriptive nouns.

Examples:

```text id="name26"
settings

preferences

metadata

theme_data

export_data
```

Avoid generic names such as `json` or `data`.

---

# Enum-like Columns

Prefer descriptive names.

Examples:

```text id="name27"
status

visibility

license_type

subscription_type
```

Do not embed implementation details into column names.

---

# File Columns

Use descriptive names.

Examples:

```text id="name28"
filename

path

mime_type

file_size

checksum
```

Media metadata should complement, not replace, Spatie Media Library records.

---

# Soft Delete Columns

Always:

```text id="name29"
deleted_at
```

Do not create custom soft-delete column names.

---

# Audit Columns

Standard:

```text id="name30"
created_by

updated_by

deleted_by
```

Use foreign keys referencing `users.id` where appropriate.

---

# Index Names

Convention:

```text id="name31"
idx_{table}_{column}
```

Examples:

```text id="name32"
idx_users_email

idx_themes_slug

idx_orders_status
```

Composite:

```text id="name33"
idx_orders_user_status
```

---

# Unique Constraint Names

Convention:

```text id="name34"
uniq_{table}_{column}
```

Examples:

```text id="name35"
uniq_users_email

uniq_themes_slug
```

Composite:

```text id="name36"
uniq_theme_version
```

---

# Foreign Key Names

Convention:

```text id="name37"
fk_{table}_{referenced_table}
```

Examples:

```text id="name38"
fk_orders_users

fk_themes_users

fk_reviews_products
```

---

# Migration Names

Convention:

```text id="name39"
create_users_table

create_theme_tokens_table

add_status_to_orders_table

drop_old_settings_table
```

One concern per migration.

---

# Seeder Names

Convention:

```text id="name40"
RoleSeeder

PermissionSeeder

ThemeSeeder

CategorySeeder
```

Group related seeders into domain-specific seed classes where appropriate.

---

# Model Names

Convention:

* Singular
* PascalCase

Examples:

```text id="name41"
User

Theme

Component

MarketplaceProduct

Subscription

Invoice
```

---

# Repository Names

Convention:

```text id="name42"
UserRepository

ThemeRepository

MarketplaceRepository
```

---

# Service Names

Convention:

```text id="name43"
ThemeService

BillingService

SearchService

DocumentationService
```

---

# Action Names

Convention:

```text id="name44"
CreateThemeAction

PublishComponentAction

PurchaseProductAction

GenerateLicenseAction
```

Use verb-first naming.

---

# Event Names

Convention:

Past tense.

Examples:

```text id="name45"
ThemePublished

ComponentCreated

OrderCompleted

SubscriptionRenewed
```

---

# Job Names

Convention:

Verb-first.

Examples:

```text id="name46"
CompileTheme

GenerateThumbnail

SendReceipt

IndexDocumentation
```

---

# Cache Keys

Convention:

```text id="name47"
gsmui:{domain}:{resource}:{id}
```

Examples:

```text id="name48"
gsmui:theme:15

gsmui:docs:v1

gsmui:user:42:dashboard
```

---

# API Resource Names

Convention:

```text id="name49"
ThemeResource

ComponentResource

OrderResource

LicenseResource
```

---

# API Route Names

Convention:

```text id="name50"
/api/v1/themes

/api/v1/components

/api/v1/orders
```

Use plural nouns and versioned prefixes.

---

# Naming Anti-Patterns

Avoid:

* Abbreviations (`usr`, `cmp`, `cfg`)
* Prefixes like `tbl_`
* Suffixes like `_tbl`
* Generic names (`data`, `info`, `temp`)
* CamelCase in database objects
* Reserved SQL keywords

Prefer explicit, business-focused terminology.

---

# Consistency Checklist

Before adding a new database object, verify:

* Uses snake_case
* Uses business terminology
* Matches Laravel conventions
* Has descriptive names
* Avoids abbreviations
* Includes appropriate indexes
* Includes foreign keys where required

Consistency should take precedence over personal preference.

The GsmUi naming conventions establish a predictable, Laravel-aligned standard across the entire database and application architecture. By adopting consistent patterns for tables, columns, relationships, indexes, migrations, models, and services, the platform becomes easier to maintain, simpler to navigate, and more resilient as it grows.

# Security

Naming conventions support security:

* Avoid reserved SQL keywords in column names
* Use `is_` prefix for boolean flags (clarity)
* Status columns use descriptive values (not codes)
* Foreign keys clearly reference parent tables
* Audit columns (`created_by`, `updated_by`) clearly named
* No cryptic abbreviations that hide sensitive data
* Consistent naming enables automated security scanning
* Table names reflect business purpose (no obfuscation)

# Performance

Naming conventions impact performance:

* Consistent naming enables query builder optimization
* Predictable foreign key names simplify joins
* Domain prefixes prevent table name collisions
* Clear status column names improve query readability
* Boolean `is_` prefix enables efficient filtering
* Slug column naming enables fast URL lookups
* Timestamp naming (`_at` suffix) enables date queries
