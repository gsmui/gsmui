# 05.06 - Folder Structure

**Project:** GsmUi
**Architecture:** Laravel 13 + Livewire 4 + Modular Monolith + Domain-Driven Design (DDD)
**Version:** 1.0.0

---

# Purpose

This document defines the physical directory structure of the GsmUi codebase. The structure reflects business domains rather than technical layers, making the application easier to navigate, test, and evolve.

Goals:

* Domain-oriented organization
* Clear ownership
* Minimal coupling
* Predictable locations
* Easy onboarding
* Future microservice compatibility

# Dependency Rules

Allowed:

```text
Livewire

↓

Action

↓

Service

↓

Repository

↓

Model
```

Forbidden:

```text
Livewire

↓

Model
```

or

```text
Controller

↓

Repository
```

All business logic passes through Actions and Services.

---

# Coding Standards

* PSR-12
* Strict typing (`declare(strict_types=1);`)
* Constructor property promotion
* Readonly properties where appropriate
* Dependency Injection
* SOLID principles
* Small focused classes
* Maximum one responsibility per class

---

# Folder Ownership Rules

Each domain owns:

* Controllers
* Livewire components
* Views
* Models
* Policies
* Events
* Jobs
* Services
* Repositories
* Tests

No domain may modify another domain's internal files directly.

---

# Architecture Benefits

This structure provides:

* Excellent discoverability
* Reduced merge conflicts
* Easier onboarding
* High cohesion
* Low coupling
* Independent testing
* Future package extraction
* Microservice readiness
* Long-term maintainability

# File Naming Conventions

## PHP Classes

```text
PascalCase for class names
One class per file
Filename matches class name

Examples:
    ComponentService.php
    ThemeRepository.php
    CreateComponentAction.php
    ComponentPublished.php
    ValidComponentSlug.php
```

## Blade Views

```text
snake_case for view names
Dot notation for directories
Component-based for reusable parts

Examples:
    components/index.blade.php
    components/show.blade.php
    admin/dashboard.blade.php
    emails/welcome.blade.php
```

## JavaScript Files

```text
camelCase for JavaScript files
kebab-case for Alpine components
PascalCase for Livewire components

Examples:
    app.js
    component-browser.js
    theme-builder.js
```

## CSS Files

```text
kebab-case for CSS files
BEM-like naming for classes

Examples:
    app.css
    component-browser.css
    theme-builder.css
```

## Database Migrations

```text
snake_case with timestamp prefix
Descriptive action verb
Plural table names

Examples:
    2024_01_01_000001_create_components_table.php
    2024_01_01_000002_create_component_versions_table.php
```

# File Organization Best Practices

## Keep Related Files Together

```text
Good:
    Components/
        Actions/
            CreateComponentAction.php
        Services/
            ComponentService.php
        Models/
            Component.php
        Tests/
            Unit/
                ComponentServiceTest.php

Bad:
    Actions/
        CreateComponentAction.php
    Services/
        ComponentService.php
    Models/
        Component.php
    Tests/
        Unit/
            ComponentServiceTest.php
```

## Avoid Deep Nesting

```text
Good:
    Components/Actions/CreateComponentAction.php

Bad:
    Components/Domain/Application/Actions/CreateComponentAction.php
```

## Use Consistent Naming

```text
Good:
    ComponentService
    ComponentRepository
    ComponentController
    ComponentPolicy

Bad:
    ComponentManager
    ComponentRepo
    ComponentHandler
    ComponentGuard
```
