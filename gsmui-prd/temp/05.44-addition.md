# Container Orchestration

GsmUi production infrastructure leverages Docker containers managed by Kubernetes for consistent, scalable deployments.

## Docker Configuration

```text
Dockerfile (multi-stage build)
+-- Stage 1: Build (node:20-alpine)
|   +-- npm ci
|   +-- npm run build
|   +-- Output: /dist
+-- Stage 2: PHP Dependencies (composer:2)
|   +-- composer install --no-dev --optimize-autoloader
|   +-- Output: /vendor
+-- Stage 3: Production (php:8.4-fpm-alpine)
|   +-- Copy /vendor from Stage 2
|   +-- Copy /dist from Stage 1
|   +-- Copy application code
|   +-- Install PHP extensions
|   +-- Configure PHP-FPM
+-- Stage 4: nginx (nginx:alpine)
    +-- Copy nginx config
    +-- Copy static assets from Stage 1
    +-- Configure reverse proxy to php-fpm
```

# Load Balancing Deep Dive

## Algorithm Selection

| Algorithm | Use Case | Implementation |
|-----------|----------|---------------|
| Round Robin | Default, even distribution | nginx upstream |
| Least Connections | Long-lived connections (WebSocket) | nginx upstream least_conn |
| IP Hash | Session affinity (sticky sessions) | nginx upstream ip_hash |
| Weighted Round Robin | Mixed instance sizes | nginx upstream with weight |

## Health Check Configuration

```nginx
    least_conn;
    server php-fpm-1:9000 max_fails=3 fail_timeout=30s;
    server php-fpm-2:9000 max_fails=3 fail_timeout=30s;
    server php-fpm-3:9000 max_fails=3 fail_timeout=30s;

location /internal/health {
    access_log off;

    add_header Content-Type application/json;

```

## Connection Draining

When instances are removed from the load balancer pool, the following sequence executes:

1. Stop sending new connections to the instance
2. Allow existing connections to complete (drain period: 30 seconds)
3. Forcefully close remaining connections after drain period
4. Remove instance from pool
5. Deregister from load balancer

# Backup and Recovery Strategy

## Backup Schedule

| Data Type | Method | Frequency | Retention | Storage |
|-----------|--------|-----------|-----------|---------|
| MySQL database | mysqldump + binlog | Daily full, hourly incremental | 30 days | S3 (cross-region) |
| Redis data | RDB snapshot + AOF | Every 15 minutes | 7 days | S3 |
| User uploads | S3 cross-region replication | Real-time | Permanent | S3 (2 regions) |
| Application code | Git repository | Every commit | Permanent | GitHub |
| Configuration | Git repository | Every change | Permanent | GitHub |
| Logs | Log aggregation (ELK) | Real-time | 90 days | S3 Glacier |

## Recovery Procedures

### Database Recovery

```text
Database Recovery Procedure
    |
    +-- Scenario: Accidental data deletion
    |   +-- Identify deletion timestamp from audit logs
    |   +-- Restore to point-in-time before deletion
    |   +-- Apply binlog events up to deletion point
    |   +-- Verify data integrity
    |   +-- Resume operations
    |
    +-- Scenario: Database corruption
    |   +-- Stop application writes
    |   +-- Take fresh backup of current state
    |   +-- Restore from last known good backup
    |   +-- Apply binlog events up to corruption point
    |   +-- Validate data consistency
    |   +-- Resume operations
    |
    +-- Scenario: Complete database loss
        +-- Provision new RDS instance
        +-- Restore from latest daily backup
        +-- Apply all binlog events since last backup
        +-- Update application connection strings
        +-- Verify connectivity and data integrity
        +-- Resume operations
```

### RTO/RPO Targets

| Scenario | RTO | RPO |
|----------|-----|-----|
| Database primary failure | 5 minutes (auto-failover) | 0 (synchronous replication) |
| Database corruption | 30 minutes | 1 hour (binlog recovery) |
| Complete region failure | 1 hour | 5 minutes (cross-region replication) |
| Accidental data deletion | 30 minutes | 0 (point-in-time recovery) |
| Application failure | 2 minutes (auto-scaling) | N/A (stateless) |

## Alert Rules

```yaml
groups:
  - name: gsmui-critical
    rules:
      - alert: HighErrorRate
        expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "High error rate detected"

      - alert: HighLatency
        expr: histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m])) > 1
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High latency detected"

      - alert: DatabaseReplicationLag
        expr: mysql_slave_status_seconds_behind_master > 10
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Database replication lag"

      - alert: RedisMemoryHigh
        expr: redis_memory_used_bytes / redis_memory_max_bytes > 0.85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Redis memory usage high"

      - alert: DiskSpaceLow
        expr: (node_filesystem_avail_bytes / node_filesystem_size_bytes) < 0.15
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Disk space low"
```

## Cache Invalidation Strategy

```text
Cache Invalidation Flow
    |
    +-- Content update occurs
    |   +-- Asset filenames change (Vite hashing)
    |   |   +-- New URL = new cache entry (no invalidation needed)
    |   |
    |   +-- HTML pages change
    |   |   +-- Purge via CloudFlare API
    |   |   +-- Purge CDN cache for specific URLs
    |   |
    |   +-- API responses change
    |       +-- No CDN cache to invalidate (API not cached)
    |
    +-- Cache purge propagation
        +-- CloudFlare: < 30 seconds global
        +-- CloudFront: < 5 minutes global
        +-- Fallback: TTL expiry (60 seconds for HTML)
```
