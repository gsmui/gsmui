# 10.02 — RBAC Architecture

**Project:** GsmUi
**Domain:** Authorization & RBAC
**Version:** 1.0.0

---

## Purpose

This document defines the detailed technical architecture of the RBAC system in GsmUi. It specifies how roles, permissions, policies, and gates compose into the authorization layer, how they are resolved at runtime, how they are cached, and how they integrate with Laravel, Fortify, Sanctum, and Spatie Permission.

See [10.01-overview.md](./10.01-overview.md) for the high-level authorization overview and [10.03-roles.md](./10.03-roles.md) for the complete role definitions.

## Core Concepts

### Role

A named set of permissions that can be assigned to users. Roles represent organizational functions (admin, creator, moderator) rather than individual capabilities. Each role has a unique name, an optional guard name, and a set of directly assigned permissions.

```php
// Role structure (Spatie Permission)
class Role extends Model
{
    protected $fillable = ['name', 'guard_name', 'level'];

    // A role has many permissions
    public function permissions(): BelongsToMany;
    
    // A role can inherit from parent roles
    public function parents(): BelongsToMany;
    
    // A role can have child roles
    public function children(): BelongsToMany;
}
```

### Permission

A named action on a resource. Permissions follow the `resource.action` naming convention. Permissions are scoped to a guard (web, api) and can be assigned directly to users or indirectly through roles.

```php
// Permission structure (Spatie Permission)
class Permission extends Model
{
    protected $fillable = ['name', 'guard_name'];

    // A permission belongs to many roles
    public function roles(): BelongsToMany;
    
    // A permission can be assigned directly to users
    public function users(): MorphToMany;
}
```

### Policy

A class that authorizes CRUD operations on a specific model. Policies combine permission checks with ownership verification and business constraints. See [10.05-policies.md](./10.05-policies.md) for the complete policy specification.

```php
class ThemePolicy
{
    public function viewAny(User $user): bool;
    public function view(User $user, Theme $theme): bool;
    public function create(User $user): bool;
    public function update(User $user, Theme $theme): bool;
    public function delete(User $user, Theme $theme): bool;
    public function publish(User $user, Theme $theme): bool;
    public function feature(User $user, Theme $theme): bool;
}
```

### Gate

A closure that checks a permission for ad-hoc authorization. Gates are used for operations that don't map to a specific model, such as `admin.access` or `system.health`. See [10.06-gates.md](./10.06-gates.md) for the complete gate specification.

```php
// Define a gate
Gate::define('admin.access', function (User $user) {
    return $user->hasRole('admin');
});

// Use in controller or Livewire
$this->authorize('admin.access');
```

### Guard

The authentication guard that scopes roles and permissions. GsmUi uses two guards:

| Guard | Purpose | Driver |
|---|---|---|
| `web` | Web application sessions | session |
| `api` | API token authentication | sanctum |

Roles and permissions are scoped to their guard. A `web` permission does not automatically apply to `api` tokens. This ensures API consumers have explicitly granted capabilities.

```php
// config/permission.php
'defaults' => [
    'guard' => 'web',
    'permission' => null,
    'role' => null,
],

'guards' => [
    'web' => [
        'driver' => 'session',
        'provider' => 'users',
    ],
    'api' => [
        'driver' => 'sanctum',
        'provider' => 'users',
    ],
],
```

## Resolution Order

When checking if a user has a specific permission, the system resolves in this order:

```text
1. Direct permission assignment
   model_has_permissions where model_id = $user->id
   ↓ (if not found)
2. Role-based permissions
   model_has_roles → role_permissions where role_id = $role->id
   ↓ (if not found)
3. Team role permissions (when teams enabled)
   team_roles → team_role_permissions where team_id = $teamId
   ↓ (if not found)
4. Parent role permissions (role hierarchy)
   role_has_roles → role_permissions for parent roles
   ↓ (if not found)
5. Deny (default when no matching permission found)
```

### Resolution Implementation

```php
// Simplified resolution logic
public function hasPermissionTo(string $permissionName, string $guardName = null): bool
{
    $guardName = $guardName ?? $this->getDefaultGuardName();

    // 1. Check direct permissions
    if ($this->permissions->contains('name', $permissionName)) {
        return true;
    }

    // 2. Check role-based permissions
    foreach ($this->roles as $role) {
        if ($role->permissions->contains('name', $permissionName)) {
            return true;
        }
        
        // 3. Check parent role permissions (hierarchy)
        if ($this->checkParentRolePermissions($role, $permissionName)) {
            return true;
        }
    }

    return false;
}
```

## Caching Strategy

Spatie Permission caches roles and permissions in the application's cache store. This is critical for performance — authorization checks happen on every request.

### Cache Architecture

```text
User → hasPermissionTo('themes.publish')
    ↓
Check in-memory collection (already loaded)
    ↓ (if not cached)
Check Redis cache (Permission::cacheKey($user))
    ↓ (if not in cache)
Query database (model_has_roles → role_permissions)
    ↓
Store in Redis (TTL: configurable)
    ↓
Store in-memory for rest of request
```

### Cache Configuration

```php
// config/permission.php
'cache' => [
    'store' => env('CACHE_DRIVER', 'redis'),
    'prefix' => 'spatie_permission_cache',
    'ttl' => 3600, // 1 hour default
],
```

### Cache Clearing

Cache must be cleared whenever permissions or role assignments change:

```php
// After assigning a role
$user->assignRole('creator');
Permission::forgetCache(); // Clear all cached permissions

// After revoking a permission
$role->revokePermissionTo('themes.publish');
Permission::forgetCache();

// After creating a new permission
Permission::create(['name' => 'themes.feature', 'guard_name' => 'web']);
Permission::forgetCache();
```

### Cache Events

```php
// Dispatched when cache is cleared
event(new PermissionCacheCleared($user));
event(new PermissionCacheCleared($role));

// Listen for cache invalidation
Event::listen(PermissionCacheCleared::class, function ($event) {
    Log::info("Permission cache cleared for: " . get_class($event->model));
});
```

```php

class SetTeamContext
{
    public function handle(Request $request, Closure $next): Response
    {
        $teamId = $request->user()?->current_team_id;
```

```php
// Assign role to user within a team
```

## Middleware

### RoleMiddleware

```php
// app/Http/Middleware/RoleMiddleware.php
class RoleMiddleware
{
    public function handle(Request $request, Closure $next, string ...$roles): Response
    {
        if (! $request->user() || ! $request->user()->hasAnyRole($roles)) {
            abort(403, 'Unauthorized. Required role: ' . implode(', ', $roles));
        }

        return $next($request);
    }
}
```

### PermissionMiddleware

```php
// app/Http/Middleware/PermissionMiddleware.php
class PermissionMiddleware
{
    public function handle(Request $request, Closure $next, string ...$permissions): Response
    {
        if (! $request->user() || ! $request->user()->hasAnyPermission($permissions)) {
            abort(403, 'Unauthorized. Required permission: ' . implode(', ', $permissions));
        }

        return $next($request);
    }
}
```

## Security Considerations

1. **Never trust client-side authorization.** Always verify permissions server-side.
2. **Cache invalidation is critical.** Stale permissions can grant unauthorized access.
3. **Team scoping must be set early.** Set team context in middleware, before any permission check.
4. **API tokens must be scoped.** Never create tokens with full permissions.
5. **Audit all permission changes.** Log who changed what and when.
6. **Rate limit authorization endpoints.** Prevent brute-force permission enumeration.
7. **Test authorization in CI.** Every policy method must have a test.

## Advanced RBAC Concepts

### Permission Scoping

Permissions can be scoped to specific contexts beyond just guard names. GsmUi uses several scoping mechanisms:

#### Context-Based Scoping

A permission may be valid only in certain contexts. For example, `themes.create` might be allowed in the creator dashboard but not in the admin panel.

```php
// Check permission within a specific context
$user->hasPermissionTo('themes.create', 'web');
$user->hasPermissionTo('themes.create', 'api');
```

#### Temporal Scoping

Permissions can have time-based constraints. For example, a trial user might have temporary access to premium features.

```php
// Check if a permission is currently active
if ($user->hasPermissionTo('ai.generate') && $user->trial_ends_at->isFuture()) {
    // Allow AI generation during trial
}
```

#### Resource-Scoped Permissions

Some permissions apply only to specific resources. For example, `themes.update` applies only to themes the user owns.

```php
// Policy enforces resource scoping
public function update(User $user, Theme $theme): bool
{
    return $user->id === $theme->user_id;
}
```

### Role Composition Patterns

#### Flat Roles

The simplest pattern. Each role has a fixed set of permissions with no hierarchy.

```text
Role A: [perm1, perm2]
Role B: [perm3, perm4]
User with Role A + Role B: [perm1, perm2, perm3, perm4]
```

Use when: Roles are independent and don't share common permission sets.

#### Hierarchical Roles

Roles inherit permissions from parent roles. This reduces duplication and simplifies management.

```text
Admin (level 7)
  └── Editor (level 6)
        └── Support (level 5)
              └── Moderator (level 4)
                    └── Creator (level 3)
                          └── Pro User (level 2)
                                └── User (level 1)
```

Use when: There's a natural progression of privileges and higher roles should include all lower role permissions.

#### Composable Roles

Users can hold multiple independent roles simultaneously. The effective permissions are the union of all role permissions.

```text
User with [creator, moderator]:
  Creator permissions: [themes.create, themes.update]
  Moderator permissions: [themes.feature, components.feature]
  Effective: [themes.create, themes.update, themes.feature, components.feature]
```

Use when: Users can have multiple responsibilities that don't fit a single hierarchy.

### Permission Resolution Algorithm

When resolving whether a user has a specific permission, the system follows this algorithm:

```php
public function resolvePermission(User $user, string $permission, ?string $guard = null): bool
{
    $guard = $guard ?? $this->getDefaultGuardName();

    // Step 1: Check direct permissions (highest priority)
    $directPermissions = $user->getDirectPermissions();
    if ($directPermissions->contains('name', $permission)) {
        return true;
    }

    // Step 2: Check role-based permissions
    $roles = $user->getRoles();
    foreach ($roles as $role) {
        // Check role's own permissions
        if ($role->permissions->contains('name', $permission)) {
            return true;
        }

        // Step 3: Check parent role permissions (hierarchy)
        $ancestors = $role->ancestors();
        foreach ($ancestors as $ancestor) {
            if ($ancestor->permissions->contains('name', $permission)) {
                return true;
            }
        }
    }

    // Step 4: Default deny
    return false;
}
```

### Permission Caching Deep Dive

#### Cache Structure

The permission cache stores resolved permission sets per user:

```text
Key: gsmui_permission:{guard}:{user_id}
Value: {
    permissions: ['themes.create', 'themes.update', ...],
    roles: ['creator', 'pro_user'],
    last_changed: '2025-01-15T10:30:00Z'
}
TTL: 3600 seconds (1 hour)
```

#### Cache Invalidation Strategy

```php
// Event-driven cache invalidation
class ClearPermissionCache
{
    public function handle($event): void
    {
        $user = $event->user ?? $event->model;
        
        if ($user instanceof User) {
            // Clear user-specific cache
            Cache::forget("gsmui_permission:web:{$user->id}");
            Cache::forget("gsmui_permission:api:{$user->id}");
        }
        
        // Clear global role/permission cache
        Permission::forgetCache();
    }
}
```

#### Cache Warm-Up

On application boot, the permission system warms the cache for active users:

```php
// In PermissionServiceProvider
public function boot(): void
{
    $this->app->booted(function () {
        // Warm cache for currently authenticated user
        if ($user = auth()->user()) {
            $user->load('roles', 'permissions');
        }
    });
}
```

```text
User holds: [creator]

3. Check team-specific role permissions (team_member)
4. Union of all: global + team-specific
```

### Performance Considerations

#### Permission Check Optimization

```php
// Efficient: Check once, cache result
if ($user->can('themes.create')) {
    // User can create themes
}

// Inefficient: Multiple checks
if ($user->can('themes.create') && $user->can('themes.update') && $user->can('themes.delete')) {
    // Better to check a combined permission or use hasAnyPermission
}

// Optimized: Batch check
if ($user->hasAnyPermission(['themes.create', 'themes.update', 'themes.delete'])) {
    // User has at least one of these permissions
}
```

#### Database Query Optimization

```sql
-- Optimized permission resolution query
SELECT DISTINCT p.name
FROM permissions p
INNER JOIN role_has_permissions rhp ON p.id = rhp.permission_id
INNER JOIN model_has_roles mhr ON rhp.role_id = mhr.role_id
WHERE mhr.model_id = ?
  AND mhr.model_type = ?
  AND p.guard_name = ?

UNION

SELECT DISTINCT p.name
FROM permissions p
INNER JOIN model_has_permissions mhp ON p.id = mhp.permission_id
WHERE mhp.model_id = ?
  AND mhp.model_type = ?
  AND p.guard_name = ?;
```

### Migration from Legacy Systems

#### Step 1: Audit Existing Authorization

```php
// Audit script to find all authorization checks
$patterns = [
    '->isAdmin()',
    '->isModerator()',
    'auth()->user()->role',
    'Gate::allows(',
    'Gate::denies(',
    '@can(',
    '@cannot(',
```

```php
class RestorePermissions extends Command

        $backupPath = $this->argument('backup');
        $data = json_decode(file_get_contents($backupPath), true);

        DB::transaction(function () use ($data) {

            Permission::unguard();
            Role::unguard();

            foreach ($data['permissions'] as $permission) {
                Permission::updateOrCreate(
                    ['name' => $permission['name'], 'guard_name' => $permission['guard_name']],
                    $permission
                );
            }

            foreach ($data['roles'] as $role) {
                Role::updateOrCreate(
                    ['name' => $role['name'], 'guard_name' => $role['guard_name']],
                    $role

            DB::table('model_has_roles')->truncate();
            DB::table('model_has_permissions')->truncate();

                DB::table('model_has_roles')->insert($mr);
            }

            foreach ($data['model_has_permissions'] as $mp) {
                DB::table('model_has_permissions')->insert($mp);
            }
```

```php
                if ($ancestor->permissions->contains('name', $permission)) {

                }
            }

                'user_id' => $user->id,
```

## Permission Resolution Algorithm

### Multi-Layer Resolution Pipeline

When a permission check is invoked via `$user->can('permission.name')` or `$user->hasPermissionTo('permission.name')`, the system runs through a multi-layer resolution pipeline. Understanding this pipeline is critical for debugging authorization failures and for architecting custom gates.

```
Gate::before() (Super Admin bypass)
    → Role-based resolution (Spatie roles)
        → Direct permission resolution (Spatie permissions)
            → Team-scoped resolution (if team context active)
                → Custom gate definitions (AppServiceProvider)
                    → Gate::after() (final fallback)
```

#### Layer 1: Super Admin Bypass

The `Gate::before()` callback intercepts every authorization check before Laravel reaches the route middleware or gate definitions. For users holding the `super_admin` role, this callback returns `true` immediately, bypassing all subsequent layers.

```php
// app/Providers/AuthServiceProvider.php

public function boot(): void
{
    Gate::before(function (User $user, string $ability) {
        if ($user->hasRole('super_admin')) {
            return true;
        }

        return null; // fall through to next layer
    });
}
```

**Important behavioral notes:**

- Returning `true` from `Gate::before()` grants the ability unconditionally — no further gates or policies are evaluated.
- Returning `null` (not `false`) signals "I don't know, keep checking." Returning `false` explicitly denies the ability and skips all remaining layers.
- The bypass only fires when the Gate system is invoked — direct Spatie API calls (`$user->hasPermissionTo()`) do not trigger `Gate::before()`.

#### Layer 2: Role-Based Resolution

Spatie checks whether the user holds a role that carries the requested permission. This is the primary resolution mechanism for most applications.

```php
// Spatie internally does:
// $user->roles->flatMap->permissions->contains('name', $ability)
```

Role-based resolution respects:

- **Permission groups** — a permission like `themes.publish` may be granted via the `themes` group.
- **Role hierarchy** — if `admin` inherits from `moderator`, all `moderator` permissions flow to `admin`.
- **Team scope** — if a team context is active, only roles assigned within that team are considered.

#### Layer 3: Direct Permission Resolution

If the user has no role carrying the permission, Spatie checks for direct permissions assigned to the user (bypassing roles entirely).

```php
// Direct permission assignment
$user->givePermissionTo('special.api.access');
$user->hasPermissionTo('special.api.access'); // true
```

Direct permissions are rare in practice but useful for one-off grants that don't warrant a role.

#### Layer 4: Team-Scoped Resolution

When a team context is active, resolution narrows to permissions available within that team. A user may hold the `editor` role globally but only the `viewer` role within a specific team.

```php
// Set team context
app(TeamContext::class)->setTeam($team);

// Now permission checks are team-scoped
$user->hasPermissionTo('posts.edit'); // checks team-scoped roles only
```

#### Layer 5: Custom Gate Definitions

If none of the above layers resolved the ability, Laravel falls through to explicit `Gate::define()` callbacks registered in `AppServiceProvider`.

```php
Gate::define('posts.edit', function (User $user, Post $post) {
    return $user->id === $post->author_id;
});
```

#### Layer 6: Gate::after() Fallback

The final layer. `Gate::after()` callbacks run after all other resolution has failed. Typically used for audit logging or emergency overrides.

```php
Gate::after(function (User $user, string $ability, $result) {
    if ($result === false) {
        ActivityLog::denied($user, $ability);
    }
});
```

### Resolution Timing and Caching

Permission resolution runs on every `$user->can()` call. The resolution itself involves database queries (loading roles and permissions), which are cached by Spatie's `PermissionRegistrar`.

```php
// Cache configuration (config/permission.php)
'cache' => [
    'enabled' => true,
    'store' => env('CACHE_DRIVER', 'file'),
    'prefix' => 'spatie.permission.cache',
    'ttl' => 600, // 10 minutes
],
```

**Cache invalidation triggers:**

1. `$user->assignRole()` — clears user-specific cache
2. `$user->removeRole()` — clears user-specific cache
3. `$user->givePermissionTo()` — clears user-specific cache
4. `$role->syncPermissions()` — clears all role-based cache
5. `Cache::tags(['permissions'])->flush()` — nuclear option

```php
// Manual cache clearing after bulk operations
public function syncRolePermissions(Role $role, array $permissions): void
{
    $role->syncPermissions($permissions);

    // Force cache clear for all users with this role
    $affectedUsers = User::role($role->name)->get();
    foreach ($affectedUsers as $user) {
        $user->forgetCachedPermissions();
    }
}
```

### Middleware Resolution Flow

Route middleware intercepts requests before the controller executes. The `role` and `permission` middleware use the same resolution pipeline described above.

```php

// Middleware execution order
```

**Middleware failure behavior:**

- `role` middleware: redirects to `/unauthorized` (configurable) if the user lacks the role.
- `permission` middleware: same behavior.
- Both middleware respect `Gate::before()` — super admins pass through without role checks.

```php
        if ($request->expectsJson()) {
            return response()->json(['error' => 'Unauthorized'], 403);
        }
        return redirect()->route('unauthorized');
    }

    return $next($request);
}
```

### Policy Resolution Integration

Policies provide model-level authorization (e.g., "can this user edit this specific post?"). Policies integrate with the RBAC system through a layered approach:

```php
// app/Policies/PostPolicy.php
class PostPolicy
{
    public function update(User $user, Post $post): bool
    {
        // Layer 1: Super admin bypass (handled by Gate::before)
        // Layer 2: Role-based check
        if ($user->hasPermissionTo('posts.edit')) {
            return true;
        }

        // Layer 3: Ownership check (fallback)
        return $user->id === $post->author_id;
    }
}
```

**Policy method naming convention:**

| Policy Method | HTTP Method | Route Pattern |
|---|---|---|
| `viewAny` | GET | `/posts` |
| `view` | GET | `/posts/{post}` |
| `create` | POST | `/posts` |
| `update` | PUT/PATCH | `/posts/{post}` |
| `delete` | DELETE | `/posts/{post}` |
| `restore` | POST | `/posts/{post}/restore` |
| `forceDelete` | DELETE | `/posts/{post}/force-delete` |

```php
// Using policies in controllers
class PostController extends Controller
{
    public function update(UpdatePostRequest $request, Post $post)
    {
        $this->authorize('update', $post); // invokes PostPolicy::update

        // Authorization passed — proceed
        $post->update($request->validated());
    }
}
```

### Error Handling and Debugging

#### Common Authorization Failures

| Symptom | Likely Cause | Resolution |
|---|---|---|
| User returns `false` for known permission | Stale permission cache | Call `$user->forgetCachedPermissions()` |
| Role middleware blocks super admin | `Gate::before()` not registered | Verify `AuthServiceProvider::boot()` |
| Team-scoped check returns wrong result | No team context set | Call `app(TeamContext::class)->setTeam()` |
| Policy method not found | Method name mismatch | Verify policy method matches HTTP verb |
| Permission denied after role sync | Cache not invalidated | Run `Cache::tags(['permissions'])->flush()` |

#### Testing Permission Resolution

```php
// tests/PermissionResolutionTest.php
class PermissionResolutionTest extends TestCase
{
    public function test_resolution_pipeline_order(): void
    {
        $user = User::factory()->create();
        $user->assignRole('editor');

        // Layer 2: role-based resolution
        $this->assertTrue($user->hasPermissionTo('posts.edit'));

        // Layer 3: direct permission
        $user->givePermissionTo('special.feature');
        $this->assertTrue($user->hasPermissionTo('special.feature'));

        // Layer 5: custom gate
        Gate::define('custom.gate', fn () => true);
        $this->assertTrue($user->can('custom.gate'));
    }

    public function test_super_admin_bypasses_all_layers(): void
    {
        $admin = User::factory()->create();
        $admin->assignRole('super_admin');

        // Should return true for any ability
        $this->assertTrue($admin->can('anything.at.all'));
        $this->assertTrue($admin->can('nonexistent.permission'));
    }

    public function test_deny_overrides_bypass(): void
    {
        $user = User::factory()->create();
        $user->assignRole('super_admin');

        Gate::before(fn () => false); // explicit deny

        // Gate::before returning false denies even super admins
        $this->assertFalse($user->can('posts.edit'));
    }
}
```

### Performance Considerations

#### Query Optimization

The default Spatie setup issues two queries per permission check (one for roles, one for permissions). Optimize with eager loading:

```php
// In User model
public function loadPermissions(): static
{
    return $this->load(['roles.permissions', 'directPermissions']);
}

// In middleware or controller
$user = $request->user()->loadPermissions();
$user->hasPermissionTo('posts.edit'); // uses loaded relationships, no extra queries
```

Monitor cache hit rates in production:

```php
// In AppServiceProvider
if (app()->isProduction()) {

        // Monitor cache performance
```

Target: >95% cache hit rate after warm-up. If hit rate is lower, investigate:
- Excessive `forgetCachedPermissions()` calls
- Frequent role/permission sync operations
- Cache store eviction under memory pressure

#### Horizontal Scaling

In multi-server deployments, permission cache is per-server (file/redis driver). Use Redis with a shared prefix:

```php
// config/permission.php
'cache' => [
    'store' => 'redis',
    'prefix' => 'production:spatie.permission.cache',
    'ttl' => 600,
],
```

Ensure Redis is shared across all application servers so cache invalidation propagates.

### Migration Considerations

#### Version Upgrade Path

When upgrading Spatie Permission between major versions:

1. **Back up the database** — especially `roles`, `permissions`, `role_has_permissions`, `model_has_roles`, `model_has_permissions` tables.
2. **Run published migrations** — `php artisan vendor:publish --provider="Spatie\Permission\PermissionServiceProvider" --tag="migrations"`
3. **Check model changes** — review `HasRoles` and `HasPermissions` traits for breaking changes.
4. **Clear all caches** — `php artisan cache:clear && php artisan permission:cache-reset`
5. **Run test suite** — verify all permission checks still pass.

```bash
# Pre-upgrade checklist
php artisan permission:cache-reset
php artisan migrate --pretend # review SQL before running
php artisan test --filter=Permission
```

### Security Hardening Checklist

- [ ] `Gate::before()` returns `null` (not `false`) for non-super-admins to allow fallthrough
- [ ] Role assignments require `roles.assign` permission (not just `auth`)
- [ ] Permission sync operations are wrapped in database transactions
- [ ] Cache is invalidated after every role/permission change
- [ ] Audit logging captures all role and permission changes
- [ ] Self-role-escalation is blocked (users cannot assign roles they don't hold)
- [ ] API tokens are scoped to specific permissions via Laravel Sanctum
- [ ] Rate limiting is applied to auth-adjacent endpoints
- [ ] Session lifetime is configured appropriately per role
- [ ] Failed authorization attempts are logged and monitored
- [ ] Permission cache prefix is unique per environment (dev/staging/prod)
- [ ] Model factory defaults don't grant elevated permissions
