# 08.08 - Livewire Architecture

**Project:** GsmUi
**Section:** 08 - Frontend Architecture
**Framework:** Livewire 4 · Laravel 13 · Blade Components · GsmUi Component Library
**Version:** 1.0.0

---

> See also: `07.19-livewire-architecture.md` (backend Livewire wiring), `08.07-blade-component-system.md` (component contract), `08.10-javascript-architecture.md` (JS behavior). This document specifies the *frontend Livewire integration and lifecycle usage* and does NOT re-document server-side component wiring.

# Purpose

This document defines how GsmUi consumes Livewire 4 on the frontend: the request lifecycle as seen by components, `wire:model` binding to `gsmui:` inputs, inline/Volt usage, persistence and hydration expectations, and performance rules. It is the contract that keeps `gsmui:` components wire-bound and hydration-safe.

---

## 1. Lifecycle (Frontend View)

```text
User event ──▶ wire:model / wire:click ──▶ Livewire request (fetch, CSP-safe)
      │                                              │
      ▼                                              ▼
 GsmUi JS (Controllable mixin) ◀── hydration diff ── Component re-render
      │
      ▼
 setAttribute/removeAttribute utils ──▶ MutationObserver on value ──▶ UI sync
```

| Phase | Frontend responsibility |
| --- | --- |
| Render | `gsmui:` components emit wire-ready markup (e.g. `role="combobox"` on input) |
| Interact | GsmUi JS captures input; debounced `wire:model` dispatch |
| Hydrate | Apply server diff without resetting focus/cursor (Controllable `detangle()`) |
| Commit | Fire `input` + `change` on keyboard commit (see `08.10-javascript-architecture.md`) |

---

## 2. `wire:model` Binding Contract

`gsmui:` inputs are the wire-bound primitives. Binding order and behavior:

| Input | Binding | Notes |
| --- | --- | --- |
| `gsmui:input` | `wire:model="field"` | Standard text binding |
| `gsmui:select` | `wire:model="field"` | Single/multiple; `searchable` variant |
| `gsmui:slider` | `wire:model="field"` | Numeric; fires `input`+`change` |
| `gsmui:date-picker` | `wire:model="field"` | ISO value via trigger/popover |
| `gsmui:color-picker` | `wire:model="field"` | Hex/rgb via `format` prop |

The docs portal shows `wire:model="color"` in code blocks (clean copy target) while previews use `value="#0ea5e9"` for visual context.

---

## 3. Inline / Volt Usage

- **Anonymous Blade components** (`gsmui:*`) are pure presentational; behavior lives in `dist/` JS, not in Blade.
- **Volt** may wrap a `gsmui:` component when a page needs a full Livewire class, but the component itself stays framework-agnostic.
- **Forbidden:** Driving GsmUi component state from Alpine `x-data` (see `08.09-alpinejs-architecture.md`).

---

## 4. Persistence & Hydration

| Concern | Rule |
| --- | --- |
| State | Server is source of truth; GsmUi JS holds ephemeral UI state only |
| Sync loops | Use `detangle()` to prevent Controllable ↔ internal-state feedback |
| Focus retention | Hydration must not move focus or caret in text inputs |
| Theme | Theme switch is hydration-safe — no reload (see `08.04-theme-architecture.md`) |

---

## 5. Performance Rules

- Debounce high-frequency inputs (`gsmui:slider`, `gsmui:select searchable`).
- Avoid full-page Livewire on docs/playground where static Blade suffices (use Laravel Folio per `08.01-overview.md`).
- Lock body scroll when a `gsmui:` popover/modal is open (date-picker pattern) to avoid layout thrash.
- Never ship CDN/SPA router; keep server-rendered + targeted Livewire islands.

## 6. Livewire 4 Lifecycle Deep Dive

Livewire 4 introduces significant improvements that GsmUi leverages for a smoother frontend experience. This section details every phase of the lifecycle as it pertains to `gsmui:` components.

### 6.1 Initial Page Load Lifecycle

```text
1. HTML arrives (server-rendered)
2. Theme bootstrap script runs (inline, pre-paint)
3. CSS loads (Tailwind + GsmUi styles)
4. GsmUi JS bundle loads (component behavior mixins)
5. Livewire JS initializes
6. Livewire finds all wire: directives in DOM
7. Livewire hydrates each component (server state → client state)
8. MutationObserver on value attributes activates
9. Components are interactive
```

Each phase has specific timing requirements:

| Phase | Timing Budget | Failure Behavior |
| --- | --- | --- |
| HTML parse | < 100ms | N/A (server-rendered) |
| Theme bootstrap | < 5ms | FOUC with default theme |
| CSS load | < 200ms | FOUT (flash of unstyled text) |
| GsmUi JS init | < 50ms | Components non-interactive |
| Livewire hydration | < 500ms | Components non-interactive |
| Full interactive | < 1.0s | Page usable |

### 6.2 Hydration Process

When Livewire hydrates a `gsmui:` component, the following sequence occurs:

```text
Server Component State
       │
       ▼
Serialization (JSON)
       │
       ▼
Transport (fetch POST to /livewire/update)
       │
       ▼
Client Deserialization
       │
       ▼
Diff Algorithm (morph DOM)
       │
       ▼
MutationObserver triggers
       │
       ▼
GsmUi JS syncs UI state
```

The diff algorithm is critical for `gsmui:` components because it preserves DOM nodes when possible, which means:
- Focus is retained on text inputs
- Cursor position is not reset
- Open/close state of popovers is preserved
- Animation state is not interrupted

### 6.3 Hydration Mapping

| Component | Hydrated Properties | DOM Impact |
| --- | --- | --- |
| `gsmui:input` | `value`, `disabled`, `invalid` | Updates input value, aria attributes |
| `gsmui:select` | `value`, `options`, `disabled` | Updates selected display, option list |
| `gsmui:slider` | `value`, `min`, `max`, `step` | Updates thumb position, aria-valuenow |
| `gsmui:date-picker` | `value`, `format`, `disabled` | Updates trigger display, calendar state |
| `gsmui:color-picker` | `value`, `format`, `swatches` | Updates color preview, hue position |
| `gsmui:toggle` | `value`, `disabled` | Updates checked state, aria-checked |
| `gsmui:modal` | `open` | Shows/hides dialog, manages focus trap |
| `gsmui:table` | `rows`, `columns`, `sort`, `page` | Updates table body, pagination |

### 6.4 Server round-trip optimization

GsmUi minimizes server round-trips through several strategies:

| Strategy | Implementation | Components |
| --- | --- | --- |
| Debouncing | 150ms default delay | `gsmui:input`, `gsmui:select searchable` |
| Throttling | 300ms minimum interval | `gsmui:slider` |
| Lazy validation | Validate on blur, not on keystroke | All form inputs |
| Optimistic updates | UI updates immediately, server confirms | `gsmui:toggle`, `gsmui:checkbox` |
| Prefetching | Load data before interaction | `gsmui:select` with remote options |

## 7. `wire:model` Binding Deep Dive

This section provides the complete specification for how each `gsmui:` component binds to Livewire via `wire:model`.

### 7.1 Binding Modes

| Mode | Syntax | Behavior | Use Case |
| --- | --- | --- | --- |
| Lazy | `wire:model="field"` | Syncs on change (blur/enter) | Text inputs, textareas |
| Eager | `wire:model.live="field"` | Syncs on every input event | Search inputs, sliders |
| Deferred | `wire:model.defer="field"` | Syncs on next Livewire request | Non-critical updates |

### 7.2 Component Binding Matrix

| Component | Recommended Binding | Rationale |
| --- | --- | --- |
| `gsmui:input` | `wire:model="field"` | Lazy by default; avoid excessive updates |
| `gsmui:input` (search) | `wire:model.live="field"` | Real-time search requires live updates |
| `gsmui:textarea` | `wire:model="field"` | Lazy by default; expensive server processing |
| `gsmui:select` | `wire:model="field"` | Syncs on selection change |
| `gsmui:date-picker` | `wire:model="field"` | Syncs on date selection |
| `gsmui:time-picker` | `wire:model="field"` | Syncs on time selection |
| `gsmui:color-picker` | `wire:model.live="field"` | Live preview requires continuous sync |
| `gsmui:slider` | `wire:model.live="field"` | Real-time value display |
| `gsmui:range` | `wire:model.live="field"` | Dual-thumb real-time sync |
| `gsmui:toggle` | `wire:model="field"` | Syncs on toggle click |
| `gsmui:checkbox` | `wire:model="field"` | Syncs on check/uncheck |
| `gsmui:radio` | `wire:model="field"` | Syncs on selection |

### 7.3 Custom Debounce Configuration

Components accept a `wire:debounce` modifier for custom timing:

```blade
<gsmui:input wire:model.debounce.300ms="search" placeholder="Search..." />
<gsmui:slider wire:model.throttle.100ms="volume" />
<gsmui:color-picker wire:model.live.50ms="themeColor" />
```

### 7.4 Binding to Nested Properties

Livewire supports dot-notation for nested properties:

```blade
<gsmui:input wire:model="user.name" />
<gsmui:input wire:model="user.email" />
<gsmui:select wire:model="user.role" :options="$roles" />
<gsmui:toggle wire:model="user.settings.notifications" />
```

### 7.5 Binding to Array Properties

Multiple selection components bind to array properties:

```blade
@gsmui:select wire:model="selectedTags" :options="$tags" multiple />
@gsmui:checkbox-group wire:model="permissions" :options="$allPermissions" />
```

### 7.6 Two-Way Binding Contract

| Direction | Mechanism | Timing |
| --- | --- | --- |
| Client → Server | `wire:model` sync | On change (lazy) or input (live) |
| Server → Client | Hydration diff | On server response |
| Server → Client (initial) | HTML render | On page load |

The server is always the source of truth. If a `wire:model` value conflicts with the client-side state, the server value wins after hydration.

## 8. Livewire Events & Dispatching

### 8.1 Component Event Dispatching

`gsmui:` components dispatch Livewire events for cross-component communication:

```blade
{{-- Component dispatches event --}}
x-on:change="$dispatch('gsmui:status-changed', { value: $event.detail })"

{{-- Parent Livewire component listens --}}
<div wire:status-changed="handleStatusChange($event.detail)">
```

### 8.2 Livewire-Native Events

| Event Type | Syntax | Use Case |
| --- | --- | --- |
| Browser event | `wire:click="method"` | Button click handler |
| Self dispatch | `wire:dispatch="event"` | Trigger event on self |
| Up dispatch | `wire:dispatch-up="event"` | Trigger event on parent |
| Named dispatch | `wire:dispatch named="{ data }"` | Custom event with payload |

### 8.3 Event Payload Patterns

```blade
{{-- Button dispatches with payload --}}
<gsmui:button wire:click="deleteItem({{ $item->id }})">
    <x-heroicon-o-trash class="w-4 h-4" />
    Delete
</gsmui:button>

{{-- Select dispatches selection change --}}
<gsmui:select
    wire:model="status"
    wire:change="filterByStatus($event.target.value)"
    :options="$statuses"
/>

{{-- Modal dispatches confirm/cancel --}}
<gsmui:modal wire:model="showConfirm">
    <x-slot:footer>
        <gsmui:button wire:click="confirmAction" variant="danger">Confirm</gsmui:button>
        <gsmui:button as="div" x-on:click="$wire.set('showConfirm', false)">Cancel</gsmui:button>
    </x-slot:footer>
</gsmui:modal>
```

### 8.4 Event Naming Convention

| Event Pattern | Convention | Example |
| --- | --- | --- |
| Component events | `gsmui:{component}:{action}` | `gsmui:select:changed` |
| Page events | `{entity}:{action}` | `order:status-changed` |
| Global events | `app:{action}` | `app:theme-changed` |

## 9. Livewire Loading States

### 9.1 Loading Indicators

GsmUi provides built-in loading state integration:

```blade
{{-- Button with loading state --}}
<gsmui:button wire:loading.attr="disabled">
    <span wire:loading.remove>Save</span>
    <span wire:loading><x-gsmui:spinner class="w-4 h-4" /> Saving...</span>
</gsmui:button>

{{-- Form section with loading overlay --}}
<div wire:loading.class="opacity-50 pointer-events-none">
    <gsmui:input wire:model="name" />
    <gsmui:input wire:model="email" />
</div>
```

### 9.2 Loading State Matrix

| Loading Pattern | Directive | Use Case |
| --- | --- | --- |
| Disable during request | `wire:loading.attr="disabled"` | Submit buttons |
| Show spinner | `wire:loading` / `wire:loading.remove` | Inline loading indicator |
| Dim content | `wire:loading.class="opacity-50"` | Section loading |
| Full-page loading | `wire:loading.class="pointer-events-none"` | Prevent interaction during save |
| Targeted loading | `wire:loading.target="#specific-element"` | Targeted loading indicator |

### 9.3 Loading Target Specificity

```blade
{{-- Target a specific Livewire component --}}
<gsmui:button wire:loading.target="#order-form">
    Submit Order
</gsmui:button>

{{-- Target all wire:model elements in a section --}}
<div wire:loading.class.delay="opacity-50">
    {{-- All inputs in this section will dim during their specific wire:model sync --}}
</div>
```

## 11. Livewire Security in GsmUi

### 11.1 CSRF Protection

All Livewire requests automatically include CSRF tokens. No manual configuration is required:

```text
Livewire JS ──adds CSRF token──▶ POST /livewire/update
                                      │
                                      ▼
                              Laravel VerifyCsrfToken middleware
                                      │
                                      ▼
                              Livewire controller processes request
```

### 11.2 Authorization

Livewire components should authorize actions server-side:

```php
class OrderForm extends Component
{
    public function updateStatus($orderId, $status)
    {
        $this->authorize('update', Order::find($orderId));
        // Proceed with update
    }
}
```

### 11.3 Input Validation

All `wire:model` bound values are validated server-side:

```php
public function updatedEmail($value)
{
    $this->validate([
        'email' => 'required|email|max:255',
    ]);
}
```

### 11.4 XSS Prevention

- Livewire escapes all output by default
- `wire:html` is never used in `gsmui:` components
- Component markup is static (pre-rendered server-side)
- Dynamic content uses `{{ }}` (escaped), never `{!! !!}`

## 12. Livewire Performance Patterns

### 12.1 Component Caching

```php
class DashboardStats extends Component
{
    public function render()
    {
        return cache()->remember('dashboard-stats', 60, function () {
            return view('livewire.dashboard-stats', [
                'stats' => Stats::summary(),
            ]);
        });
    }
}
```

### 12.2 Selective Hydration

Use `wire:ignore` to prevent Livewire from re-rendering expensive sections:

```blade
<div wire:ignore>
    {{-- Chart.js renders here; Livewire won't touch it --}}
    <canvas id="chart" wire:ignore></canvas>
</div>
```

### 12.3 Lazy Loading Components

```blade
{{-- Defer loading until component enters viewport --}}
@gsmui:card wire:init="loadStats" x-intersect.once="$wire.loadStats()">
    @if($loaded)
        {{-- Render stats --}}
    @else
        <gsmui:skeleton class="h-32 w-full" />
    @endif
</gsmui:card>
```

### 12.4 DOM Diffing Strategy

Livewire 4 uses an optimized DOM diffing algorithm that:
- Preserves text nodes when content hasn't changed
- Skips attribute updates when values are identical
- Maintains element identity across re-renders
- Uses keyed reconciliation for lists

### 12.5 Performance Budget

| Metric | Target | Measurement |
| --- | --- | --- |
| Initial hydration | < 500ms | Livewire debug bar |
| Subsequent updates | < 100ms | Network tab round-trip |
| DOM diff time | < 16ms (60fps) | Chrome DevTools performance |
| Memory per component | < 10KB | Chrome DevTools memory |
| Network per update | < 5KB | Network tab payload |

## 13. Livewire Testing Patterns

### 13.1 Component Unit Testing

```php
use Tests\TestCase;
use Livewire\Livewire;

class OrderFormTest extends TestCase
{
    public function test_can_update_order_status(): void
    {
        Livewire::test(OrderForm::class)
            ->set('status', 'shipped')
            ->assertSet('status', 'shipped')
            ->assertDispatched('order:status-changed');
    }

    public function test_validates_email(): void
    {
        Livewire::test(OrderForm::class)
            ->set('email', 'invalid')
            ->assertHasErrors(['email']);
    }
}
```

### 13.2 Browser Testing with Playwright

```js
// tests/Browser/livewire-binding.spec.js
const { test, expect } = require("@playwright/test");

test("gsmui:input syncs with Livewire", async ({ page }) => {
    await page.goto("/test/livewire-form");

    // Type into gsmui:input
    await page.fill("[data-gsmui-input] input", "hello");

    // Verify Livewire component received the value
    const result = await page.locator("[data-livewire-output]").textContent();
    expect(result).toBe("hello");
});
```

### 13.3 Hydration Testing

```js
test("component hydrates without errors", async ({ page }) => {
    const errors = [];
    page.on("console", msg => {
        if (msg.type() === "error") errors.push(msg.text());
    });

    await page.goto("/test/component");
    await page.waitForTimeout(1000);

    expect(errors).toEqual([]);
    await expect(page.locator("[data-gsmui-component]")).toBeVisible();
});
```

## 14. Livewire Debugging

### 14.1 Debug Mode

Enable Livewire debug mode in development:

```php
// config/livewire.php
'debug' => env('APP_DEBUG', false),
```

### 14.2 Debug Toolbar

Livewire provides a debug toolbar that shows:
- Component tree
- Hydration timing
- Network requests
- DOM diff operations
- Event dispatches

### 14.3 Common Issues & Solutions

| Issue | Cause | Solution |
| --- | --- | --- |
| FOUC | Theme not loaded before paint | Add pre-paint theme bootstrap |
| Focus loss on hydration | Livewire re-renders focused element | Use `wire:ignore` on focused element |
| Slow updates | Large DOM diff | Use `wire:ignore` on static sections |
| Stale state | Missing `wire:model` binding | Verify `wire:model` attribute exists |
| Double request | Rapid fire events | Add `wire:debounce` modifier |
| Memory leak | Components not destroyed | Use `wire:destroy` on navigation |

## 15. Livewire 4 Migration Notes

### 15.1 Livewire 3 → 4 Key Changes

| Area | Livewire 3 | Livewire 4 |
| --- | --- | --- |
| Rendering | Full component re-render | Targeted DOM diff |
| Hydration | Heavy payload | Optimized serialization |
| JavaScript | Alpine integration | Standalone with Alpine interop |
| Navigation | Full page reload | SPA-like `wire:navigate` |
| Styling | Manual CSS loading | Automatic asset loading |

### 15.2 GsmUi Adaptation for Livewire 4

| Component Pattern | Livewire 3 | Livewire 4 |
| --- | --- | --- |
| State sync | `wire:model` + polling | `wire:model` + optimized diff |
| Loading | `wire:loading` (basic) | `wire:loading` (targeted) |
| Events | `$emit` / `$dispatch` | `$dispatch` + browser events |
| Navigation | `wire:click` + redirect | `wire:navigate` |

## 18. Livewire Offline & Error Handling

### 18.1 Offline Detection

```blade
<div wire:offline.class="opacity-50 pointer-events-none">
    <gsmui:button wire:loading.attr="disabled">
        Save
    </gsmui:button>
    <gsmui:alert type="warning" x-show="$wire.isOffline">
        You are offline. Changes will be saved when connection is restored.
    </gsmui:alert>
</div>
```

### 18.2 Error Recovery

| Error Type | Behavior | User Feedback |
| --- | --- | --- |
| Network error | Retry up to 3 times | Toast notification |
| Validation error | Show inline errors | `data-invalid` styles |
| Server error (500) | Show error toast | Red alert banner |
| Timeout | Retry once, then show error | Timeout message |
| CSRF expired | Refresh page | "Session expired" toast |

### 18.3 Connection Status Monitoring

```js
// In app.js
window.addEventListener("online", () => {
    document.documentElement.removeAttribute("data-offline");
});

window.addEventListener("offline", () => {
    document.documentElement.setAttribute("data-offline", "");
});
```

## 19. Livewire Accessibility Integration

### 19.1 Live Region Updates

When Livewire updates content, screen readers are notified through ARIA live regions:

```blade
{{-- Status updates announced to screen readers --}}
<div role="status" aria-live="polite" class="sr-only">
    {{ $statusMessage }}
</div>

{{-- Error announcements --}}
<div role="alert" aria-live="assertive" class="sr-only">
    {{ $errorMessage }}
</div>
```

### 19.2 Focus Management After Livewire Updates

```blade
{{-- Preserve focus after Livewire re-render --}}
<gsmui:input
    wire:model="query"
    x-ref="searchInput"
    x-on:keyup.escape="$refs.searchInput.blur()"
/>

{{-- Restore focus after modal close --}}
<gsmui:modal wire:model="showModal">
    <x-slot:trigger>
        <gsmui:button x-ref="modalTrigger">Open</gsmui:button>
    </x-slot:trigger>
    <x-slot:default>
        <p>Modal content</p>
```

## 26. Livewire Architecture Deep Dive

### 26.1 Livewire 4 Lifecycle (Complete)

Livewire 4 introduces significant improvements that GsmUi leverages for a smoother frontend experience. This section details every phase of the lifecycle as it pertains to `gsmui:` components.

```text
┌─────────────────────────────────────────────────────────────┐
│                 Livewire 4 Lifecycle Phases                  │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Phase 1: Initial Page Load                                  │
│  └─ HTML arrives (server-rendered)                           │
│  └─ Theme bootstrap script runs (inline, pre-paint)         │
│  └─ CSS loads (Tailwind + GsmUi styles)                     │
│  └─ GsmUi JS bundle loads (component behavior mixins)       │
│  └─ Livewire JS initializes                                 │
│  └─ Livewire finds all wire: directives in DOM              │
│  └─ Livewire hydrates each component                        │
│  └─ MutationObserver on value attributes activates           │
│  └─ Components are interactive                               │
│                                                              │
│  Phase 2: User Interaction                                   │
│  └─ User interacts with component                           │
│  └─ GsmUi JS captures event                                 │
│  └─ wire:model dispatches to server (debounced)             │
│  └─ Livewire request (fetch, CSP-safe)                      │
│  └─ Server validates and processes                           │
│  └─ Server returns hydration diff                            │
│  └─ DOM morph applied                                        │
│  └─ MutationObserver triggers                                │
│  └─ GsmUi JS syncs UI state                                 │
│                                                              │
│  Phase 3: Navigation                                         │
│  └─ User clicks link                                        │
│  └─ wire:navigate intercepts                                 │
│  └─ Fetch new page HTML                                      │
│  └─ Morph current page to new page                           │
│  └─ Livewire components rehydrate                            │
│  └─ State preserved across navigation                        │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 26.2 Hydration Process

When Livewire hydrates a `gsmui:` component, the following sequence occurs:

```text
Server Component State
       │
       ▼
Serialization (JSON)
       │
       ▼
Transport (fetch POST to /livewire/update)
       │
       ▼
Client Deserialization
       │
       ▼
Diff Algorithm (morph DOM)
       │
       ▼
MutationObserver triggers
       │
       ▼
GsmUi JS syncs UI state
```

The diff algorithm is critical for `gsmui:` components because it preserves DOM nodes when possible, which means:
- Focus is retained on text inputs
- Cursor position is not reset
- Open/close state of popopers is preserved
- Animation state is not interrupted

### 26.3 Hydration Mapping

| Component | Hydrated Properties | DOM Impact |
| --- | --- | --- |
| `gsmui:input` | `value`, `disabled`, `invalid` | Updates input value, aria attributes |
| `gsmui:select` | `value`, `options`, `disabled` | Updates selected display, option list |
| `gsmui:slider` | `value`, `min`, `max`, `step` | Updates thumb position, aria-valuenow |
| `gsmui:date-picker` | `value`, `format`, `disabled` | Updates trigger display, calendar state |
| `gsmui:color-picker` | `value`, `format`, `swatches` | Updates color preview, hue position |
| `gsmui:toggle` | `value`, `disabled` | Updates checked state, aria-checked |
| `gsmui:modal` | `open` | Shows/hides dialog, manages focus trap |
| `gsmui:table` | `rows`, `columns`, `sort`, `page` | Updates table body, pagination |

### 26.4 Server round-trip optimization

GsmUi minimizes server round-trips through several strategies:

| Strategy | Implementation | Components |
| --- | --- | --- |
| Debouncing | 150ms default delay | `gsmui:input`, `gsmui:select searchable` |
| Throttling | 300ms minimum interval | `gsmui:slider` |
| Lazy validation | Validate on blur, not on keystroke | All form inputs |
| Optimistic updates | UI updates immediately, server confirms | `gsmui:toggle`, `gsmui:checkbox` |
| Prefetching | Load data before interaction | `gsmui:select` with remote options |

## 27. `wire:model` Binding Deep Dive

### 27.1 Binding Modes

| Mode | Syntax | Behavior | Use Case |
| --- | --- | --- | --- |
| Lazy | `wire:model="field"` | Syncs on change (blur/enter) | Text inputs, textareas |
| Eager | `wire:model.live="field"` | Syncs on every input event | Search inputs, sliders |
| Deferred | `wire:model.defer="field"` | Syncs on next Livewire request | Non-critical updates |

### 27.2 Component Binding Matrix

| Component | Recommended Binding | Rationale |
| --- | --- | --- |
| `gsmui:input` | `wire:model="field"` | Lazy by default; avoid excessive updates |
| `gsmui:input` (search) | `wire:model.live="field"` | Real-time search requires live updates |
| `gsmui:textarea` | `wire:model="field"` | Lazy by default; expensive server processing |
| `gsmui:select` | `wire:model="field"` | Syncs on selection change |
| `gsmui:date-picker` | `wire:model="field"` | Syncs on date selection |
| `gsmui:time-picker` | `wire:model="field"` | Syncs on time selection |
| `gsmui:color-picker` | `wire:model.live="field"` | Live preview requires continuous sync |
| `gsmui:slider` | `wire:model.live="field"` | Real-time value display |
| `gsmui:range` | `wire:model.live="field"` | Dual-thumb real-time sync |
| `gsmui:toggle` | `wire:model="field"` | Syncs on toggle click |
| `gsmui:checkbox` | `wire:model="field"` | Syncs on check/uncheck |
| `gsmui:radio` | `wire:model="field"` | Syncs on selection |

### 27.3 Custom Debounce Configuration

Components accept a `wire:debounce` modifier for custom timing:

```blade
<gsmui:input wire:model.debounce.300ms="search" placeholder="Search..." />
<gsmui:slider wire:model.throttle.100ms="volume" />
<gsmui:color-picker wire:model.live.50ms="themeColor" />
```

### 27.4 Binding to Nested Properties

Livewire supports dot-notation for nested properties:

```blade
<gsmui:input wire:model="user.name" />
<gsmui:input wire:model="user.email" />
<gsmui:select wire:model="user.role" :options="$roles" />
<gsmui:toggle wire:model="user.settings.notifications" />
```

### 27.5 Binding to Array Properties

Multiple selection components bind to array properties:

```blade
@gsmui:select wire:model="selectedTags" :options="$tags" multiple />
@gsmui:checkbox-group wire:model="permissions" :options="$allPermissions" />
```

### 27.6 Two-Way Binding Contract

| Direction | Mechanism | Timing |
| --- | --- | --- |
| Client → Server | `wire:model` sync | On change (lazy) or input (live) |
| Server → Client | Hydration diff | On server response |
| Server → Client (initial) | HTML render | On page load |

The server is always the source of truth. If a `wire:model` value conflicts with the client-side state, the server value wins after hydration.

## 31. Livewire Security in GsmUi

### 31.1 CSRF Protection

All Livewire requests automatically include CSRF tokens. No manual configuration is required:

```text
Livewire JS ──adds CSRF token──▶ POST /livewire/update
                                      │
                                      ▼
                              Laravel VerifyCsrfToken middleware
                                      │
                                      ▼
                              Livewire controller processes request
```

### 31.2 Authorization

Livewire components should authorize actions server-side:

```php
class OrderForm extends Component
{
    public function updateStatus($orderId, $status)
    {
        $this->authorize('update', Order::find($orderId));
        // Proceed with update
    }
}
```

### 31.3 Input Validation

All `wire:model` bound values are validated server-side:

```php
public function updatedEmail($value)
{
    $this->validate([
        'email' => 'required|email|max:255',
    ]);
}
```

### 31.4 XSS Prevention

- Livewire escapes all output by default
- `wire:html` is never used in `gsmui:` components
- Component markup is static (pre-rendered server-side)
- Dynamic content uses `{{ }}` (escaped), never `{!! !!}`

## 38. Livewire Offline & Error Handling

### 38.1 Offline Detection

```blade
<div wire:offline.class="opacity-50 pointer-events-none">
    <gsmui:button wire:loading.attr="disabled">
        Save
    </gsmui:button>
    <gsmui:alert type="warning" x-show="$wire.isOffline">
        You are offline. Changes will be saved when connection is restored.
    </gsmui:alert>
</div>
```

### 38.2 Error Recovery

| Error Type | Behavior | User Feedback |
| --- | --- | --- |
| Network error | Retry up to 3 times | Toast notification |
| Validation error | Show inline errors | `data-invalid` styles |
| Server error (500) | Show error toast | Red alert banner |
| Timeout | Retry once, then show error | Timeout message |
| CSRF expired | Refresh page | "Session expired" toast |

### 38.3 Connection Status Monitoring

```js
// In app.js
window.addEventListener("online", () => {
    document.documentElement.removeAttribute("data-offline");
});

window.addEventListener("offline", () => {
    document.documentElement.setAttribute("data-offline", "");
});
```

```blade

    wire:model="query"
    x-ref="searchInput"
    x-on:keyup.escape="$refs.searchInput.blur()"
/>

{{-- Restore focus after modal close --}}
<gsmui:modal wire:model="showModal">
    <x-slot:trigger>
        <gsmui:button x-ref="modalTrigger">Open</gsmui:button>
    </x-slot:trigger>
    <x-slot:default>
        <p>Modal content</p>
    </x-slot:default>
    <x-slot:footer>

        </gsmui:button>
```

## 40. Livewire & Theme Integration

### 40.1 Theme-Aware Components

Livewire components respect the current theme without any additional configuration:

```text
Server renders HTML with theme attributes
       │
       ▼
GsmUi CSS reads --gsmui-* tokens from :root
       │
       ▼
Components render with correct theme colors
       │
       ▼
Livewire updates preserve theme state (DOM diff, not full re-render)
```

### 40.2 Theme Switching During Livewire Requests

Theme switching is hydration-safe:

```php
class ThemeController extends Component
{
    public function switchTheme($theme)
    {
        session(['theme' => $theme]);
        $this->dispatch('theme-changed', theme: $theme);
    }
}
```

```blade
{{-- Client listens for theme change --}}
<div x-on:theme-changed.window="
    document.documentElement.setAttribute('data-theme', $event.detail.theme);
">
    {{-- Livewire component --}}
</div>
```

### 40.3 Theme Persistence Across Navigation

| Storage | Duration | Use Case |
| --- | --- | --- |
| `localStorage` | Session | Theme preference |
| Cookie | 1 year | Server-side theme detection |
| Database | Permanent | User account theme preference |

### 41.2 Asset Optimization

| Asset | Strategy | Impact |
| --- | --- | --- |
| `livewire.js` | Self-hosted, minified | ~30KB gzipped |
| Livewire update endpoint | HTTP/2 multiplexed | Reduced latency |

## 42. Livewire Best Practices for GsmUi

### 42.1 Component Design Principles

| Principle | Rule |
| --- | --- |
| Single responsibility | One Livewire component per functional unit |
| Minimal state | Only store state that needs server sync |
| Lazy hydration | Use `wire:init` for below-the-fold content |
| Targeted updates | Use `wire:target` for specific loading states |
| Event-driven | Use events for cross-component communication |

### 42.2 Code Organization

| Practice | Example |
| --- | --- |
| Keep components small | < 200 lines PHP, < 100 lines Blade |
| Extract to sub-components | Split complex forms into smaller pieces |
| Use traits for reuse | Extract common logic into traits |
| Test at component level | Unit test each component independently |
| Document component API | List all public properties and methods |

### 42.3 Common Anti-Patterns

| Anti-Pattern | Problem | Solution |
| --- | --- | --- |
| Storing everything in public | Unnecessary hydration overhead | Use `#[Locked]` for display-only |
| Polling on every component | Network overhead | Poll only where needed |
| Full re-render on every change | Performance hit | Use `wire:ignore` for static sections |
| Missing `wire:model.lazy` | Excessive server requests | Use lazy binding for text inputs |
| Deeply nested components | Hydration bloat | Flatten component hierarchy |
