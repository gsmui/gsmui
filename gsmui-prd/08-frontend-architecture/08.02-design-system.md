# 08.02 - Design System

**Project:** GsmUi
**Section:** 08 - Frontend Architecture
**Framework:** Blade Components · GsmUi Component Library · Tailwind CSS v4 · Design Token Engine · CSS Variables
**Version:** 1.0.0

---

> See also: `05.17-component-engine.md` (component schema/registry), `06.20-components.md` (component definitions), `08.03-design-tokens.md` (token taxonomy). This document specifies the *design language and component taxonomy* and does NOT re-document the component schema that lives in 06.

# Purpose

This document makes the GsmUi design language unambiguous: the principles that govern every component, the taxonomy used to classify components, and the precise position of the self-hosted `gsmui:` component library within the broader design system. Implementers use it to decide *which* component to reach for and *how* it should behave before reading the per-component contracts in `06.20-components.md` and `08.07-blade-component-system.md`.

---

## 1. Design Principles

These principles mirror the AGENTS.md philosophy and are binding on every component.

| # | Principle | Implementation Rule |
| --- | --- | --- |
| 1 | Internal consistency > external best practices | Match `gsmui:input` before inventing a new pattern |
| 2 | Punt semi-aggressively | Cut features that add complexity without proportional value |
| 3 | Separate-component rule | A fundamentally different shape is a new component, not a prop |
| 4 | Best variant is default | Don't make users opt-in to the better experience |
| 5 | Lean on the browser | Use native APIs; no lookup tables/parsers the browser handles |
| 6 | Outside-in development | Start from the docs page and user experience, then go inward |
| 7 | Verify visually | Playwright screenshots, not eyeballing, before claiming done |

## 2. Component Taxonomy

Components are grouped by interaction role. The `~70` components in `stubs/resources/views/gsmui/*` map into these categories.

| Category | Examples (gsmui:) | Traits |
| --- | --- | --- |
| Inputs | `input`, `textarea`, `select`, `date-picker`, `slider`, `color-picker` | Wire-bound, validation-aware, `data-invalid` states |
| Disclosure | `accordion`, `modal`, `popover`, `dropdown`, `command` | Trigger + state root + lock-scroll pattern |
| Feedback | `toast`, `alert`, `badge`, `spinner` | Non-blocking, ARIA live regions |
| Data display | `table`, `card`, `list`, `chart` | Composable, paged or virtualized |
| Layout | `app-layout`, `sidebar`, `header`, `stack`, `grid` | Structural, token-driven spacing |
| Action | `button`, `icon-button`, `link` | Native cursor defaults, no `cursor-pointer` |

---

## 3. Naming Conventions

AGENTS.md mandates short, natural prop names. These are the lexical rules:

- **Boolean opt-in behaviors** use the `-able` suffix: `clearable`, `copyable`, `searchable`, `expandable`, `dropper`.
- **Trigger variants** use a `type` prop, not boolean flags: `type="input"` vs `type="button"`.
- **Format demos** use meaningful labels only: `label="hex"`; never echo section titles.
- Component files live at `stubs/resources/views/gsmui/<component>/index.blade.php`.

---

## 4. GsmUi Library Position

The GsmUi library is the **only** sanctioned source of UI primitives. Product UI (marketing, docs, playground, marketplace) composes pages *exclusively* from `gsmui:` components plus plain Blade layout — it never hand-rolls buttons, inputs, or popovers.

| Concern | Owner |
| --- | --- |
| Primitive components (`gsmui:*`) | `stubs/resources/views/gsmui/*` + `dist/` JS |
| Page composition | Product Blade views consuming `gsmui:` |
| Styling | Tailwind v4 utilities + `--gsmui-*` CSS variables |
| Behavior | GsmUi JS mixins (`Controllable`, `Disableable`, …) — see `08.10-javascript-architecture.md` |

Forbidden: introducing a second component library, CDN design systems, or bespoke CSS that bypasses the token engine.

## 5. Visual State Contract

Every interactive component must render, and be Playwright-verified in, this minimal state set (AGENTS.md §Verification):

| State | Required behavior |
| --- | --- |
| Base | Default render, no modifier classes |
| Disabled | `[&[disabled]]:shadow-none!` on custom elements; native `:disabled` on form elements |
| Invalid | Layered `data-invalid:` classes over base — never ternary-swap the whole class block |
| Sizes | `default / sm / xs` height progression `h-10 / h-8 / h-6` |
| Focus-visible | Native outline on `<button>`/`<input>`; `has-focus-visible:outline-2` on custom `tabindex` elements |

## 6. Component Anatomy

Every `gsmui:` component follows a consistent internal anatomy. Understanding this structure is essential for building new components that feel native to the system.

### 6.1 Standard Component Structure

```text
┌─────────────────────────────────────────────────┐
│  Label (optional)                                │
│  ┌─────────────────────────────────────────────┐ │
│  │  Trigger / Input Area                       │ │
│  │  ┌─────────────────────────────┬──────────┐ │ │
│  │  │  Value / Placeholder        │ Actions  │ │ │
│  │  │                             │ (clear,  │ │ │
│  │  │                             │  copy)   │ │ │
│  │  └─────────────────────────────┴──────────┘ │ │
│  └─────────────────────────────────────────────┘ │
│  Description (optional)                          │
│  Error message (when data-invalid)               │
│                                                   │
│  ┌─────────────────────────────────────────────┐ │
│  │  Popover / Dropdown (when open)             │ │
│  │  ┌─────────────────────────────────────────┐│ │
│  │  │  Content area                          ││ │
│  │  │  (options, calendar, color grid, etc.)  ││ │
│  │  └─────────────────────────────────────────┘│ │
│  │  Footer (optional)                         │ │
│  └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
```

### 6.2 Component Layers

Each component is composed of layers, ordered from innermost to outermost:

| Layer | Purpose | Example |
| --- | --- | --- |
| **State Root** | Manages internal state (open/closed, value, focus) | `<div data-gsmui-select>` |
| **Trigger** | The interactive element that initiates action | `<button>`, `<input>` |
| **Display** | Shows current value or placeholder | `<span>`, `<input value>` |
| **Actions** | Utility buttons (clear, copy, dropper) | `<gsmui:button>` |
| **Popover** | Floating content container | `<div role="dialog">` |
| **Content** | The actual interactive content | Options list, calendar grid |
| **Footer** | Bottom actions (Today, Clear, etc.) | `<div>` with buttons |

### 6.3 State Root Convention

Every component has a state root element that carries the component's identity and state attributes:

```html
<!-- State root carries data-gsmui-* attribute -->
<div data-gsmui-select
     data-gsmui-value=""
     data-gsmui-disabled=""
     data-gsmui-invalid=""
     data-gsmui-open="">
  <!-- children -->
</div>
```

The state root is what GsmUi JS observes via MutationObserver. Changes to `data-gsmui-*` attributes drive UI updates.

## 7. Component Composition Patterns

### 7.1 Composition Over Configuration

GsmUi favors composition over deep prop configuration. When a component needs significant structural variation, it becomes a separate component rather than adding props.

**Good (composition):**
```blade
<gsmui:input-group>
    <x-slot:prepend>
        <gsmui:button icon="search" />
    </x-slot:prepend>
    <gsmui:input wire:model="search" placeholder="Search..." />
    <x-slot:append>
        <gsmui:button icon="x" />
    </x-slot:append>
</gsmui:input-group>
```

**Bad (configuration explosion):**
```blade
{{-- Don't do this --}}
<gsmui:input
    prepend-icon="search"
    append-icon="x"
    prepend-action="search"
    append-action="clear"
    prepend-disabled="false"
    append-disabled="false"
/>
```

### 7.2 Slot Patterns

| Slot Type | Convention | Use Case |
| --- | --- | --- |
| Default slot | Children content | Accordion items, list items |
| Named slots | `x-slot:name` | Trigger content, footer, header |
| Conditional slots | `@if($slot->isNotEmpty())` | Optional sections |
| Fragment slots | Multiple root elements | Complex popover content |

### 7.3 Render Delegation

Some components delegate rendering to slots while maintaining structural guarantees:

```blade
{{-- Component provides structure; slot provides content --}}
<gsmui:accordion-item>
    <x-slot:trigger>
        <span>Section Title</span>  {{-- Caller controls content --}}
    </x-slot:trigger>
    <x-slot:content>
        <p>Section body</p>        {{-- Caller controls content --}}
    </x-slot:content>
</gsmui:accordion-item>
```

The component enforces the accordion structure (trigger + content, expand/collapse behavior) while the caller controls the visual content.

## 8. Visual Language

### 8.1 Color Philosophy

GsmUi uses a restrained, neutral-dominant color palette. Color is used sparingly for emphasis and status, not decoration.

| Role | Light Mode | Dark Mode | Usage |
| --- | --- | --- | --- |
| Background | `white` | `zinc-900` | Page background |
| Surface | `zinc-50` | `zinc-800` | Card, popover background |
| Border | `zinc-200` | `white/10` | Dividers, input borders |
| Text primary | `zinc-900` | `zinc-100` | Headings, body text |
| Text secondary | `zinc-500` | `zinc-400` | Descriptions, placeholders |
| Accent | `blue-600` | `blue-500` | Links, focus rings, primary actions |
| Danger | `red-600` | `red-500` | Errors, destructive actions |
| Success | `green-600` | `green-500` | Success states |

## 10. Responsive Behavior Rules

### 10.1 Component Response to Viewport

Every component has defined responsive behavior. The viewport thresholds and component responses are:

| Viewport | Width | Component Behavior |
| --- | --- | --- |
| Mobile | < 640px | Full-width, touch targets 44px, simplified layouts |
| Tablet | 640px - 1024px | Adaptive layouts, mixed touch/pointer |
| Desktop | > 1024px | Standard layouts, 32px touch targets |

### 10.2 Responsive Component Matrix

| Component | Mobile Behavior | Tablet Behavior | Desktop Behavior |
| --- | --- | --- | --- |
| `gsmui:modal` | Full screen with drag handle | Centered dialog | Centered dialog |
| `gsmui:select` | Full-width bottom sheet | Positioned dropdown | Positioned dropdown |
| `gsmui:date-picker` | Full-screen calendar | Centered popover | Positioned dropdown |
| `gsmui:sidebar` | Hidden (hamburger menu) | Collapsible sidebar | Persistent sidebar |
| `gsmui:command` | Full-screen search | Centered dialog | Centered dialog |
| `gsmui:table` | Card layout | Scrollable table | Full table |
| `gsmui:toast` | Full-width top | Positioned top-right | Positioned top-right |
| `gsmui:tooltip` | Disabled (touch device) | Delayed show | Immediate show |

### 10.3 Touch vs Pointer Detection

GsmUi detects input method to optimize interaction:

```css
/* Touch devices: larger targets, disabled hover */
@media (pointer: coarse) {
  .gsmui-touch-target {
    min-height: 44px;
    min-width: 44px;
  }
}

/* Pointer devices: standard targets, hover effects */
@media (pointer: fine) {
  .gsmui-pointer-target {
    min-height: 32px;
    min-width: 32px;
  }
}
```

## 11. Animation Contracts

### 11.1 Enter/Exit Animations

| Component | Enter | Exit | Duration |
| --- | --- | --- | --- |
| Popover | Fade + slide down | Fade + slide up | 200ms / 150ms |
| Modal | Fade + scale up | Fade + scale down | 300ms / 200ms |
| Dropdown | Fade + slide down | Fade + slide up | 150ms / 100ms |
| Toast | Slide in from right | Slide out to right | 300ms / 200ms |
| Toast (mobile) | Slide in from top | Slide out to top | 300ms / 200ms |
| Accordion | Height expand | Height collapse | 200ms / 150ms |
| Tab panel | Fade | Fade | 150ms / 100ms |
| Spinner | Continuous rotation | — | 1000ms linear |

### 11.2 Transition Easings

| Easing Name | Value | Use Case |
| --- | --- | --- |
| `ease-out` | `cubic-bezier(0, 0, 0.2, 1)` | Elements entering |
| `ease-in` | `cubic-bezier(0.4, 0, 1, 1)` | Elements exiting |
| `ease-in-out` | `cubic-bezier(0.4, 0, 0.2, 1)` | State transitions |
| `spring` | Custom spring curve | Bouncy interactions |

### 11.3 Reduced Motion

All animations respect `prefers-reduced-motion: reduce`. When reduced motion is preferred:
- All animations are instant (duration = 0.01ms)
- No continuous animations (spinners become static)
- No parallax effects
- Content changes are immediate

## 12. Dark Mode Design Rules

### 12.1 Dark Mode Principles

| Principle | Rule |
| --- | --- |
| Never pure black | Use `zinc-900` (#18181b), not `#000000` |
| Reduced contrast | Lower contrast ratios in dark mode to reduce eye strain |
| Inverted elevation | Higher elevation = lighter surface (opposite of light mode) |
| Color adjustment | Colors are desaturated slightly in dark mode |
| Border opacity | Borders use `white/10` instead of solid colors |

### 12.2 Dark Mode Color Mapping

| Light Token | Dark Token | Transformation |
| --- | --- | --- |
| `bg-white` | `dark:bg-zinc-900` | Swap to dark neutral |
| `bg-zinc-50` | `dark:bg-zinc-800` | Surface stays lighter than bg |
| `border-zinc-200` | `dark:border-white/10` | Use opacity for subtlety |
| `text-zinc-900` | `dark:text-zinc-100` | Invert text |
| `text-zinc-500` | `dark:text-zinc-400` | Lighten secondary text |
| `shadow-sm` | `dark:shadow-none` | Remove shadows (not needed) |

### 12.3 Dark Mode Testing

Every component must be verified in dark mode. Playwright tests include:

```js
test("component renders correctly in dark mode", async ({ page }) => {
  await page.goto("/test/component");
  await page.evaluate(() => {
    document.documentElement.setAttribute("data-theme", "dark");
  });
  await expect(page.locator("[data-gsmui-component]")).toHaveScreenshot();
});
```

## 13. State Management Patterns

### 13.1 Component State Lifecycle

```text
Initialization → Ready → Interaction → State Change → Re-render → Ready
     │              │         │              │              │
     ▼              ▼         ▼              ▼              ▼
  Set defaults   Render    Capture      Update        Apply diff
  from props     base      event        state         to DOM
```

### 13.2 State Categories

| Category | Source | Lifetime | Example |
| --- | --- | --- | --- |
| Props | Parent component | Render cycle | `size="sm"` |
| Internal state | Component JS | Component lifetime | `isOpen`, `focusedIndex` |
| Wire state | Livewire server | Server round-trip | `wire:model` value |
| Theme state | CSS variables | Session/global | `--gsmui-color-accent` |

### 13.3 State Synchronization Rules

| Rule | Implementation |
| --- | --- |
| Server is source of truth | `wire:model` value is authoritative |
| No sync loops | `detangle()` prevents Controllable ↔ internal feedback |
| Ephemeral UI state | Focus, open/close, hover — never persisted |
| Debounced updates | High-frequency inputs debounced at 150ms |
| Optimistic updates | UI updates immediately; server confirms async |

### 18.1 Component Documentation Structure

Each component's documentation page follows this structure:

```markdown
# Component Name

Brief description of what the component does and when to use it.

## Examples
### Basic Usage
Preview + code block

### With Labels
Preview + code block

### Sizes
Preview showing all sizes

### Disabled State
Preview with disabled example

### Invalid State
Preview with validation error

## Reference
### Props
Table of all props in canonical order

### Events
Table of events emitted

### Slots
Table of available slots

### CSS Variables
Component-specific CSS variables
```

### 18.2 Preview vs Code Block Convention

| Element | Content | Purpose |
| --- | --- | ---|
| Preview | `value="#0ea5e9"`, styled up | Visual demonstration |
| Code block | `wire:model="color"`, minimal | Clean copy-paste target |
| Both | Don't need to match | Different audiences |

### 18.3 Label Conventions

| Rule | Example | Why |
| --- | --- | --- |
| Use contextually meaningful labels | `label="hex"` | Shows what the input controls |
| Never echo section titles | ~~`label="Clearable"`~~ | Redundant with section heading |
| Never use random fillers | ~~`label="Brand"``~~ | Meaningless to the reader |
| When in doubt, no label | (no label attribute) | Labels are optional, not mandatory |

## 21. Component Performance Rules

### 21.1 Rendering Performance

| Rule | Implementation |
| --- | --- |
| Minimal DOM | Only render visible content |
| CSS containment | `contain: layout style paint` on isolated components |
| Debounced updates | 150ms default for high-frequency inputs |
| Lazy rendering | Popover content rendered only when open |
| Virtual scrolling | Large lists use virtual scrolling |

### 21.2 JavaScript Performance

| Rule | Implementation |
| --- | --- |
| Event delegation | Use single listener on state root |
| RequestAnimationFrame | Batch DOM updates |
| Passive event listeners | Scroll/touch events |
| WeakMap/WeakRef | Avoid memory leaks |
| No forced reflow | Batch reads and writes |

### 21.3 CSS Performance

| Rule | Implementation |
| --- | --- |
| No deep selectors | Max 2 levels of nesting |
| No universal selectors | Avoid `*` in component CSS |
| Use transform/opacity | Never animate layout properties |
| Containment | Use `contain` on isolated components |
| Will-change | Apply sparingly for animations only |

## 35. Component Interaction Patterns Deep Dive

### 35.1 Trigger-Popover Pattern

The trigger-popover pattern is the most complex interaction pattern in GsmUi, used by select, date-picker, color-picker, dropdown, and command palette. Understanding this pattern is essential for building consistent disclosure components.

```text
┌─────────────────────────────────────────────────────────────┐
│                    Trigger-Popover Flow                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  User clicks trigger                                        │
│       │                                                     │
│       ▼                                                     │
│  GsmUi JS sets isOpen = true                                │
│       │                                                     │
│       ▼                                                     │
│  setAttribute('data-open', '')                              │
│       │                                                     │
│       ▼                                                     │
│  CSS applies popover styles                                 │
│  [data-open] + .gsmui-popover { display: block; }          │
│       │                                                     │
│       ▼                                                     │
│  Popover enters DOM (conditional rendering)                 │
│       │                                                     │
│       ▼                                                     │
│  Animation lifecycle begins                                 │
│  data-entering → animation → data-entered                   │
│       │                                                     │
│       ▼                                                     │
│  Focus moves to popover content                             │
│       │                                                     │
│       ▼                                                     │
│  User interacts with popover content                        │
│       │                                                     │
│       ▼                                                     │
│  Selection made or Escape pressed                           │
│       │                                                     │
│       ▼                                                     │
│  GsmUi JS sets isOpen = false                               │
│       │                                                     │
│       ▼                                                     │
│  Exit animation plays                                       │
│       │                                                     │
│       ▼                                                     │
│  Popover removed from DOM                                   │
│       │                                                     │
│       ▼                                                     │
│  Focus restored to trigger                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 35.2 State Root Convention

Every GsmUi component has a state root element that carries the component's identity and state attributes. The state root is the anchor point for CSS selectors, JavaScript observation, and accessibility.

| State Root Attribute | Purpose | Example |
| --- | --- | --- |
| `data-gsmui-{component}` | Component identity | `data-gsmui-select` |
| `data-gsmui-value` | Current value | `data-gsmui-value="option-1"` |
| `data-gsmui-disabled` | Disabled state | `data-gsmui-disabled=""` |
| `data-gsmui-invalid` | Validation error | `data-gsmui-invalid=""` |
| `data-gsmui-open` | Disclosure state | `data-gsmui-open=""` |
| `data-gsmui-loading` | Loading state | `data-gsmui-loading=""` |

## 36. Component Variant Architecture

### 36.1 Variant Types

| Variant Type | Description | Example |
| --- | --- | --- |
| Size | Physical dimensions | `sm`, `default`, `xs` |
| Color | Visual emphasis | `primary`, `danger`, `neutral` |
| Style | Visual treatment | `solid`, `outline`, `ghost` |
| Shape | Physical form | `rounded`, `square`, `circle` |
| State | Interaction state | `disabled`, `loading`, `invalid` |

### 36.2 Variant Application Rules

| Rule | Implementation |
| --- | --- |
| Layer, don't swap | Add variant classes on top of base; never replace entire class block |
| Base first | Apply base classes, then variant classes override specific properties |
| State last | State classes (`data-invalid:`, `data-disabled:`) always win |
| Caller override | Caller's `class` attribute merged last via `Gsmui::classes()` |

### 36.3 Variant Class Pattern

```blade
@php
$classes = Gsmui::classes(
    // Base (always present)
    'inline-flex items-center justify-center gap-2 font-medium',

    // Size variant
    match($size) {
        'sm' => 'h-8 text-sm px-3',
        'xs' => 'h-6 text-xs px-2',
        default => 'h-10 text-base px-4',
    },

    // Color variant
    match($variant) {
        'primary' => 'bg-accent text-text-inverse hover:bg-accent-hover',
        'danger' => 'bg-danger text-text-inverse hover:bg-danger-hover',
        default => 'bg-surface text-text border border-border hover:bg-surface-hover',
    },

    // State modifiers (layered on top)
    'data-disabled:opacity-50 data-disabled:pointer-events-none',
    'data-invalid:border-danger',

    // Caller overrides
    $attributes->get('class'),
);
@endphp
```

## 37. Component Slot Architecture

### 37.1 Slot Hierarchy

| Slot Level | Purpose | Example |
| --- | --- | --- |
| Default slot | Primary content | Button text, card body |
| Named slots | Secondary content areas | Header, footer, trigger |
| Scoped slots | Render delegation | Option rendering, cell rendering |
| Conditional slots | Optional sections | Description, error message |

### 37.2 Slot Rendering Rules

| Rule | Implementation |
| --- | --- |
| Check emptiness | `@if(isset($slot) && $slot->isNotEmpty())` |
| Render once | `@once` for expensive content |
| Scope isolation | Scoped slots don't share parent scope |
| Fallback content | `{{ $slot ?? 'Default text' }}` |

### 37.3 Slot Composition Pattern

```blade
{{-- Parent component --}}
<gsmui:select wire:model="status" :options="$statuses">
    {{-- Trigger slot: custom trigger content --}}
    <x-slot:trigger>
        <div class="flex items-center gap-2">
            <x-heroicon-o-chevron-down class="w-4 h-4" />
            <span>{{ $selectedLabel }}</span>
        </div>
    </x-slot:trigger>

    {{-- Option slot: custom option rendering --}}
    <x-slot:option let="$option">
        <div class="flex items-center gap-2">
            <span class="w-2 h-2 rounded-full" style="background: {{ $option->color }}"></span>
            <span>{{ $option->label }}</span>
        </div>
    </x-slot:option>

    {{-- Footer slot: actions below options --}}
    <x-slot:footer>
        <gsmui:button size="xs" variant="ghost">Clear</gsmui:button>
    </x-slot:footer>
</gsmui:select>
```

## 45. Component Composition Patterns

### 45.1 Compound Component Pattern

Compound components share internal state via context, creating cohesive APIs:

```blade
{{-- Select compound component --}}
<x-gsmui::select wire:model="selected">
    <x-gsmui::select.trigger placeholder="Choose..." />
    <x-gsmui::select.content>
        <x-gsmui::select.group label="Fruits">
            <x-gsmui::select.item value="apple">Apple</x-gsmui::select.item>
            <x-gsmui::select.item value="banana">Banana</x-gsmui::select.item>
        </x-gsmui::select.group>
    </x-gsmui::select.content>
</x-gsmui::select>
```

### 45.2 Renderless Component Pattern

Components that provide logic without markup:

```blade
{{-- GsmUi renderless pagination --}}
<gsmui:pagination
    :total="100"
    :per-page="10"
    wire:model="page"
>
    <x-slot:default="{ items, hasMore, hasPrev }">
        {{-- Consumer renders their own markup --}}
        @foreach ($items as $item)
            <div>{{ $item->name }}</div>
        @endforeach
    </x-slot:default>
</gsmui:pagination>
```

### 45.3 Adapter Component Pattern

Components that bridge different data formats:

```blade
{{-- Table adapter for API data --}}
<gsmui:table
    :columns="[
        ['key' => 'name', 'label' => 'Name', 'sortable' => true],
        ['key' => 'email', 'label' => 'Email'],
        ['key' => 'role', 'label' => 'Role', 'format' => 'badge'],
    ]"
    :rows="$users"
    wire:model="sort"
    sortable
    paginated
/>
```

### 45.4 Composition vs Configuration Decision Matrix

| Scenario | Use Composition | Use Configuration |
| --- | --- | --- |
| Variations in structure | Yes | No |
| Variations in behavior | No | Yes |
| Variations in content placement | Yes | No |
| Variations in data binding | No | Yes |
| Variations in styling only | No | Yes |
| Complex multi-section layouts | Yes | No |
| Simple prop-driven states | No | Yes |
