# 08.47 - SEO

**Project:** GsmUi
**Section:** 08 - Frontend Architecture
**Framework:** Laravel 13 · Blade Components · Laravel Folio (optional) · Tailwind CSS v4
**Version:** 1.0.0

---

> See also: `08.23-documentation-ui.md` (docs portal rendering), `05.06-folder-structure.md` (route/view layout). This document specifies the *frontend SEO contract* (meta, structured data, crawlability) and does NOT re-document routing schema or content modeling.

# Purpose

GsmUi's public surfaces (marketing, docs portal, blog, showcase) must be fully indexable without JavaScript and without any external SEO service. Because pages render server-side through Blade (and optionally Laravel Folio), SEO is achieved with first-class `<head>` metadata and JSON-LD injected at render time — never via client-side injection (which would violate CSP and break crawlers).

This document covers every SEO concern in the GsmUi frontend: metadata templates, social sharing tags, structured data schemas, sitemap generation, robots directives, crawlability analysis for Livewire-driven pages, canonical URL strategy, breadcrumb structured data, image SEO, performance-related SEO signals, and the testing gates that ensure SEO correctness. It also defines the integration points between SEO and the CSP model, the i18n system, the documentation portal, and the marketing site.

## 1. Head Metadata (Server-Rendered)

All meta lives in Blade layouts, rendered before `dist/` JS executes. No client-side `<title>`/`meta` mutation.

```html
<head>
  <title>{{ $title ?? __('gsmui::seo.default_title') }}</title>
  <meta name="description" content="{{ $description }}">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <link rel="canonical" href="{{ url()->current() }}">
</head>
```

Localized strings use `__()` per `08.45-internationalization.md`.

### 1.1 Title Tag Strategy

The `<title>` tag is the single most important on-page SEO element. GsmUi uses a consistent pattern across all public surfaces:

| Page Type | Title Pattern | Example |
| --- | --- | --- |
| Homepage | `{{ $siteName }} — {{ $tagline }}` | `GsmUi — Laravel UI Components` |
| Component docs | `{{ $componentName }} — GsmUi` | `Date Picker — GsmUi` |
| Blog post | `{{ $postTitle }} — GsmUi Blog` | `Building Accessible Forms — GsmUi Blog` |
| Template | `{{ $templateName }} Template — GsmUi` | `Admin Dashboard Template — GsmUi` |
| Error pages | `{{ $statusCode }} — GsmUi` | `404 — GsmUi` |

The title length must stay between 30 and 60 characters for optimal search display. The Blade partial `gsmui::seo.title` enforces this by truncating with `Str::limit()` when the computed title exceeds 60 characters:

```blade
{{-- partials/seo/title.blade.php --}}
@props(['title' => null, 'siteName' => config('app.name', 'GsmUi')])
@php
  $computed = $title ? "{$title} — {$siteName}" : __('gsmui::seo.default_title');
  $truncated = \Illuminate\Support\Str::limit($computed, 60, '…');
@endphp
<title>{{ $truncated }}</title>
```

### 1.2 Meta Description

Each page type has a meta description defined in the page's Blade data or the Folio page metadata. Descriptions must be between 120 and 160 characters. The Blade partial validates this at render time in non-production environments and logs a warning if the description falls outside the range:

```blade
{{-- partials/seo/description.blade.php --}}
@props(['description' => null])
@if($description)
  @if(env('APP_DEBUG') && (strlen($description) < 120 || strlen($description) > 160))
    {{-- Log warning in dev, still render for crawlers --}}
  @endif
  <meta name="description" content="{{ $description }}">
@endif
```

### 1.3 Meta Robots

All public pages default to `index, follow`. Admin pages, preview routes, and draft content use `noindex, nofollow`:

```blade
<meta name="robots" content="{{ $robots ?? 'index, follow' }}">
```

Story routes (see `08.54-storybook-strategy.md`) always set `noindex, nofollow` to prevent component isolation pages from appearing in search results.

### 1.4 Viewport Meta

The viewport meta is identical across all pages — it never changes:

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

The viewport meta must not include `maximum-scale=1` or `user-scalable=no` — these harm accessibility (WCAG 1.4.4) and are increasingly penalized by search engines.

### 1.5 Charset and Language

```html
<meta charset="UTF-8">
<html lang="{{ str_replace('_', '-', app()->getLocale()) }}">
```

The `<html lang>` attribute is set dynamically based on the current locale from `08.45-internationalization.md`. Search engines use this to serve the correct language version to users.

## 2. Open Graph / Social

For share cards, render OG/Twitter tags server-side. No external pixel or script tags (CSP: `connect-src 'self'`, no third-party embeds).

```html
<meta property="og:title" content="{{ $title }}">
<meta property="og:type" content="website">
<meta property="og:url" content="{{ url()->current() }}">
```

### 2.3 Social Image Generation

Social share images (OG images) are generated server-side using Blade templates rendered to PNG via a headless browser (Puppeteer or similar) during the build step — NOT at request time. The generated images are stored in `public/images/og/` and served via `img-src 'self'`. This approach:

- Avoids CSP violations (no external image services)
- Avoids runtime performance cost
- Allows consistent branding across all share targets

The OG image dimensions are 1200×630 pixels (Facebook/Twitter standard). Each page type has a template:

| Page Type | Image Template | Dynamic Element |
| --- | --- | --- |
| Homepage | `og-home.png` | None (static brand image) |
| Component docs | `og-component.png` | Component name overlaid |
| Blog post | `og-blog.png` | Post title + author |
| Template gallery | `og-template.png` | Template name + preview |
| Error pages | `og-error.png` | Error code |

### 2.4 Social Tag Validation

Before deploying any page that introduces new social tags, validate with:

1. Facebook Sharing Debugger (manual check, no automated tool needed)
2. Twitter Card Validator (manual check)
3. Playwright assertion that the correct `<meta>` tags are present in the `<head>`

```javascript
// Playwright assertion example
const ogTitle = await page.locator('meta[property="og:title"]').getAttribute('content');
expect(ogTitle).toContain('GsmUi');
```

### 2.5 CSP Considerations for Social

Social sharing requires NO external resources:

- OG images are self-hosted (`img-src 'self'`)
- No Facebook pixel, Twitter analytics, or social embed scripts
- No third-party tracking pixels
- The `connect-src 'self'` directive means no social API calls from the frontend

If social sharing analytics are needed in the future, they must be implemented server-side (e.g., tracking share counts via a first-party API endpoint).

## 3. Structured Data (JSON-LD)

Inject `application/ld+json` inline in Blade. This is static, trusted markup (not executable), so it is CSP-compatible under `script-src 'self'` when emitted by the server.

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "SoftwareApplication",
  "name": "GsmUi",
  "url": "{{ url('/') }}"
}
</script>
```

Note: the `https://schema.org` URL is a vocabulary identifier in JSON, not a network fetch — no CSP `connect-src` impact.

### 3.1 SoftwareApplication Schema (Homepage)

The homepage uses the `SoftwareApplication` schema to identify GsmUi as a software product:

```blade
<script type="application/ld+json">
@json([
  "@context" => "https://schema.org",
  "@type" => "SoftwareApplication",
  "name" => "GsmUi",
  "url" => url('/'),
  "description" => __('gsmui::seo.default_description'),
  "applicationCategory" => "DeveloperApplication",
  "operatingSystem" => "Web",
  "offers" => [
    "@type" => "Offer",
    "price" => "0",
    "priceCurrency" => "USD",
  ],
  "softwareVersion" => config('gsmui.version', '1.0.0'),
  "sameAs" => [
    "https://github.com/gsmui/gsmui",
  ],
])
</script>
```

### 3.2 BreadcrumbList Schema

All pages with a hierarchical navigation path include breadcrumb structured data:

```blade
<script type="application/ld+json">
@json([
  "@context" => "https://schema.org",
  "@type" => "BreadcrumbList",
  "itemListElement" => $breadcrumbs->map(fn($crumb, $i) => [
    "@type" => "ListItem",
    "position" => $i + 1,
    "name" => $crumb['label'],
    "item" => $crumb['url'],
  ])->values(),
])
</script>
```

The `BreadcrumbList` schema helps search engines understand page hierarchy and can generate breadcrumb-rich results in SERPs.

### 3.3 Article Schema (Blog)

Blog posts use the `Article` schema:

```blade
<script type="application/ld+json">
@json([
  "@context" => "https://schema.org",
  "@type" => "Article",
  "headline" => $post->title,
  "description" => $post->excerpt,
  "author" => [
    "@type" => "Person",
    "name" => $post->author->name,
  ],
  "datePublished" => $post->published_at->toIso8601String(),
  "dateModified" => $post->updated_at->toIso8601String(),
  "publisher" => [
    "@type" => "Organization",
    "name" => config('app.name'),
    "logo" => [
      "@type" => "ImageObject",
      "url" => url('/images/logo.png'),
    ],
  ],
  "image" => $post->featured_image_url,
  "mainEntityOfPage" => url()->current(),
])
</script>
```

### 3.4 FAQPage Schema (Docs)

Documentation pages with FAQ-style content (common questions, troubleshooting) use the `FAQPage` schema:

```blade
@if(isset($faqs) && count($faqs))
<script type="application/ld+json">
@json([
  "@context" => "https://schema.org",
  "@type" => "FAQPage",
  "mainEntity" => $faqs->map(fn($faq) => [
    "@type" => "Question",
    "name" => $faq['question'],
    "acceptedAnswer" => [
      "@type" => "Answer",
      "text" => $faq['answer'],
    ],
  ])->values(),
])
</script>
@endif
```

### 3.5 HowTo Schema (Tutorials)

Tutorial pages that describe step-by-step instructions use the `HowTo` schema:

```blade
@if(isset($steps) && count($steps))
<script type="application/ld+json">
@json([
  "@context" => "https://schema.org",
  "@type" => "HowTo",
  "name" => $pageTitle,
  "description" => $description,
  "step" => $steps->map(fn($step, $i) => [
    "@type" => "HowToStep",
    "position" => $i + 1,
    "name" => $step['title'],
    "text" => $step['description'],
  ])->values(),
])
</script>
@endif
```

### 3.6 JSON-LD Validation

All JSON-LD must validate against schema.org before deployment:

1. Each JSON-LD block is generated via `@json()` which produces valid JSON
2. Schema types are verified against schema.org vocabulary
3. Required properties per schema type are enforced by the Blade partial
4. Playwright tests assert that `<script type="application/ld+json">` blocks exist and contain valid JSON

```javascript
// Playwright JSON-LD validation
const jsonLdBlocks = await page.locator('script[type="application/ld+json"]').all();
for (const block of jsonLdBlocks) {
  const content = await block.textContent();
  const parsed = JSON.parse(content);
  expect(parsed['@context']).toBe('https://schema.org');
  expect(parsed['@type']).toBeTruthy();
}
```

### 3.7 JSON-LD CSP Safety

The `<script type="application/ld+json">` tag is NOT executable JavaScript — browsers never execute it as code. It is purely data. This means:

- It does NOT require `script-src` relaxation
- It does NOT require `unsafe-eval`
- It is emitted by the server (Blade) so it is trusted content
- The `https://schema.org` URL in `@context` is a JSON string value, not a network request

## 4. Crawlability & Sitemap

| Concern | Approach |
| --- | --- |
| SSR content | All public pages render in Blade → full HTML in initial response |
| Livewire islands | Keep SEO-critical copy outside `wire:` dynamic regions |
| Sitemap | Laravel route scan → `sitemap.xml` (self-hosted) |
| Robots | `robots.txt` shipped in public root; no external crawler service |

### 4.1 SSR vs Livewire Split

GsmUi pages fall into two categories for SEO purposes:

**Fully SSR (Blade-only):**
- Marketing homepage
- Pricing page
- About page
- Blog posts
- Error pages (404, 500)
- Template showcase pages
- Component documentation (read-only pages)

These pages render complete HTML in the initial Blade response. No JavaScript is required to see the content. Crawlers index them fully.

**Livewire Islands (interactive regions within SSR shell):**
- Search interface
- Comment sections
- Live data tables
- Form submissions
- Dashboard widgets
- Theme builder
- Playground

These pages have an SSR-rendered shell (header, footer, SEO-critical content) with Livewire-powered interactive regions. The SEO-critical content (title, description, body text) is outside the `wire:` regions.

### 4.2 Livewire Crawlability Rules

For pages with Livewire interactive regions:

1. **Never** put critical page content inside `wire:id` elements — crawlers may not execute JavaScript
2. **Always** provide a server-rendered fallback for content that should be indexed
3. **Use `wire:initial`** to show default content before Livewire hydrates
4. **Keep navigation links outside Livewire** — the main nav must be static HTML

```blade
{{-- Good: SSR content outside Livewire --}}
<h1>{{ $post->title }}</h1>
<p>{{ $post->excerpt }}</p>

{{-- Livewire handles comments, but the article body is static --}}
<article>{!! $post->body !!}</article>

<div wire:id="comments-section">
  {{-- Comments load via Livewire, but the heading is static --}}
  <h2>Comments</h2>
  @livewire('comments', ['postId' => $post->id])
</div>
```

### 4.3 Sitemap Generation

GsmUi generates `sitemap.xml` using a dedicated artisan command that scans all public routes:

```php
// app/Console/Commands/GenerateSitemap.php
class GenerateSitemap extends Command
{
    protected $signature = 'gsmui:sitemap';

    public function handle(): void
    {
        $urls = $this->collectUrls();
        $xml = $this->buildXml($urls);
        file_put_contents(public_path('sitemap.xml'), $xml);
    }

    private function collectUrls(): Collection
    {
        return collect()
            ->merge($this->getMarketingRoutes())
            ->merge($this->getDocsRoutes())
            ->merge($this->getBlogRoutes())
            ->merge($this->getTemplateRoutes())
            ->merge($this->getComponentDocRoutes())
            ->filter(fn($url) => !$url['noindex']);
    }
}
```

The sitemap includes:

| Page Type | Change Frequency | Priority |
| --- | --- | --- |
| Homepage | weekly | 1.0 |
| Component docs | monthly | 0.9 |
| Blog posts | monthly | 0.8 |
| Template pages | monthly | 0.7 |
| Pricing | monthly | 0.6 |
| About | yearly | 0.3 |
| Error pages | excluded | excluded |

### 4.4 Sitemap XML Structure

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9"
        xmlns:xhtml="http://www.w3.org/1999/xhtml">
  <url>
    <loc>https://gsmui.dev/</loc>
    <lastmod>2026-07-01</lastmod>
    <changefreq>weekly</changefreq>
    <priority>1.0</priority>
    <xhtml:link rel="alternate" hreflang="en" href="https://gsmui.dev/" />
    <xhtml:link rel="alternate" hreflang="ar" href="https://gsmui.dev/ar/" />
  </url>
</urlset>
```

### 4.5 Sitemap Index

If the sitemap exceeds 50,000 URLs or 50MB, split into a sitemap index:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <sitemap>
    <loc>https://gsmui.dev/sitemap-marketing.xml</loc>
    <lastmod>2026-07-01</lastmod>
  </sitemap>
  <sitemap>
    <loc>https://gsmui.dev/sitemap-docs.xml</loc>
    <lastmod>2026-07-01</lastmod>
  </sitemap>
  <sitemap>
    <loc>https://gsmui.dev/sitemap-blog.xml</loc>
    <lastmod>2026-07-01</lastmod>
  </sitemap>
</sitemapindex>
```

The `robots.txt` file is served from `public/robots.txt`:

### 4.7 Canonical URLs

Every page declares its canonical URL to prevent duplicate content issues:

```html
<link rel="canonical" href="{{ url()->current() }}">
```

For pages accessible at multiple URLs (e.g., with/without trailing slash, with query parameters), the canonical URL is normalized:

```blade
<link rel="canonical" href="{{ Str::_finish(url()->current(), '/') }}">
```

Pagination pages use the current page as canonical:

```blade
@if($currentPage > 1)
  <link rel="canonical" href="{{ url()->current() }}?page={{ $currentPage }}">
@else
  <link rel="canonical" href="{{ url()->current() }}">
@endif
```

### 4.8 Pagination SEO

Paginated content uses `rel="prev"` and `rel="next"` link elements:

```blade
@if($currentPage > 1)
  <link rel="prev" href="{{ url()->current() }}?page={{ $currentPage - 1 }}">
@endif
@if($currentPage < $lastPage)
  <link rel="next" href="{{ url()->current() }}?page={{ $currentPage + 1 }}">
@endif
```

## 5. CSP-Safe SEO

- No analytics `<script src="https://...">` (would require `script-src` relax + network). Use first-party, self-hosted, or omit.
- Icons/og-images: inline SVG or same-origin `img-src 'self' data:` only.

### 5.1 Analytics Without External Scripts

GsmUi does NOT use Google Analytics, Mixpanel, Amplitude, or any external analytics service. Instead, it uses a first-party analytics approach:

1. **Server-side log analytics:** Apache/Nginx access logs are processed by a first-party script
2. **Livewire-based event tracking:** User interactions are sent to a first-party `/api/analytics` endpoint (covered by `connect-src 'self'`)
3. **No cookies from external domains:** All tracking uses first-party cookies only

```blade
{{-- First-party analytics — CSP-safe --}}
<script>
  document.addEventListener('click', function(e) {
    var el = e.target.closest('[data-track]');
    if (el) {
      fetch('/api/analytics/event', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
          event: el.dataset.track,
          path: window.location.pathname,
          timestamp: Date.now(),
        }),
      });
    }
  });
</script>
```

This approach:
- Stays within `script-src 'self'`
- Stays within `connect-src 'self'`
- Requires no external scripts or pixels
- Provides equivalent insight to third-party analytics

### 5.2 Self-Hosted Fonts and Assets

GsmUi uses system fonts exclusively — no `@font-face`, no Google Fonts, no CDN-hosted typefaces. This means:

- No `font-src` CSP directive needed
- No render-blocking font downloads
- No FOUT/FOIT layout shift
- Faster initial paint (font display is instant with system fonts)

### 5.3 Image SEO

All images on GsmUi pages follow these rules:

| Rule | Implementation |
| --- | ---|
| Descriptive `alt` text | `alt="{{ $component }} component preview"` |
| Consistent dimensions | `width` and `height` attributes on all `<img>` tags |
| Modern formats | WebP/AVIF via `<picture>` when supported, PNG fallback |
| Lazy loading | `loading="lazy"` on below-fold images |
| Self-hosted | All images in `public/images/` — no CDN |

```blade
<picture>
  <source srcset="{{ $imageWebp }}" type="image/webp">
  <img
    src="{{ $imagePng }}"
    alt="{{ $altText }}"
    width="{{ $width }}"
    height="{{ $height }}"
    loading="{{ $eager ? 'eager' : 'lazy' }}"
    decoding="async"
  >
</picture>
```

### 5.4 Performance as SEO Signal

Core Web Vitals directly impact search rankings. GsmUi addresses these:

| Metric | Target | Implementation |
| --- | --- | --- |
| LCP | < 2.5s | SSR, system fonts, self-hosted assets, `<link rel="preload">` |
| FID | < 100ms | `defer` on all scripts, minimal JS execution on load |
| CLS | < 0.1 | Explicit `width`/`height` on images, `font-display: swap` (not needed with system fonts) |
| INP | < 200ms | Efficient event handlers, `requestAnimationFrame` for animations |

See `08.46-performance.md` for the full performance architecture.

## 6. Hreflang and Multi-Locale SEO

When GsmUi ships content in multiple locales (per `08.45-internationalization.md`), each locale-specific page includes `hreflang` link elements:

```blade
@if(count(config('gsmui.locales', [])) > 1)
  @foreach(config('gsmui.locales') as $locale => $localeName)
    <link
      rel="alternate"
      hreflang="{{ str_replace('_', '-', $locale) }}"
      href="{{ url($locale . '/' . $relativePath) }}"
    >
  @endforeach
  <link rel="alternate" hreflang="x-default" href="{{ url('/' . $relativePath) }}">
@endif
```

### 6.1 Hreflang Rules

1. Every locale page must reference all other locales including itself
2. The `x-default` hreflang points to the default locale (English)
3. Hreflang URLs must be absolute
4. Bidirectional linking: if page A links to page B's locale, page B must link back to page A's locale
5. Hreflang keys use ISO 639-1 codes with optional region subtags (e.g., `en`, `ar`, `pt-BR`)

### 6.2 Locale URL Structure

GsmUi uses the prefix-based locale URL structure:

| Pattern | Example |
| --- | --- |
| Default locale | `/components/date-picker` |
| Localized | `/ar/components/date-picker` |
| Localized with region | `/pt-BR/components/date-picker` |

The default locale does NOT have a prefix — it uses the bare URL. This keeps the primary locale URLs clean and short.

### 6.3 Locale Detection

Locale detection follows this priority:

1. URL prefix (`/ar/...`)
2. User preference (stored in profile)
3. `Accept-Language` header
4. Default locale (English)

Detection happens server-side in middleware, NOT via JavaScript — crawlers must see the correct locale in the initial HTML response.

The documentation portal (`08.23-documentation-ui.md`) has specific SEO requirements:

### 7.1 Component Documentation Pages

Each component has a dedicated documentation page that must be indexable:

```blade
@verbatim

@endverbatim
```

### 7.2 Docs Internal Linking

Documentation pages cross-link to related components, guides, and API references:

### 10.3 Error Page SEO Rules

1. Always return the correct HTTP status code (404, 500, etc.)
2. Always include `<meta name="robots" content="noindex">` on error pages
3. Never redirect error pages to the homepage (bad for crawlers and users)
4. Include a link to the homepage for user recovery
5. Keep the page lightweight — no heavy JS or CSS bundles

## 11. Image and Media SEO

### 11.1 Image Optimization Pipeline

All images pass through an optimization pipeline before deployment:

1. **Source images** are stored in `resources/images/` (not committed to production)
2. **Build step** generates optimized variants: WebP, AVIF, multiple sizes
3. **Output images** are placed in `public/images/` with content-hash filenames
4. **Blade references** use the hashed filenames for cache-busting

```blade
<img
  src="{{ Vite::asset('resources/images/hero.webp') }}"
  alt="GsmUi component library"
  width="1200"
  height="630"
  loading="eager"
  fetchpriority="high"
>
```

### 11.2 SVG Icons

All icons are inline SVG — no external icon font files, no CDN-hosted icon libraries:

```blade
{{-- Inline SVG icon, CSP-safe --}}
<svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2">
  <path d="M12 2L2 7l10 5 10-5-10-5z"/>
  <path d="M2 17l10 5 10-5"/>
  <path d="M2 12l10 5 10-5"/>
</svg>
```

SVG icons are:
- CSP-safe (no external resource loading)
- Accessible (wrapped in `<span role="img" aria-label="...">` when semantic meaning needed)
- Performant (no font file download, no FOUT)
- SEO-neutral (no text content for crawlers)

### 11.3 Video Content

If GsmUi pages include video content (tutorials, demos):

1. Self-host videos in `public/videos/` — no YouTube/Vimeo embeds (would require external scripts)
2. Use native `<video>` element with poster image
3. Include `<track>` element for captions (accessibility + SEO)
4. Generate a video thumbnail for OG image


## 12. Mobile SEO

### 12.1 Mobile-First Indexing

Google uses mobile-first indexing — the mobile version of a page is the primary version for ranking. GsmUi ensures:

1. All content is visible on mobile (no hidden content on small screens)
2. Same structured data on mobile and desktop
3. Same meta tags on mobile and desktop
4. Responsive images via `<picture>` and `srcset`
5. Touch-friendly tap targets (minimum 44×44px per WCAG 2.5.8)

### 12.2 Responsive Image Strategy

```blade
<picture>
  <source media="(min-width: 1024px)" srcset="{{ $imageLg }}">
  <source media="(min-width: 640px)" srcset="{{ $imageMd }}">
  <img src="{{ $imageSm }}" alt="{{ $alt }}" width="{{ $width }}" height="{{ $height }}">
</picture>
```

### 12.3 Mobile Viewport

The viewport meta is set to allow user scaling (accessibility requirement):

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

Never set `maximum-scale=1` or `user-scalable=no` — these violate WCAG 1.4.4 and harm mobile SEO.

### 16.2 Slug Generation

Models use slugs for human-readable, SEO-friendly URLs:

```php

{
    static::creating(function (Post $post) {
        $post->slug = Str::slug($post->title);
    });
}
```

### 16.3 URL Redirects

When URLs change, permanent redirects (301) preserve SEO equity:

```php
Route::redirect('/old-path', '/new-path', 301);
```

For dynamic redirects (e.g., renamed components):

```php
Route::get('/components/{oldSlug}', function ($oldSlug) {
    $newSlug = Component::where('old_slug', $oldSlug)->value('slug');
    if ($newSlug) {
        return redirect("/components/{$newSlug}", 301);
    }
    abort(404);
});
```

## 18. Open Questions / Risks

- **Livewire SEO split:** confirm which routes are fully Blade (Folio) vs Livewire islands, so crawlable copy is never inside a `wire:` region.
- **Hreflang:** if multi-locale docs ship, add `hreflang` link tags; coordinate key format with `08.45`.
- **Dynamic structured data:** if any structured data requires user-specific content (e.g., personalized pricing), ensure it is only on `noindex` pages.
- **Video SEO:** if tutorial videos are added, decide between self-hosted (CSP-safe) vs external platform (requires CSP relaxation).
- **A/B testing:** any A/B testing must be server-side — client-side testing tools would violate CSP.
- **Social login:** OAuth flows for social login require external redirects but no frontend CSP changes.

## 19. Content Strategy for SEO

### 19.1 Keyword Research Integration

GsmUi's content pages should be informed by keyword research. The documentation and blog sections target specific search intents:

| Content Type | Search Intent | Target Keywords |
| --- | --- | --- |
| Component docs | Informational | `{component} laravel`, `laravel {component} component` |
| Blog posts | Informational | `laravel livewire best practices`, `tailwind css components` |
| Templates | Transactional | `laravel admin template`, `livewire dashboard template` |
| Getting started | Informational | `laravel ui library`, `laravel component library` |
| Changelog | Navigational | `gsmui changelog`, `gsmui updates` |

### 19.2 Content Length Guidelines

| Page Type | Minimum Words | Ideal Words |
| --- | --- | --- |
| Component doc | 300 | 800–1200 |
| Blog post | 800 | 1500–2500 |
| Getting started guide | 500 | 1000–1500 |
| Template description | 100 | 200–400 |
| API reference | 200 | 500–800 |

### 19.3 Heading Hierarchy

Every public page follows a strict heading hierarchy:

```html
<h1>Page Title (exactly one per page)</h1>
  <h2>Major Section</h2>
    <h3>Subsection</h3>
      <h4>Detail</h4>
```

Rules:
1. Exactly one `<h1>` per page
2. No skipped levels (h2 → h4 is forbidden)
3. Headings describe content, not style
4. Headings include target keywords naturally

### 19.4 Internal Linking Strategy

GsmUi's internal linking follows a hub-and-spoke model:

- **Hub pages:** Component index, Blog index, Template index — link to all spoke pages
- **Spoke pages:** Individual component docs, blog posts, template details — link back to hub and to related spokes
- **Cross-links:** Related components link to each other (e.g., date-picker links to time-picker)

```blade
{{-- Cross-linking component docs --}}
<div class="see-also">
  <h3>See Also</h3>
  <ul>
    <li><a href="/components/input">Input</a> — single-line text entry</li>
    <li><a href="/components/select">Select</a> — dropdown selection</li>
    <li><a href="/docs/forms">Forms Guide</a> — building forms with GsmUi</li>
  </ul>
</div>
```

### 19.5 Content Freshness

Search engines favor fresh content. GsmUi signals freshness through:

1. **`<lastmod>` in sitemap** — updated when page content changes
2. **`dateModified` in structured data** — matches the last content edit
3. **Changelog entries** — new entries signal active development
4. **Blog publishing cadence** — regular posts signal active maintenance

## 34. SEO for Livewire Full-Page Components

For Livewire components that occupy a full page (not just an island), SEO considerations include:

1. **Render initial content in Blade** — the Livewire component's initial render should include all SEO-critical HTML
2. **Use `wire:init` for progressive enhancement** — load additional content after the initial render
3. **Avoid `wire:ignore` on SEO-critical content** — crawlers need to see the full content

```blade
{{-- Full-page Livewire component with SEO-safe initial render --}}
<title>{{ $pageTitle }}</title>
<meta name="description" content="{{ $pageDescription }}">

<h1>{{ $pageTitle }}</h1>

{{-- SEO-critical content rendered in Blade --}}
<div class="content">
  {!! $pageBody !!}
</div>

{{-- Interactive region uses Livewire --}}
@livewire('interactive-widget', ['id' => $pageId])
```

## 35. SEO for SPA-like Behavior

When GsmUi uses Turbolinks or similar for SPA-like page transitions:

1. **Server-side rendering is the primary** — every URL must return full HTML
2. **Client-side navigation is progressive enhancement** — not required for content access
3. **`<title>` updates happen on the client** — but the server-rendered title is the SEO source
4. **History API updates** — `pushState` URLs must match the server-side routes

```javascript
// Client-side title update for SPA navigation (progressive enhancement)
document.addEventListener('turbolinks:load', function() {
  var title = document.querySelector('[data-page-title]');
  if (title) {
    document.title = title.dataset.pageTitle;
  }
});
```

## 36. SEO Performance Budget

| Metric | Budget | Enforcement |
| --- | --- | --- |
| HTML document size | < 50KB | Build-time check |
| Number of `<link>` tags | < 10 | Lint rule |
| Number of `<script type="application/ld+json">` | < 5 | Lint rule |
| Title tag length | 30–60 chars | Render-time warning in dev |
| Meta description length | 120–160 chars | Render-time warning in dev |
| Image `alt` attribute | Required on all `<img>` | Lint rule |
| Internal links per page | > 2 | Content guideline |
| External links per page | 0 (CSP constraint) | Automated check |

## 37. SEO Migration Guide

When restructuring URLs or content:

1. **Map old URLs to new URLs** — create a redirect map
2. **Implement 301 redirects** — permanent redirects preserve SEO equity
3. **Update the sitemap** — remove old URLs, add new URLs
4. **Update internal links** — change all internal references to new URLs
5. **Monitor crawl errors** — watch Google Search Console for 404s
6. **Keep old content accessible** — redirect, don't delete

```php
// SEO migration redirects
Route::prefix('old-docs')->group(function () {
    Route::redirect('/input', '/components/input', 301);
    Route::redirect('/select', '/components/select', 301);
    // ... all old component URLs
});
```
