# 08.09 - Alpine.js Architecture

**Project:** GsmUi
**Section:** 08 - Frontend Architecture
**Framework:** Alpine.js · Livewire 4 · GsmUi Component Library
**Version:** 1.0.0

---

> See also: `08.08-livewire-architecture.md` (Livewire integration), `08.10-javascript-architecture.md` (GsmUi JS mixins), `07.57-security.md` (CSP). This document specifies the *Alpine.js usage boundary* and does NOT re-document Livewire lifecycle.

# Purpose

AGENTS.md states Alpine should be *rarely* used in GsmUi — only when reasonably necessary. This document makes that boundary unambiguous: where Alpine is allowed, the `x-data` patterns to follow, how it may (and may not) interact with GsmUi JS, and the explicit cases where it is forbidden. It prevents the dual-state bugs that arise from mixing Alpine reactivity with GsmUi's own mixin system.

---

## 1. When Alpine Is Allowed

| Allowed | Condition |
| --- | --- |
| Tiny presentational toggle | A pure UI show/hide with no GsmUi component state involved |
| Folio marketing page micro-interaction | No `gsmui:` component owns the state |
| One-off DOM utility | E.g. copy-to-clipboard on a non-component element |

Rule of thumb: if a `gsmui:` component is involved, Alpine is **not** the tool — use the component's JS mixin.

---

## 2. When Alpine Is Forbidden

| Forbidden case | Reason |
| --- | --- |
| Driving `gsmui:` component state | GsmUi owns its state via mixins; Alpine would create a second source of truth |
| Replacing `wire:model` | Livewire 4 is the binding layer (`08.08-livewire-architecture.md`) |
| Popover/modal open state | Handled by GsmUi Controllable/Disableable mixins |
| Any `eval`-like expression | CSP forbids `eval()`/`Function()` (AGENTS.md §CSP) |

---

## 3. `x-data` Patterns (Allowed Cases)

When Alpine is genuinely needed, follow minimal patterns:

```html
<div x-data="{ open: false }" x-cloak>
  <button @click="open = !open" :aria-expanded="open">Toggle</button>
  <div x-show="open">Panel</div>
</div>
```

| Rule | Why |
| --- | --- |
| Inline `x-data` object only | No external Alpine component classes |
| No `x-init` logic that touches GsmUi | Avoid sync races |
| `x-cloak` + CSS to hide pre-hydration | Prevent flash |
| No `x-html` with remote content | CSP / XSS safety (`07.57-security.md`) |

---

## 4. Interplay with GsmUi JS

GsmUi JS is framework-agnostic vanilla JS (see `08.10-javascript-architecture.md`). The boundary:

```text
Alpine  ──(DOM events only, e.g. CustomEvent)──▶ GsmUi component
GsmUi   ──(setAttribute / dispatched events)──▶ Alpine (read-only)
```

- Alpine may *listen* to GsmUi-dispatched DOM events; it must not *mutate* GsmUi internal state.
- GsmUi components must not depend on Alpine being present. They are standalone.

---

## 5. CSP Compatibility

Alpine itself is self-hosted (no CDN). Ensure:

- `script-src 'self'` covers the Alpine bundle.
- No `Function()`/`eval()` in `x-` expressions (Alpine's `x-text`/`x-bind` are safe; `x-html` with dynamic content is not).
- Verification via Playwright on `tests/Browser/` matching sibling patterns.

---

## 6. Open Questions / Risks

- **Default posture:** Confirm whether new components should ship with a lint rule banning `x-data` inside `stubs/resources/views/gsmui/*`.
- **Migration:** Audit existing components for accidental Alpine usage that should move to mixins.

## 7. Detailed Alpine Lifecycle

### 7.1 Initialization Order

When Alpine initializes on a page containing GsmUi components, the execution order matters to prevent race conditions:

1. Alpine.js `Alpine.start()` fires — walks the DOM for `x-data` attributes.
2. GsmUi custom element `connectedCallback()` fires — sets up MutationObserver, mixin state, initial render.
3. Alpine's `x-init` fires — any presentational state is set.
4. GsmUi's internal `Controllable` mixin reads the initial `value` attribute pushed by Livewire via `wire:model`.

**Critical rule:** GsmUi custom elements MUST NOT depend on Alpine being present. If Alpine is removed, every GsmUi component must function identically. This is enforced by the standalone mixin system (`08.10-javascript-architecture.md`).

### 7.2 Hydration Flash Prevention

Alpine uses `x-cloak` to hide elements before hydration. GsmUi uses a parallel strategy:

```css
[x-cloak] { display: none !important; }
[data-gsmui-cloak] { display: none !important; }
```

- `x-cloak` is Alpine's standard — applied to Alpine-only micro-interactions.
- `data-gsmui-cloak` is GsmUi's — applied to custom elements before their `connectedCallback` fires.
- Both are removed immediately after their respective initialization completes.

### 7.3 Event Loop Discipline

Alpine's reactivity loop and GsmUi's MutationObserver must not cascade:

```text
❌ BAD:  Alpine x-set → Gsmui setAttribute → MutationObserver → Alpine x-effect → ...
✅ GOOD: Alpine x-set → DOM update (Alpine-owned) — OR — Gsmui mixin → setAttribute → MutationObserver (GsmUi-owned)
```

The boundary is absolute: Alpine owns its reactive tree, GsmUi owns its mixin state. They communicate only through DOM events (CustomEvent), never through shared reactive variables.

## 8. Alpine Patterns by Use Case

### 8.1 Marketing Page Micro-Interactions

Folio marketing pages may use Alpine for purely presentational toggles that no GsmUi component handles:

```html
<section x-data="{ visible: false }" x-intersect:enter="visible = true">
  <div x-show="visible" x-transition.opacity.duration.500ms
       class="opacity-0" :class="{ 'opacity-100': visible }">
    <h2>Feature Section</h2>
  </div>
</section>
```

Rules:
- No `gsmui:` components are children of this Alpine scope.
- The `visible` boolean is purely presentational — it does not affect any component state.
- Scroll-triggered reveals use `x-intersect` (Alpine Intersect plugin) which is self-hosted and CSP-safe.

### 8.2 Copy-to-Clipboard on Non-Component Elements

When a plain HTML element needs copy functionality (not inside a `gsmui:input`):

```html
<div x-data="{ copied: false }">
  <code>const x = 1;</code>
  <button @click="
    navigator.clipboard.writeText('const x = 1;');
    copied = true;
    setTimeout(() => copied = false, 2000);
  ">
    <span x-show="!copied">Copy</span>
    <span x-show="copied">Copied!</span>
  </button>
</div>
```

Rules:
- Uses `navigator.clipboard` API — no `execCommand` polyfill (AGENTS.md: dead polyfills are a liability).
- The `copied` state is purely visual feedback; no component state is affected.
- If this pattern is needed inside a `gsmui:input`, use the built-in `copyable` prop instead.

### 8.3 Dropdown Menus (Non-Component)

A simple dropdown that is NOT a `gsmui:select` or `gsmui:navmenu`:

```html
<div x-data="{ open: false }" @click.outside="open = false" @keydown.escape="open = false">
  <button @click="open = !open" :aria-expanded="open" aria-haspopup="true">
    Options
  </button>
  <div x-show="open" x-transition
       role="menu" class="absolute mt-1 bg-white dark:bg-zinc-800 border rounded-lg shadow-xl">
    <a href="#" role="menuitem" class="block px-4 py-2 text-sm">Item 1</a>
    <a href="#" role="menuitem" class="block px-4 py-2 text-sm">Item 2</a>
  </div>
</div>
```

Rules:
- Must include `@keydown.escape` to close — keyboard accessibility requirement.
- Must include `@click.outside` to close — prevents "stuck open" state.
- Uses ARIA `role="menu"` and `role="menuitem"` per APG Menu pattern.
- If this needs complex selection, search, or form integration → use `gsmui:select` instead.

### 8.4 Notification Banner Dismissal

A dismissible banner that is NOT a `gsmui:alert`:

```html
<div x-data="{ show: true }" x-show="show" x-transition.opacity>
  <p>New features available!</p>
  <button @click="show = false" aria-label="Dismiss notification">×</button>
</div>
```

Rules:
- If this needs theming, icons, action buttons, or wire:model persistence → use `gsmui:alert` instead.
- The dismiss action is permanent for the page session (no server round-trip).

## 10. Lint Rules & Enforcement

### 10.1 ESLint / PHPStan Blade Rules

To enforce the Alpine boundary, the following lint rules should be configured:

```php
// In a custom PHPStan rule or Blade linter:
// FORBID: x-data inside stubs/resources/views/gsmui/<any-component>/
// ALLOW:  x-data inside stubs/resources/views/gsmui/pages/ (Folio marketing)
// ALLOW:  x-data inside resources/views/ (non-component Blade)
```

### 10.2 Playwright Verification

Every page that uses Alpine must be tested with Playwright:

```javascript
// tests/Browser/alpine-boundary.spec.js
test('no x-data inside gsmui component views', async ({ page }) => {
  const gsmuiComponentViews = await page.locator('[data-gsmui-component] [x-data]').count();
  expect(gsmuiComponentViews).toBe(0);
});
```

### 10.3 Migration Checklist

When auditing existing components for accidental Alpine usage:

1. `grep -r "x-data" stubs/resources/views/gsmui/` — find all Alpine usage.
2. Classify each usage:
   - Inside a component directory (`gsmui/input/`, `gsmui/modal/`, etc.) → **must migrate to mixin**.
   - Inside a page/layout directory → **acceptable if it follows section 8 patterns**.
3. For each migration, identify the equivalent GsmUi mixin:
   - Toggle → `Controllable` mixin.
   - Visibility → `data-open` attribute + CSS.
   - Form binding → `wire:model` via Livewire.

## 11. Testing Strategy

### 11.1 Unit Tests for Alpine-Only Code

Alpine-only code (marketing pages) does not get Playwright component tests. It gets:
- Visual regression screenshots at defined breakpoints.
- Keyboard navigation verification (Escape closes, Tab moves focus).

### 11.2 Integration Tests for Hybrid Pages

Pages that combine GsmUi components with Alpine micro-interactions:
- Verify GsmUi components work with Alpine removed (simulate `window.Alpine = undefined`).
- Verify no sync loops (monitor MutationObserver callback count during interaction).

### 11.3 CSP Compliance Tests

```javascript
// Verify no eval() in Alpine expressions
test('Alpine expressions are CSP-safe', async ({ page }) => {
  const violations = await page.evaluate(() => {
    // Monitor for eval calls during Alpine initialization
    let evalCount = 0;
    const origEval = window.eval;
    window.eval = () => { evalCount++; return origEval.apply(this, arguments); };
    // Trigger Alpine re-init
    window.Alpine?.start();
    return evalCount;
  });
  expect(violations).toBe(0);
});
```

## 12. Common Anti-Patterns

### 12.1 Alpine Driving Component State

```html
<!-- ❌ WRONG: Alpine owns the open state of a gsmui:popover -->
<div x-data="{ open: false }">
  <gsmui:popover :open="open">
```

**Fix:** Use `gsmui:popover`'s built-in `Controllable` mixin. The popover manages its own open state via `data-open` attribute.

### 12.2 Alpine Replacing wire:model

```html
<!-- ❌ WRONG: Alpine two-way binding instead of Livewire -->
<input x-model="form.email" @input="save()">
```

**Fix:** Use `wire:model="form.email"` — Livewire is the binding layer.

### 12.3 Alpine with Remote Content

```html
<!-- ❌ WRONG: x-html with fetched content — CSP XSS risk -->
<div x-html="await fetch('/api/content').then(r => r.text())"></div>
```

**Fix:** Use Livewire's HTML response or Blade components. Never inject remote content via Alpine.

### 12.4 Alpine Animating GsmUi Components

```html
<!-- ❌ WRONG: Alpine transitions on a gsmui:modal -->
<div x-data="{ show: false }">
  <gsmui:modal x-show="show" x-transition>
```

**Fix:** Use `gsmui:modal`'s built-in transition system which respects `prefers-reduced-motion` and follows the Motion & Animation Layer (`08.15-animation-system.md`).

### 12.5 Alpine Event Handlers on Custom Elements

```html
<!-- ❌ WRONG: Alpine @click on a gsmui custom element -->
<gsmui:button @click="handleClick()">
```

**Fix:** Use Livewire's `wire:click` or the component's own event system. Alpine event handlers on custom elements may fire before the element's `connectedCallback` completes.

## 13. Performance Considerations

### 13.1 Alpine Bundle Size

Alpine.js adds approximately 15KB gzipped to the page. This is acceptable for marketing/Folio pages but should NOT be loaded on pages that only use GsmUi components.

```blade
{{-- Only load Alpine on marketing pages --}}
@stack('alpine-scripts')
@section('alpine')
    <script defer src="{{ mix('vendor/alpine.js') }}"></script>
@endsection
```

### 13.2 Initialization Performance

Alpine scans the entire DOM on `start()`. On pages with many GsmUi components, this adds measurable time:

| Page type | Expected Alpine init time | Acceptable? |
| --- | --- | --- |
| Marketing (5-10 Alpine scopes) | < 5ms | ✅ |
| Dashboard (0 Alpine scopes) | 0ms | ✅ |
| Hybrid (2-3 Alpine + 20 GsmUi components) | < 10ms | ✅ |
| Worst case (50+ Alpine scopes) | > 50ms | ❌ — migrate to mixins |

### 13.3 MutationObserver Overhead

When Alpine and GsmUi both observe DOM mutations on the same subtree, performance degrades:

```text
Alpine reactivity → DOM mutation → GsmUi MutationObserver fires → setAttribute → Alpine reactivity fires again
```

This is the "dual-state bug" that section 4 (Interplay) prevents. The fix is architectural: never let both systems own the same DOM subtree.

---

## 14. Accessibility Implications

### 14.1 Alpine and Focus Management

Alpine's `x-trap` (from `@alpinejs/focus`) should NOT be used when a GsmUi component already manages focus:

- `gsmui:modal` traps focus via its own JS mixin.
- `gsmui:drawer` traps focus via the same pattern.
- Using both Alpine trap and GsmUi trap simultaneously causes focus to "double-lock" — Tab key becomes unusable.

### 14.2 Alpine and aria-attributes

Alpine can SET aria-attributes (e.g. `:aria-expanded="open"`), but it must not OVERRIDE attributes set by GsmUi components:

```html
<!-- ❌ WRONG: Alpine overrides GsmUi's aria-expanded -->
<gsmui:select :aria-expanded="open">
```

Alpine should only control aria on elements it owns (non-GsmUi elements).

### 14.3 Alpine and Reduced Motion

Alpine's `x-transition` respects `prefers-reduced-motion` via CSS — the same global rule in `08.15-animation-system.md` neutralizes Alpine transitions. No extra configuration is needed.

## 15. Debugging Guide

### 15.1 Identifying Alpine vs GsmUi Issues

When a bug occurs in a hybrid page:

1. **Disable Alpine** (`window.Alpine = undefined` before page load) — does the bug persist?
   - Yes → GsmUi issue, debug via `08.10-javascript-architecture.md`.
   - No → Alpine issue, debug Alpine's reactive tree.

2. **Check MutationObserver count** — if observers are firing > 100 times per interaction, there is likely a sync loop between Alpine and GsmUi.

3. **Inspect the DOM** — look for duplicate attributes (e.g. two `aria-expanded` attributes on the same element). This indicates both Alpine and GsmUi are trying to control the same attribute.

### 15.2 Common Error Messages

| Error | Cause | Fix |
| --- | --- | --- |
| `Cannot read property 'start' of undefined` | Alpine not loaded | Ensure Alpine script is included on the page |
| `MutationObserver loop limit exceeded` | Sync loop between Alpine and GsmUi | Remove Alpine from GsmUi component scope |
| `x-cloak not removing` | Alpine not initialized | Check for JS errors before Alpine.start() |

## 16. Future Considerations

### 16.1 Alpine Removal

If GsmUi's component library matures to cover all marketing page needs, Alpine could be removed entirely. The migration path:

1. Replace `x-show` with CSS `not-data-open:hidden` (GsmUi pattern).
2. Replace `x-transition` with GsmUi's Motion & Animation Layer.
3. Replace `x-model` with `wire:model`.
4. Replace `x-on:*` with native event listeners in component JS.

### 16.2 Alpine v4 Compatibility

If Alpine releases a v4 with breaking changes:
- GsmUi components are NOT affected (they don't depend on Alpine).
- Marketing pages using Alpine will need migration — but these are low-coupling, high-isolation pages.

### 16.3 Server-Driven Alpine Configuration

A future enhancement could allow Laravel to ship Alpine configuration from the server:

```blade
<script>
  document.addEventListener('alpine:init', () => {
    Alpine.data('marketingBanner', () => ({
      open: @js($banner->defaultOpen),
      timeout: @js($banner->autoCloseMs),
    }));
  });
</script>
```

This remains CSP-safe (no eval, no remote content) and keeps Alpine as a presentational tool, not a state management tool.

## 17. Alpine.js Reactivity Model

### 17.1 How Alpine Reactivity Works

Alpine's reactivity is based on JavaScript Proxies (or `Object.defineProperty` fallback). When `x-data` is evaluated, Alpine wraps the data object in a reactive proxy:

```html
<div x-data="{ count: 0 }">
  <span x-text="count"></span>
  <button @click="count++">Increment</button>
</div>
```

Alpine creates a reactive scope for the `<div>`. Any child element reading `count` via `x-text` is automatically notified when `count` changes. This is a fine-grained reactive system — only the specific DOM node reading `count` updates, not the entire subtree.

### 17.2 Why This Matters for GsmUi

GsmUi components use MutationObserver (not Alpine's reactivity) for state management. The critical distinction:

| System | Reactivity mechanism | State ownership |
| --- | --- | --- |
| Alpine.js | Proxy-based, automatic DOM diffing | Local to `x-data` scope |
| GsmUi | MutationObserver on attributes | Shared between Blade/Livewire and JS |

When both systems operate on the same DOM subtree, they can conflict:

```text
Alpine sets x-data.count → Alpine updates x-text DOM
GsmUi sets value attr → MutationObserver fires → GsmUi re-renders
If both touch the same element → unpredictable final state
```

### 17.3 Safe Coexistence Pattern

The only safe coexistence pattern is **complete DOM separation**:

```blade
{{-- Alpine owns this subtree --}}
<div x-data="{ show: true }">
  <button @click="show = !show">Toggle</button>
  <div x-show="show">Alpine content</div>
</div>

{{-- GsmUi owns this subtree --}}
<gsmui:select wire:model="selected">
    <option value="a">A</option>
</gsmui:select>
```

The two subtrees must never overlap — no Alpine `x-data` ancestor of a `gsmui:` component.

### 17.4 Proxy Traps and Performance

Alpine's Proxy intercepts property access (get) and mutation (set). On each set:

1. Alpine marks the reactive property as "dirty."
2. Alpine schedules a micro-task to re-evaluate all `x-text`, `x-bind`, etc. expressions that read the dirty property.
3. DOM is patched only where expressions changed.

This is efficient for small scopes (5-10 reactive properties) but degrades with many nested scopes — hence the "max 50 Alpine scopes" performance rule.

## 18. Alpine.js Plugin Architecture

### 18.1 Plugin Loading Order

Alpine plugins must be registered before `Alpine.start()`:

```html
<script defer src="{{ mix('vendor/alpine.js') }}"></script>
<script>
  document.addEventListener('alpine:init', () => {
    Alpine.plugin(AlpineIntersect);
    Alpine.plugin(AlpineCollapse);
    Alpine.plugin(AlpineFocus);
  });
</script>
```

| Order | Plugin | Why this order |
| --- | --- | --- |
| 1st | `intersect` | Needed by scroll-triggered reveals (foundational) |
| 2nd | `collapse` | Used by accordion-like patterns |
| 3rd | `focus` | Only used in rare cases (prefer GsmUi's native focus) |

### 18.2 Plugin Bundle Impact

| Plugin | Size (gzipped) | Load impact |
| --- | --- | --- |
| `@alpinejs/intersect` | ~1.5KB | Minimal |
| `@alpinejs/collapse` | ~1KB | Minimal |
| `@alpinejs/focus` | ~2KB | Minimal |
| All three | ~4.5KB | Acceptable on marketing pages |
| Alpine core | ~15KB | Main cost |

### 18.3 Plugin Conflicts with GsmUi

| Plugin | Potential conflict | Mitigation |
| --- | --- | --- |
| `@alpinejs/focus` | Double focus trap with `gsmui:modal` | Never use `x-trap` inside a GsmUi modal |
| `@alpinejs/collapse` | Height animation conflicts with GsmUi accordion | Use GsmUi accordion, not Alpine collapse |
| `@alpinejs/intersect` | None (safe to use alongside GsmUi) | No mitigation needed |

## 19. Alpine.js State Patterns

### 19.1 Local State (Allowed)

Alpine's local state is safe when confined to a marketing page micro-interaction:

```html
<div x-data="{ activeTab: 'overview' }">
  <nav>
    <button @click="activeTab = 'overview'"
            :class="{ 'font-bold': activeTab === 'overview' }">Overview</button>
    <button @click="activeTab = 'specs'"
            :class="{ 'font-bold': activeTab === 'specs' }">Specs</button>
  </nav>
  <div x-show="activeTab === 'overview'">Overview content</div>
  <div x-show="activeTab === 'specs'">Specs content</div>
</div>
```

**Why this is safe:** No GsmUi component is involved. This is a purely presentational tab switch.

**Why `gsmui:tabs` exists for this:** If this pattern appears alongside GsmUi components, migrate to `gsmui:tabs` for consistency.

### 19.2 Shared State (Forbidden)

```html
<!-- ❌ WRONG: Two Alpine scopes sharing state -->
<div x-data="{ selected: null }">
  <gsmui:select x-model="selected">...</gsmui:select>
  <span x-text="selected"></span>
</div>
```

**Why this is wrong:**
1. `x-model` on a `gsmui:select` custom element attempts two-way binding.
2. GsmUi's `Controllable` mixin also manages `value` via MutationObserver.
3. Both systems fight over the same DOM attribute → sync loop.

### 19.3 State Lifting via CustomEvent (Safe)

When a marketing page needs to react to a GsmUi component's state change:

```blade
{{-- Blade template --}}
<div x-data="{ lastAction: '' }"
     @gsmui:select.window="lastAction = $event.detail.value">

  <gsmui:select wire:model="action">
    <option value="edit">Edit</option>
    <option value="delete">Delete</option>
  </gsmui:select>

  <p x-show="lastAction === 'delete'" class="text-red-500">
    This action cannot be undone.
  </p>
</div>
```

**Why this is safe:**
1. Alpine only **reads** via `@gsmui:select.window` — it never writes to GsmUi state.
2. GsmUi dispatches `gsmui:select` events from its own JS — it never touches Alpine.
3. The communication direction is strictly one-way: GsmUi → Alpine.

### 19.4 State Mapping via Livewire (Preferred)

When both Alpine and GsmUi state are needed, Livewire is the mediator:

```blade
<div x-data>
  <gsmui:select wire:model.live="selectedOption">
    <option value="a">Option A</option>
    <option value="b">Option B</option>
  </gsmui:select>

  {{-- Livewire re-renders this section on change --}}
  @if($selectedOption === 'b')
    <p>Option B selected — extra info shown</p>
  @endif
</div>
```

Livewire's `wire:model.live` pushes the value to the server. Blade re-renders the conditional section. Alpine is not involved in state management — it's just the `x-data` container.

## 20. Alpine.js in Marketing Pages

### 20.1 Marketing Page Architecture

Marketing/Folio pages are the primary (and nearly only) legitimate use case for Alpine in GsmUi:

```blade
@extends('layouts.marketing')

@section('content')
  {{-- Hero section — no Alpine needed --}}
  <section class="py-24">
    <h1 class="text-5xl font-bold">{{ __('Welcome') }}</h1>
    <p class="text-xl text-zinc-600">{{ __('Build faster with GsmUi') }}</p>
  </section>

  {{-- Feature section — Alpine for scroll reveal --}}
  <section x-data="{ visible: false }" x-intersect:enter="visible = true"
           class="py-16">
    <div x-show="visible" x-transition.opacity.duration.500ms
         class="opacity-0" :class="{ 'opacity-100': visible }">
      <h2>{{ __('Features') }}</h2>
    </div>
  </section>

  {{-- Pricing section — Alpine for toggle --}}
  <section x-data="{ annual: true }" class="py-16">
    <div class="flex justify-center gap-4 mb-8">
      <button @click="annual = false"
              :class="{ 'font-bold': !annual }">{{ __('Monthly') }}</button>
      <button @click="annual = true"
              :class="{ 'font-bold': annual }">{{ __('Annual') }}</button>
    </div>
    {{-- Pricing cards update based on `annual` --}}
  </section>
@endsection
```

### 20.2 Marketing Page Rules

| Rule | Rationale |
| --- | --- |
| No `gsmui:` components inside `x-data` | Prevents dual-state conflicts |
| Max 3-5 Alpine scopes per page | Performance (section 13.1) |
| All `x-transition` values from approved list | Consistency with GsmUi motion layer |
| Use `__()` for all text | Localization readiness |
| Test without Alpine (`window.Alpine = undefined`) | GsmUi components must work standalone |

### 20.3 Transition from Marketing to App

When a marketing page needs a Gsmui component (e.g., a CTA button):


## 22. Alpine.js Migration Guide

### 22.1 Migrating Alpine State to GsmUi Mixins

When a component accidentally uses Alpine for state that should be managed by GsmUi:

| Alpine pattern | GsmUi equivalent | Migration steps |
| --- | --- | --- |
| `x-data="{ open: false }"` on a popover | `gsmui:popover` with `Controllable` | Remove `x-data`, use `gsmui:popover`'s `data-open` |
| `x-model="value"` on an input | `wire:model="value"` | Replace `x-model` with `wire:model` |
| `x-show="condition"` on a panel | CSS `not-data-open:hidden` | Use component's visibility mechanism |
| `x-on:click="handler()"` | `wire:click="handler"` | Replace Alpine handler with Livewire |
| `x-transition` on a modal | Component's built-in transition | Remove `x-transition`, use modal's default animation |

### 22.2 Step-by-Step Migration Process

1. **Identify the Alpine scope:** Find the `x-data` attribute.
2. **Determine ownership:** Does a `gsmui:` component live inside this scope?
3. **If yes → migrate:**
   a. Remove `x-data` and all `x-*` directives from the GsmUi component.
   b. Use the component's own props/mixins for state.
   c. Use `wire:model` for server-side state.
   d. If presentational state (e.g., tooltip visibility) remains, keep Alpine on non-component elements only.
4. **If no → keep:** Alpine-only marketing interactions are acceptable.
5. **Test:** Run the migration checklist (section 10.3).

### 22.3 Common Migration Pitfalls

| Pitfall | Symptom | Fix |
| --- | --- | --- |
| Removing x-data but leaving x-on | Event handlers silently fail | Convert to `wire:click` or native listeners |
| Leaving x-model on a custom element | Two-way binding fights with Controllable | Use `wire:model` |
| Keeping x-transition on a GsmUi component | Transition conflicts with component's own | Remove `x-transition` |
| Forgetting x-cloak removal | Elements flash visible before Alpine initializes | Ensure component has its own cloak |

## 24. Alpine.js Error Handling

### 24.1 Silent Error Pattern

Alpine expressions that reference undefined variables fail silently (Alpine catches errors internally). This is generally fine for marketing pages but can hide bugs during development:

```html
<!-- This silently fails if 'item' is undefined -->
<div x-text="item.name">Loading...</div>
```

### 24.2 Defensive Expressions

Use optional chaining in Alpine expressions:

```html
<!-- Safe access -->
<span x-text="item?.name ?? 'Unknown'">Loading</span>

<!-- Safe method call -->
<div x-show="items?.length > 0">Items found</div>
```

### 24.3 Alpine Error Events

Alpine dispatches `alpine:init` and `alpine:initialized` events. Errors during initialization are caught and logged to `console.error`:

```javascript
window.addEventListener('alpine:init', () => {
  // Alpine is about to initialize
});

window.addEventListener('alpine:initialized', () => {
  // All x-data scopes are active
});
```

### 24.4 Debugging Alpine

In development, enable Alpine's debug mode:

```javascript
window.Alpine = window.Alpine || {};
window.Alpine.debug = true; // Verbose logging
```

This logs:
- Each `x-data` scope initialization.
- Each reactive property change.
- Each DOM update triggered by reactivity.

Never ship with `debug = true` in production.

## 25. Alpine.js Security Considerations

### 25.1 CSP Compliance Review

Alpine expressions are evaluated using `new Function()` internally. Under strict CSP (`script-src 'self'` without `'unsafe-eval'`), this would fail. However, Alpine v3 uses a technique that avoids `eval()`:

1. Alpine compiles expressions at runtime using `new Function()`.
2. Under CSP without `'unsafe-eval'`, `new Function()` is blocked.
3. **Solution:** GsmUi self-hosts a modified Alpine build that uses an expression compiler compatible with CSP.

### 25.2 Self-Hosted Alpine Build

The GsmUi Alpine bundle (`vendor/alpine.js`) is built from a patched Alpine source that replaces `new Function()` with a CSP-safe expression parser:

```js
// Simplified — actual implementation is in the upstream build
function compileExpression(expression) {
  // CSP-safe: uses a simple property accessor instead of Function constructor
  return (scope) => {
    return new Proxy(scope, {
      get(target, prop) {
        return target[prop];
      }
    })[expression];
  };
}
```

### 25.3 XSS Prevention

Alpine expressions should never render unsanitized HTML:

```html
<!-- ❌ WRONG: XSS vulnerability -->
<div x-html="userContent"></div>

<!-- ✅ SAFE: text content only -->
<div x-text="userContent"></div>
```

`x-text` uses `textContent` (safe). `x-html` uses `innerHTML` (unsafe with user content).

### 25.4 CDN Prevention

Alpine must never be loaded from a CDN:

```html
<!-- ❌ WRONG: CDN loads violate CSP and supply chain security -->
<script src="https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js"></script>

<!-- ✅ CORRECT: Self-hosted -->
<script src="{{ mix('vendor/alpine.js') }}" defer></script>
```

## 26. Alpine.js & Livewire Integration Patterns

### 26.1 Alpine as Livewire's View Layer

In GsmUi, Livewire handles state and server communication, while the view layer (Blade + Alpine) handles presentation. Alpine is only used for presentational logic that Livewire cannot handle:

| Logic type | Handler | Example |
| --- | --- | --- |
| Server state | Livewire | Form data, user data, list items |
| Server mutations | Livewire | Submit form, toggle record |
| Presentational toggle | Alpine | Show/hide tooltip on hover |
| Scroll-triggered reveal | Alpine (intersect) | Fade in section on scroll |
| Form validation | Livewire | Server-side validation errors |

### 26.2 wire:model vs x-model Decision Tree

```text
Does the value need to go to the server?
  → Yes: Use wire:model
  → No: Is it inside a gsmui: component?
    → Yes: Use the component's own state mechanism
    → No: Use Alpine x-model (acceptable for non-component elements)
```

### 26.3 Livewire Wire:Init + Alpine Coordination

When a Livewire component needs to initialize Alpine state:

```blade
<div wire:ignore x-data="{ color: @js($initialColor) }">
    {{-- Alpine manages the color picker interaction --}}
    <div class="color-grid" x-on:click="color = $event.target.dataset.color">
        {{-- Color swatches --}}
    </div>

    {{-- Livewire syncs the final selection --}}
    <input type="hidden" wire:model="selectedColor" :value="color" />
</div>
```

The `wire:ignore` directive prevents Livewire from morphing this subtree, allowing Alpine to manage it independently.

### 26.4 Event Bridge Pattern

```blade
{{-- Livewire dispatches an event --}}
<div wire:dispatch="item-selected" wire:dispatch-item="{{$itemId}}">
    <gsmui:button> {{ __('Select') }} </gsmui:button>
</div>

{{-- Alpine listens for the event (non-component context) --}}
<div x-data @item-selected.window="handleSelection($event.detail)">
    {{-- Presentation logic --}}
</div>
```

Alpine components can communicate via custom DOM events:

```html
        <option value="dark">Dark</option>
    </select>
</div>
```

```html
</div>
```

## 36. Alpine.js Common Pitfalls

### 36.1 Pitfall Reference

| Pitfall | Symptom | Prevention |
| --- | --- | --- |
| Alpine inside GsmUi component | Dual-state bugs | Never use Alpine inside gsmui: components |
| `x-model` on Livewire element | State sync conflict | Use `wire:model` instead |
| Multiple x-data on same element | Unexpected behavior | One `x-data` per scope root |
| MutationObserver loops | Performance degradation | Use `detangle()` pattern |
| Using `x-html` | CSP violation | Use `x-text` instead |
| Forgetting `x-cloak` | Flash of unstyled content | Always add `x-cloak` + CSS rule |
| Nested x-data scopes | Variable shadowing | Keep scopes flat, avoid nesting |
| Alpine on server-rendered content | FOUC on Livewire morph | Use `wire:ignore` |

### 36.2 Pitfall Prevention Checklist

| Step | Action | When |
| --- | --- | --- |
| 1 | Check if a gsmui: component exists for this use case | Before writing any Alpine |
| 2 | Ensure Alpine is only on marketing pages | Every PR |
| 3 | Verify no `x-data` inside gsmui: component views | Every PR |
| 4 | Run CSP check | Before deploy |
| 5 | Check MutationObserver count < 50 | Performance testing |
| 6 | Test with Alpine disabled (`window.Alpine = undefined`) | Regression testing |

## 37. Alpine.js Security Considerations

### 37.1 Security Rules

| Rule | Rationale | Implementation |
| --- | --- | --- |
| Never use `x-html` | XSS vulnerability | Always use `x-text` |
| Sanitize user input | Prevent injection | Server-side validation + escaping |
| No `eval()` | CSP violation | Alpine never uses eval |
| No CDN loading | Supply chain risk | Self-host only |
| No `Function()` constructor | CSP violation | Not used by Alpine |
| Validate `x-effect` side effects | Prevent unintended state changes | Code review |
| Audit `$dispatch` payloads | Prevent data leakage | Sanitize event detail |

### 37.2 CSP Configuration for Alpine

```php
// CSP middleware configuration
'script-src' => [
    "'self'",                          // Self-hosted scripts
    // No 'unsafe-eval' needed (Alpine doesn't use it)
    // No 'unsafe-inline' needed (Alpine uses deferred scripts)
],
```

### 37.3 XSS Prevention Patterns

| Pattern | Safe | Unsafe |
| --- | --- | --- |
| Display user text | `x-text="userInput"` | `x-html="userInput"` |
| Set attribute | `:href="url"` | `:onclick="handler"` |
| Event handler | `@click="doSomething()"` | `@click="eval(code)"` |
| Dynamic class | `:class="condition ? 'a' : 'b'"` | `:class="eval(expr)"` |
| Style binding | `:style="{ color: value }"` | `:style="eval(css)"` |

## 38. Alpine.js Summary

### 38.1 Decision Flowchart

```text
Do I need client-side interactivity?
├── NO → Use static Blade template
└── YES → Is there a gsmui: component?
    ├── YES → Use the component (no Alpine needed)
    └── NO → Is it server-side state?
        ├── YES → Use Livewire (wire:model)
        └── NO → Is it purely presentational?
            ├── YES → Use Alpine (follow section 8 patterns)
            └── NO → Consider creating a gsmui: component
```

### 38.2 Alpine.js in GsmUi - Quick Reference

| Aspect | Guideline |
| --- | --- |
| Where allowed | Marketing pages only |
| Where forbidden | Inside gsmui: component views |
| State management | Alpine handles local UI state |
| Server communication | Livewire (never Alpine fetch) |
| CSS framework | Tailwind CSS utilities |
| JS interaction | GsmUi component JS (not Alpine) |
| CSP compliance | Required (no eval, no CDN) |
| Testing | Playwright browser tests |
| Performance | < 5 Alpine scopes per page |
| Accessibility | GsmUi component (not Alpine) |

### 38.3 Key Takeaways

1. **Alpine is NOT part of GsmUi component architecture.** GsmUi components use custom elements + mixins.
2. **Alpine is acceptable for marketing pages** where no GsmUi component is involved.
3. **Never use Alpine inside gsmui: component Blade views** — this causes dual-state bugs.
4. **Use Livewire for server state**, Alpine for purely presentational toggles.
5. **CSP compliance is mandatory** — no eval, no CDN, no x-html.
6. **Performance budget** — max 5 Alpine scopes per page, init < 5ms.
7. **Accessibility comes from GsmUi components**, not from Alpine.

## 39. Alpine.js Integration Patterns with Livewire

### 39.1 Livewire + Alpine Communication

Alpine and Livewire can coexist on marketing pages where Livewire handles form submissions and Alpine handles client-side interactivity.

| Pattern | Direction | Mechanism |
| --- | --- | --- |
| Alpine dispatches to Livewire | Client → Server | `$wire.call('method', args)` |
| Livewire dispatches to Alpine | Server → Client | `$this->dispatch('event', data)` |
| Shared state | Bidirectional | `Alpine.store()` + `wire:poll` |

### 39.2 Alpine Store + Livewire Sync Pattern

```html
<script>
document.addEventListener('alpine:init', () => {
    Alpine.store('cart', {
        items: [],
        count: 0,
        total: 0,
        syncFromServer(data) {
            this.items = data.items;
            this.count = data.count;
            this.total = data.total;
        }
    });
});
</script>

<div x-data>
    <span x-text="$store.cart.count"></span>
    <span x-text="$store.cart.total"></span>
</div>

<!-- Livewire component syncs server state to Alpine store -->
<div wire:poll.visible.5s="syncCart"
     x-data
     x-init="$watch('$wire.cartData', val => $store.cart.syncFromServer(val))">
</div>
```

### 39.3 Livewire Event to Alpine Store

```blade
{{-- Livewire component --}}
<div wire:dispatch="cart-updated" x-data>
    {{-- Alpine listens --}}
    <div @cart-updated.window="$store.cart.refresh()">
</div>
```

### 39.4 Anti-Patterns for Alpine + Livewire

| Anti-pattern | Problem | Correct approach |
| --- | --- | --- |
| Alpine `x-model` on `wire:model` element | Dual-state conflict | Use `wire:model` only |
| Alpine `x-data` inside Livewire template | Reinitializes on morph | Use `wire:ignore` or Alpine store |
| Alpine `fetch()` for server calls | Bypasses CSRF, auth | Use Livewire `$wire` |
| Alpine DOM manipulation on Livewire targets | Livewire morph overwrites | Use Livewire for DOM |

## 40. Alpine.js Custom Directives

### 40.1 Creating Custom Directives

```javascript
document.addEventListener('alpine:init', () => {
    Alpine.directive('tooltip', (el, { expression, modifiers }, { effect, evaluateLater }) => {
        const tooltip = document.createElement('div');
        tooltip.textContent = expression;
        tooltip.className = 'absolute z-50 bg-zinc-900 text-white text-xs px-2 py-1 rounded';
        tooltip.style.display = 'none';
        el.style.position = 'relative';
        el.appendChild(tooltip);

        el.addEventListener('mouseenter', () => {
            tooltip.style.display = 'block';
        });
        el.addEventListener('mouseleave', () => {
            tooltip.style.display = 'none';
        });
    });
});
```

### 40.2 Directive Modifier Pattern

```javascript
Alpine.directive('click-outside', (el, { expression, modifiers }, { evaluate }) => {
    const handler = (e) => {
        if (!el.contains(e.target)) {
            evaluate(expression);
        }
    };
    document.addEventListener('click', handler);
    el._clickOutsideCleanup = () => document.removeEventListener('click', handler);
});
```

### 40.3 GsmUi Custom Directive Rules

| Rule | Rationale |
| --- | --- |
| No custom directives inside gsmui: components | Component JS owns behavior |
| Only on marketing pages | Alpine boundary |
| No DOM manipulation of component internals | Prevents dual-state |
| Use `effect()` for reactive updates | Automatic cleanup |
| Clean up listeners in destroy hook | Prevents memory leaks |

## 41. Alpine.js State Management Patterns

### 41.1 Local State vs Global State

| State type | Scope | Implementation | Use case |
| --- | --- | --- | --- |
| Local state | Single component | `x-data="{ ... }"` | Toggle, form inputs |
| Shared state | Multiple scopes | `Alpine.store()` | Cart, theme, user |
| Server state | Application | Livewire properties | Database data |
| URL state | Navigation | `wire:model` + query | Filters, pagination |

### 41.2 Alpine Store Patterns

```javascript
// Store definition
Alpine.store('notifications', {
    items: [],
    add(message, type = 'info') {
        this.items.push({ id: Date.now(), message, type });
        setTimeout(() => this.remove(this.items[0].id), 5000);
    },
    remove(id) {
        this.items = this.items.filter(n => n.id !== id);
    }
});

// Usage in HTML
<div x-data>
    <template x-for="notification in $store.notifications.items" :key="notification.id">
        <div x-text="notification.message"
             :class="notification.type === 'error' ? 'bg-red-500' : 'bg-blue-500'">
        </div>
    </template>
</div>
```

### 41.3 State Derivation Pattern

```javascript
Alpine.store('filters', {
    search: '',
    category: 'all',
    sort: 'newest',
    get filteredItems() {
        return Alpine.store('items')
            .filter(item => {
                const matchesSearch = item.name.includes(this.search);
                const matchesCategory = this.category === 'all' || item.category === this.category;
                return matchesSearch && matchesCategory;
            })
            .sort((a, b) => {
                if (this.sort === 'newest') return b.date - a.date;
                if (this.sort === 'name') return a.name.localeCompare(b.name);
                return 0;
            });
    }
});
```

## 42. Alpine.js Error Handling

### 42.1 Error Boundaries

```javascript
// Global Alpine error handler
window.addEventListener('alpine:init', () => {
    Alpine.errorHandler = (error, component, message) => {
        console.error(`[Alpine] ${message}:`, error);
        // Report to error tracking service
        if (window.errorTracker) {
            window.errorTracker.captureException(error, {
                component: component.$el?.tagName,
                message
            });
        }
    };
});
```

### 42.2 Graceful Degradation

```html
<div x-data="{ open: false }" x-cloak>
    <button @click="open = !open">Toggle</button>
    <div x-show="open">Content</div>
</div>

<!-- Fallback when Alpine fails to load -->
<noscript>
    <details>
        <summary>Toggle</summary>
        <div>Content</div>
    </details>
</noscript>
```

### 42.3 Error Handling Checklist

| Check | Implementation | Priority |
| --- | --- | --- |
| Alpine load failure | `noscript` fallback | High |
| Reactive expression error | `Alpine.errorHandler` | High |
| Event handler error | try/catch in handler | Medium |
| Store subscription error | Error in `effect()` | Medium |
| Network error in `$wire` | Livewire error handling | High |
