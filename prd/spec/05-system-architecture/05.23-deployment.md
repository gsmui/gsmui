# Purpose

This document outlines the deployment architecture, including environments, CI/CD pipelines, release strategies, and operational procedures. It serves as the operational reference for how code moves from development to production and how the platform is maintained in production.

---

# Architecture Overview

The deployment architecture follows a multi-environment strategy with automated pipelines for testing and deployment. Code flows from developer workstations through a series of automated gates before reaching production, with manual approval required for production deployments.

The infrastructure is containerized using Docker with orchestration through Laravel Forge and Envoyer for zero-downtime deployments. Database migrations are applied automatically during deployment with rollback support. Asset compilation happens in the CI pipeline, and compiled assets are deployed alongside the application code.

The platform uses a monolithic deployment model where the entire application is deployed as a single unit. This simplifies deployment orchestration and reduces the surface area for deployment failures. Future plans include modular deployment for high-traffic components.

# Environments

| Environment | Purpose | Access | Data |
|-------------|---------|--------|------|
| Local Development | Individual developer workspaces | All developers | Synthetic test data |
| CI Environment | Automated testing on every push | GitHub Actions | Ephemeral test database |
| Staging | Pre-production validation | Team + QA | Production-mirror data (anonymized) |
| Production | Live platform | Production team | Real user data |

## Environment Configuration

Each environment maintains its own configuration through Laravel's environment-based configuration system. Sensitive values are stored in environment variables and managed through the deployment platform's secret management.

```text
.env.development     # Local development defaults
.env.ci              # CI pipeline configuration
.env.staging         # Staging-specific values
.env.production      # Production secrets
```

## Environment Parity

Staging mirrors production as closely as possible:
- Same PHP version and extensions
- Same database version and configuration
- Same cache and queue drivers
- Same external service connections (test modes where available)
- Same resource allocation (scaled down, not different architecture)

# CI/CD Pipeline

## Pipeline Overview

```text
Code Push / PR
    |
GitHub Actions Trigger
    |
Stage 1: Validation
    |- PHP Linting (php -l)
    |- Code Style (Pint)
    |- Static Analysis (Larastan)
    |
Stage 2: Testing
    |- Unit Tests (PHPUnit)
    |- Feature Tests (PHPUnit)
    |- Database Tests (with migrations)
    |
Stage 3: Build
    |- NPM Install
    |- Vite Build
    |- Asset Hashing
    |
Stage 4: Deploy Staging
    |- SSH Deploy
    |- Migration Run
    |- Cache Clear
    |- Queue Restart
    |
Stage 5: Verification
    |- Health Check
    |- Smoke Tests
    |- E2E Tests (Playwright)
    |
Stage 6: Deploy Production
    |- Manual Approval Gate
    |- Blue-Green Deploy
    |- Traffic Shift
    |- Monitoring Watch
```

## Pipeline Stages Detail

### Stage 1: Validation

Code style and static analysis run first to catch issues before tests. Laravel Pint enforces consistent code style with zero-configuration defaults. Larastan provides static analysis at level 6, catching type errors and potential bugs without runtime execution.

```yaml
- name: PHP Lint
  run: find app -name "*.php" -exec php -l {} \;

- name: Code Style
  run: vendor/bin/pint --test

- name: Static Analysis
  run: vendor/bin/phpstan analyse --memory-limit=512M
```

### Stage 2: Testing

Unit and feature tests run against a MySQL database spun up as a GitHub Actions service. Database state is isolated per test run through migrations and transactions. Test coverage is tracked and must not decrease from the previous build.

```yaml
services:
  mysql:
    image: mysql:8.0
    env:
      MYSQL_ROOT_PASSWORD: testing
      MYSQL_DATABASE: gsmui_testing

- name: Unit Tests
  run: vendor/bin/phpunit --testsuite=Unit --coverage-text

- name: Feature Tests
  run: vendor/bin/phpunit --testsuite=Feature
```

### Stage 3: Build

Frontend assets are compiled using Vite with production optimizations: minification, tree shaking, code splitting, and content hashing for cache busting. The build output is uploaded as a GitHub Actions artifact for deployment.

### Stage 4: Deploy Staging

Deployment uses Envoyer for zero-downtime deploys. The process clones the repository, installs dependencies, runs migrations, warms caches, and restarts workers without dropping active connections.

### Stage 5: Verification

Post-deployment verification runs health checks and smoke tests against the staging environment. Playwright E2E tests validate critical user flows. If any check fails, the deployment is automatically rolled back.

### Stage 6: Deploy Production

Production deployment requires manual approval from a team lead. The blue-green strategy maintains two identical production environments. Traffic is shifted from the old environment to the new one after verification completes.

### PHP-FPM

- Process manager: `dynamic`
- Max children: `50` (production), `10` (staging)
- Start servers: `10` (production), `2` (staging)
- Min spare: `5` (production), `1` (staging)
- Max requests: `500` (recycle after 500 requests)

### MySQL

- InnoDB buffer pool: 2GB (production), 256MB (staging)
- Max connections: 200 (production), 50 (staging)
- Binary logging enabled for point-in-time recovery
- Read replicas for analytics queries (production only)

### Redis

- Memory limit: 1GB (production), 256MB (staging)
- Maxmemory policy: `allkeys-lru`
- Persistence: RDB snapshots every 5 minutes
- Used for: sessions, cache, queue, rate limiting

## Staging Stack

Staging uses the same software stack as production with reduced resource allocation. External services (payment processing, email, search) use test/sandbox modes. The staging environment is automatically rebuilt weekly to prevent drift.

# Release Strategy

## Versioning

Semantic versioning: `MAJOR.MINOR.PATCH`

- **MAJOR**: Breaking changes to API, database schema, or component interfaces
- **MINOR**: New features, non-breaking enhancements, new components
- **PATCH**: Bug fixes, security patches, performance improvements

Release candidates use the format `MAJOR.MINOR.PATCH-rc.N` and are deployed to staging for validation before production release.

## Branching

| Branch | Purpose | Deployment |
|--------|---------|------------|
| `main` | Production-ready code | Production (manual approval) |
| `develop` | Integration branch | Staging (automatic) |
| `feature/*` | Feature development | CI only |
| `release/*` | Release preparation | Staging (automatic) |
| `hotfix/*` | Critical production fixes | Production (expedited) |

## Release Process

1. Feature complete on `develop` branch
2. Create `release/*` branch from `develop`
3. Deploy to staging for QA validation
4. Fix any issues found during QA
5. Merge to `main` and tag release
6. Deploy to production with monitoring

## Deployment Types

- **Full Deploy**: Complete new version with all changes. Used for standard releases.
- **Hotfix**: Critical fixes only, minimal change set. Used for security patches and critical bugs.
- **Feature Flag**: Features deployed but hidden behind flags. Used for gradual rollouts and A/B testing.

# Rollback Strategy

## Automatic Rollback

The deployment system monitors application health after each deployment. If health checks fail or error rates spike above threshold, automatic rollback triggers:

1. Traffic shifted back to previous environment
2. Database migrations rolled back (if reversible)
3. Cache cleared and warmed with previous version data
4. Alerts sent to the team

## Manual Rollback

For issues discovered after the automatic rollback window:

1. Select previous deployment in Envoyer
2. Click "Rollback" to restore previous release artifacts
3. Run `php artisan migrate:rollback` if database changes were applied
4. Clear and rebuild caches
5. Restart queue workers

## Database Rollback

Migrations are designed to be reversible. Each `up` method has a corresponding `down` method. The rollback strategy:

- Review migration `down` methods before deployment
- Test rollback in staging before production deployment
- Maintain data integrity through careful foreign key management
- Use transactions for multi-step migrations

# Security Considerations

## Deployment Security

- SSH key-based authentication for all server access
- Environment variables stored in encrypted vaults, not in repositories
- Deployment tokens with minimal required permissions
- Audit logging for all deployment actions
- Two-factor authentication for production deployment access

## Runtime Security

- PHP `disable_functions` for dangerous functions
- Open_basedir restriction to application directory
- Session cookie security (HttpOnly, Secure, SameSite)
- Content Security Policy headers
- Rate limiting at Nginx and application levels

```dockerfile
# Set working directory

# Copy application files
COPY . /var/www

# Install dependencies

# Set permissions

    && chmod -R 755 /var/www/storage \
    && chmod -R 755 /var/www/bootstrap/cache

COPY docker/php-fpm.conf /usr/local/etc/php-fpm.d/www.conf

# OPcache configuration
COPY docker/opcache.ini /usr/local/etc/php/conf.d/opcache.ini
```

# Deployment Scripts

## Pre-Deployment Script

```bash
#!/bin/bash
# scripts/pre-deploy.sh

set -e

ENVIRONMENT=$1
VERSION=$2

echo "Pre-deployment checks for $ENVIRONMENT..."

# Check if version exists
if ! git rev-parse "$VERSION" >/dev/null 2>&1; then
    echo "Error: Version $VERSION not found"
    exit 1
fi

# Check if deployment is locked
if [ -f "/tmp/gsmui-deploy.lock" ]; then
    echo "Error: Deployment in progress"
    exit 1
fi

# Create deployment lock
touch /tmp/gsmui-deploy.lock

# Run tests
echo "Running tests..."
php artisan test --parallel

# Check database migrations
echo "Checking migrations..."
php artisan migrate:status

# Check disk space
DISK_FREE=$(df -BG /var/www | tail -1 | awk '{print $4}' | sed 's/G//')
if [ "$DISK_FREE" -lt 5 ]; then
    echo "Warning: Low disk space ($DISK_FREE GB free)"
fi

# Check PHP extensions
echo "Checking PHP extensions..."
php -m | grep -E "pdo_mysql|mbstring|xml|bcmath|gd|redis" || {
    echo "Error: Missing required PHP extensions"
    exit 1
}

echo "Pre-deployment checks passed!"
```

## Deployment Script

```bash
#!/bin/bash
# scripts/deploy.sh

set -e

ENVIRONMENT=$1
VERSION=$2
DEPLOY_DIR="/var/www/gsmui"
BACKUP_DIR="/var/backups/gsmui"
LOG_FILE="/var/log/gsmui/deploy.log"

log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $1" | tee -a $LOG_FILE
}

deploy() {
    log "Starting deployment of version $VERSION to $ENVIRONMENT..."

    # Create backup
    log "Creating backup..."
    mkdir -p $BACKUP_DIR
    tar -czf "$BACKUP_DIR/gsmui-$(date +%Y%m%d%H%M%S).tar.gz" -C $DEPLOY_DIR .
```

## Horizontal Scaling Script

```bash
#!/bin/bash
# scripts/scale-app.sh

ENVIRONMENT=$1
ACTION=$2  # scale_up or scale_down
COUNT=${3:-1}

echo "Scaling $ENVIRONMENT: $ACTION by $COUNT instances..."

case $ACTION in
    scale_up)
        # Add new application servers
        for i in $(seq 1 $COUNT); do
            echo "Launching new instance $i..."
            # AWS CLI example
            aws ec2 run-instances \
                --image-id ami-xxxxx \
                --instance-type t3.large \
                --count 1 \
                --key-name gsmui-$ENVIRONMENT \
                --security-group-ids sg-xxxxx \
                --subnet-id subnet-xxxxx \
                --tag-specifications "ResourceType=instance,Tags=[{Key=Name,Value=gsmui-$ENVIRONMENT-app-$(date +%s)}]"
        done
        
        # Wait for instances to be ready
        sleep 60
        
        # Register with load balancer
        ./scripts/register-instances.sh $ENVIRONMENT
        
        # Deploy application to new instances
        ./scripts/deploy-to-instances.sh $ENVIRONMENT
        ;;
    
    scale_down)
        # Identify instances to terminate
        INSTANCES=$(aws ec2 describe-instances \
            --filters "Name=tag:Environment,Values=$ENVIRONMENT" \
                     "Name=tag:Role,Values=app" \
                     "Name=instance-state-name,Values=running" \
            --query 'Reservations[].Instances[].InstanceId' \
            --output text)
        
        # Keep minimum instances
        INSTANCE_COUNT=$(echo $INSTANCES | wc -w)
        MIN_INSTANCES=2
        
        if [ $INSTANCE_COUNT -gt $MIN_INSTANCES ]; then
            TERMINATE_COUNT=$((INSTANCE_COUNT - MIN_INSTANCES))
            INSTANCES_TO_TERMINATE=$(echo $INSTANCES | cut -d' ' -f1-$TERMINATE_COUNT)
            
            for INSTANCE in $INSTANCES_TO_TERMINATE; do
                echo "Terminating instance $INSTANCE..."
                aws ec2 terminate-instances --instance-ids $INSTANCE
            done
        fi
        ;;
esac

echo "Scaling complete!"
```

## Backup Scripts

```bash
#!/bin/bash
# scripts/backup-database.sh

ENVIRONMENT=$1
BACKUP_DIR="/var/backups/gsmui/database"
RETENTION_DAYS=30

    --user=$DB_USERNAME \
    --password=$DB_PASSWORD \
    --host=$DB_HOST \
    --single-transaction \
    --routines \
    --triggers \
    --events \

gzip $BACKUP_FILE

# Upload to S3
aws s3 cp "${BACKUP_FILE}.gz" "s3://gsmui-backups/database/${ENVIRONMENT}/${DATE}.sql.gz"

# Clean old backups
find $BACKUP_DIR -name "*.sql.gz" -mtime +$RETENTION_DAYS -delete

echo "Backup complete: ${BACKUP_FILE}.gz"
```

```bash
BACKUP_FILE=$2

echo "Restoring database for $ENVIRONMENT from $BACKUP_FILE..."

# Download from S3 if needed
if [[ $BACKUP_FILE != /* ]]; then
    aws s3 cp "s3://gsmui-backups/database/${ENVIRONMENT}/${BACKUP_FILE}" "/tmp/${BACKUP_FILE}"
    BACKUP_FILE="/tmp/${BACKUP_FILE}"
fi

# Decompress if compressed
if [[ $BACKUP_FILE == *.gz ]]; then
    gunzip $BACKUP_FILE
    BACKUP_FILE="${BACKUP_FILE%.gz}"
fi

# Stop application
sudo systemctl stop nginx
php artisan queue:stop

# Restore database
mysql \
    --user=$DB_USERNAME \
    --password=$DB_PASSWORD \
    --host=$DB_HOST \
    $DB_DATABASE < $BACKUP_FILE

# Verify data
php artisan db:verify

# Restart application
sudo systemctl start nginx
php artisan queue:work &

echo "Restore complete!"
```

## Backup Monitoring

```php
// app/Console/Commands/VerifyBackups.php
class VerifyBackups extends Command
{
    protected $signature = 'backup:verify {--environment=production}';

    public function handle(): int
    {
        $environment = $this->option('environment');
        
        // Check if recent backup exists
        $latestBackup = $this->getLatestBackup($environment);
        
        if (!$latestBackup) {
            $this->error('No backup found for ' . $environment);
            return 1;
        }
        
        // Verify backup is not too old
        $backupAge = now()->diffInHours($latestBackup['created_at']);
        if ($backupAge > 24) {
            $this->warn("Latest backup is {$backupAge} hours old");
        }
        
        // Test restore on staging
        if ($environment === 'production') {
            $this->info('Testing restore on staging...');
            // Run restore test on staging environment
        }
        
        $this->info('Backup verification passed');
        return 0;
    }
}
```

```php
// app/Services/DeploymentMetrics.php
class DeploymentMetrics
{
    public function recordDeployment(array $data): void
    {
        Deployment::create([
            'version' => $data['version'],
            'environment' => $data['environment'],
            'started_at' => $data['started_at'],
            'completed_at' => $data['completed_at'],
            'duration' => $data['duration'],
            'status' => $data['status'],
            'deployed_by' => $data['deployed_by'],
            'rollback_available' => true,
        ]);
    }

    public function getMetrics(string $period = '30d'): array
    {
        $deployments = Deployment::where('created_at', '>=', now()->sub($period))->get();

        return [
            'total_deployments' => $deployments->count(),
            'successful_deployments' => $deployments->where('status', 'success')->count(),
            'failed_deployments' => $deployments->where('status', 'failed')->count(),
            'average_duration' => $deployments->avg('duration'),
            'rollback_rate' => $deployments->where('rolled_back', true)->count() / $deployments->count() * 100,
        ];
    }
}
```

# Incident Response

## Incident Severity Levels

| Level | Description | Response Time | Examples |
|-------|-------------|---------------|----------|
| P1 - Critical | Complete outage | 15 minutes | Database down, payment system failure |
| P2 - High | Major feature broken | 1 hour | Login failing, downloads broken |
| P3 - Medium | Minor feature issue | 4 hours | Search not working, slow performance |
| P4 - Low | Cosmetic issue | 24 hours | UI glitch, typo |

## Incident Response Process

1. **Detection**
   - Automated monitoring alerts
   - User reports
   - Internal discovery

2. **Triage**
   - Assess severity
   - Assign incident lead
   - Create incident channel

3. **Resolution**
   - Investigate root cause
   - Implement fix
   - Deploy fix
   - Verify resolution

4. **Post-Mortem**
   - Document timeline
   - Identify root cause
   - Create action items
   - Share learnings
