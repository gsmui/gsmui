## Editorial Workflow States

```
draft --> in_review --> scheduled --> published
   |          |                          |
   |          +--> draft (returned)      +--> archived
   +--> published (direct, permission)   +--> updated (revision)
```

| Transition | Requirement |
|------------|-------------|
| draft → in_review | Assign reviewer; checklist initiated |
| in_review → published | `blog.publish` + checklist pass |
| draft → scheduled | Valid future datetime + checklist pass |
| scheduled → published | Scheduler (≤ 30s precision) |
| published → updated | Draft overlay model (live unchanged until publish) |
| any → archived | Unpublish + keep with noindex |

## Editorial Checklist (Pre-Publish Gate)

| Check | Blocking |
|-------|----------|
| Title 30-60 chars | Warning |
| Excerpt present (≤ 160 chars) | Yes |
| Featured image set + alt text | Yes |
| Category assigned | Yes |
| ≥ 1 tag | Warning |
| Internal links resolve | Yes |
| No broken embeds | Yes |
| SEO score ≥ threshold (configurable, default 80) | Warning (overridable) |
| Author bio complete | Warning |
| Reading time computed | Automatic |

SEO score components: title length, meta description, keyword in title/first paragraph, heading structure, image alts, link coverage.

## Scheduling System

- Timezone: author's configured timezone; stored UTC.
- Scheduler job runs every minute; precision target ≤ 30s.
- Missed schedule detection: if scheduler heartbeat stale, alert + catch-up dispatch.
- Conflict guard: rescheduling after miss requires explicit confirmation.
- Scheduled posts visible in saved view with countdown badges.

## Revision Model

- Autosaves rolling 20; publish snapshots permanent.
- Compare view with diff highlighting.
- Restore creates new revision (non-destructive); published restore requires `blog.publish`.
- Editor lock: 5-min soft lock with heartbeat (parity with docs module).

# Comment System

## Comment Lifecycle

```
submitted --> auto_screen --> pending --> approved
                        \--> spam
                        \--> approved (auto for trusted)
pending --> rejected
approved --> removed (post-approval moderation)
```

## Auto-Screening Pipeline

| Stage | Tool | Action |
|-------|------|--------|
| 1 | Rate limiter | > 5/min same IP → block + log |
| 2 | Duplicate detection | > 90% similarity recent comment → hold |
| 3 | Link policy | Links from new accounts → hold for review |
| 4 | Toxicity classifier | Score > threshold → hold; > high threshold → spam |
| 5 | Spam signatures | Known patterns → spam |
| 6 | Trusted commenter bypass | ≥ 3 approved history → auto-approve |

## Moderation Queue UI

| Element | Behavior |
|---------|----------|
| Queue | Pending oldest first; spam separate tab |
| Context | Parent post + thread position shown |
| Actions | Approve, reject (reason), spam, ban commenter |
| Bulk | Approve all from trusted user; mark spam batch |
| Keyboard | j/k navigation, a approve, s spam, x reject |
| Notifications | Pending count badge on nav (reviews.moderate) |

## Banning & Escalation

| Action | Effect |
|--------|--------|
| Ban commenter | Future comments auto-spam; existing preserved |
| Shadow restrict | Comments held always; user unaware |
| IP rate tighten | Per-incident threshold reduction |
| Escalate to security | Coordinated brigading patterns |

# Runbooks (Blog & CMS)

## Symptom: Scheduled posts not publishing

1. Check `SchedulerHeartbeatJob` status.
2. Verify `PublishScheduledPostsJob` queue health.
3. Manual dispatch catch-up for missed posts.
4. If systemic: incident declared; timezone config verified.

## Symptom: Comment spam flood

1. Verify rate limiter active; tighten thresholds temporarily.
2. Bulk-spam obvious batches; hold borderline.
3. Add signatures to screening rules.
4. If coordinated: security escalation + temporary comment pause per affected posts.

## Symptom: Newsletter complaints spike

1. Pause trigger job via flag.
2. Review last send content + segment.
3. Unsubscribe rate analysis; provider health check.
4. Resume with corrected segment; post-incident note.

## Symptom: CMS page rendering broken post-deploy

1. Compare template registry versions.
2. Roll back template registration if needed.
3. Verify content_json schema migration ran.
4. Edge purge + verification.

# Appendix: Content Domain Model

The blog and CMS module manages editorial content: posts, pages, series, and announcements. It separates authoring concerns from delivery concerns so that the public site can render cached content without touching the authoring database on every request.

## Core Entities

| Entity | Purpose | Key Fields |
|--------|---------|------------|
| `Post` | Editorial article | `id`, `slug`, `status`, `author_id`, `published_at` |
| `PostRevision` | Immutable snapshot | `post_id`, `revision`, `content_hash`, `created_at` |
| `Page` | Static marketing page | `id`, `slug`, `template`, `status` |
| `Series` | Ordered post collection | `id`, `slug`, `title` |
| `SeriesItem` | Membership + order | `series_id`, `post_id`, `position` |
| `Category` | Hierarchical grouping | `id`, `slug`, `parent_id` |
| `Tag` | Flat label | `id`, `slug` |
| `Comment` | Reader response | `id`, `post_id`, `status`, `author_id` |
| `Redirect` | Legacy slug mapping | `from_path`, `to_path`, `status_code` |

## Relationships

- A `Post` belongs to one `Category` and many `Tag` records.
- A `Post` may belong to many `Series` through `SeriesItem`.
- A `Post` has many `PostRevision` records ordered by revision number.
- A `Page` may reference shared blocks managed elsewhere.
- A `Redirect` maps old paths to current slugs for SEO continuity.

## Lifecycle

```
draft -> in_review -> scheduled -> published -> archived
                  \-> rejected -> draft
```

`published` posts are immutable in content terms; edits create a new revision and re-trigger the publish pipeline.

# Appendix: Authoring Editor Specification

The editor is a rich text surface backed by a structured document model rather than raw HTML. This guarantees consistent rendering and safe output.

## Document Model

Content is stored as a tree of blocks:

| Block | Fields |
|-------|--------|
| `paragraph` | inline content |
| `heading` | level, inline content |
| `code` | language, code text |
| `image` | media reference, alt text, caption |
| `embed` | provider, url, fallback |
| `list` | ordered flag, items |
| `quote` | inline content, attribution |
| `callout` | variant, inline content |

Inline content is a sequence of text and marks (bold, italic, code, link). Links carry an explicit target and rel attribute.

## Editor Guarantees

- No raw HTML is accepted from untrusted authors.
- Code blocks are sanitised and escaped at render time.
- Images reference media library assets by id, never by raw URL.
- Every save creates a revision.

## Autosave

Drafts autosave every 30 seconds and on navigation. Autosave conflicts are resolved by revision compare, never silent overwrite.

# Appendix: Publishing Workflow

Publishing is a gated pipeline with explicit states and approvals.

## States

| State | Meaning |
|-------|---------|
| `draft` | Author is editing |
| `in_review` | Awaiting editorial review |
| `scheduled` | Approved for future publish |
| `published` | Live on the public site |
| `archived` | Removed from public listing |
| `rejected` | Returned to author with notes |

## Gates

1. Content validation (required fields, broken links).
2. Editorial review sign-off.
3. SEO metadata completeness.
4. Media licence check.
5. Publish scheduling.

## Scheduling

Scheduled posts publish at their `published_at` time via the scheduler. If the scheduler is delayed, the post publishes on the next tick and the delay is recorded in telemetry.

## Unpublishing

Unpublishing returns a post to `draft` and invalidates its cache entries. A redirect may be created if the slug changes.

---

# Appendix: Revisions and Version History

Every save produces an immutable revision. Revisions enable audit, rollback, and diff review.

## Revision Fields

- `revision` (monotonic integer).
- `content_hash` (sha256 of canonical blocks).
- `author_id`.
- `created_at`.
- `note` (optional change summary).

## Diffing

Diffs are computed at the block level. Inline diffs are shown within changed blocks, preserving reading context.

## Rollback

Rolling back creates a new revision whose content equals the chosen older revision. History is never rewritten.

## Retention

Revisions are retained indefinitely for published posts and for 90 days for drafts. Retention policy is configurable per plan.

# Appendix: Taxonomy Management

Categories form a shallow hierarchy; tags are flat. Both are managed in the admin panel with strict slug rules.

## Slug Rules

- Lowercase, hyphen-separated.
- ASCII only for canonical slugs.
- Unique within the taxonomy type.
- Reserved slugs rejected (`admin`, `api`, `new`).

## Category Hierarchy

Categories support at most three levels. Moving a category rewrites descendant paths and emits redirects when public URLs change.

## Tag Hygiene

Tags are deduplicated by normalised name. Unused tags are reported weekly and may be merged into canonical tags.

# Appendix: Comments and Moderation

Comments are optional per post and disabled by default for announcements.

## Comment States

```
pending -> approved -> visible
        \-> spam
        \-> rejected
```

## Moderation

- Akismet-style spam scoring runs on ingest.
- High-confidence spam is auto-rejected.
- Borderline items enter the moderation queue.
- Approved comments are cached with the post.

## Threading

Comments support one level of replies. Deeper threading is not supported to keep rendering predictable.

## Author Controls

Authors may close comments on a post. Closing hides the form and preserves existing comments.

# Appendix: Newsletter Integration

Posts can be promoted to the newsletter. The newsletter module (05.03.03.21) consumes a post digest.

## Digest Rules

- A post is eligible once published.
- The digest includes title, excerpt, hero image, and canonical link.
- Scheduled sends respect subscriber time zones.
- Unsubscribe links are mandatory.

## Consent

Only subscribers with confirmed consent receive digests. Consent state is owned by the newsletter module, not the CMS.

# Appendix: Media Library Integration

Images and files are referenced by media id. The CMS never stores raw URLs for uploaded media.

- Uploads go through the media library (05.03.03.15).
- Variants (thumbnail, hero, og) are generated by the media pipeline.
- Deleting a referenced asset is blocked until references are removed.
- Alt text is required for content images.

# Appendix: Localisation

Content localisation is supported per locale.

## Locale Model

- A post has one canonical locale.
- Translations are separate post records linked by `translation_group`.
- Each translation has its own slug per locale.
- Fallback to canonical locale when a translation is missing.

## Workflow

Translations enter `draft` independently and follow the same publish gates. Missing translations surface as a completeness report.

| Block | Variants | Notes |

## Custom Blocks

Workspaces may register custom blocks by contract. Custom blocks must declare a renderer, a schema, and a sanitisation policy. Blocks without a sanitisation policy are rejected.

## Block Versioning

A block schema is versioned. Changing a block schema requires a migration that transforms existing stored blocks. Migrations run offline against revisions and are audited.

# Appendix: Content Import and Export

Bulk content movement is supported for migrations and backups.

## Import Formats

- Markdown with front matter.
- JSON block documents.
- WordPress XML (best-effort compatibility).

## Import Pipeline

1. Parse source into intermediate representation.
2. Map fields to the internal model.
3. Validate required metadata.
4. Create drafts (never publish on import).
5. Report unresolved references (media, taxonomy).

## Export

Export produces a JSON bundle containing posts, revisions metadata, taxonomy, and media references. Media binaries are exported separately by the media library.

## Round-trip Guarantees

Exports are lossless for block content and taxonomy. Redirects and comments are included by default.

# Appendix: Content Scheduling and Calendar

Editors plan publishing on a calendar view.

## Calendar Features

- Month, week, and list views.
- Drag to reschedule scheduled posts.
- Conflict warnings when two posts target the same slot.
- Locale-aware time display.

## Scheduling Rules

- Scheduled time must be in the future.
- Approvals must be complete before scheduling.
- Rescheduling emits an audit entry.
- A scheduled post may be cancelled and returned to draft.

## Timezone Handling

Times are stored in UTC and displayed in the workspace timezone. Publication uses UTC to avoid daylight-saving ambiguity.

# Appendix: Search and Content Discovery

The CMS exposes a content search used by both the admin and the public site.

## Indexed Fields

- Title and excerpt (boosted).
- Body text.
- Taxonomy names.
- Author name.

## Filters

- Status, type, category, tag.
- Author.
- Date range.
- Locale.

## Ranking

Ranking blends text relevance with recency and post type weight. Announcements receive a recency boost; tutorials favour completeness signals such as word count and heading depth.

## Index Freshness

The index updates on publish, unpublish, and archive. Drafts are not indexed for the public search but are searchable in the admin.

# Appendix: Content Delivery and Caching

Public delivery is served from a cache with explicit invalidation.

## Cache Layers

| Layer | Scope | Invalidation |
|-------|-------|--------------|
| Edge cache | Per URL | Purge on publish |
| Application cache | Rendered fragments | Tag-based purge |
| Revision cache | Post JSON | On revision create |

## Purge Strategy

Publishing a post purges its URL, listing pages, taxonomy pages, and the sitemap. Purges are batched to avoid thundering herds.

## Stale-While-Revalidate

Listings serve stale content briefly while revalidating in the background. This keeps the site responsive during traffic spikes.

# Appendix: Content Accessibility Requirements

Editorial content must meet baseline accessibility expectations.

- Heading levels are sequential; the editor warns on skips.
- Images require alt text unless marked decorative.
- Link text must be descriptive; "click here" is flagged.
- Tables require header cells.
- Video embeds require captions where the provider supports them.
- Colour is never the sole carrier of meaning in callouts; icons accompany variants.

## Audit Tooling

The editor runs an accessibility lint pass on save. Blocking issues prevent publish; advisory issues are listed in the review panel.

# Appendix: Internationalisation Details

## Locale Registry

Locales are registered with a code, display name, and fallback chain. The fallback chain determines which content is served when a translation is missing.

## URL Strategy

Localised URLs use a locale prefix. The canonical locale may omit the prefix depending on workspace configuration.

## RTL Support

Right-to-left locales are supported. The editor and public theme both handle RTL layout. Numeric and code blocks remain left-to-right.

## Translation Completeness

A completeness report lists posts missing translations by locale. Editors can prioritise from this report.

# Appendix: Content Migration Playbook

When migrating from another CMS:

1. Inventory existing content and taxonomies.
2. Map source fields to the internal model.
3. Import as drafts.
4. Reconcile media references with the media library.
5. Build redirects for changed slugs.
6. Review a sample of migrated posts for fidelity.
7. Publish in waves, validating each wave.

## Rollback

Because imports create drafts, rollback is simply discarding the drafts. Redirects are tracked separately and can be removed in bulk.
