# Part II: Detailed Showcase Specification

This part expands the showcase module from a conceptual overview into an implementable specification. It defines the domain model, submission and moderation workflows, gallery behaviour, discovery mechanics, and the operational envelope required to run the showcase at scale.

---

# Chapter 1: Purpose and Positioning

The showcase exists to convert passive library users into active community members. It does so by making community work visible, creditable, and discoverable.

## 1.1 Primary Outcomes

| Outcome | Signal | Target |
|---------|--------|--------|
| Discovery | Gallery views per session | 3 or more |
| Inspiration | Outbound clicks to project sites | 12% of detail views |
| Contribution | New submissions per week | 40 |
| Quality | Approved-to-rejected ratio | 3:1 or better |
| Retention | Authors submitting again within 90 days | 35% |

## 1.2 Non-Goals

The showcase is explicitly not:

- A code hosting platform. It links to external repositories; it does not host source.
- A marketplace. Paid products live in the marketplace module (05.03.03.10).
- A social network. Profiles are lightweight and non-interactive beyond attribution.
- A bug tracker. Issues belong in the project's own tracker.
- A general image host. Every image must belong to a showcase entry.

## 1.3 Relationship to Other Modules

| Module | Relationship |
|--------|--------------|
| Marketplace | Showcase is free; marketplace is paid. Cross-links only. |
| Media library | Showcase images are stored and served by the media library. |
| Moderation | Showcase submission uses the shared review queue primitives. |
| Notifications | Moderation outcomes notify authors. |
| Analytics | Showcase emits view and click events for reporting. |
| Audit | Every moderation action is audited. |
| Security | Abuse reporting and rate limits apply. |

## 1.4 Design Principles

1. **Credit first.** Every entry names its author prominently and links to their profile.
2. **Friction where it matters.** Submission is easy; approval is deliberate.
3. **Fast gallery.** The gallery must feel instantaneous on mobile networks.
4. **Honest curation.** Featured status is editorial, not pay-to-play.
5. **Reversible moderation.** Rejections are explained and appealable.

# Chapter 2: Personas

## 2.1 Visitor

A visitor browses the gallery without an account. They can view entries, open detail pages, and click through to project sites. They cannot submit or react without signing in; anonymous reporting is rate limited.

## 2.2 Author

An author submits projects. They manage their own entries, respond to moderation feedback, and update screenshots. Authors own their submissions and may withdraw them at any time.

## 2.3 Curator

A curator reviews submissions against the quality rubric, approves or rejects with reasons, and can feature entries in collections.

## 2.4 Moderator

A moderator handles abuse reports, removes policy-violating content, and can suspend authors for repeated violations.

## 2.5 Administrator

An administrator configures the showcase, manages collections, and can override any curation decision with an audit trail.

## 2.6 Persona Capability Matrix

| Capability | Visitor | Author | Curator | Moderator | Admin |
|------------|---------|--------|---------|-----------|-------|
| Browse gallery | yes | yes | yes | yes | yes |
| View detail | yes | yes | yes | yes | yes |
| Submit project | no | yes | yes | no | yes |
| Edit own entry | no | yes | no | no | yes |
| Approve submission | no | no | yes | no | yes |
| Reject submission | no | no | yes | no | yes |
| Feature entry | no | no | yes | no | yes |
| Remove content | no | no | no | yes | yes |
| Suspend author | no | no | no | yes | yes |
| Configure module | no | no | no | no | yes |

## 3.2 Entry Fields

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `title` | string | yes | 3–80 characters |
| `slug` | string | yes | Derived, unique |
| `summary` | text | yes | 40–240 characters |
| `description` | blocks | yes | Structured content |
| `author_id` | ulid | yes | Owner |
| `stack` | array | no | Framework and tool tags |
| `status` | enum | yes | Lifecycle state |
| `featured` | boolean | no | Editorial flag |
| `published_at` | timestamp | no | Set on approval |
| `withdrawn_at` | timestamp | no | Set on withdrawal |

## 3.3 Lifecycle States

```
draft -> submitted -> in_review -> approved -> published
                  \-> changes_requested -> submitted
                  \-> rejected
published -> withdrawn
published -> removed (moderation)
```

## 3.4 State Semantics

| State | Visible Publicly | Editable By Author | Notes |
|-------|------------------|--------------------|-------|
| `draft` | no | yes | Pre-submission |
| `submitted` | no | no | Queued for review |
| `in_review` | no | no | Curator assigned |
| `changes_requested` | no | yes | Author must revise |
| `approved` | no | no | Awaiting publish tick |
| `published` | yes | limited | Copy edits allowed |
| `rejected` | no | yes | May resubmit |
| `withdrawn` | no | yes | Author-initiated |
| `removed` | no | no | Moderation action |

## 3.5 Invariants

- An entry has exactly one author.
- An entry has at least one media item when published.
- An entry has at most one primary link.
- A published entry's slug never changes without a redirect.
- A moderation decision is immutable; a new decision supersedes it.
- Featured status requires `published`.

# Chapter 4: Submission Workflow

## 4.1 Submission Steps

1. **Author identity.** The author must be signed in with a verified email.
2. **Project basics.** Title, summary, description.
3. **Media.** At least one image; up to eight.
4. **Links.** One primary link plus optional secondary links.
5. **Classification.** Up to five tags; optional stack entries.
6. **Declaration.** Author affirms ownership and licence.
7. **Submit.** Entry enters `submitted`.

## 4.2 Validation Rules

| Rule | Enforcement |
|------|-------------|
| Title length | 3–80 characters |
| Summary length | 40–240 characters |
| Description blocks | At least one paragraph |
| Media count | 1–8 for publish |
| Primary link | Required, https only |
| Tags | Maximum 5 |
| Ownership declaration | Required checkbox |
| Duplicate detection | Block on identical primary link from same author |

## 4.3 Draft Autosave

Drafts autosave locally and to the server every 20 seconds. Conflicts resolve by revision compare; the newer edit wins only when the author confirms.

## 4.4 Withdrawal

An author may withdraw a published entry at any time. Withdrawal removes it from galleries immediately and schedules media cleanup after a grace period. Withdrawal is reversible within 30 days.

## 4.5 Resubmission

Rejected entries may be resubmitted after edits. Resubmission increments the `submission_attempt` counter. More than three attempts requires curator invitation.

---

# Chapter 5: Moderation Pipeline

## 5.1 Queue Assignment

Submissions enter a shared review queue. Curators claim entries to avoid duplicate review. Claims expire after 30 minutes of inactivity.

## 5.2 Review Steps

1. **Automated pre-checks.** Link reachability, image safety, duplicate scan.
2. **Rubric assessment.** Curator scores each rubric dimension.
3. **Decision.** Approve, request changes, or reject.
4. **Feedback.** Reason code and notes are mandatory for non-approval.
5. **Notification.** Author is notified with the decision and notes.

## 5.3 Automated Pre-Checks

| Check | Failure Behaviour |
|-------|-------------------|
| Primary link reachable | Request changes |
| Images decodable | Request changes |
| Duplicate primary link | Reject with duplicate reason |
| Prohibited content scan | Route to senior moderator |
| Author verification | Block submission |

## 5.4 Reason Codes

| Code | Meaning | Author Action |
|------|---------|---------------|
| `incomplete` | Missing required information | Complete and resubmit |
| `low_quality` | Rubric below threshold | Improve and resubmit |
| `broken_links` | Links unreachable | Fix links |
| `duplicate` | Already exists | Do not resubmit |
| `licence` | Ownership unclear | Clarify licence |
| `prohibited` | Policy violation | Do not resubmit |
| `spam` | Promotional abuse | Do not resubmit |

## 5.5 Appeals

Authors may appeal a rejection once. Appeals go to a different curator. The appeal decision is final for that submission attempt.

## 5.6 SLA

| Stage | Target |
|-------|--------|
| Claim within | 24 hours |
| First decision within | 72 hours |
| Appeal decision within | 5 business days |

# Chapter 6: Quality Rubric

## 6.1 Dimensions

| Dimension | Weight | Description |
|-----------|--------|-------------|
| Craft | 30% | Visual polish and component use |
| Originality | 20% | Distinct concept or execution |
| Completeness | 20% | Working links, full screens |
| Relevance | 15% | Uses GsmUi meaningfully |
| Presentation | 15% | Screenshots and copy quality |

## 6.2 Scoring

Each dimension is scored 1–5. The weighted score must reach 3.0 to approve. Scores below 2 on any dimension trigger `changes_requested` regardless of total.

## 6.3 Score Anchors

### Craft

| Score | Anchor |
|-------|--------|
| 1 | Broken layout or visible rendering errors |
| 2 | Functional but inconsistent spacing and typography |
| 3 | Competent, conventional use of components |
| 4 | Polished and cohesive |
| 5 | Exemplary detail and finish |

### Originality

| Score | Anchor |
|-------|--------|
| 1 | Direct clone of an existing entry |
| 2 | Generic template with minimal change |
| 3 | Familiar pattern executed well |
| 4 | Distinct concept or novel combination |
| 5 | Genuinely new idea |

### Completeness

| Score | Anchor |
|-------|--------|
| 1 | Dead links, missing screens |
| 2 | Partial flow |
| 3 | Primary flow complete |
| 4 | Multiple flows complete |
| 5 | Comprehensive with edge states |

### Relevance

| Score | Anchor |
|-------|--------|
| 1 | GsmUi barely used |
| 2 | Incidental use |
| 3 | Meaningful use of components |
| 4 | Components central to the design |
| 5 | Showcases component breadth |

### Presentation

| Score | Anchor |
|-------|--------|
| 1 | Unreadable screenshots, error-filled copy |
| 2 | Poor crops, typos |
| 3 | Adequate screenshots and copy |
| 4 | Clear, well-cropped, well-written |
| 5 | Editorial quality |

## 6.4 Rubric Governance

Rubric changes require curator consensus and a two-week trial. Score distributions are reviewed monthly to detect drift.

# Chapter 11: Curation and Featured Entries

## 11.1 Editorial Independence

Featured status is granted by curators against the rubric and editorial calendar. No paid placement exists in the showcase. Sponsored collections, if ever introduced, must be clearly labelled and are out of scope for v1.

## 11.2 Featured Slots

| Slot | Location | Rotation |
|------|----------|----------|
| Hero feature | Gallery top | Weekly |
| Editor's picks | Gallery sidebar | Biweekly |
| Collection cover | Collection page | Per collection |
| Homepage teaser | Marketing site | Monthly |

## 11.3 Selection Criteria

- Rubric score of 4.0 or higher.
- Author has no active policy violations.
- Entry demonstrates a distinct pattern or technique.
- Representative of component breadth.
- Not previously featured within 180 days.

## 11.4 Featuring Workflow

1. Curator nominates an entry.
2. Second curator confirms.
3. Entry gains the `featured` flag with a window.
4. Notification sent to the author.
5. Flag automatically expires at the end of the window.

## 11.5 Rotation Rules

- Hero features rotate weekly on Monday 09:00 UTC.
- Editor's picks rotate every other Wednesday.
- A featured entry cannot repeat in the same slot within 180 days.
- Rotation is deterministic given the editorial schedule.

## 11.6 Editorial Calendar

| Field | Purpose |
|-------|---------|
| `slot` | Which featured slot |
| `entry_id` | Selected entry |
| `starts_at` | Window start |
| `ends_at` | Window end |
| `curator_id` | Responsible curator |
| `note` | Rationale |

## 11.7 Unfeaturing

Unfeaturing is immediate and may occur when:

- A policy violation is confirmed.
- The entry's primary link breaks.
- The author requests removal.
- The entry is withdrawn.

# Chapter 12: Author Profiles

## 12.1 Profile Contents

- Handle and display name.
- Short bio (max 280 characters).
- Optional avatar from the media library.
- Links to personal site and social profiles.
- Published entries count.
- Featured entries count.
- Aggregate reactions.

## 12.2 Handle Rules

- 3–30 characters.
- Lowercase alphanumerics and hyphens.
- Unique across the platform.
- Reserved handles rejected.

## 12.3 Profile Visibility

Profiles are public by default. An author may hide their profile, which removes it from listings while keeping attribution on entries visible as a display name only.

## 12.4 Entry Listing

A profile lists published entries newest first, paginated at 12 per page. Withdrawn and removed entries are excluded.

## 12.5 Author Verification

A verified badge indicates a confirmed ownership of the primary link domain. Verification is optional and manual in v1.

## 12.6 Profile Editing

Authors may edit handle, bio, avatar, and links. Handle changes require a redirect from the old handle to preserve inbound links.

## 12.7 Profile Moderation

Moderators may hide a profile that violates policy. Hiding a profile does not remove its entries unless each entry is separately actioned.

# Chapter 13: Reactions

## 13.1 Purpose

Reactions provide lightweight appreciation without threading or comment spam. They are a popularity signal, never a quality judgment.

## 13.2 Reaction Kinds

| Kind | Label | Notes |
|------|-------|-------|
| `like` | Like | Default |
| `bookmark` | Save | Private to the user |

Additional kinds are intentionally not supported in v1 to keep the UI calm.

## 13.3 Rules

- One reaction per user per entry per kind.
- Reactions require a signed-in account.
- Reaction counts are eventually consistent.
- Authors cannot react to their own entries.
- Reactions on unpublished entries are disabled.

## 13.4 Abuse Controls

| Control | Detail |
|---------|--------|
| Rate limit | 60 reactions per hour per user |
| Duplicate guard | Unique constraint per user-entry-kind |
| Sybil guard | Accounts younger than 24 hours excluded from counts |
| Anomaly detection | Sudden spikes flag the entry for review |

## 13.5 Display

Counts are shown on cards and detail pages. Counts below a display threshold are hidden to avoid discouraging new authors.

# Chapter 14: Abuse Reporting

## 14.1 Report Categories

| Category | Description |
|----------|-------------|
| `spam` | Promotional or irrelevant content |
| `plagiarism` | Content copied without credit |
| `prohibited` | Content violating policy |
| `broken` | Non-functional project |
| `impersonation` | False identity or attribution |
| `other` | Free-form |

## 14.2 Reporting Flow

1. Reporter selects a category.
2. Optional free-text detail.
3. Report enters the moderation queue.
4. Moderator triages within SLA.
5. Resolution is recorded with a reason.

## 14.3 Report States

```
open -> triaged -> actioned
               \-> dismissed
               \-> escalated
```

## 14.4 Reporter Anonymity

Anonymous reports are accepted with rate limiting and captcha. Reporter identity is never shown to the author.

## 14.5 Duplicate Reports

Multiple reports for the same entry and category are consolidated into one case with a report count.

## 14.6 Escalation

Escalated cases go to a senior moderator. Escalation is mandatory for `prohibited` and `impersonation` categories.

# Chapter 15: Accessibility Requirements

## 15.1 Standards

The showcase targets WCAG 2.2 AA. Every interactive element is operable by keyboard and announced correctly by assistive technology.

## 15.2 Gallery Accessibility

- Cards are links, not nested interactive regions.
- Focus order matches visual order.
- Focus ring is visible on all themes.
- Filter controls expose labels and state.
- Results count is announced on filter change.

## 15.3 Detail Page Accessibility

- Image gallery supports arrow keys and Home/End.
- Lightbox traps focus and restores it on close.
- Captions are associated with images.
- External link warns that it opens a new tab.

## 15.4 Motion

Reduced motion preference disables hover previews and lightbox transitions. No autoplaying media exists in the showcase.

## 15.5 Colour

Status badges never rely on colour alone. Every badge includes a text label or icon.

## 15.6 Audit Cadence

An automated accessibility scan runs weekly. Manual audits occur quarterly and before major UI changes.

# Chapter 23: Security and Trust

## 23.1 Threat Model

| Threat | Vector | Mitigation |
|--------|--------|------------|
| Spam submissions | Automated accounts | Verification + rate limits |
| Stored XSS | Description blocks | Structured blocks + escaping |
| Malicious links | Primary link | Scheme allowlist, no inline HTML |
| Image-based abuse | Media uploads | Automated scan + review |
| Reaction farming | Sybil accounts | Account age + anomaly detection |
| Report brigading | Coordinated reports | Consolidation + reviewer judgment |
| Handle squatting | Reserved handles | Reserved list |
| Impersonation | Author identity | Verification + reports |

## 23.2 Input Validation

- All text fields are length-limited and normalised.
- URLs must be https and pass a scheme allowlist.
- Blocks are validated against the schema.
- Media references must resolve to owned assets.

## 23.3 Output Safety

- Rendered blocks are escaped.
- External links use `noopener noreferrer`.
- No user-controlled HTML is rendered.
- CSP blocks inline scripts and external fonts.

## 23.4 Authorisation

Every mutating endpoint checks a specific ability. Object-level checks ensure an author may only edit their own entries. Curators act on any entry but cannot edit author copy.

# Chapter 25: Operational Runbooks

## 25.1 RB-SCW-01: Review Backlog

1. Check queue depth and curator availability.
2. Reassign unclaimed entries.
3. Recruit additional curators per onboarding checklist.
4. Communicate revised SLA if needed.
5. Review root cause if backlog recurs.

## 25.2 RB-SCW-02: Report Surge

1. Confirm surge via metrics.
2. Increase moderation staffing.
3. Enable temporary captcha for anonymous reports.
4. Consolidate duplicates aggressively.
5. Post-incident, review brigading signals.

## 25.3 RB-SCW-03: Gallery Performance Regression

1. Identify the deploy or data change.
2. Inspect cache hit rate and image sizes.
3. Roll back if a deploy caused it.
4. Purge and warm cache.
5. Add a regression test for the failure.

## 25.4 RB-SCW-04: Compromised Author Account

1. Suspend the account pending review.
2. Freeze all entries owned by the account.
3. Contact the author through verified channels.
4. Restore access after verification.
5. Audit all changes made during the window.

## 25.5 RB-SCW-05: Search Index Divergence

1. Compare index count to database count.
2. Run a full reindex in the background.
3. Verify sample entries appear.
4. Monitor zero-result rate.
5. Fix the incremental pipeline cause.

# Chapter 34: Taxonomy and Tag Governance

## 34.1 Controlled Vocabulary

Tags are drawn from a controlled vocabulary with a proposal process. Free-form tags create duplication and degrade discovery.

## 34.2 Tag Categories

| Category | Examples | Notes |
|----------|----------|-------|
| Component | `tables`, `forms`, `modals` | GsmUi components |
| Domain | `inventory`, `billing`, `crm` | Business domain |
| Pattern | `onboarding`, `checkout`, `settings` | UX pattern |
| Platform | `laravel`, `livewire`, `filament` | Stack |

## 34.3 Proposal Process

1. Author proposes a tag with rationale.
2. Curator checks for synonyms.
3. Approved tags are added to the vocabulary.
4. Authors may then apply the tag.

## 34.4 Merging

Duplicate tags are merged into a canonical tag. Merging rewrites entry pivots and emits redirects where tag pages exist.

## 34.5 Deprecation

Unused tags are deprecated after 90 days without a published entry. Deprecated tags are removed from the picker but retained on historical entries.

## 34.6 Tag Limits

Authors may apply at most five tags. Curators may apply additional editorial tags not available to authors.

# Appendix F: Final Statement

The Community Showcase is a curation product, not a feed. Its value comes from deliberate editorial judgment, clear attribution, and a gallery that loads fast everywhere. Every design decision in this specification serves one of those three goals. Implementers should resist adding reaction kinds, threading, or algorithmic ranking without revisiting the guarantees in Chapter 31.

Document 05.03.03.12 is closed for v1.
