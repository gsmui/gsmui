# Permission Matrix Page

Dedicated custom page `/admin/roles/permissions/matrix`.

## Layout

- Rows: permissions grouped by category (collapsible).
- Columns: roles (horizontal scroll beyond 6 roles; sticky first column).
- Cells: checkbox for granted/denied/unset states (tri-state for overrides).
- Header row: role names with member counts.

## Interactions

| Interaction | Behavior |
|-------------|----------|
| Toggle cell | Immediate optimistic UI; staged changes highlighted |
| Row bulk (permission → all roles) | "Grant to all" / "Revoke from all" with confirmation |
| Column bulk (role → all permissions) | Category-select modal |
| Search filter | Permissions by name/slug |
| Category collapse | Remembered in session |
| Save | Single commit of all staged changes; sudo required |
| Diff preview | Before save: modal lists grant/revoke counts per role |
| Discard | Clear staged changes |

## Tri-State Semantics

| State | Meaning |
|-------|---------|
| Granted (check) | Role grants permission |
| Denied (X) | Explicit deny on role (overrides inherited allow) |
| Unset (empty) | Inherited or default-deny resolution |

Deny state renders in red; tooltips explain inheritance source.

## Matrix Performance

- Virtualized rows (100+ permissions) and sticky headers.
- One API call loads full matrix state (roles × permissions sparse map).
- Save sends only staged diff (not full matrix).
- Target: 50 roles × 200 permissions renders < 1s.

## Permission: `roles.matrix.manage`

Required to toggle cells; without it matrix renders read-only with "View only" badge.

# Role Inheritance

## Model

- Roles may inherit from one parent (single inheritance for clarity).
- Child effective permissions = parent permissions ∪ child grants − child denies.
- Deny on child overrides parent allow.

## DAG Validation Rules

| Rule | Enforcement |
|------|-------------|
| No cycles | Validated on save; cycle error lists path |
| Max depth 3 | Deeper chains rejected (complexity guard) |
| Parent removal | Children keep current effective set (snapshotted as explicit grants) |
| Parent permission added | Propagates to children automatically (cache invalidation) |

## Inheritance Display

- Matrix cells show inheritance source on hover ("via moderator").
- Role detail shows tree with expandable permissions per level.
- Cloning flattens inheritance (no inherited link copied by default).

# Permission Resolution Algorithm

```text
function can(user, permission):
    if user.hasRole('super-admin'): return true       # short-circuit
    denies = []
    allows = []
    for role in user.roles(effective):
        if role.denies(permission): denies.append(role)
        if role.grants(permission): allows.append(role)
        for ancestor in role.ancestors():
            if ancestor.denies(permission): denies.append(ancestor)
            if ancestor.grants(permission): allows.append(ancestor)
    if denies: return false                           # deny wins
    return allows.isNotEmpty()
```

| Property | Value |
|----------|-------|
| Complexity | O(roles + ancestors) bounded by depth 3 |
| Caching | Per-user result cached keyed by permission set version |
| Invalidation | Any role mutation bumps `permission-set-version` counter |
| Fallback | Cache miss computes synchronously (< 10ms target) |

# Permission Evaluation Middleware

## Request Lifecycle Integration

Every admin request passes through `VerifyAdminPermission` middleware after authentication:

| Step | Operation |
|------|-----------|
| 1 | Determine route permission key from route action metadata |
| 2 | Load user's resolved permission set (version-checked cache) |
| 3 | Evaluate key against set using resolution algorithm |
| 4 | On deny: consistent 403 response (no capability hints) |
| 5 | On allow: attach set version to request context for audit |

## Route Permission Metadata

Routes declare requirements via controller/resource attributes:

```php
#[RequiresPermission('components.review')]
```

Filament resources map page types to permission verbs automatically:

| Edit | `{domain}.edit` |

Custom pages declare explicitly; missing declaration fails CI (fail-closed lint).

## Scheduler Job

| Property | Value |
|----------|-------|

# Two-Person Approval for Sensitive Changes

## Trigger Conditions

| Change | Requires Second Approval |
|--------|--------------------------|
| Grant `users.impersonate` | Always |
| Grant `roles.matrix.manage` | Always |
| Any super-admin membership change | Always |
| > 50 grants in one matrix save | Always |

## Workflow

1. Initiator submits; action stored as `pending-approval`.
2. All other super-admins notified (database + email).
3. Approver reviews diff + blast radius summary.
4. Approve → executes with both actors in audit.
5. Deny → initiator notified with note.
6. Auto-expiry: approvals expire in 72h.

Self-approval never allowed; system enforces distinct approver.

# Runbook (Roles & Permissions)

## Symptom: Admin reports access removed unexpectedly

1. Check user's role timeline (revocations/expiries).
2. Verify temporary role expiry job ran.
3. Check matrix change audit around same time.
4. If legitimate, point to notification record; else escalate to security (possible mis-change).

## Symptom: Permission cache not invalidating

1. Check Redis `permissions:set-version` incrementing.
2. Verify event listeners registered (`php artisan event:list`).
3. Inspect worker queue health.
4. Manual cache clear via diagnostics (audit logged).

## Symptom: Matrix save conflict loop

1. Check for stuck staged changes in another tab (user action).
2. Verify no failing partial applies in logs.
3. Force version resync via matrix reload.

# Appendix: Acceptance Criteria Addendum (Roles)

## AC-RP-1: Matrix Concurrent Save

- **Given** two admins with staged changes on same cell
- **When** second save attempted
- **Then** 409 with refresh prompt; no partial application.

## AC-RP-2: Two-Person Approval Integrity

- **Given** pending approval for impersonate grant
- **When** initiator attempts self-approval
- **Then** blocked; only distinct super-admin may approve.

## AC-RP-3: SoD Block

- **Given** user holds `orders.refund`
- **When** granting `finance.export` with blocking rule
- **Then** assignment refused with rule name shown.

## AC-RP-4: Token Live Denial

- **Given** token with scope tied to revoked permission
- **When** request made post-revocation
- **Then** 403 within same minute.

## AC-RP-5: Audit Immutability

- **Given** audit storage DB user
- **When** UPDATE attempted
- **Then** permission denied at DB level.

# Appendix: Roles Module Glossary

| Term | Definition |
|------|------------|
| Permission | Atomic capability grant, e.g. `users:suspend` |
| Role | Named collection of permissions assignable to principals |
| Matrix | Administrative UI rendering all roles x permissions |
| SoD | Separation of duties; preventing conflicting privileges on one principal |
| Recertification | Periodic human confirmation that assignments remain appropriate |
| Privilege escalation | Acquisition of unauthorized permissions; monitored and alerted |
| Golden snapshot | Authoritative fixture of the permission matrix used for regression |
| Principal | User, service account, or token subject to policy evaluation |
| Quorum | Minimum approvals required before a matrix change is committed |
| Drift | Undetected divergence between cached and authoritative permissions |
