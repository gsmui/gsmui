# Theme Editor (Deep Dive)

## Design Token Schema

Themes customize the platform through `--gsmui-*` CSS custom properties plus a JSON token manifest.

### Token Categories

| Category | Tokens (examples) | Editor Control |
|----------|-------------------|----------------|
| Colors | `--gsmui-primary`, `--gsmui-surface`, `--gsmui-muted`, `--gsmui-border` | Color picker with hex input |
| Typography | font-family list, base size, heading scale | Select + number steppers |
| Spacing | spacing scale factor (0.75-1.25x) | Slider |
| Radius | `--gsmui-radius-sm/md/lg/full` | Slider + presets |
| Shadows | shadow presets (none/sm/md/lg) | Preset cards |
| Focus | focus ring color + width | Color + width |

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `name` | string | Yes | Matches slug |
| `version` | semver | Yes | |

| `dark_tokens` | object | No | Overrides for dark mode |
| `component_overrides` | object | No | Component-scoped styles |

# Validation Engine

## Contrast Checker

- Computes WCAG contrast ratio for every text/surface token pair defined in the contract checklist.
- Pairs checked: body text/surface, muted text/surface, primary/button-text, badge text/tint, link/surface.
- Thresholds: normal text ≥ 4.5:1 (fail), large text ≥ 3:1 (fail), warnings at 4.5-4.7 range.
- Failed pairs block approval; warnings require reviewer acknowledgement.

## Breakpoint Suite

Playwright renders the component gallery in each theme at:

| Width | Checks |
|-------|--------|
| 375px | No horizontal scroll, touch targets ≥ 32px |
| 768px | Grid collapses correctly |
| 1280px | Full layout renders |
| 1920px | No over-stretching artifacts |

## Accessibility Scan

| Check | Threshold |
|-------|-----------|
| axe-core on gallery with theme applied | 0 critical, ≤ 3 serious (warn) |
| Focus visibility | All focusable elements show ring |
| Reduced motion | Animations disabled under media query |
| Color-only state | Badges include non-color affordances |

## Validation Report Persistence

- Results stored per version; displayed on Validation Report tab.
- Re-run available for reviewers after author fix.
- Report JSON exportable for author feedback attachment.

```

                  |
                  +--> needs_changes --> resubmitted
                  +--> rejected
```

| Check | Pass Criteria |
|-------|---------------|

| Token completeness | All required tokens present |
| Static scan | No eval/exec/obfuscation |
| No web fonts | Only system font stacks |
| No external network | connect-src none in preview |
| Screenshots | Light + dark, ≥ 800x600 |
| Description | ≥ 200 chars |
| Size | Package ≤ 5MB |

## Human Review Criteria

| # | Criterion |
|---|-----------|
| 1 | Gallery renders consistently across modes |
| 2 | Token choices are intentional (not random defaults) |

| 4 | No placeholder content |
| 5 | Component overrides respect usage patterns |
| 6 | Screenshots match actual output |

## Decision Requirements

Same as Templates module: approve requires satisfied checklist; reject requires category + feedback ≥ 20 chars.

# Version & Distribution Pipeline

## Version Upload Flow

1. Upload zip (admin or author portal).
2. Validation engine runs (contrast, breakpoints, a11y, static).
3. Version record `submitted`.
4. Review (fast-track eligible).
5. Approve → release pipeline.

## Release Pipeline Steps

| Step | Action |
|------|--------|
| 1 | Checksum verify |
| 2 | Build preview bundle (compiled CSS per theme) |
| 3 | Store versioned package private disk |
| 4 | CDN sync |
| 5 | Update `themes.latest_version` + counters |
| 6 | Invalidate marketplace caches |
| 7 | Notify installed users (update available) |
| 8 | Audit entry |

## Installation Tracking

| Signal | Source |
|--------|--------|
| Install event | End-user applies theme via platform settings |
| Active installs | Daily distinct users with theme applied |
| Uninstall | Reverted to default |
| Compatibility error report | Auto-flag to admin if error rate spikes |

## Update Delivery

- Installed users see update badge in their theme settings.
- Breaking token contract changes require new major + migration notes.
- Update notifications batched daily to avoid spam.

## Token Contract Versioning

| Concept | Detail |
|---------|---------|
| Contract version | Integer defining required token surface |
| Upgrade path | Migration guide per version bump |
| Enforcement | Themes below current-1 show "migration needed" badge |
| Admin tooling | Bulk report of themes needing migration |

# Appendix: Theme Authoring Workflow

Theme authoring is a first-class workflow with explicit gates. Authors do not hand-edit compiled bundles; they edit source theme files and submit them to the validation pipeline.

## Workflow Stages

1. **Draft.** Author creates a theme directory containing `theme.json`, `tokens.css`, and optional `preview.png`. The manifest declares name, slug, contract version, and supported modes.
2. **Local validate.** Running the CLI validator checks schema conformance, token completeness, and contrast targets before submission.
3. **Submit.** The theme is uploaded to the preview sandbox, where it is compiled and rendered against golden frames.
4. **Visual diff.** Automated diff compares the rendered output against operator-supplied golden frames. Diffs above threshold block promotion.
5. **Accessibility audit.** Contrast, focus visibility, and reduced-motion compliance are re-checked in both light and dark modes.
6. **Review.** A design systems reviewer inspects the preview and signs off.
7. **Publish.** The theme is promoted to the marketplace catalogue with a pinned contract version.

## Author Responsibilities

- Keep token coverage complete for every surface, text, border, and focus group.
- Provide both light and dark variants unless the theme explicitly opts out.
- Avoid hardcoded color values inside component overrides; always reference tokens.
- Declare any font usage; external font URLs are rejected by CSP enforcement.
- Document known limitations in the theme README.

## Reviewer Checklist

- [ ] Manifest parses and declares a supported contract version.
- [ ] Every required token group is present.
- [ ] Contrast targets met for primary and secondary text.
- [ ] Focus ring visible on base, raised, and sunken surfaces.
- [ ] Golden frame diff under threshold.
- [ ] Reduced-motion variant renders without animation.
- [ ] No external resource references.

# Appendix: Theme Contract Versioning

The theme contract follows semantic versioning. The contract version is declared in `theme.json` as `contract` and must match a version the platform supports.

## Compatibility Matrix

| Contract | Platform Min | Status | Notes |
|----------|--------------|--------|-------|
| `1.0` | `2.15.0` | Supported | Baseline token set |
| `1.1` | `2.16.0` | Supported | Added focus tokens |
| `1.2` | `2.18.0` | Supported | Added radius tokens |
| `2.0` | `3.0.0` | Scheduled | Token namespacing change |

## Breaking Changes

A breaking change requires a major contract bump and a migration note. Examples:

- Renaming a token.
- Removing a token group.
- Changing the meaning of an existing token.
- Changing the required token set for a mode.

## Deprecation Policy

Deprecated tokens remain supported for two minor platform releases. During that window, the validator emits warnings but does not fail. After the window, the token is removed and the contract is bumped.

# Appendix: Theme Runtime Data Model

The runtime resolves a theme by combining a tenant's pinned theme version with platform defaults and any user-level overrides.

## Resolution Order

1. **User preference.** A user may select a variant within the tenant's allowed set.
2. **Tenant pin.** The tenant's explicitly pinned theme version.
3. **Platform default.** The platform fallback theme.
4. **Hard fallback.** The built-in baseline token set, used if all else fails.

## Entities

| Entity | Fields | Notes |
|--------|--------|-------|
| `Theme` | `id`, `slug`, `name`, `contract`, `status` | Catalogue entry |
| `ThemeVersion` | `theme_id`, `version`, `checksum`, `published_at` | Immutable release |
| `TenantThemePin` | `tenant_id`, `theme_version_id`, `pinned_at` | Explicit selection |
| `UserThemePreference` | `user_id`, `variant`, `updated_at` | Variant only |
| `ThemeAudit` | `actor_id`, `action`, `theme_version_id`, `at` | Immutable log |

## Invariants

- A `ThemeVersion` is immutable once published.
- A tenant may pin at most one `ThemeVersion` at a time.
- A `UserThemePreference` may only select a variant allowed by the pinned version.
- Every pin or unpin writes a `ThemeAudit` row.

# Appendix: Theme Migration Guide

When the platform contract increments, existing themes must be migrated.

## Migration Steps

1. Read the contract changelog for the target version.
2. Run the migration linter against the theme source.
3. Apply automated token renames where provided.
4. Manually resolve any token group changes.
5. Re-run validation and golden frame diff.
6. Publish as a new theme version.

## Automated Renames

The linter ships a rename map per contract bump. Renames are applied only when the target token exists and the source token is unambiguous. Ambiguous cases are reported for manual resolution.

## Rollback

If a migrated theme regresses, operators unpin it and re-pin the prior version. Published versions remain immutable, so rollback is always a pin change, never a rewrite.

# Appendix: Theme Security Considerations

- Theme source files are untrusted input and must be validated before compilation.
- Compiled bundles are checksummed; mismatches are rejected at serve time.
- Theme metadata is sanitized to prevent stored script injection.
- Preview sandbox is isolated and cannot access tenant data.
- Only actors with `themes.publish` may promote a draft.

| Privilege escalation | Ability checks on every mutation |
| Preview sandbox escape | Isolated origin + no credentials |
