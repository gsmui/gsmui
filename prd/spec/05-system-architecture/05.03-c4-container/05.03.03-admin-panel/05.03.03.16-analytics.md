# Chapter 2: Data Architecture

## 2.1 Layers

```
events (raw) -> normalised -> aggregates -> query layer -> dashboards
```

| Layer | Purpose | Retention |
|-------|---------|-----------|
| Raw events | Replay and audit | 90 days |
| Normalised | Canonical schema | 2 years |
| Aggregates | Fast queries | 5 years |
| Query layer | Cached results | Minutes |

## 2.2 Event Envelope

| Field | Type | Required |
|-------|------|----------|
| `event_id` | uuid | yes |
| `name` | string | yes |
| `occurred_at` | timestamp | yes |
| `actor_id` | ulid | conditional |
| `session_id` | ulid | conditional |
| `tenant_id` | ulid | yes |
| `properties` | json | yes |
| `context` | json | yes |

## 2.3 Naming Convention

Events use `object_action` in past tense: `user_signed_up`, `component_downloaded`, `invoice_paid`. Names are lowercase snake case and never change once shipped.

## 2.4 Property Conventions

- Keys are snake case.
- Values are string, number, boolean, or null.
- No nested objects beyond one level; flatten instead.
- Currency amounts include a `currency` sibling.

## 2.5 Identity

Anonymous visitors receive a session id. On sign-in, the session is stitched to the actor id. Stitching is additive and never rewrites historical actor ids.

# Chapter 4: Metric Definitions

## 4.1 Active Users

```
active_users(d) = distinct actor_id with any event on d
```

Monthly active users use a rolling 30-day window ending on the report date.

## 4.2 New Users

```
new_users(d) = distinct actor_id whose first event is on d
```

First event is determined from the full history, not the reporting window.

## 4.3 Conversion Rate

```
conversion = completed_checkouts / checkout_started
```

Both numerator and denominator use the same window. Conversions are attributed to the day of start, not completion.

## 4.4 Retention

```
retention(d, n) = users active on d and again on d+n / users active on d
```

Cohorts are defined by first activity date. Weekly and monthly cohorts are supported.

## 4.5 Churn

```
churn(period) = subscriptions_cancelled / subscriptions_active_at_start
```

## 4.6 Download Rate

```
download_rate = component_downloaded / component_viewed
```

Rates below a minimum denominator are suppressed to avoid noise.

## 4.7 Metric Registry

Every metric has an entry with: name, definition, owner, source events, refresh cadence, and known caveats. The registry is the single source of truth.

# Chapter 6: Segmentation

## 6.1 Segment Types

| Type | Dimensions |
|------|------------|
| Plan | free, pro, team, company |
| Lifecycle | new, active, dormant, churned |
| Geography | country, region |
| Acquisition | source, campaign |
| Behaviour | feature adopters, power users |

## 6.2 Segment Rules

Segments are defined by predicates over actor attributes and event history. Predicates combine with AND/OR at most two levels deep.

## 6.3 Segment Size Limits

Segments with fewer than 50 actors are suppressed in dashboards to protect privacy. Analysts may query small segments only with explicit permission.

## 6.4 Dynamic Segments

Dynamic segments recompute daily. Static segments snapshot membership at creation for reproducible analysis.

# Chapter 7: Funnels

## 7.1 Funnel Definition

A funnel is an ordered list of steps, each an event or event property condition. Users must complete steps in order within a window.

## 7.2 Step Semantics

| Rule | Detail |
|------|--------|
| Ordering | Strictly increasing timestamps |
| Window | Configurable, default 14 days |
| Repeats | Each step counted once per user |
| Completion | Last step reached |

## 7.3 Standard Funnels

| Funnel | Steps |
|--------|-------|
| Activation | signup, first download, second download |
| Purchase | product_viewed, cart_added, checkout_started, checkout_completed |
| Documentation | doc_viewed, doc_searched, doc_viewed again |

## 7.4 Drop-off Analysis

Each step reports entry count, completion count, and drop-off rate. Breakdowns by dimension show where segments diverge.

## 7.5 Attribution

Funnel entry is attributed to the timestamp of the first step. Completion is attributed to the same cohort.

---

# Chapter 8: Retention Analysis

## 8.1 Cohort Grid

Rows are cohorts by first activity. Columns are periods after first activity. Cells are the percentage of the cohort active in that period.

## 8.2 Retention Windows

| Granularity | Periods |
|-------------|---------|
| Daily | 1–30 |
| Weekly | 1–12 |
| Monthly | 1–12 |

## 8.3 Curves

Retention curves plot the average across cohorts. Flattening indicates durable engagement; decay indicates churn risk.

## 8.4 Reactivation

A user inactive for 30 days who returns is counted as reactivated. Reactivation is reported separately from retention.

## 8.5 Interpretation Guidance

Retention is diagnostic, not a target. Improvements should come from product changes, not from metric manipulation.

# Chapter 12: Privacy and Compliance

## 12.1 Data Minimisation

Analytics stores actor ids and event properties, not personal profile data. Free-text searches are stored with the actor id but never joined to contact details.

## 12.2 Small Segment Suppression

Segments under 50 actors are suppressed in shared views. This prevents re-identification.

## 12.3 Retention

| Data | Retention |
|------|-----------|
| Raw events | 90 days |
| Normalised | 2 years |
| Aggregates | 5 years |
| Saved reports | While owned |

## 12.4 Subject Requests

Actor-level data can be exported or deleted on request. Deletion removes raw events and remaps aggregates where possible; aggregates that cannot be remapped are documented as exceptions.

## 12.5 Consent

Analytics respects consent flags. Actors who decline product analytics are excluded from behavioural metrics but still counted in aggregate service metrics where legally permitted.

# Chapter 20: Runbooks

## 20.1 RB-AN-01: Ingest Drop

1. Check ingestion endpoint health.
2. Verify rate limits not blocking clients.
3. Inspect recent deploy for schema changes.
4. Replay buffered events if available.
5. Update client SDKs if needed.

## 20.2 RB-AN-02: Pipeline Lag

1. Identify backlog size.
2. Scale normalisation workers.
3. Check for a poison event causing retries.
4. Quarantine the poison event.
5. Confirm lag returns to target.

## 20.3 RB-AN-03: Metric Discrepancy

1. Compare metric to source events.
2. Check aggregate partition for missing data.
3. Rebuild the affected aggregate.
4. Document the discrepancy window.
5. Add a regression check.

## 20.4 RB-AN-04: Export Backlog

1. Inspect export queue depth.
2. Scale export workers.
3. Prioritise smaller exports.
4. Notify owners of delays.
5. Review export limits.

# Chapter 22: Metric Governance

## 22.1 Ownership

Every metric has exactly one owner team. Owners approve definition changes and are responsible for accuracy.

## 22.2 Change Process

1. Propose change with rationale.
2. Owner reviews impact.
3. Update registry with a version note.
4. Communicate to consumers.
5. Monitor for anomalies for two weeks.

## 22.3 Deprecation

Deprecated metrics remain queryable for one year with a warning. Consumers are notified at 90, 30, and 7 days.

## 22.4 Definition Drift

Definitions are reviewed quarterly. Any metric whose code drifted from its documentation is corrected or re-documented.

# Chapter 29: Support FAQ

**Why does a metric differ from billing?** Billing is the financial source of truth; analytics mirrors behavioural events and may lag or differ on edge cases.

**Why is my segment hidden?** Segments below 50 actors are suppressed to protect privacy.

**Why is my report too broad?** Narrow the time range or add filters to stay within the cost limit.

**How current is the data?** Metrics refresh within five minutes; dashboards state their refresh cadence.

**Can I export raw events?** No. Exports contain aggregates; raw events are engineering-only.

# Chapter 33: Ingestion SDK Contract

## 33.1 Client Responsibilities

| Responsibility | Detail |
|----------------|--------|
| Buffering | Queue events in memory up to 100 |
| Batching | Flush every 5 s or 50 events |
| Retry | Exponential backoff, 3 attempts |
| Deduplication | Reuse event ids on retry |
| Consent | Skip emission when declined |

## 33.2 Server Responsibilities

| Responsibility | Detail |
|----------------|--------|
| Authentication | Tenant-scoped key |
| Validation | Envelope and schema |
| Idempotency | Dedupe by event id |
| Acknowledgement | Return accepted ids |
| Backpressure | 429 with retry-after |

## 33.3 Failure Semantics

Clients never block UI on analytics. Dropped events are acceptable; blocking is not. Loss is logged locally and reported in aggregate.

## 33.4 Versioning

SDKs send their version in `context`. Breaking protocol changes require a new endpoint version; old versions are supported for one year.

# Chapter 34: Schema Registry

## 34.1 Purpose

The registry defines the allowed shape of every event. It prevents silent drift and enables validation at ingest.

## 34.2 Schema Format

| Field | Notes |
|-------|-------|
| `name` | Event name |
| `version` | Integer |
| `properties` | Map of key to type |
| `required` | Subset of keys |
| `owner` | Team |
| `status` | active, deprecated |

## 34.3 Compatibility Rules

- Adding optional properties is backward compatible.
- Removing a property is a breaking change.
- Changing a type is a breaking change.
- Renaming is removal plus addition.

## 34.4 Enforcement

Ingest validates against the active schema. Unknown properties are allowed but flagged; missing required properties reject the event.

## 34.5 Evolution

Schemas version upward. Multiple versions may be active during client rollouts. The registry never deletes versions.

# Chapter 35: Aggregation Internals

## 35.1 Rollup Levels

| Level | Grain | Use |
|-------|-------|-----|
| Raw | Per event | Ad hoc |
| Minute | Per minute | Live widgets |
| Hour | Per hour | Product dashboards |
| Day | Per day | Executive |
| Month | Per month | Trends |

## 35.2 Rollup Job

1. Read events for the closed bucket.
2. Group by metric and dimensions.
3. Compute value.
4. Upsert aggregate.
5. Mark bucket complete.

## 35.3 Late Events

Events arriving after a bucket closes trigger a partial recompute of the affected bucket and its parents. Late events are accepted within 24 hours.

## 35.4 Idempotency

Rollups are idempotent because they replace bucket values rather than incrementing them.

## 35.5 Backfill

Backfills recompute from raw events for a date range. They run at low priority and are rate limited to protect query performance.

# Chapter 36: Query Engine

## 36.1 Query Planning

The engine selects the finest aggregate that satisfies the requested grain, falling back to raw only when required.

## 36.2 Cost Control

| Guard | Value |
|-------|-------|

| Max dimensions | 3 |

## 36.3 Caching

| Cache | TTL |
|-------|-----|
| Metric series | 60 s |

## 36.4 Result Pagination

Series results paginate by date. Table results paginate by row. Cursors are opaque and expire after 10 minutes.

## 36.5 Query Auditing

Queries touching sensitive dimensions are logged with actor, range, and dimensions. Logs are retained for 90 days.

| Driver | Notes |
|--------|-------|
| Ingestion | Per million events |

| Query compute | Per scan |

## 37.1 Optimisation Levers

- Longer aggregate retention reduces raw scans.
- Query caching absorbs repeat dashboard loads.

## 37.3 Reporting

Costs are reported monthly by team and driver. Unexplained spikes are investigated as potential bugs.

# Chapter 38: Migration Guide

## 38.1 From Legacy Analytics

1. Inventory legacy events and metrics.
2. Map to registry names.
3. Dual-emit for two weeks.
4. Verify parity on key metrics.
5. Cut over dashboards.
6. Retire legacy emission.

## 38.2 Historical Import

Historical aggregates may be imported when raw events are unavailable. Imported aggregates are marked `imported` and excluded from recompute.

## 38.3 Verification

Parity is checked on three metrics across four weeks. A variance over 2% blocks cutover.

# Appendix U: Aggregation Pseudocode

```
for bucket in closed_buckets:
    events = read(events, where: occurred_at in bucket)
    grouped = group_by(events, metric.dimensions)
    for key, rows in grouped:
        value = metric.compute(rows)
        upsert(aggregates, bucket, metric.key, key, value)
    mark_complete(bucket)
```

## U.1 Late Event Handling

```
for event in late_events:
    for bucket in affected_buckets(event.occurred_at):
        recompute(bucket)
```

Recompute is bounded to the last 24 hours by default.

# Appendix V: Retention Mathematics

## V.1 Cohort Retention

```
retention(n) = active_in_period_n / cohort_size
```

Example: a cohort of 1,000 users with 220 active in month 3 gives 22% retention.

## V.2 Weighted Average

```
weighted = sum(active_n) / sum(cohort_size)
```

Weighting by cohort size prevents small cohorts from distorting the curve.

## V.3 Confidence

Cohorts smaller than 100 users are flagged as low confidence and excluded from trend lines.

# Appendix W: Incident Examples

## W.1 Double Counting

A client SDK retried without reusing event ids, doubling downloads. Fix: memory owns id reuse across retries. Detection: download rate spike without corresponding view spike.

## W.2 Schema Drift

A property changed from string to number, causing aggregate failures. Fix: schema registry blocks ingest. Detection: ingest error rate spike.

## W.3 Stale Dashboard

A rollup job failed silently, leaving yesterday's values. Fix: bucket completion alerts. Detection: freshness SLO breach.

## W.4 Privacy Regression

A report exposed a 20-user segment. Fix: suppression enforced at query layer. Detection: automated privacy test in CI.

# Appendix X: Extended FAQ

**Can I query raw events?** Only engineering can, for debugging and backfills. Analysts use aggregates.

**Why is my number different from last week's report?** Late events can change recent buckets. Historical buckets older than 24 hours are stable.

**Can I create a metric?** Metrics require an owner and a registry entry, reviewed by the data lead.

**What happens to opted-out users?** They are excluded from behavioural metrics but counted in aggregate service metrics.

**Are dashboards public?** No. Sharing is internal by link only in v1.

**How long do exports live?** Download links expire after 24 hours.
