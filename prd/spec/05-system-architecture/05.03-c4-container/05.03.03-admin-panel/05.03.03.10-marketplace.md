# Marketplace Architecture Context

The admin Marketplace module is the curation and operations layer over the public Marketplace container:

| Boundary | Owner | Admin Module Role |
|----------|-------|-------------------|
| Product catalog | Type modules (Components/Templates/Themes/Icons/UI Kits) | Unified view, cross-type actions |
| Checkout & payments | Payments container | Read events, process refunds |

| Downloads | CDN service | Signed URL monitoring |
| Payouts | Finance container | Prepare runs, approvals |
| Fraud | Risk service | Configure rules, review flags |

All cross-boundary communication via events with signature verification and replay protection.

# Review Pipeline (Unified)

## Unified Queue

| Element | Behavior |
|---------|----------|
| Single queue across types | Filterable by type chips |
| Claim locks | Same soft-lock model as type modules |
| Type-specific checks | Delegated to originating module's pipeline |
| Price verification step | New marketplace-level check |
| Publishing | Publishes to marketplace storefront cache |

## Price Verification Checklist

| Check | Rule |
|-------|------|
| Price within category band | Warn if > 2x category median |
| Screenshot ↔ price consistency | Reviewer judgment (premium look) |
| No misleading "free trial" copy | Reject if deceptive |
| Support SLA declared for paid | Required field |
| License terms present | Blocking |

## Decision Flow

```
submitted --> validated (type checks passed)
          --> price_verified
          --> approved --> published
          |-> needs_changes (feedback) --> resubmitted
          |-> rejected (reason + cooldown)
```

All decisions emit events consumed by originating modules (keeps module state consistent).

### Order States

```
pending_payment --> processing --> completed --> refunded (full/partial)
       |               |
       +--> failed     +--> disputed --> chargeback_lost / chargeback_won
       +--> canceled
completed --> cancellation_requested --> canceled
```

| State | Description |
|-------|-------------|
| pending_payment | Payment intent created, awaiting confirmation |
| processing | Webhook received, entitlement grant in progress |
| completed | Entitlement granted, receipt sent |
| failed | Payment failed; retryable |
| canceled | Pre-fulfillment cancel |
| refunded | Full/partial refund processed |
| disputed | Chargeback/dispute open |
| chargeback_lost/won | Dispute outcome |

## Refund Policy Enforcement

| Rule | Enforcement |
|------|-------------|
| Refund window | Configurable per product type (default 30 days) |
| Download usage check | > N downloads → requires `orders.refund.override` |
| Duplicate refund guard | Remaining balance computed; over-refund blocked |
| Reason required | Min 10 chars; categories for analytics |
| Ledger entries | Immutable; counter-entries for corrections |
| Buyer notification | Template email with entitlement note |

## Dispute Workflow

1. Provider webhook opens dispute; order state `disputed`.
2. Evidence pack generated (license, download logs, IP timestamps, support history).
3. Admin uploads additional evidence before provider deadline (countdown shown).
4. Outcome recorded; won → entitlement restored; lost → loss ledger + risk review.
5. Pattern analysis feeds fraud rules (same buyer, same product type).

# Fraud Controls

## Rule Engine

| Rule | Signal | Action |
|------|--------|--------|
| Velocity | > 10 orders/hour same fingerprint | Hold + flag |
| Card testing | Multiple failed small orders | Block fingerprint |
| Refund cycling | > 2 refunds same product/user | Review flag |
| Coupon abuse | Same code burst > threshold | Auto-pause coupon |
| Self-purchase | Author buying own products | Flag + block |
| Chargeback pattern | Buyer with prior losses | Pre-authorization hold |

## Flag Resolution Workflow

1. Flag raised with evidence bundle.
2. Assigned to fraud reviewer (`marketplace.fraud`).
3. Actions: clear / restrict buyer / void orders / refer to payments provider.
4. All resolutions audited; pattern feeds rule tuning.

## Buyer Restriction Levels

| Level | Effect |
|-------|--------|
| watch | Extra signals logged |
| hold | Orders require manual release |
| block | Purchases disabled; support path only |

# Runbooks (Marketplace)

## Symptom: Webhook storm / provider incident

1. Check provider status page; incident declared if confirmed.
2. Webhooks queue in `payments` queue; no data loss (signature-verified on drain).
3. Entitlement grants drain post-incident; reconciliation job verifies parity.
4. Buyer-facing: banner if delays > 1h.

## Symptom: Ledger variance detected

1. Pull reconciliation report; identify entry deltas.
2. Classify: timing (webhook delay) vs true variance.
3. True variance → incident; ledger correction via counter-entry with dual approval.
4. Root cause review; webhook ordering check.

## Symptom: Coupon abuse spike

1. Auto-pause triggered; verify velocity chart.
2. Identify redemptions post-flag; assess legitimacy.
3. Revoke suspicious entitlements; restrict buyers per workflow.
4. Tune rule thresholds; post-incident report.

## Symptom: Payout run disbursement failure

1. Provider error codes reviewed per author.
2. Failed entries retry queue; author contacted for payment details.
3. Partial run completion allowed; exceptions listed.
4. Audit both approvers + failure handling.

# Appendix: Webhook Processing Specification

## Inbound Webhook Contract

| Property | Value |
|----------|-------|
| Signature header | `X-GsmUi-Payment-Signature` (HMAC-SHA256 over raw body) |
| Timestamp tolerance | ±5 minutes (replay guard) |
| Event ledger | Event IDs stored permanently for dedup |
| Ordering | Per-intent sequencing via intent id |
| Failure policy | Exponential backoff retries (max 8), then DLQ + alert |

## Processing Pipeline

1. Verify signature + timestamp.
2. Check event ledger for dedup.
3. Persist raw event (audit).
4. Route to handler by event type.
5. Idempotent state application.
6. Emit domain events (internal).

## Critical Event Types

| Provider Event | Internal Action |
|----------------|-----------------|
| `payment_intent.succeeded` | → processing → completed, grant entitlement |
| `payment_intent.failed` | → failed, retry guidance |
| `charge.refunded` | Reconcile refund records |
| `charge.dispute.created` | → disputed, evidence pack |
| `charge.dispute.closed` | Outcome ledger |
| `payout.paid` / `payout.failed` | Payout run status |

# Appendix: Entitlement Lifecycle

```
granted --> active --> revoked (refund/abuse)
                   --> expired (subscription ends, future)
active --> reinstated (dispute won)
```

| Event | Effect |
|-------|--------|
| Order completed | granted |
| Refund | revoked with reason |
| Dispute lost | revoked |
| Dispute won | reinstated |
| Manual support grant | granted with incident ref |

Downloads/install endpoints re-check entitlement per request; revoked → 403 with support path.

# Appendix: Marketplace Domain Model

The marketplace is the commercial surface of GsmUi. It sells templates, component packs, theme bundles, and swag items. The domain model separates catalogue concerns from transaction concerns so that pricing, inventory, and fulfilment can evolve independently.

## Core Entities

| Entity | Purpose | Key Fields |
|--------|---------|------------|
| `Product` | Sellable catalogue entry | `id`, `slug`, `type`, `status`, `vendor_id` |
| `ProductVariant` | Purchasable form of a product | `product_id`, `sku`, `price_cents`, `currency` |
| `Price` | Effective price snapshot | `variant_id`, `amount_cents`, `tax_behavior` |
| `Order` | Customer intent to purchase | `id`, `customer_id`, `status`, `total_cents` |
| `OrderItem` | Line item on an order | `order_id`, `variant_id`, `qty`, `unit_cents` |
| `Payment` | Attempt to collect funds | `order_id`, `provider`, `status`, `amount_cents` |
| `Refund` | Return of funds | `payment_id`, `amount_cents`, `reason` |
| `Dispute` | Chargeback or claim | `payment_id`, `status`, `evidence_due_at` |
| `Coupon` | Discount instrument | `code`, `kind`, `value`, `constraints` |
| `Campaign` | Time-bound promotion | `id`, `window`, `rules`, `budget_cents` |
| `Payout` | Vendor disbursement | `vendor_id`, `period`, `amount_cents`, `status` |
| `LedgerEntry` | Immutable money movement | `account`, `direction`, `amount_cents`, `ref` |

## Entity Relationships

- A `Product` has one or more `ProductVariant` records.
- A `ProductVariant` has exactly one active `Price`.
- An `Order` has one or more `OrderItem` records.
- An `Order` may have multiple `Payment` attempts but at most one captured `Payment`.
- A `Payment` may have zero or more `Refund` records whose sum never exceeds the captured amount.
- A `Payment` may have at most one active `Dispute`.
- Every money movement writes a `LedgerEntry` in the same transaction.

## Lifecycle States

### Product Lifecycle

```
draft -> review -> published -> archived
```

### Order Lifecycle

```
created -> pending_payment -> paid -> fulfilled -> completed
                          \-> cancelled
```

### Payment Lifecycle

```
initiated -> authorized -> captured
           \-> failed
           \-> cancelled
captured -> refunded (partial or full)
captured -> disputed
```

### Payout Lifecycle

```
scheduled -> processing -> paid
                        \-> failed -> retry_scheduled
```

# Appendix: Catalogue and Unified Product Model

GsmUi sells digital goods (templates, packs, themes) and physical goods (swag). The catalogue normalises both behind a unified product model so that search, cart, and checkout logic do not branch on product type.

## Product Types

| Type | Fulfilment | Inventory | Examples |
|------|-----------|-----------|----------|
| `template` | Instant download | None | Starter dashboard template |
| `component_pack` | Instant download | None | Form components pack |
| `theme` | Entitlement grant | None | Marketplace theme bundle |
| `swag` | Physical shipment | Tracked | Hoodie, sticker pack |

## Unified Attributes

All products expose a common attribute set for search and listing:

- `title`, `slug`, `summary`, `description`.
- `price_range` derived from variants.
- `media` gallery references.
- `tags` and `categories`.
- `vendor` and `rating_summary`.
- `availability` derived from type and inventory.

## Digital Entitlements

Digital purchases grant entitlements rather than files. An entitlement references the purchased `ProductVariant` and the customer, with a validity window. Downloads are issued as short-lived signed URLs scoped to the entitlement.

## Physical Inventory

Swag products track inventory at the variant level. Inventory decrements on order placement and restores on cancellation or refund before shipment. Low-stock thresholds emit alerts to the operations channel.

# Appendix: Checkout Flow Specification

Checkout is a multi-step flow guarded by idempotency keys at every mutation boundary.

## Steps

1. **Cart validation.** Re-price all items server-side; reject stale prices.
2. **Address capture.** Collected only for physical goods.
3. **Discount application.** Coupons and campaign rules evaluated server-side.
4. **Tax calculation.** Tax computed against the effective price snapshot.
5. **Payment intent.** A payment intent is created with the final amount.
6. **Confirmation.** The order transitions to `paid` on capture.

## Idempotency

- Cart mutations require an `Idempotency-Key` header.
- Payment intent creation derives its idempotency key from the order id.
- Webhook processing is idempotent by provider event id.

## Failure Handling

| Failure | Behaviour |
|---------|-----------|
| Price changed | Reject with `price_stale`, force re-review |
| Coupon invalid | Remove coupon, continue with warning |
| Payment declined | Keep order in `pending_payment`, allow retry |
| Inventory exhausted | Reject line item, offer alternative |
| Tax service outage | Block checkout, alert on-call |

## Guest Checkout

Guest checkout is supported for digital goods only. Physical goods require an account so that shipment tracking can be attached to a durable customer record.

# Appendix: Payments Integration

Payments are processor-agnostic. The platform integrates one or more processors behind a common interface.

## Processor Interface

| Operation | Contract |
|-----------|----------|
| `authorize` | Reserve funds, return authorization id |
| `capture` | Capture a prior authorization |
| `refund` | Return funds against a capture |
| `void` | Release an authorization |
| `fetch` | Read current payment state |

## Supported Methods

- Card payments via hosted fields; no card data touches GsmUi servers.
- Wallet payments where the processor supports them.
- Manual invoice for enterprise customers.

## PCI Scope

GsmUi remains out of PCI scope for card data because card entry happens in processor-hosted fields. The platform stores only processor tokens and the last four digits for display.

## Retry Policy

Failed captures retry with exponential backoff up to three attempts. Each retry reuses the same idempotency key so that a duplicate capture cannot occur.

# Appendix: Dispute and Chargeback Handling

Disputes are initiated by the payment processor on behalf of the cardholder. The platform must respond with evidence before the processor's deadline.

## Dispute Lifecycle

```
opened -> evidence_due -> under_review -> won | lost
```

## Evidence Package

- Order and payment records.
- Delivery or entitlement proof.
- Customer communication history.
- Refund policy acknowledgement at purchase.

## Deadlines

The processor sets `evidence_due_at`. The platform schedules reminders at 72, 24, and 4 hours before the deadline. Missing the deadline results in an automatic loss.

## Outcomes

- **Won.** Funds remain; dispute closed.
- **Lost.** Funds reversed; ledger entry written; customer notified.
- **Accepted.** Operator may accept a dispute early to reduce overhead.

# Appendix: Coupons and Campaigns

Coupons are static discount instruments. Campaigns are time-bound promotions that may generate coupons or apply rules dynamically.

## Coupon Kinds

| Kind | Behaviour |
|------|-----------|
| `percent` | Percentage off eligible subtotal |
| `fixed` | Fixed amount off eligible subtotal |
| `free_shipping` | Waive shipping for physical goods |
| `bundle` | Discount applied to a product set |

## Constraints

- Minimum subtotal.
- Maximum redemptions.
- Per-customer limit.
- Product or category scope.
- Validity window.

## Campaign Rules

A campaign evaluates rules in order and applies the first matching rule. Rules may stack with coupons only when explicitly allowed. Campaign budgets cap total discount spend; exhausted budgets disable the campaign automatically.

## Velocity Checks

Coupon redemption velocity is monitored per customer and per IP. Sudden spikes trigger the fraud pipeline.

# Appendix: Payouts and Reconciliation

Vendors are paid on a periodic schedule from captured funds net of refunds, disputes, and platform fees.

## Payout Calculation

```
payout = captured - refunds - disputes_lost - platform_fee - reserve_hold
```

## Reserve Policy

A rolling reserve holds a percentage of captured funds for a fixed window to cover future refunds and disputes. The reserve releases after the window elapses without claims.

## Reconciliation

Reconciliation matches ledger entries against processor settlement reports. Any unmatched entry raises a reconciliation exception.

| Check | Frequency |
|-------|-----------|
| Captured vs settled | Daily |
| Refunds vs settled | Daily |
| Disputes vs settled | Daily |
| Reserve release | Weekly |
| Payout balance | Per payout |

## Exceptions

Exceptions are triaged within one business day. Unresolved exceptions block the next payout cycle for the affected vendor.

# Appendix: Fraud Detection Rules

Fraud rules run at checkout and post-capture. Rules are scored and combined into a risk decision.

## Rule Examples

| Rule | Signal | Action |
|------|--------|--------|
| Velocity | Too many orders per IP | Review |
| Mismatch | Billing and shipping far apart | Review |
| Disposable email | Known disposable domain | Challenge |
| Card testing | Many small declines | Block |
| Coupon abuse | Repeated coupon reuse | Block |
| Refund abuse | High refund ratio | Review |

## Decisions

- **Allow.** No action.
- **Challenge.** Require additional verification.
- **Review.** Hold for manual review.
- **Block.** Reject the transaction.

## Feedback Loop

Confirmed fraud and confirmed legitimate orders feed back into rule tuning. Rule changes are versioned and audited.

# Appendix: Webhooks and Idempotency

The marketplace receives webhooks from payment processors and emits webhooks to vendors.

## Inbound Webhooks

- Verified with a shared secret signature.
- Deduplicated by provider event id.
- Processed asynchronously with retries.
- Failures routed to a dead-letter queue.

## Outbound Webhooks

- Signed with a per-vendor secret.
- Retried with exponential backoff for 24 hours.
- Delivery attempts recorded for audit.

## Idempotency Contract

Every webhook handler is idempotent. Replaying the same event must not double-count money or state transitions. Handlers key on the provider event id and the affected aggregate id.

# Appendix: Marketplace Operational Runbooks

## RB-MKT-01: Payment Processor Outage

1. Confirm outage via processor status page.
2. Switch checkout to maintenance banner.
3. Queue orders in `pending_payment`.
4. Resume when processor recovers.
5. Replay queued payment intents idempotently.

## RB-MKT-02: Refund Queue Backlog

1. Inspect queue depth and worker health.
2. Scale refund workers.
3. Prioritise disputes and defective-goods refunds.
4. Verify ledger consistency after drain.

## RB-MKT-03: Reconciliation Exception Spike

1. Pull exception report.
2. Group by processor and date.
3. Escalate systemic mismatches to finance.
4. Block affected payouts until resolved.

## RB-MKT-04: Vendor Payout Failure

1. Identify failed payout and reason.
2. Verify vendor banking details unchanged.
3. Retry payout with the same idempotency key.
4. Notify vendor if retry fails twice.
