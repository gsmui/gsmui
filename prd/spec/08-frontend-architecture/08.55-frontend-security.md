# 08.55 - Frontend Security

**Project:** GsmUi
**Section:** 08 - Frontend Architecture
**Framework:** Laravel 13 · GsmUi Component Library · Content Security Policy
**Version:** 1.0.0

---

> See also: `07.57-security.md` (backend security), `08.06-css-architecture.md` (style injection model), `08.48-pwa.md` (worker-src additions). This document specifies the *frontend CSP contract* and does NOT re-document server-auth or encryption.

# Purpose

GsmUi bundles load **zero external resources** — no CDN fonts, no external scripts, no iframes. This makes a strict Content Security Policy possible and is a core selling point. This document pins the CSP resource profile, the `CspMiddleware`, the publishable config, and the hard "never" rules implementers must obey.

---

## 1. CSP Resource Profile

| Resource | Status | CSP Directive |
| --- | --- | --- |
| Scripts | `dist/gsmui.js` (self-hosted) | `script-src 'self'` |
| Styles | `dist/editor.css` + `adoptedStyleSheets` | `style-src 'self' 'unsafe-inline'` |
| Fonts | System fonts only — no `@font-face` | Not needed |
| Images | Inline SVG icons only | `img-src 'self' data:` |
| Network | No `fetch()`, XHR, WebSocket, Workers | `connect-src 'self'` |
| `eval()` | Not used — no `unsafe-eval` required | Not needed |

---

## 2. CspMiddleware

Located at `src/Http/Middleware/CspMiddleware.php`. It injects the CSP header on every response. Publishable config lives at `stubs/config/gsmui-pro-csp.php`:

```bash
php artisan vendor:publish --tag=gsmui-pro-csp-config
```

The middleware reads the config array and builds the `Content-Security-Policy` header. Adding a worker requires extending the config (see `08.48`).

---

## 3. Hard "Never" Rules

From `AGENTS.md`:

- **Never** add CDN script/style/font tags to Blade templates — bundle everything in `dist/`.
- **Never** use `eval()`, `Function()`, `blob:`, or `data:` URIs for executable content.
- If you add a network request (`fetch`, XHR, WebSocket), update the CSP config docs.
- If you add Web Workers or Service Workers, add `worker-src 'self'` to the config.
- Prefer `adoptedStyleSheets` over inline `<style>` tags for dynamic CSS.

---

## 4. XSS / Injection Surface

| Vector | Mitigation |
| --- | --- |
| User HTML in docs/preview | Blade auto-escaping; `@verbatim` for samples (`08.53`) |
| Livewire payload | Signed/encrypted by Livewire 4; no manual handling |
| Inline SVG icons | First-party only; `img-src 'self' data:` |
| JSON-LD | Server-rendered static; not executable (`08.47`) |

The PHP test `tests/Browser/CspHeaderTest.php` asserts the header contains `script-src 'self'` and no `unsafe-eval`. Playwright runs against `/gsmui-csp-test` with `CSP_ENABLED=true` (`08.49`). Any new resource type must extend both the config and these tests.

## 6. Open Questions / Risks

- **`unsafe-inline` for styles:** `style-src 'self' 'unsafe-inline'` is required for `adoptedStyleSheets`/runtime styles. Track whether constructable stylesheets can drop `'unsafe-inline'` entirely.
- **Third-party integrations:** if a future feature needs an external font/API, it breaks the zero-external guarantee — flag before building.
- **Config drift:** published `gsmui-pro-csp.php` copies can fall out of sync with the package default; add a config-diff check.

## 7. Content Security Policy — Directive Reference

This section provides a comprehensive reference for every CSP directive relevant to GsmUi, including how each directive interacts with the component library and what violations look like in practice.

### 7.1 `script-src`

The `script-src` directive controls which JavaScript sources the browser will execute. GsmUi pins this to `'self'`, meaning only scripts served from the same origin are permitted.

**Configuration in `gsmui-pro-csp.php`:**

```php
'script-src' => [
    "'self'",
],
```

**What this blocks:**
- Inline `<script>` tags (except the bootstrap primer, which must use `'unsafe-inline'` or be moved to a nonce)
- CDN-hosted scripts (`https://cdn.jsdelivr.net/...`)
- `eval()` / `new Function()` calls
- Blob URLs (`blob:`)
- Data URIs with executable content (`data:text/javascript,...`)

**Bootstrap primer exception:** The dark-mode FOUC-prevention script in `<head>` is inline. To remain CSP-clean without `'unsafe-inline'`, Gsmui uses one of these strategies:

| Strategy | Directive Additions | Trade-off |
| --- | --- | --- |
| Nonce-based | `'nonce-<random>'` generated per request | Requires server-side nonce injection; nonce must rotate per response |
| Hash-based | `'sha256-<hash>'` of the exact script text | Script must never change; any edit requires a new hash |
| External file | `'self'` only (no inline exception) | Slightly delayed FOUC prevention; script must be `<script src>` |

**Recommended approach:** Hash-based. The bootstrap script is stable and rarely changes, so a static hash is acceptable. The CSP config ships a pre-computed `sha256` of the canonical bootstrap snippet, and the `CspMiddleware` includes it in the `script-src` directive.

**Violation reporting:** In development, CSP violations appear in the browser console as `Refused to execute inline script`. In production, GsmUi can optionally report violations to an endpoint:

```php
'script-src' => [
    "'self'",
    // "'report-uri'" => '/csp-report', // uncomment for violation logging
],
```

### 7.2 `style-src`

The `style-src` directive controls CSS sources. GsmUi requires `'unsafe-inline'` for runtime-generated styles via `adoptedStyleSheets`.

**Configuration:**

```php
'style-src' => [
    "'self'",
    "'unsafe-inline'",
],
```

**Why `'unsafe-inline'` is needed:**
- `adoptedStyleSheets` (constructable stylesheets) are injected by component JS at runtime
- Tailwind v4's JIT compiler may emit inline `style` attributes on some elements
- Dynamic theme overrides use `element.style.setProperty()` which CSP does not block (inline *styles* via `style` attribute are not governed by `style-src` — only `<style>` tags and `style=` attributes in certain contexts)

**Path to dropping `'unsafe-inline'`:**
- Use `CSSStyleSheet` constructor + `replaceSync()` exclusively (already the pattern)
- Ensure no `<style>` tags are created at runtime
- Use `nonce`-based approach for any remaining `<style>` tags
- Track progress in the security backlog

**Violation pattern:** `Refused to apply inline style` — typically caused by a component creating a `<style>` element instead of using `adoptedStyleSheets`.

### 7.3 `img-src`

The `img-src` directive controls image sources. GsmUi uses `'self'` and `data:` for inline SVG icons.

**Configuration:**

```php
'img-src' => [
    "'self'",
    'data:',
],
```

**Why `data:` is needed:**
- Inline SVG icons rendered via `<img src="data:image/svg+xml,...">` in some legacy components
- Avatar placeholder images encoded as data URIs
- Component documentation previews showing data-URI images

**Best practice:** Phase out `data:` images in favor of inline `<svg>` elements (which are governed by `img-src` only when used as `<img>` src, not when embedded directly in the DOM). Pure inline `<svg>` is not restricted by CSP at all — it is treated as markup, not an external resource.

### 7.4 `connect-src`

The `connect-src` directive controls `fetch()`, `XMLHttpRequest`, `WebSocket`, and `EventSource` connections. GsmUi pins this to `'self'`.

**Configuration:**

```php
'connect-src' => [
    "'self'",
],
```

**What this blocks:**
- External API calls from client-side JS
- WebSocket connections to third-party servers
- Server-Sent Events from external origins

**Livewire exception:** Livewire 4 uses `fetch()` internally for wire:model round-trips. Since Livewire requests go to the same origin, `'self'` covers this. If the app uses a separate API domain, the config must add it:

```php
'connect-src' => [
    "'self'",
    'https://api.example.com',
],
```

**Monitoring:** Any new `fetch()`, `XMLHttpRequest`, or `WebSocket` call in the codebase must be audited against this directive. Add a lint rule that flags network calls outside of approved locations.

### 7.5 `font-src`

The `font-src` directive controls font loading. GsmUi uses system fonts only — no `@font-face` declarations exist in the codebase.

**Configuration:**

```php
'font-src' => [
    "'self'",
],
```

**System font stack:**

```css
--gsmui-font-sans: ui-sans-serif, system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif;
--gsmui-font-mono: ui-monospace, SFMono-Regular, "SF Mono", Menlo, Consolas, "Liberation Mono", monospace;
```

**Violation scenario:** If a developer accidentally adds a Google Fonts `<link>` tag, the browser will block the font file and log `Refused to load the font`. This is the intended behavior — bundle fonts locally or use system fonts.

### 7.6 `frame-src` / `child-src`

GsmUi does not use iframes or child frames. These directives are omitted entirely (defaulting to `'none'`).

```php
// No frame-src or child-src configuration needed
// CSP default: 'none' for both
```

**Exception:** If a future feature needs an embedded video (YouTube, Vimeo), it requires adding `frame-src` with the specific provider origin. This must be flagged as a security review item before implementation.

### 7.7 `worker-src`

Web Workers and Service Workers have their own directive. GsmUi adds this only when PWA features are enabled (`08.48-pwa.md`).

**Configuration (PWA disabled):**

```php
// No worker-src needed
```

**Configuration (PWA enabled):**

```php
'worker-src' => [
    "'self'",
],
```

**What this blocks:**
- `new Worker('https://external.com/worker.js')` — external workers
- `new SharedWorker('blob:...')` — blob-based workers
- `navigator.serviceWorker.register('...')` — third-party service workers

### 7.8 `base-uri`

The `base-uri` directive controls the `<base>` element, preventing attackers from injecting a base tag to hijack relative URLs.

```php
'base-uri' => [
    "'self'",
],
```

### 7.9 `form-action`

The `form-action` directive controls where forms can submit. GsmUi pins this to `'self'`.

```php
'form-action' => [
    "'self'",
],
```

### 7.10 `frame-ancestors`

The `frame-ancestors` directive controls who can embed the GsmUi site in an iframe (clickjacking protection). This replaces the older `X-Frame-Options` header.

```php
'frame-ancestors' => [
    "'self'",
],
```

### 7.11 `upgrade-insecure-requests`

Forces all HTTP requests to HTTPS. GsmUi enables this in production:

```php
'upgrade-insecure-requests' => true,
```

### 7.12 Full CSP Configuration Array

```php
<?php

return [
    /*
    |--------------------------------------------------------------------------
    | Content Security Policy Configuration
    |--------------------------------------------------------------------------
    |
    | GsmUi CSP: zero external resources, eval-free, self-hosted only.
    | Published via: php artisan vendor:publish --tag=gsmui-pro-csp-config
    |
    */

    'enabled' => env('CSP_ENABLED', true),

    'report-only' => env('CSP_REPORT_ONLY', false),

    'directives' => [
        'default-src' => ["'self'"],
        'script-src'  => ["'self'"],
        'style-src'   => ["'self'", "'unsafe-inline'"],
        'img-src'     => ["'self'", 'data:'],
        'connect-src' => ["'self'"],
        'font-src'    => ["'self'"],
        'base-uri'    => ["'self'"],
        'form-action' => ["'self'"],
        'frame-ancestors' => ["'self'"],
    ],

    'report-uri' => env('CSP_REPORT_URI'),

    'nonce' => [
        'enabled' => false,
        'length'  => 32,
    ],

    'hash' => [
        // Pre-computed sha256 of the dark-mode bootstrap script
        'script' => 'sha256-ABC123...', // update when bootstrap changes
    ],
];
```

## 8. Security Headers Beyond CSP

CSP is the centerpiece, but GsmUi should ship a complete set of security headers. The `CspMiddleware` can be extended or a companion middleware added for these.

### 8.1 `X-Content-Type-Options`

Prevents MIME-type sniffing. Always set to `nosniff`.

```
X-Content-Type-Options: nosniff
```

This is critical for preventing the browser from interpreting uploaded files as scripts. If a user uploads a file with a `.txt` extension that contains HTML, `nosniff` prevents the browser from rendering it as HTML.

### 8.2 `Referrer-Policy`

Controls how much referrer information is sent with requests.

```
Referrer-Policy: strict-origin-when-cross-origin
```

**Options considered:**

| Value | Behavior | GsmUi Fit |
| --- | --- | --- |
| `no-referrer` | Never send referrer | Too aggressive; breaks analytics |
| `origin` | Send origin only, not full path | Acceptable |
| `strict-origin-when-cross-origin` | Full path for same-origin, origin only for cross-origin | **Recommended** |
| `same-origin` | Only send referrer for same-origin requests | Acceptable |

### 8.3 `X-Frame-Options`

Legacy clickjacking protection. Superseded by `frame-ancestors` in CSP but still useful for older browsers.

```
X-Frame-Options: SAMEORIGIN
```

### 8.4 `Permissions-Policy`

Controls browser features (camera, microphone, geolocation, etc.). GsmUi disables features not used by the application.

```
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), magnetometer=(), gyroscope=(), accelerometer=()
```

**Implementation in middleware:**

```php
protected function permissionsPolicy(): string
{
    $directives = [
        'camera'       => '()',
        'microphone'   => '()',
        'geolocation'  => '()',
        'payment'      => '()',
        'usb'          => '()',
        'magnetometer' => '()',
        'gyroscope'    => '()',
        'accelerometer'=> '()',
    ];

    return collect($directives)
        ->map(fn ($value, $key) => "{$key}={$value}")
        ->implode(', ');
}
```

### 8.5 `Strict-Transport-Security` (HSTS)

Forces browsers to use HTTPS for all future requests to the domain.

```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
```

**Note:** HSTS is typically set by the web server (Nginx, Apache) or reverse proxy (Cloudflare), not by PHP middleware. However, the middleware can set it as a fallback.

### 8.6 `X-XSS-Protection`

Legacy XSS filter in older browsers. Modern browsers have deprecated this in favor of CSP.

```
X-XSS-Protection: 0
```

Setting to `0` disables the legacy filter, which can actually *introduce* XSS vulnerabilities in some edge cases. CSP is the authoritative protection.

### 8.7 Complete Security Headers Middleware

```php
<?php

namespace GsmUi\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class SecurityHeadersMiddleware
{
    public function handle(Request $request, Closure $next): Response
    {
        $response = $next($request);

        if (! config('gsmui-pro.security_headers.enabled', true)) {
            return $response;
        }

        $response->headers->set('X-Content-Type-Options', 'nosniff');
        $response->headers->set('X-Frame-Options', 'SAMEORIGIN');
        $response->headers->set('Referrer-Policy', 'strict-origin-when-cross-origin');
        $response->headers->set('Permissions-Policy', $this->permissionsPolicy());
        $response->headers->set('X-XSS-Protection', '0');

        if (config('app.env') === 'production') {
            $response->headers->set(
                'Strict-Transport-Security',
                'max-age=63072000; includeSubDomains; preload'
            );
        }

        return $response;
    }

    protected function permissionsPolicy(): string
    {
        return 'camera=(), microphone=(), geolocation=(), payment=(), usb=()';
    }
}
```

## 9. Subresource Integrity (SRI)

Although GsmUi self-hosts all assets (making SRI technically optional), SRI provides defense-in-depth against compromised build pipelines or CDN hijacking.

### 9.1 When SRI Applies

| Scenario | SRI Needed? | Reason |
| --- | --- | --- |
| Self-hosted `dist/gsmui.js` | Optional | Same-origin; integrity verified by build pipeline |
| External CDN script (forbidden) | N/A | CDN scripts are banned by policy |
| Third-party embed (forbidden) | N/A | Iframes are banned by CSP |
| Shared hosting with cache layers | Recommended | Intermediate proxies could modify assets |

### 9.2 SRI Hash Generation

Build pipeline integration:

```bash
# Generate SRI hash for a built asset
openssl dgst -sha256 -binary dist/gsmui.js | openssl base64 -A
```

The hash is embedded in `<script>` tags:

```html
<script src="/dist/gsmui.js"
        integrity="sha256-ABC123..."
        crossorigin="anonymous"></script>
```

### 9.3 Build Pipeline Integration

The Vite build can automatically inject SRI hashes into the manifest:

```js
// vite.config.js
import { sri } from 'vite-plugin-sri';

export default {
    plugins: [
        sri({
            algorithm: 'sha256',
            fileBlackList: [/\.css$/], // CSS SRI is optional
        }),
    ],
};
```

### 9.4 Limitations

- SRI does not protect against first-party code injection (compromised build server)
- SRI hashes change on every build — must be regenerated in CI
- `adoptedStyleSheets` cannot have SRI (no `<link>` tag to attach it to)
- Cross-origin resources require `crossorigin="anonymous"` for SRI to work

## 10. XSS Attack Vectors and Mitigations

This section catalogs every XSS vector relevant to a Laravel/Livewire/Blade stack and maps each to GsmUi's specific mitigation.

### 10.1 Stored XSS

**Scenario:** User submits content (e.g., a comment, profile field) that is stored in the database and rendered to other users.

**Mitigation in GsmUi:**
- Blade `{{ $variable }}` auto-escaping converts `<script>` to `&lt;script&gt;`
- `{!! $variable !!}` (raw output) is **forbidden** in all `gsmui:` component templates
- Livewire 4 escapes all bound properties by default
- Admin CMS fields use a whitelist-based HTML purifier

**Audit checklist:**
- [ ] Search codebase for `{!!` in Blade templates — every instance must have a documented justification
- [ ] Verify Livewire component properties are not passed through `@json` without encoding
- [ ] Confirm database content is escaped on output, not on input

### 10.2 Reflected XSS

**Scenario:** User-controlled data appears in the URL (query parameters, path segments) and is reflected in the page without escaping.

**Mitigation in GsmUi:**
- Blade auto-escaping handles `{{ request('param') }}`
- Livewire route parameters are escaped by the framework
- 404/error pages (`08.19-feedback-components.md`) render the requested URL without executing it

**Audit checklist:**
- [ ] All `request()` calls in Blade templates use `{{ }}`, not `{!! !!}`
- [ ] Error pages do not reflect the full URL in an unescaped context
- [ ] Search results pages escape query terms

### 10.3 DOM-Based XSS

**Scenario:** Client-side JavaScript reads user-controlled data (URL fragment, `document.referrer`, `localStorage`) and injects it into the DOM via `innerHTML`, `document.write`, or similar.

**Mitigation in GsmUi:**
- JS code uses `textContent` instead of `innerHTML` for dynamic text
- `setAttribute`/`removeAttribute` from `utils.js` never interprets HTML
- URL parameters are read via `URLSearchParams` and inserted via `textContent`
- No `document.write()` calls exist in the codebase

**Audit checklist:**
- [ ] Grep for `innerHTML` — every instance must be justified and sanitized
- [ ] Grep for `document.write` — must be zero
- [ ] Grep for `.html(` in Alpine — must be zero in GsmUi components
- [ ] URL fragment parsing uses `URLSearchParams`, not regex

### 10.4 Mutation XSS (mXSS)

**Scenario:** Browser parsing quirks cause sanitized HTML to re-appear as executable content after DOM manipulation.

**Mitigation in GsmUi:**
- Blade escaping is server-side — DOM manipulation does not affect it
- `adoptedStyleSheets` inject CSS, not HTML
- Component templates are static Blade files, not dynamically constructed

### 10.5 XSS via SVG

**Scenario:** SVG files can contain `<script>` tags, event handlers (`onload`, `onerror`), and foreignObject elements with HTML.

**Mitigation in GsmUi:**
- All SVG icons are inline `<svg>` elements in Blade templates, not uploaded files
- No SVG upload functionality exists in the component library
- SVG icons do not contain `<script>` tags — they are pure path/shape markup
- CSP `script-src 'self'` blocks script execution in SVGs served as resources

## 11. CSRF Protection

Cross-Site Request Forgery is handled by Laravel's CSRF middleware, but GsmUi components have specific considerations.

### 11.1 Livewire CSRF

Livewire 4 includes CSRF tokens automatically in every request. The token is embedded in the Livewire payload and validated server-side. No manual CSRF handling is needed in Gsmui components.

### 11.2 Form Components

`<gsmui:input>` and related form components wrap standard `<form>` elements. Laravel's `@csrf` directive must be included in every form:

```blade
<form wire:submit="save">
    @csrf
    <gsmui:input wire:model="name" />
    <gsmui:button type="submit">Save</gsmui:button>
</form>
```

### 11.3 CSRF Token Refresh

Livewire refreshes the CSRF token on every page load. If a session expires, Livewire prompts re-authentication. No manual token refresh logic is needed.

### 11.4 API Routes

Stateless API routes (if any) use Sanctum or Passport tokens, not session-based CSRF. These are outside the GsmUi component scope.

## 12. Third-Party Script Policy

GsmUi maintains a strict "zero external scripts" policy. This section documents the process for evaluating any future exceptions.

### 12.1 Default Position

No third-party scripts. Period. Every JavaScript file loaded on the page must be:
- Served from the same origin
- Built from source in the `dist/` directory
- Auditable by the development team

### 12.2 Exception Request Process

If a feature requires a third-party script (e.g., analytics, payment widget, embedded video):

1. **Document the need:** What does the third-party script do? Can it be replaced with first-party code?
2. **Security review:** Does the third-party use `eval()`? Does it load additional scripts? Does it phone home?
3. **CSP impact:** What directives must be relaxed? Can they be scoped to specific pages?
4. **Performance impact:** What is the script size? Does it block rendering?
5. **Availability:** What happens if the third-party CDN is down? Is there a fallback?
6. **Privacy:** Does the script set cookies? Send user data to a third party?
7. **Approval:** Requires sign-off from the security lead and project owner

### 12.3 Common Third-Party Requests and Responses

| Request | Response |
| --- | --- |
| Google Analytics | Use a server-side analytics proxy or self-hosted Matomo |
| YouTube embed | Use `<a href>` link with thumbnail, not iframe embed |
| Stripe.js | Allowed — Stripe requires their script for PCI compliance; scope to billing pages only |
| reCAPTCHA | Use hCaptcha or Turnstile (more CSP-friendly), or server-side CAPTCHA |
| Intercom / Drift | Build a first-party chat component using Livewire |
| Google Fonts | Use system fonts (already the Gsmui standard) |
| Font Awesome | Use inline SVG icons (already the Gsmui standard) |

### 12.4 Scoping Exceptions

If a third-party script is approved, it must be:
- Scoped to the minimum necessary pages (not global)
- Loaded with `async` or `defer` to avoid blocking
- Subject to Subresource Integrity (if the provider supports it)
- Monitored for changes (the provider could ship malicious code)

**CSP scoping example:**

```php
// In the page-specific middleware or route group
'connect-src' => [
    "'self'",
    'https://api.stripe.com', // only on billing pages
],
'script-src' => [
    "'self'",
    "'nonce-{{ $nonce }}'", // only the nonce for this page
],
```

## 13. Secure Development Practices

### 13.1 Dependency Auditing

Every npm and composer dependency is a potential attack vector. GsmUi enforces:

```bash
# Composer audit
composer audit

# npm audit
npm audit --production

# Automated in CI — fails the build on critical vulnerabilities
```

**Policy:**
- Critical vulnerabilities: must be fixed before merge
- High vulnerabilities: must be fixed within 48 hours
- Medium/Low: track in backlog, fix opportunistically

### 13.2 Lock Files

`composer.lock` and `package-lock.json` must be committed. They ensure reproducible builds and prevent supply-chain attacks via version range manipulation.

### 13.3 Pinning Dependencies

For critical security-sensitive packages, pin to exact versions:

```json
{
    "dependencies": {
        "dompurify": "3.0.6"
    }
}
```

### 13.4 CI Security Checks

| Check | Tool | Frequency |
| --- | --- | --- |
| PHP dependency audit | `composer audit` | Every PR |
| JS dependency audit | `npm audit` | Every PR |
| CSP header validation | `CspHeaderTest.php` | Every push to main |
| XSS pattern grep | Custom script | Every PR |
| Secrets detection | `gitleaks` or `trufflehog` | Every PR |
| License compliance | `composer licenses` | Weekly |

### 13.5 Secrets Management

- Never commit API keys, tokens, or passwords to the repository
- Use `.env` for local configuration (`.env` is in `.gitignore`)
- Production secrets live in the deployment platform's secret store
- CSP nonces are generated per-request, never hardcoded

## 14. Input Sanitization on the Frontend

While server-side sanitization is the authoritative layer, GsmUi components provide a first line of defense.

### 14.1 `innerHTML` Prohibition

All `gsmui:` JS code uses `textContent` for dynamic text insertion. The `innerHTML` property is banned in component code. If HTML must be inserted (e.g., rich text rendering), it goes through a sanitization library:

```js
import DOMPurify from 'dompurify';

function sanitizeHTML(dirty) {
    return DOMPurify.sanitize(dirty, {
        ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a', 'p', 'br', 'ul', 'ol', 'li'],
        ALLOWED_ATTR: ['href', 'target', 'rel'],
    });
}
```

### 14.2 URL Validation

Components that accept URLs (links, image sources) validate before insertion:

```js
function isAllowedURL(url) {
    try {
        const parsed = new URL(url, window.location.origin);
        // Only allow same-origin or known-safe protocols
        return ['http:', 'https:', 'mailto:'].includes(parsed.protocol);
    } catch {
        return false;
    }
}
```

### 14.3 Attribute Injection Prevention

The `setAttribute` utility from `utils.js` sanitizes attribute values:

```js
export function setAttribute(el, name, value) {
    // Prevent attribute injection via newlines or special characters
    const sanitized = String(value).replace(/[\n\r]/g, '');
    el.setAttribute(name, sanitized);
}
```

### 14.4 Template Injection in Blade

Blade components never construct HTML from user input. The pattern is:

```blade
{{-- CORRECT: Blade renders the value safely --}}
<div>{{ $userInput }}</div>

{{-- INCORRECT: Never do this --}}
<div>{!! $userInput !!}</div>

{{-- INCORRECT: Never construct HTML in JS --}}
<script>
    element.innerHTML = userInput; // XSS vulnerability
</script>
```

## 18. Incident Response

### 18.1 CSP Violation in Production

1. **Triage:** Determine if the violation is an attack or a legitimate feature
2. **If attack:** Block the source, investigate the entry point, rotate session keys
3. **If legitimate:** Add the specific source to the CSP config with the narrowest possible scope

### 18.2 XSS Vulnerability Discovery

3. **Fix:** Patch the vulnerability, add a test to prevent regression
4. **Audit:** Search the codebase for similar patterns
5. **Report:** Notify affected users if data was compromised
6. **Post-mortem:** Document the root cause and preventive measures

### 18.3 Supply Chain Compromise

If a dependency is compromised:

1. **Immediate:** Remove the dependency or pin to the last known-good version
2. **Audit:** Check `dist/` builds for the affected time period
3. **Rebuild:** Rebuild from source with the clean dependency
4. **Deploy:** Push the clean build to production
5. **Monitor:** Watch for unusual CSP violations or network activity

## 19. Future Security Enhancements

### 19.1 Trusted Types

The [Trusted Types](https://web.dev/trusted-types/) API provides a browser-native defense against DOM XSS. GsmUi should evaluate adoption:

```js
// Policy definition
const policy = trustedTypes.createPolicy('gsmui', {
    createHTML: (input) => DOMPurify.sanitize(input),
    createScriptURL: (input) => {
        const url = new URL(input, window.location.origin);
        if (url.origin !== window.location.origin) throw new Error('Blocked');
        return url.href;
    },
});
```

**Status:** Experimental. Monitor browser support and evaluate when >90% of target browsers support it.

### 19.2 CSP Nonce Rotation

Moving from hash-based to nonce-based CSP for the bootstrap script:

- Nonces are generated per-request by the server
- Each nonce is single-use (one response)
- Provides stronger security than static hashes

**Status:** Requires server-side nonce generation infrastructure. Track in backlog.

### 19.3 `strict-dynamic`

The `strict-dynamic` CSP directive allows trusted scripts to load additional scripts without whitelisting each one. This is useful for bundlers that produce multiple chunks:

```css
script-src 'self' 'strict-dynamic' 'nonce-<random>';
```

**Status:** Evaluate when the build pipeline produces chunked output.

### 19.4 CSP Reporting v2

The CSP Reporting API (v2) provides better-structured violation reports. Adopt when browser support reaches the GsmUi target threshold.

## 20. Appendix — CSP Violation Debugging

### Common Violations and Fixes

| Violation Message | Cause | Fix |
| --- | --- | --- |
| `Refused to execute inline script` | `<script>` tag without nonce/hash | Move to external file or add nonce/hash |
| `Refused to apply inline style` | `<style>` tag or `style=` attribute | Use `adoptedStyleSheets` or add to `style-src` |
| `Refused to load the script` | External script URL | Self-host the script or add origin to `script-src` |
| `Refused to load the image` | External image URL | Self-host or add origin to `img-src` |
| `Refused to connect to` | `fetch()` to external URL | Add origin to `connect-src` or proxy server-side |
| `Refused to load the font` | External font file | Use system fonts or self-host |
| `Refused to frame` | iframe with external src | Remove iframe or add origin to `frame-src` |

### Debugging Workflow

1. Open browser DevTools → Console tab
2. Look for red CSP violation messages
3. Note the violated directive, blocked URI, and source location
4. Cross-reference with the CSP config in `gsmui-pro-csp.php`
5. Determine if the blocked resource is legitimate
6. If legitimate: narrow-scope add the origin to the specific directive
7. If not legitimate: investigate the code path and remove the external reference

### CSP Report-Only Mode

During development and staged rollouts, set `CSP_REPORT_ONLY=true`:

```env
CSP_REPORT_ONLY=true
```

This sends violations to the report endpoint without blocking resources, allowing you to identify issues before enforcing.

## 21. Content Security Policy — Advanced Topics

### 21.1 CSP and Single Page Applications

GsmUi is not a traditional SPA — it uses server-rendered Blade with Livewire for partial updates. However, understanding CSP in the SPA context helps explain why GsmUi's architecture is more secure:

| SPA Pattern | CSP Challenge | GsmUi Solution |
| --- | --- | --- |
| Client-side routing | `eval()` for lazy routes | Server-rendered routes; Livewire for partial updates |
| Virtual DOM diffing | Inline styles during reconciliation | Livewire morphs are server-rendered; CSS variables handle theming |
| Dynamic module imports | `blob:` URLs for chunks | Vite code splitting with self-hosted chunks |
| State management | `eval()` for store hydration | Livewire snapshot (signed, server-side) |
| Client-side templating | `innerHTML` for rendering | Blade compiles server-side; no client templating |

### 21.2 CSP and Livewire

Livewire 4 is fully CSP-compatible when configured correctly:

**Livewire's internal mechanisms:**
- `fetch()` for HTTP requests → covered by `connect-src 'self'`
- DOM morphing → pure DOM manipulation, no CSP restriction
- Snapshot serialization → JSON in `data` attributes, no executable content
- Event dispatching → custom DOM events, no CSP restriction

**Potential CSP conflicts:**
- Livewire's `wire:click` uses `eval()` internally for some directives → use `wire:submit` or method binding instead
- Livewire's `x-init` (if Alpine is used) requires `unsafe-eval` → avoid Alpine in Livewire components
- Livewire's `@this` in Blade templates is server-rendered → no CSP impact

**Testing Livewire with CSP:**

```php
// In your test:
public function test_livewire_component_works_with_csp(): void
{
    config(['gsmui-pro.csp.enabled' => true]);

    $component = Livewire::test(DatePickerComponent::class);

    $component->assertStatus(200);
    // Verify no CSP violations were triggered
}
```

### 21.4 CSP and Third-Party Browser Extensions

Some browser extensions inject scripts or styles into pages. CSP cannot block these because:
- Extensions run with elevated privileges
- CSP is enforced by the page's origin, not the extension's

**Impact on GsmUi:** Users with ad blockers or password managers that inject scripts may see CSP violation reports. These are expected and should be filtered in the reporting pipeline.

**Filtering strategy:**

```php
// In the CSP report handler
$blockedUri = $report['csp-report']['blocked-uri'] ?? '';

// Filter known extension patterns
$extensionPatterns = [
    '/chrome-extension:\/\//,
    '/moz-extension:\/\//,
    '/safari-web-extension:\/\//,
    '/-extension:\/\//,
];

foreach ($extensionPatterns as $pattern) {
    if (preg_match($pattern, $blockedUri)) {
        return response()->json(['status' => 'ignored']); // Don't log extension violations
    }
}
```

### 21.5 CSP and Web Components

GsmUi components use a pattern inspired by Web Components (custom elements, Shadow DOM concepts) but does not use actual Shadow DOM. This is important for CSP because:

- Shadow DOM encapsulates styles → no CSP impact (styles are still loaded from same origin)
- Custom elements use `connectedCallback` → no CSP impact (DOM manipulation, not script loading)
- `adoptedStyleSheets` → CSP `style-src` applies to the document, not Shadow roots
- If actual Shadow DOM were used, CSP would still apply to the document level

**Future consideration:** If GsmUi adopts Shadow DOM for stronger style encapsulation, CSP remains unchanged. The key difference is that Shadow DOM prevents style leaking in/out, but CSP controls what scripts/styles can be loaded.

### 21.6 CSP and Progressive Enhancement

GsmUi's server-rendered architecture naturally supports progressive enhancement:

```
1. No JS: Blade renders semantic HTML with inline SVG icons
   → All content visible, forms submit via POST
   → CSP fully enforced (no scripts to load)

2. JS available: gsmui.js adds interactive behaviors
   → Components become interactive (date pickers, sliders, etc.)
   → CSP still fully enforced (self-hosted scripts only)

3. Livewire available: Real-time updates via wire:model
   → Components sync with server without page reload
   → CSP still fully enforced (fetch to self only)
```

This layered approach means CSP protects every layer independently.

## 25. Security Glossary

| Term | Definition |
| --- | --- |
| **CSP** | Content Security Policy — HTTP header that restricts which resources a page can load |
| **XSS** | Cross-Site Scripting — injection of malicious scripts into trusted websites |
| **CSRF** | Cross-Site Request Forgery — tricking a user into submitting unintended requests |
| **SRI** | Subresource Integrity — verifying that a fetched resource hasn't been tampered with |
| **HSTS** | HTTP Strict Transport Security — forcing HTTPS for all future requests |
| **FOUC** | Flash of Unstyled Content — momentary display of unstyled content before CSS loads |
| **mXSS** | Mutation XSS — XSS that bypasses sanitizers through DOM parsing quirks |
| **CSP Report** | Structured JSON report sent to the server when a CSP violation occurs |
| **Nonce** | A random, single-use value added to CSP headers to allow specific inline scripts |
| **Hash** | SHA-256 hash of allowed inline script content, added to CSP `script-src` |
| **Self-hosted** | All assets served from the same origin, not from CDNs |
| **Eval-free** | No use of `eval()`, `Function()`, or other code-execution mechanisms |
| **Signed payload** | Livewire's encrypted request/response data to prevent tampering |
| **DOM morph** | Livewire's method of applying server-rendered HTML changes to the client DOM |
| **MutationObserver** | Browser API that watches for DOM changes — used by gsmui.js for state reconciliation |
| **adoptedStyleSheets** | Browser API for injecting CSS via constructable stylesheets (no `<style>` tags) |
| **Trusted Types** | Browser API that prevents DOM XSS by requiring trusted values for dangerous sinks |

- [ ] Does this feature need a new CSP directive? If yes, document the impact.
- [ ] Does this feature handle user input? If yes, plan server-side sanitization.

### During Development

## 27. Security Architecture Patterns

### 27.1 Defense in Depth

GsmUi implements multiple layers of security, so that if one layer fails, others still protect the application:

```
Layer 1: Server-Side Rendering (Blade)
  └─ HTML is rendered server-side with auto-escaping
  └─ No client-side template execution
  └─ Crawlers and security scanners see safe HTML

Layer 2: Content Security Policy
  └─ Restricts which scripts, styles, and resources can load
  └─ Blocks inline scripts, external CDNs, eval()
  └─ Prevents XSS even if user input escapes Blade escaping

Layer 3: Livewire Signed Payloads
  └─ All Livewire requests are signed and encrypted
  └─ Prevents tampering with component state
  └─ Server validates every mutation

Layer 4: Input Validation
  └─ Server-side validation on every form submission
  └─ Client-side validation is optimistic (visual only)
  └─ Never trust client-side validation alone

Layer 5: Output Encoding
  └─ Blade {{ }} auto-escapes HTML entities
  └─ JS textContent avoids innerHTML
  └─ Attribute values sanitized via setAttribute utility

Layer 6: Security Headers
  └─ X-Content-Type-Options prevents MIME sniffing
  └─ X-Frame-Options prevents clickjacking
  └─ Referrer-Policy limits information leakage
  └─ Permissions-Policy disables unused browser features
```

### 27.2 Secure by Default

Every GsmUi component is secure by default:

| Feature | Default | Opt-in |
| --- | --- | --- |
| CSP enforcement | Enabled | `CSP_ENABLED=false` to disable |
| HTML escaping | Always on | `{!! !!}` requires explicit opt-in |
| CSRF protection | Always on | Stateless APIs use tokens instead |
| Cookie security | HttpOnly, Secure, SameSite | Configurable per environment |
| Session encryption | Enabled | `SESSION_ENCRYPT=true` |
| Error disclosure | Disabled in production | `APP_DEBUG=true` for development |

### 27.3 Principle of Least Privilege

GsmUi components request only the permissions they need:

| Component | Permissions Needed | Justification |
| --- | --- | --- |
| Date picker | None | Pure DOM manipulation |
| Color picker | None | Pure DOM manipulation |
| File upload | File system access (via server) | User-initiated file selection |
| Search | None | Client-side filtering |
| Chart | None | Canvas rendering |
| Editor (Playground) | None | Monaco editor (self-hosted) |

No component requests:
- Geolocation
- Camera/microphone
- Notifications (browser)
- Clipboard (except explicit copy button)
- Full storage access

## 28. Security Testing Scripts

### 28.1 CSP Validation Script

```bash
#!/bin/bash
# scripts/validate-csp.sh
# Validates that CSP headers are correctly configured

set -e

URL="${1:-http://localhost:8000/gsmui-csp-test}"
echo "Testing CSP headers at: $URL"

# Fetch headers
HEADERS=$(curl -sI "$URL")

# Check CSP header exists
if ! echo "$HEADERS" | grep -qi "content-security-policy"; then
    echo "FAIL: CSP header not found"
    exit 1
fi
echo "PASS: CSP header found"

# Check script-src
CSP=$(echo "$HEADERS" | grep -i "content-security-policy" | head -1)

if echo "$CSP" | grep -q "unsafe-eval"; then
    echo "FAIL: unsafe-eval found in CSP"
    exit 1
fi
echo "PASS: No unsafe-eval in CSP"

if echo "$CSP" | grep -q "unsafe-inline"; then
    # Check if only in style-src (acceptable)
    STYLE_LINE=$(echo "$CSP" | grep -o "style-src[^;]*")
    SCRIPT_LINE=$(echo "$CSP" | grep -o "script-src[^;]*")
    if echo "$SCRIPT_LINE" | grep -q "unsafe-inline"; then
        echo "FAIL: unsafe-inline found in script-src"
        exit 1
    fi
    echo "PASS: unsafe-inline only in style-src (acceptable)"
else
    echo "PASS: No unsafe-inline in CSP"
fi

# Check for external domains
if echo "$CSP" | grep -qE "https?://"; then
    echo "WARN: External domains found in CSP"
    echo "$CSP" | grep -oE "https?://[^ ;]*"
else
    echo "PASS: No external domains in CSP"
fi

echo ""
echo "CSP validation complete"
```

### 28.2 XSS Pattern Scanner

```bash
#!/bin/bash
# scripts/scan-xss-patterns.sh
# Scans codebase for potential XSS vulnerabilities

set -e

echo "Scanning for XSS patterns..."

# Check for raw Blade output
echo "--- Checking for {!! !!} in Blade templates ---"
RAW_OUTPUT=$(grep -rn '{!!' stubs/resources/views/ --include="*.blade.php" | grep -v '@verbatim' | grep -v '@php' | grep -v '@json' || true)
if [ -n "$RAW_OUTPUT" ]; then
    echo "WARN: Raw Blade output found (review each instance):"
    echo "$RAW_OUTPUT"
else
    echo "PASS: No raw Blade output"
fi

echo ""
echo "--- Checking for innerHTML in JavaScript ---"
INNERHTML=$(grep -rn 'innerHTML' resources/js/ --include="*.js" || true)
if [ -n "$INNERHTML" ]; then
    echo "WARN: innerHTML usage found (ensure DOMPurify is used):"
    echo "$INNERHTML"
else
    echo "PASS: No innerHTML usage"
fi

echo ""
echo "--- Checking for eval() in JavaScript ---"
EVAL=$(grep -rn 'eval(' resources/js/ --include="*.js" || true)
if [ -n "$EVAL" ]; then
    echo "FAIL: eval() found in JavaScript"
    echo "$EVAL"
    exit 1
else
    echo "PASS: No eval() usage"
fi

echo ""
echo "--- Checking for document.write() ---"
DOCWRITE=$(grep -rn 'document.write' resources/js/ --include="*.js" || true)
if [ -n "$DOCWRITE" ]; then
    echo "FAIL: document.write() found"
    echo "$DOCWRITE"
    exit 1
else
    echo "PASS: No document.write() usage"
fi

echo ""
echo "--- Checking for Function() constructor ---"
FUNCTION=$(grep -rn 'new Function(' resources/js/ --include="*.js" || true)
if [ -n "$FUNCTION" ]; then
    echo "FAIL: new Function() found"
    echo "$FUNCTION"
    exit 1
else
    echo "PASS: No new Function() usage"
fi

echo ""
echo "--- Checking for CDN references in Blade ---"
CDN=$(grep -rn 'https://cdn' stubs/resources/views/ --include="*.blade.php" || true)
if [ -n "$CDN" ]; then
    echo "FAIL: CDN references found in Blade templates"
    echo "$CDN"
    exit 1
else
    echo "PASS: No CDN references"
fi

echo ""
echo "XSS pattern scan complete"
```

## 29. Security Configuration per Environment

### 29.1 Development

```env
# Development — relaxed for productivity
CSP_ENABLED=false
CSP_REPORT_ONLY=true
SECURITY_HEADERS_ENABLED=false
APP_DEBUG=true
SESSION_ENCRYPT=false
SESSION_SECURE=false
```

**Rationale:** In development, CSP can interfere with hot-reload, browser extensions, and debugging tools. Disable CSP enforcement but keep report-only mode to catch violations early.

### 29.2 Staging

```env
# Staging — mirrors production
CSP_ENABLED=true
CSP_REPORT_ONLY=true
SECURITY_HEADERS_ENABLED=true
APP_DEBUG=false
SESSION_ENCRYPT=true
SESSION_SECURE=true
CSP_REPORT_URI=/csp-report
```

**Rationale:** Staging uses full CSP in report-only mode to catch violations before they affect users. Reports are logged but not enforced.

### 29.3 Production

```env
# Production — full enforcement
CSP_ENABLED=true
CSP_REPORT_ONLY=false
SECURITY_HEADERS_ENABLED=true
APP_DEBUG=false
SESSION_ENCRYPT=true
SESSION_SECURE=true
SESSION_HTTP_ONLY=true
SESSION_SAME_SITE=lax
CSP_REPORT_URI=/csp-report
```

**Rationale:** Production enforces all security headers. Violations are reported and investigated. No debug information is exposed.

### 29.4 Comparison Table

| Setting | Development | Staging | Production |
| --- | --- | --- | --- |
| CSP enabled | false | true (report-only) | true (enforce) |
| Security headers | false | true | true |
| APP_DEBUG | true | false | false |
| Session encrypt | false | true | true |
| Session secure | false | true | true |
| Error disclosure | full | minimal | none |
| CSP reporting | disabled | enabled | enabled |

## 31. Appendix A — CSP Directive Quick Reference Card

This section provides a printable quick-reference card for developers working on GsmUi components. It summarizes every CSP directive, its purpose, GsmUi's configuration, and common violations.

| Directive | Purpose | GsmUi Config | Common Violation |
| --- | --- | --- | --- |
| `default-src` | Fallback for unspecified directives | `'self'` | None (fallback only) |
| `script-src` | Controls JavaScript execution | `'self'` | Inline `<script>`, external CDN, `eval()` |
| `style-src` | Controls CSS loading | `'self' 'unsafe-inline'` | `<style>` tags at runtime, external CSS |
| `img-src` | Controls image loading | `'self' 'data:'` | External image URLs |
| `connect-src` | Controls fetch/XHR/WebSocket | `'self'` | External API calls |
| `font-src` | Controls font loading | `'self'` | External font files |
| `frame-src` | Controls iframe loading | (omitted — `'none'`) | Any iframe usage |
| `worker-src` | Controls Web Worker loading | `'self'` (if PWA) | External worker scripts |
| `base-uri` | Controls `<base>` element | `'self'` | Injected `<base>` tag |
| `form-action` | Controls form submission targets | `'self'` | Forms submitting to external URLs |
| `frame-ancestors` | Controls who can embed the page | `'self'` | External sites iframing the page |
| `upgrade-insecure-requests` | Forces HTTP → HTTPS | `true` (production) | HTTP resources |

**How to use this card:**

1. When adding a new feature, check if it requires any resource type listed above
2. If it requires a resource not currently in the CSP config, you must update the config
3. If the resource is external, follow the exception request process (Section 12.2)
4. Test with `CSP_REPORT_ONLY=true` before enforcing
5. Update this card when the CSP config changes
