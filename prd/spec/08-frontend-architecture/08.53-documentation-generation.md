# Purpose

GsmUi's docs portal renders component reference pages from Blade, with live `gsmui:` previews alongside minimal copy-paste code blocks. A critical constraint: code samples containing `gsmui:` tags must be wrapped in `@verbatim` so Blade does **not** process them. This document pins the generation flow, the `@verbatim` rule, and the preview/code split convention.

This document covers every aspect of documentation generation: the `@verbatim` rule in detail, the preview/code split convention, documentation page structure, navigation and table of contents, API reference generation, code sample formatting, localization in docs, versioned documentation, docs testing, docs performance optimization, and the integration points between the docs engine and the GsmUi component system.

## 1. Docs Page Structure

Each component reference page follows the pattern from `AGENTS.md`:

```blade
<x-docs.variant level="3">Sub-component</x-docs.variant>

{{-- Dressed-up live preview --}}
<gsmui:color-picker value="#0ea5e9" />

{{-- Minimal code block for copy-paste --}}
@verbatim
<gsmui:color-picker wire:model="color" />
@endverbatim
```

Container components are listed **before** their children.

## 2. The `@verbatim` Rule (Critical)

Any fenced code sample that contains a `gsmui:` (or any Blade) directive MUST be inside `@verbatim ... @endverbatim`. Otherwise Blade attempts to compile the sample as a real component, throwing or rendering it inside the code block.

| Sample contains | Wrap in `@verbatim`? |
| --- | --- |
| `<gsmui:input wire:model="x" />` | Yes |
| Plain HTML `<input>` | No (safe) |
| `{{ }}` PHP echo | Yes |

Per `AGENTS.md` verification: **after every docs change, open the page in Playwright and verify rendering, especially inside `@verbatim` blocks** where Blade components don't process.

### 2.1 Why `@verbatim` is Critical

Blade's `@verbatim` directive tells the Blade compiler to treat the enclosed content as raw text, not as Blade template code. Without it:

1. `<gsmui:input>` would be compiled as a real component, rendering the component inside the code block
2. `{{ $variable }}` would be evaluated as PHP, potentially throwing errors
3. `@if`, `@foreach`, etc. would be processed as Blade directives
4. The code sample would appear broken or empty in the documentation

### 2.2 `@verbatim` Usage Rules

```blade
{{-- CORRECT: gsmui: tag inside @verbatim --}}
@verbatim
  <gsmui:input wire:model="name" label="Name" />
@endverbatim

{{-- CORRECT: PHP echo inside @verbatim --}}
@verbatim
  {{ $user->name }}
@endverbatim

{{-- CORRECT: Blade directive inside @verbatim --}}
@verbatim
  @if($condition)
    <gsmui:alert type="success">Saved!</gsmui:alert>
  @endif
@endverbatim

{{-- INCORRECT: gsmui: tag WITHOUT @verbatim --}}
<gsmui:input wire:model="name" label="Name" />
{{-- Blade will compile this as a real component! --}}

{{-- CORRECT: Plain HTML doesn't need @verbatim --}}
<pre><code>&lt;input type="text" name="name"&gt;</code></pre>
```

### 2.3 `@verbatim` with Syntax Highlighting

When code samples include syntax highlighting (e.g., via a Blade component), the highlighting component wraps the `@verbatim` block:

```blade
<x-docs.code language="html">
@verbatim
<gsmui:input wire:model="name" label="Name" />
@endverbatim
</x-docs.code>
```

The `<x-docs.code>` component handles syntax highlighting, while `@verbatim` ensures Blade doesn't process the sample.

### 2.4 `@verbatim` in Markdown-Style Docs

If docs are rendered from Markdown (via a docs engine), the `@verbatim` rule still applies. The Markdown renderer must preserve `@verbatim` blocks:

```markdown
Here is a code sample:

```blade
@verbatim
<gsmui:input wire:model="name" />
@endverbatim
```
```

### 2.5 `@verbatim` Verification

Playwright tests verify that `@verbatim` blocks render correctly:

```javascript
// tests/Browser/docs/verbatim.spec.js
test('code samples show gsmui tags as text, not compiled components', async ({ page }) => {
  await page.goto('/components/date-picker');

  // Find all code blocks
  const codeBlocks = await page.locator('pre code').all();

  for (const block of codeBlocks) {
    const text = await block.textContent();

    // If the code block contains gsmui:, it should be displayed as text
    if (text.includes('gsmui:')) {
      // Should NOT contain rendered component markup
      expect(text).not.toContain('class="gsmui-');
      // Should contain the raw tag
      expect(text).toContain('gsmui:');
    }
  }
});
```

### 2.6 `@verbatim` Lint Rule

A custom lint rule flags `gsmui:` tags outside `@verbatim` in code fences:

```javascript
// scripts/lint-verbatim.js
const fs = require('fs');
const glob = require('glob');

const files = glob.sync('resources/views/gsmui-docs/**/*.blade.php');

files.forEach(file => {
  const content = fs.readFileSync(file, 'utf8');
  const lines = content.split('\n');

  let inVerbatim = false;
  let inCodeFence = false;

  lines.forEach((line, i) => {
    if (line.trim() === '@verbatim') inVerbatim = true;
    if (line.trim() === '@endverbatim') inVerbatim = false;
    if (line.trim().startsWith('```')) inCodeFence = !inCodeFence;

    if (inCodeFence && !inVerbatim && line.includes('gsmui:')) {
      console.error(`${file}:${i + 1}: gsmui: tag outside @verbatim in code fence`);
    }
  });
});
```

## 3. Preview vs Code Split

| Block | Content | Styling intent |
| --- | --- | --- |
| Preview | `value="#0ea5e9"` for visual context | dressed up, shows real state |
| Code | `wire:model="color"` | minimal, clean copy target |

They do not need to match. Never put scaffolding/testing sections in shipped docs (`AGENTS.md` launch blocker).

### 3.1 Preview Block

Preview blocks render live `gsmui:` components with visual context:

```blade
{{-- Preview: dressed up for visual context --}}
<div class="not-prose my-6 p-6 rounded-xl border border-zinc-200 dark:border-white/10 bg-white dark:bg-zinc-800">
  <gsmui:color-picker value="#0ea5e9" />
</div>
```

Preview blocks:
- Show the component in a realistic state
- Include visual context (borders, padding, background)
- Use real `gsmui:` components (not screenshots)
- Are interactive (users can click, type, etc.)

### 3.2 Code Block

Code blocks show minimal, copy-paste-ready code:

```blade
{{-- Code: minimal, clean copy target --}}
@verbatim
<pre class="not-prose"><code class="text-sm font-mono">&lt;gsmui:color-picker wire:model="color" /&gt;</code></pre>
@endverbatim
```

Code blocks:
- Show only the essential markup
- Use `wire:model` instead of `value` (demonstrating Livewire binding)
- Are not interactive (just text)
- Are optimized for copy-paste

### 3.3 Preview/Code Mismatch

It is acceptable for preview and code to differ:

| Preview shows | Code shows | Why |
| --- | --- | --- |
| `value="#0ea5e9"` | `wire:model="color"` | Preview shows visual, code shows binding |
| `size="default"` | (no size prop) | Default size doesn't need explicit prop |
| `label="Hex"` | (no label prop) | Label is for visual context, not essential |
| `disabled` | (no disabled prop) | Disabled is for visual demo, not default |

### 3.4 Multiple Previews Per Component

Components with many variants show multiple previews:

```blade
<h3>Sizes</h3>
<div class="not-prose my-6 flex items-end gap-4">
  <gsmui:input size="xs" placeholder="Extra small" />
  <gsmui:input size="sm" placeholder="Small" />
  <gsmui:input size="default" placeholder="Default" />
</div>

@verbatim
<pre><code>&lt;gsmui:input size="xs" /&gt;
&lt;gsmui:input size="sm" /&gt;
&lt;gsmui:input /&gt;</code></pre>
@endverbatim
```

## 4. Labels & Honesty

- `label="hex"` for a format demo — meaningful only.
- Never `label="Clearable"` (echoes title) or `label="Brand"` (filler).
- Document limitations explicitly: e.g. "copyable does not work with `type="button"`".

### 4.1 Good Labels

| Label | Context | Why It Works |
| --- | --- | --- |
| `label="hex"` | Color picker format demo | Describes the format, not the component |
| `label="Email"` | Input with type="email" | Describes the expected input |
| `label="Search"` | Search input | Describes the purpose |
| `label="Name"` | Text input | Describes the field |

### 4.2 Bad Labels

| Label | Why It Fails |
| --- | --- |
| `label="Clearable"` | Echoes the section title "Clearable" |
| `label="Brand"` | Random filler, no meaning |
| `label="Input"` | Echoes the component name |
| `label="Type here"` | Instruction, not a label |

### 4.3 Limitation Documentation

When a prop doesn't work with a variant, document it explicitly:

```blade
<h3 id="copyable">Copyable</h3>
<p>
  The <code>copyable</code> prop adds a copy button to the input trigger.
</p>
<p class="text-sm text-zinc-500 dark:text-zinc-400">
  <strong>Note:</strong> The <code>copyable</code> prop does not work with
  <code>type="button"</code>. Use <code>type="input"</code> for copyable inputs.
</p>
```

## 5. Localization in Docs

All visible strings use `__()` (see `08.45-internationalization.md`). The docs engine renders server-side so crawlers and translators see full HTML (`08.47-seo.md`).

### 5.1 Localized Doc Strings

```blade
<h1>{{ __('gsmui::docs.date_picker.title') }}</h1>
<p>{{ __('gsmui::docs.date_picker.description') }}</p>

<h2>{{ __('gsmui::docs.events') }}</h2>
<h2>{{ __('gsmui::docs.slots') }}</h2>

### 5.2 Localized Code Comments

Code samples with comments use `__()` for the comments:

```blade

Prop descriptions in the API reference are localized:

```

### 6.4 Prop Order Convention

Props are listed in this order (from `AGENTS.md`):

1. `wire:model`
2. `value`
3. `name`
4. `format`
5. `type`
6. `placeholder`
7. `size`
8. Behavioral props (swatches, dropper, clearable, copyable, searchable)
9. `label`
10. `description`
11. `disabled`
12. `invalid`

### 8.2 Copy Button

The copy button uses the Clipboard API (CSP-safe):

```javascript
// In dist/gsmui.js
document.querySelectorAll('[data-copy]').forEach(function(btn) {
  btn.addEventListener('click', function() {
    var code = btn.closest('.not-prose').querySelector('code');
    navigator.clipboard.writeText(code.textContent).then(function() {
      var original = btn.textContent;
      btn.textContent = 'Copied!';
      setTimeout(function() { btn.textContent = original; }, 2000);
    });
  });
});
```

### 11.1 Lazy Loading Previews

```blade

```javascript
// In dist/gsmui.js: lazy load previews
var observer = new IntersectionObserver(function(entries) {
  entries.forEach(function(entry) {
    if (entry.isIntersecting) {
      var el = entry.target;
      var url = el.dataset.lazyPreview;
      fetch(url).then(function(response) {
        return response.text();
      }).then(function(html) {
        el.innerHTML = html;
        observer.unobserve(el);
      });
    }
  });
}, { rootMargin: '200px' });

document.querySelectorAll('[data-lazy-preview]').forEach(function(el) {
  observer.observe(el);
});
```

## 14. Documentation Search

### 14.1 Static Search Index

The docs search index is generated at build time:

```php
// app/Console/Commands/GenerateDocsSearchIndex.php
class GenerateDocsSearchIndex extends Command
{
    protected $signature = 'gsmui:docs:search-index';

    public function handle(): void
    {
        $pages = DocsPage::all()->map(fn($page) => [
            'slug' => $page->slug,
            'title' => $page->title,
            'description' => $page->description,
            'content' => strip_tags($page->body),
            'url' => "/docs/{$page->slug}",
        ]);

        file_put_contents(
            public_path('docs-search-index.json'),
            json_encode($pages)
        );
    }
}
```

### 14.2 Client-Side Search

The search uses a lightweight client-side library (e.g., Lunr.js or FlexSearch):

```javascript
// In dist/docs-search.js
fetch('/docs-search-index.json')
  .then(function(response) { return response.json(); })
  .then(function(pages) {
    var index = lunr(function() {
      this.ref('slug');
      this.field('title');
      this.field('description');
      this.field('content');

      pages.forEach(function(page) {
        this.add(page);
      }, this);
    });

    window.gsmuiSearch = {
      search: function(query) {
        return index.search(query).map(function(result) {
          return pages.find(function(p) { return p.slug === result.ref; });
        });
      }
    };
  });
```

## 15. Open Questions / Risks

- **`@verbatim` leakage:** add a docs-build lint that flags `gsmui:` outside `@verbatim` inside code fences.
- **Playwright docs check:** automate a per-page screenshot of `@verbatim` blocks to catch accidental compilation.
- **Variant nesting:** confirm `<x-docs.variant level="3">` depth rules for deeply nested sub-components.
- **Versioned docs storage:** decide between database-stored versions and filesystem-based version directories.
- **Search indexing:** decide between client-side (static JSON) and server-side (first-party API) search.
- **Docs page weight:** monitor docs page size as component count grows — lazy-load previews if needed.
- **Code sample freshness:** ensure code samples are tested in CI to prevent stale examples.

## Appendix C: Documentation Checklist

- [ ] Page has `<title>` with component name + "GsmUi Docs"
- [ ] Page has `<meta name="description">` with component description
- [ ] Page has `<link rel="canonical">` with current URL

- [ ] Preview renders the actual `gsmui:` component (not a screenshot)
- [ ] Code blocks show minimal, copy-paste-ready markup
- [ ] Props table lists all props in correct order (per AGENTS.md)
- [ ] Events table lists all events with payload types
- [ ] Slots table lists all slots with scope information
- [ ] Keyboard navigation table documents all key bindings
- [ ] ARIA section documents all ARIA attributes
- [ ] "See also" links to related components

- [ ] Labels are contextually meaningful (not filler)

- [ ] Dark mode renders correctly
- [ ] RTL layout renders correctly (if applicable)

## Appendix D: Documentation Glossary

| Term | Definition |
| --- | --- |
| `@verbatim` | Blade directive that prevents processing of enclosed content |
| `gsmui:` | Blade component namespace prefix for GsmUi components |
| `<x-docs.variant>` | Docs Blade component for rendering variant sections |
| `<x-docs.code>` | Docs Blade component for syntax-highlighted code blocks |
| `<x-docs.preview>` | Docs Blade component for wrapping live component previews |
| `<x-docs.callout>` | Docs Blade component for notes, warnings, and tips |
| `<x-docs.props-table>` | Docs Blade component for auto-rendering props tables |
| `<x-docs.example>` | Docs Blade component for preview+code side-by-side |
| SSR | Server-side rendering — Blade renders full HTML before sending to browser |
| SEO | Search Engine Optimization — making pages discoverable by crawlers |
| JSON-LD | Structured data format for search engines |
| FOUT | Flash of Unstyled Text — avoided by using system fonts |

## Appendix E: Documentation Page Rendering Pipeline

### E.1 Full Rendering Flow

```
HTTP Request
    ↓
Laravel Router → DocsController@show
    ↓
Resolve page from database/filesystem
    ↓
Blade compiles template
    ↓
@verbatim blocks preserved as raw text
    ↓
gsmui: components render as live HTML
    ↓
Full HTML response (SSR)
    ↓
Browser receives complete page
    ↓
gsmui.js initializes components
    ↓
Page is interactive
```

### E.2 SSR Benefits

| Benefit | Description |
| --- | --- |
| SEO | Crawlers receive full HTML with content |
| Performance | No client-side rendering delay |
| Accessibility | Screen readers get complete markup |
| Print | Print stylesheet works without JS |
| CSP | No `unsafe-eval` needed for rendering |

### E.3 Static Generation Option

For high-traffic docs sites, pages can be pre-rendered:

```bash
# Generate static docs pages
php artisan gsmui:docs:generate-static

# Output: public/docs-static/
# ├── index.html
# ├── components/
# │   ├── button.html
# │   ├── input.html
# │   └── ...
# └── guides/
#     ├── getting-started.html
#     └── ...
```

### E.4 Cache Strategy

| Page Type | Cache Duration | Invalidation |
| --- | --- | --- |
| Component docs | 1 hour | On component update |
| Guide pages | 24 hours | On guide update |
| Changelog | 5 minutes | On new entry |
| Search index | 1 hour | On any content change |
