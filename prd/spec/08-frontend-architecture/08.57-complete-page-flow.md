# Purpose

It traces a single page from Blade compilation through `gsmui:` component render, `dist/` JS initialization (mixins + MutationObserver), the Livewire `wire:model` round-trip, and `adoptedStyleSheets` CSS application — then ties the frontend lifecycle back to the backend flow in `07.60-complete-request-flow.md`.

## 1. Phase 0 — Bootstrap (Pre-Framework)

Before any bundle runs, an inline, eval-free primer in `<head>` resolves the mode (see `08.43-dark-mode.md`) to avoid FOUC:

```html
<script>
  var m = localStorage.getItem('gsmui-theme')
    || (matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
  if (m === 'dark') document.documentElement.classList.add('dark');
</script>
```

This sets `.dark` on `<html>` so all descendant `dark:` utilities and `--gsmui-*` overrides (`08.03-design-tokens.md`, `08.04-theme-architecture.md`) apply on first paint. No CDN, no `eval` — CSP-clean (`08.55-frontend-security.md`).

---

## 2. Phase 1 — Blade Compile & `gsmui:` Render

The Laravel 13 kernel compiles Blade. The `gsmui:` namespace (`08.50-folder-structure.md`) resolves `<gsmui:input>` → `stubs/resources/views/gsmui/input/index.blade.php`. Components:

- Merge classes via `Gsmui::classes()` (never `Flux`).
- Resolve all user strings + aria-labels via `__()` (`08.45-internationalization.md`).
- Emit localized, server-rendered HTML so crawlers see full content (`08.47-seo.md`).
- Declare ARIA per closest sibling pattern: `role="combobox"` on input triggers, `aria-haspopup="dialog"` on button triggers (`08.52-component-guidelines.md`).

Livewire 4 wraps interactive regions, signing/encrypting the payload (`07.60-complete-request-flow.md`).

---

## 3. Phase 2 — Asset Delivery

The service provider injects `dist/` assets via `manifest.json` (`08.51-build-pipeline.md`): `gsmui.js` (deferred), `editor.js` (Playground-only), `editor.css`. All self-hosted → `script-src 'self'`. Dynamic/editor styles use `adoptedStyleSheets` rather than inline `<style>` (`08.46-performance.md`, `08.55`).

---

## 4. Phase 3 — `dist/gsmui.js` Init (Mixins + MutationObserver)

On DOM ready, `gsmui.js` initializes each component:

1. Apply JS mixins — Controllable, Disableable, Submittable, Focusable (`08.52`).
2. Compose sub-elements (e.g. color picker reuses `ui-slider`); sub-elements call methods on the state root.
3. Register a **MutationObserver watching the `value` attribute + config attributes** (`AGENTS.md` JS conventions).
4. Use `detangle()` to prevent sync loops between Controllable and internal state.
5. Use `setAttribute`/`removeAttribute` from `utils.js` (never native DOM) so the observer fires correctly.

---

## 5. Phase 4 — Livewire Hydrate / Request / Hydrate

User interaction (typing, selecting) updates the controlled `value`:

```text
input event ─▶ wire:model bound property
   └─▶ Livewire request (signed payload) ─▶ 07.60 backend
         └─▶ action/service/repo ─▶ response
               └─▶ Livewire hydrate ─▶ re-render gsmui: component
                     └─▶ MutationObserver detects value change
                           └─▶ component reconciles UI (no full reload)
```

Per `AGENTS.md`, keyboard changes fire **both** `input` and `change` (range spec); `change` commits on pointer release, not popover close. Alpine is used RARELY — only when necessary; coordination logic lives in JS.

---

## 6. Phase 5 — CSS & Theme Reconciliation

- Theme flip (`08.44-theme-switcher.md`) toggles `.dark` on `<html>` via `setAttribute`, persists to `localStorage`, and dispatches `gsmui:theme-changed`. Because `.dark` lives outside the Livewire payload, it survives every hydrate.
- `--gsmui-*` variables swap; components re-skin with zero markup change.
- `tabular-nums` keeps rapidly-changing numerics stable (`08.52`).

---

## 7. Phase 6 — Verification Gate

Before "done", Playwright (`08.49-testing.md`) must confirm, headless, across the state matrix (`08.54-storybook-strategy.md`): base, open, disabled, invalid, sizes, keyboard focus, empty. Screenshots after every CSS change; zero console errors; DOM-state assertions only (never `el.state.s`). CSP header test (`tests/Browser/CspHeaderTest.php`) asserts `script-src 'self'` with no `unsafe-eval`.

## Synthesis

The GsmUi frontend is a server-rendered Blade + Livewire 4 surface where every `gsmui:` component is a thin, CSP-safe shell over a self-hosted `dist/` runtime. A request begins in the Laravel kernel (Phase 1, mirrored by the backend lifecycle in `07.60-complete-request-flow.md`), compiles Blade against the `gsmui:` namespace, and emits localized, crawlable HTML with `.dark` already resolved to prevent FOUC. After delivery of the `dist/` bundles, `gsmui.js` initializes components through shared mixins and a `value`-watching MutationObserver, then stays in lockstep with Livewire: user input fires `wire:model`, travels as a signed payload through the 07.60 backend path, and returns via hydrate to reconcile the DOM without a reload. Theme, tokens, focus, invalid, and disabled states are expressed purely through `--gsmui-*` variables and the verbatim class contracts of `08.52`, so the entire experience remains zero-external, eval-free, and verifiable end-to-end with Playwright across the mandated state matrix. Together, Sections 05–08 describe one coherent system: conceptual architecture (05), data (06), backend implementation (07), and this frontend lifecycle (08) — with `07.60-complete-request-flow.md` and this document forming the joined backbone of the full request-to-render story.

## 9. Phase 7 — Error Recovery & Edge Cases

### 9.1 Network Failure During Livewire Round-Trip

When a `wire:model` update triggers a Livewire request and the network fails:

```
input event ─▶ wire:model bound property
   └─▶ Livewire request (signed payload)
         └─▶ ✖ Network error (timeout, offline, 5xx)
               └─▶ Livewire reconnect strategy
                     ├─▶ Retry 1 (immediate)
                     ├─▶ Retry 2 (2s delay)
                     ├─▶ Retry 3 (5s delay)
                     └─▶ Show reconnection banner
                           └─▶ User sees "Reconnecting..." toast
```

**Component behavior during failure:**
- The `value` attribute retains the last known server-side value
- The UI shows the optimistic local value (what the user typed/selected)
- A subtle indicator (e.g., a yellow dot or "Saving..." label) appears near the component
- On successful reconnect, the component reconciles to the server value via MutationObserver
- If the server value differs from the optimistic value, the server wins (no conflict dialog)

**Livewire configuration:**

```php
// config/livewire.php
'connection_timeout' => 10, // seconds
'message_timeout' => 30,    // seconds
'reconnect_max_attempts' => 3,
'reconnect_delay' => [0, 2000, 5000], // ms delays per attempt
```

### 9.2 Session Expiry Mid-Interaction

When the session expires while the user is interacting with a component:

```
user clicks "Save"
   └─▶ Livewire request
         └─▶ 419 (Session Expired) response
               └─▶ Livewire catches 419
                     └─▶ Full page reload (redirect to login)
                           └─▶ User authenticates
                                 └─▶ Redirect back to original page
                                       └─▶ Session state restored from URL/flash
```

**Component considerations:**
- No component-level handling needed — Livewire manages this globally
- `wire:model` bindings are re-initialized on page reload
- User input since the last successful sync is lost (session expired = stale state)

### 9.3 Component Hydration Mismatch

When Livewire's server-rendered HTML differs from the client-side DOM after hydration:

```
server HTML:    <div data-value="initial">
client DOM:     <div data-value="initial">  (matches — OK)

After JS init:  <div data-value="reconciled">  (JS modified value)
Livewire check: <div data-value="initial">  ≠ "reconciled" → mismatch
```

**Mitigation:**
- Components must NOT modify the DOM during hydration in a way that changes `wire:model`-bound attributes
- Use `detangle('livewire', ...)` to wrap Livewire-initiated changes
- The MutationObserver only reconciles on *attribute* changes, not on initial DOM parse

### 9.4 Rapid Sequential Updates

When the user types quickly into a `wire:model.live` input:

```
keystroke 1 → request 1 (sent)
keystroke 2 → request 2 (queued, request 1 still in flight)
keystroke 3 → request 3 (queued)
...
request 1 completes → UI updates
request 2 arrives → out of order? No — Livewire batches
request 3 arrives → Livewire applies latest value
```

**Livewire 4 batching:**
- `wire:model` uses debouncing (default 150ms for `wire:model.live`)
- `wire:model.blur` only syncs on blur (no batching needed)
- `wire:model.lazy` syncs on change event (not input)

**Component considerations:**
- Never override Livewire's built-in debouncing with custom debounce logic
- If a component needs non-standard sync timing, use a Livewire method instead of `wire:model`

### 9.5 Concurrent Livewire Updates from Multiple Components

When two components update simultaneously:

```
Component A: wire:model="name" → request A
Component B: wire:model="email" → request B
Both in flight simultaneously
```

**Livewire 4 handles this:**
- Each component's request is independent
- Responses are applied to their respective component DOM subtrees
- No cross-component conflicts (each component has its own Livewire snapshot)

## 10. Phase 8 — Lifecycle Hooks & Event Flow

### 10.1 Livewire Component Lifecycle

```
mount()                    ← First render only
  └─▶ Component renders Blade template
        └─▶ dist/gsmui.js initializes component JS
              └─▶ Mixins applied (Controllable, Disableable, etc.)
              └─▶ MutationObserver registered
              └─▶ Event listeners attached

update()                   ← Every subsequent render
  └─▶ Livewire re-renders component
        └─▶ DOM diff applied (morph)
        └─▶ MutationObserver detects value change
        └─▶ Component reconciles UI (no full re-init)

dehydrate()                ← Before Livewire sends snapshot to client
  └─→ Component state serialized into snapshot

hydrate()                  ← After Livewire receives response
  └─→ Component state restored from snapshot
  └─→ DOM re-rendered from Blade template
  └─→ MutationObserver detects value change
  └─→ Component reconciles UI

destroy()                  ← Component removed from DOM
  └─→ Event listeners removed
  └─→ MutationObserver disconnected
  └─→ No memory leaks
```

### 10.2 GsmUi Component Lifecycle

```
constructor(el)            ← Called by gsmui.js on DOM ready
  └─▶ Store element reference
  └─▶ Read initial attributes (value, disabled, invalid, config)
  └─▶ Apply mixin behaviors
  └─▶ Register MutationObserver
  └─▶ Attach event listeners
  └─▶ Render initial state

connectedCallback()        ← Called when element is added to DOM (Web Components pattern)
  └─▶ Re-attach listeners if needed

attributeChangedCallback() ← Called by MutationObserver
  └─▶ Reconcile internal state with attribute value
  └─▶ Update sub-elements
  └─▶ Dispatch events if needed

disconnectedCallback()     ← Called when element is removed from DOM
  └─▶ Disconnect MutationObserver
  └─▶ Remove event listeners
  └─▶ Clean up sub-elements

destroy()                  ← Explicit cleanup (called by gsmui.js on page unload)
  └─▶ All cleanup from disconnectedCallback
  └─▶ Nullify references
```

### 10.3 Event Sequence for a Complete Interaction

Example: User selects a date in the date picker.

```
1. User clicks trigger button
   └─▶ gsmui.js: open() method called
         └─▶ Popover rendered via DOM manipulation
         └─▶ aria-expanded set to "true" (via setAttribute)
         └─▶ Focus moved to calendar grid
         └─▶ Scroll lock applied (document.body.style.overflow = 'hidden')

2. User clicks a date in the calendar
   └─▶ gsmui.js: select(date) method called
         └─▶ Internal state updated
         └─▶ value attribute updated (via setAttribute)
         └─▶ MutationObserver fires (attributeChangedCallback)
         └─▶ Component reconciles: updates display text, closes popover
         └─▶ dispatchEvent(new Event('input', { bubbles: true }))
         └─▶ dispatchEvent(new Event('change', { bubbles: true }))

3. Livewire catches change event
   └─▶ wire:model binding triggers request
         └─▶ Livewire snapshot includes new value
         └─▶ HTTP POST to /livewire/message/{component}
               └─▶ CspMiddleware adds CSP header to response
               └─▶ Livewire processes update
               └─▶ Server-side component re-renders

4. Livewire response arrives
   └─▶ Livewire applies DOM diff (morph)
         └─▶ Component DOM updated
         └─▶ MutationObserver fires (value attribute changed by morph)
         └─▶ Component reconciles (no-op if value matches)
         └─▶ Any server-side computed properties reflected in DOM

5. Component idle
   └─▶ No pending mutations
   └─▶ No active observers beyond MutationObserver
   └─▶ Memory footprint: minimal (one observer, event listeners)
```

### 10.4 Event Flow Diagram

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   Browser    │     │   gsmui.js   │     │   Livewire   │
│  DOM Events  │────▶│  Component   │────▶│   Server     │
│              │     │    JS        │     │              │
└──────────────┘     └──────────────┘     └──────────────┘
       │                    │                     │
       │  click/input/      │  setAttribute(      │  HTTP POST
       │  keydown/etc.      │  'value', val)      │  (signed payload)
       │                    │                     │
       │◀───────────────────│  dispatchEvent      │◀───────────────
       │  (bubbling)        │  (input, change)    │  Response
       │                    │                     │  (morph DOM)
       │                    │  MutationObserver   │
       │                    │  fires on morph     │
       │                    │                     │
       │                    │  reconcile()        │
       │                    │  (no-op if matched) │
       │                    │                     │
       │◀───────────────────│─────────────────────│
       │  Final DOM state   │                     │
       └────────────────────┴─────────────────────┘
```

## 11. Phase 9 — Theme & Dark Mode Reconciliation

### 11.1 Theme Flip Event Flow

```
User clicks theme toggle
  └─▶ gsmui.js: themeSwitcher.toggle()
        └─▶ Read current mode from <html> classList
        └─▶ Determine new mode ('dark' ↔ 'light')
        └─▶ setAttribute(document.documentElement, 'class', newMode)
        └─▶ localStorage.setItem('gsmui-theme', newMode)
        └─▶ dispatchEvent('gsmui:theme-changed', { mode: newMode })
        └─▶ All --gsmui-* CSS variables swap (via Tailwind dark: utilities)
        └─▶ All components re-skin (zero markup change)
```

### 11.2 Theme Persistence Across Page Loads

```
Page load:
  └─▶ Bootstrap script reads localStorage('gsmui-theme')
        └─▶ If 'dark': add 'dark' class to <html> BEFORE first paint
        └─▶ If 'light': no class needed (light is default)
        └─▶ No FOUC: dark mode applied synchronously in <head>

Page navigation (SPA-style via Livewire):
  └─▶ Theme class persists on <html> (not in Livewire payload)
        └─▶ New components inherit the theme
        └─▶ No re-read of localStorage needed

Page reload:
  └─▶ Bootstrap script runs again
        └─▶ Reads localStorage
        └─▶ Applies class
        └─▶ No FOUC
```

### 11.3 CSS Variable Cascade

```
:root {
    --gsmui-bg-primary: #ffffff;
    --gsmui-text-primary: #09090b;
    /* ... */
}

.dark {
    --gsmui-bg-primary: #18181b;
    --gsmui-text-primary: #fafafa;
    /* ... */
}

/* Component consumes variables: */
.gsmui-button {
    background-color: var(--gsmui-bg-primary);
    color: var(--gsmui-text-primary);
}

/* Tailwind dark: utilities also work: */
<div class="bg-white dark:bg-zinc-800">
```

### 11.4 Theme-Aware Component Reconciliation

When the theme flips, components do NOT need to re-render. The CSS cascade handles the visual change:

1. `.dark` class added/removed on `<html>`
2. All `dark:` Tailwind utilities activate/deactivate
3. All `--gsmui-*` variables swap values
4. Components styled with CSS variables update automatically
5. `adoptedStyleSheets` with `:root`/`.dark` selectors update

No MutationObserver firing, no Livewire request, no DOM manipulation — pure CSS.

## 12. Phase 10 — Scroll Lock & Focus Management

### 12.1 Scroll Lock

When a popover or dialog opens, the background page must be scroll-locked:

```js
// In gsmui.js popover open logic:
function lockScroll() {
    const scrollbarWidth = window.innerWidth - document.documentElement.clientWidth;
    document.body.style.overflow = 'hidden';
    document.body.style.paddingRight = scrollbarWidth + 'px'; // prevent layout shift
}

function unlockScroll() {
    document.body.style.overflow = '';
    document.body.style.paddingRight = '';
}
```

**Pattern copied from date-picker (per AGENTS.md):**
- `max-sm:max-h-full!` on popover for mobile full-height
- `max-sm:fixed! max-sm:inset-0!` for mobile overlay
- `sm:backdrop:bg-transparent` for desktop backdrop (no scroll lock needed on desktop for small popovers)

### 12.2 Focus Trap

Dialogs and popovers trap keyboard focus within their boundary:

```js
function trapFocus(container) {
    const focusable = container.querySelectorAll(
        'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
    );
    const first = focusable[0];
    const last = focusable[focusable.length - 1];

    container.addEventListener('keydown', (e) => {
        if (e.key !== 'Tab') return;

        if (e.shiftKey && document.activeElement === first) {
            e.preventDefault();
            last.focus();
        } else if (!e.shiftKey && document.activeElement === last) {
            e.preventDefault();
            first.focus();
        }
    });
}
```

### 12.3 Focus Restoration

When a popover/dialog closes, focus returns to the trigger element:

```js
function openPopover(trigger, popover) {
    const previousFocus = document.activeElement;
    // ... open popover ...
    popover._previousFocus = previousFocus;
}

function closePopover(popover) {
    popover._previousFocus?.focus();
}
```

## 14. Phase 12 — Performance Optimization Flow

### 14.1 Lazy Loading Strategy

```
Page loads
  └─▶ Critical CSS inlined (<style> in <head>)
  └─▶ gsmui.js loaded with defer
  └─▶ Above-the-fold components initialize
  └─▶ Below-the-fold components deferred:
        └─▶ IntersectionObserver triggers load
        └─▶ Component JS initializes on visibility
        └─▶ No layout shift (dimensions pre-defined)
```

### 14.2 Component-Level Optimization

| Optimization | Implementation | Impact |
| --- | --- | --- |
| `contain: layout` | CSS containment on isolated components | Prevents layout recalcs |
| `will-change: transform` | Only during active animations | GPU-accelerated compositing |
| `content-visibility: auto` | On off-screen components | Skip rendering until visible |
| `font-display: swap` | On any web fonts (currently none) | Prevents FOIT |
| `loading="lazy"` | On `<img>` elements (if any) | Deferred image loading |

### 14.3 Livewire-Specific Optimizations

```
wire:model.lazy     → Only syncs on change event (not every keystroke)
wire:model.blur     → Only syncs on blur (minimum server requests)
wire:model.throttle → Custom throttle interval
wire:loading        → Show/hide loading indicators during requests
wire:target         → Scope loading indicators to specific actions
```

### 14.4 Memory Management Flow

```
Component created
  └─▶ Allocations:
        ├─▶ Element reference (~100 bytes)
        ├─▶ MutationObserver (~500 bytes)
        ├─ Event listeners (~200 bytes per listener)
        └─▶ Internal state (~1 KB)

Component destroyed
  └─▶ Cleanup:
        ├─▶ observer.disconnect()
        ├─▶ el.removeEventListener() for each listener
        ├─▶ Nullify references
        └─▶ GC reclaims memory

Memory leak prevention:
  └─▶ Every observer has a destroy()
  └─▶ Every event listener is removable
  └─▶ No closures holding element references beyond component lifetime
  └─▶ Playwright heap snapshot tests for long-lived pages
```

## 16. State Reconciliation Deep Dive

### 16.1 Value Attribute → Internal State

```
1. Component reads initial value from attribute:
   this.value = this.el.getAttribute('value') || this.defaultValue

2. User interacts (types, clicks, selects):
   this.value = newValue  (internal state)
   setAttribute(this.el, 'value', newValue)  (triggers MutationObserver)

3. MutationObserver fires:
   onAttributeChanged('value') → reconcileValue()
   reconcileValue() compares this.value with this.el.getAttribute('value')
   If same → no-op
   If different → update sub-elements, dispatch events

4. Livewire receives event, sends request, returns response:
   Livewire morphs DOM → value attribute may change
   MutationObserver fires → reconcileValue()
   Server value takes precedence over local optimistic value
```

### 16.2 Disabled State Reconciliation

```
1. Component reads initial disabled state:
   this.disabled = this.el.hasAttribute('disabled')

2. Server updates disabled via Livewire re-render:
   Livewire morphs DOM → disabled attribute added/removed
   MutationObserver fires → reconcileDisabled()

3. Reconcile behavior:
   If now disabled:
     - Set tabindex="-1" on all focusable children
     - Add aria-disabled="true"
     - Apply [&[disabled]]: CSS classes
     - Remove event listeners (or ignore events via flag)
   If now enabled:
     - Restore tabindex
     - Remove aria-disabled
     - Re-apply event listeners
```

### 16.3 Invalid State Reconciliation

```
1. Component reads initial invalid state:
   this.invalid = this.el.getAttribute('data-invalid') === 'true'

2. Server updates invalid via Livewire re-render:
   Livewire morphs DOM → data-invalid attribute changes
   MutationObserver fires → reconcileInvalid()

3. Reconcile behavior:
   If now invalid:
     - Set aria-invalid="true"
     - Show error message (role="alert")
     - Apply data-invalid: CSS classes
     - Focus management: optionally focus first invalid field
   If now valid:
     - Remove aria-invalid
     - Hide error message
     - Remove data-invalid: CSS classes
```

## 20. Synthesis — The Full Story in One Paragraph

The GsmUi frontend lifecycle begins with an inline, eval-free bootstrap script that reads the user's theme preference from `localStorage`, sets `.dark` on `<html>` to prevent FOUC, and ensures all `--gsmui-*` CSS variables are ready on first paint (Phase 0). The Laravel 13 kernel then compiles Blade templates against the `gsmui:` namespace, producing localized, crawlable HTML where every `Gsmui::classes()` merge, `__()` string resolution, and ARIA attribute follows the conventions of `08.52-component-guidelines.md` (Phase 1). Self-hosted `dist/` assets arrive via `manifest.json` — `gsmui.js` with `defer`, editor assets lazy — all CSP-clean under `script-src 'self'` (Phase 2). On DOM ready, `gsmui.js` initializes each component through shared JS mixins (Controllable, Disableable, Submittable, Focusable), registers MutationObservers watching `value` and config attributes, attaches event listeners using `setAttribute`/`removeAttribute` from `utils.js`, and applies `detangle()` to prevent sync loops between Livewire-driven and user-driven state changes (Phase 3). When the user interacts — typing into an input, selecting a date, dragging a slider — the component fires `input` and `change` events (per the range spec), which `wire:model` catches and sends as signed Livewire payloads through the backend path documented in `07.60-complete-request-flow.md`; the server processes the update, re-renders the component Blade template, and returns a morph response that the client applies to the DOM (Phase 4). Theme flips toggle `.dark` via `setAttribute`, persist to `localStorage`, dispatch `gsmui:theme-changed`, and cascade through `--gsmui-*` variables and Tailwind `dark:` utilities — all pure CSS with zero markup change and no Livewire round-trip (Phase 5). Focus management traps keyboard navigation within open popovers and dialogs, restores focus to triggers on close, and updates `aria-expanded`/`aria-selected`/`aria-invalid` attributes exclusively through the utility functions to keep MutationObserver in sync. Scroll lock prevents background interaction during overlays. Error recovery handles network failures with Livewire's retry strategy, session expiry with automatic re-authentication, hydration mismatches by deferring to server values, and rapid sequential updates through Livewire's built-in debouncing. Memory management ensures every MutationObserver has a `destroy()`, every event listener is removable, and no closures hold references beyond component lifetime. The complete lifecycle — from the inline bootstrap to Playwright verification across the state matrix (base, open, disabled, invalid, sizes, keyboard focus, empty) — is CSP-safe, eval-free, zero-external, and verifiable end-to-end. Together with `07.60-complete-request-flow.md`, this document forms the joined backbone of the full request-to-render story for the GsmUi platform.

## 23. MutationObserver — Complete Flow

### 23.1 Observer Registration

```js
// In gsmui.js component initialization:
class MyComponent {
    constructor(el) {
        this.el = el;
        this.observer = new MutationObserver((mutations) => {
            for (const mutation of mutations) {
                this.handleMutation(mutation);
            }
        });

        this.observer.observe(el, {
            attributes: true,
            attributeFilter: [
                'value',         // The component's value
                'disabled',      // Disabled state
                'invalid',       // Invalid state
                'data-config',   // Component configuration
                'data-format',   // Display format
            ],
        });
    }

    handleMutation(mutation) {
        switch (mutation.attributeName) {
            case 'value':
                this.reconcileValue();
                break;
            case 'disabled':
                this.reconcileDisabled();
                break;
            case 'invalid':
                this.reconcileInvalid();
                break;
            case 'data-config':
            case 'data-format':
                this.reconcileConfig();
                break;
        }
    }
}
```

### 23.2 Value Reconciliation Flow

```
Livewire morphs DOM
  │
  ├─▶ value attribute changes on element
  │
  MutationObserver fires
  │
  ├─▶ handleMutation({ attributeName: 'value' })
  │
  reconcileValue()
  │
  ├─▶ Read new value: el.getAttribute('value')
  ├─▶ Compare with internal state: this.value
  │
  ├─▶ If same → no-op (prevents infinite loop)
  │
  └─▶ If different:
        ├─▶ Update internal state: this.value = newValue
        ├─▶ Update sub-elements (display text, visual state)
        ├─▶ Dispatch custom event if needed
        └─▶ No further MutationObserver firing (value attribute not changed again)
```

### 23.3 Disabled Reconciliation Flow

```
Livewire morphs DOM
  │
  ├─▶ disabled attribute added/removed on element
  │
  MutationObserver fires
  │
  ├─▶ handleMutation({ attributeName: 'disabled' })
  │
  reconcileDisabled()
  │
  ├─▶ Read new state: el.hasAttribute('disabled')
  │
  ├─▶ If now disabled:
  │     ├─▶ Set tabindex="-1" on all focusable children
  │     ├─▶ Add aria-disabled="true"
  │     ├─▶ Apply [&[disabled]]: CSS classes
  │     ├─▶ Remove or ignore event listeners
  │     └─▶ If element has focus, blur it
  │
  └─▶ If now enabled:
        ├─▶ Restore tabindex to original values
        ├─▶ Remove aria-disabled
        ├─▶ Remove disabled CSS classes
        └─▶ Re-attach event listeners
```

## 27. Error Flow — Complete Error Handling

### 27.1 Network Error During Livewire Request

```
1. User interacts with component
2. wire:model triggers Livewire request
3. fetch() fails (network error)
4. Livewire catches error
5. Livewire retries (1st attempt: immediate)
6. Livewire retries (2nd attempt: 2s delay)
7. Livewire retries (3rd attempt: 5s delay)
8. All retries fail
9. Livewire shows reconnection banner
10. User sees "Connection lost. Retrying..."
11. Livewire continues retrying in background
12. Network恢复
13. Livewire sends pending update
14. Server processes
15. Response applied (DOM morph)
16. Reconnection banner disappears
17. Component reconciles to server state
```

### 27.2 Validation Error During Livewire Request

```
1. User submits form (wire:submit)
2. Livewire sends request to server
3. Server validates input
4. Validation fails
5. Livewire receives 422 response
6. Livewire populates $errors bag
7. Blade re-renders with error messages
8. Livewire morphs DOM (adds error messages)
9. MutationObserver fires (invalid attribute added)
10. Component reconciles (shows error styles)
11. Screen reader announces error (role="alert")
12. Focus moves to first invalid field (if configured)
```

### 27.3 Server Error During Livewire Request

```
1. User interacts with component
2. wire:model triggers Livewire request
3. Server throws exception (500)
4. Livewire receives 500 response
5. Livewire shows error notification
6. Component reverts to last known good state
7. User sees "Something went wrong. Please try again."
8. Developer receives error in logging system (Sentry, etc.)
```

### 27.4 Session Expiry Flow

```
1. User is interacting with a component
2. Session expires (timeout)
3. User triggers a Livewire request
4. Server returns 419 (Session Expired)
5. Livewire catches 419
6. Livewire triggers full page reload
7. Browser navigates to login page
8. User authenticates
9. Laravel redirects back to original page
10. Session restored from flash data
11. Livewire re-hydrates all components
12. User continues where they left off (if URL state was preserved)
```

## 30. Complete Request-to-Render Timeline

```
Time 0ms:     User types in input field
Time 1ms:     input event fires on <input> element
Time 2ms:     gsmui.js component handler captures event
Time 3ms:     setAttribute(el, 'value', 'new text') — triggers MutationObserver
Time 4ms:     MutationObserver fires — reconcileValue() runs
Time 5ms:     reconcileValue() detects value change, updates internal state
Time 6ms:     component dispatches 'input' + 'change' events (bubbles)
Time 7ms:     Livewire catches change event on wire:model element
Time 8ms:     Livewire creates snapshot of component state
Time 9ms:     Debounce timer starts (150ms for wire:model.live)
Time 159ms:   Debounce timer fires — Livewire sends fetch() POST
Time 160ms:   fetch() request sent to /livewire/message/{component}
Time 161ms:   CspMiddleware adds CSP header to request
Time 162ms:   Request travels to server
Time 180ms:   Server receives request
Time 181ms:   Livewire validates signed payload
Time 182ms:   Livewire hydrates component from snapshot
Time 183ms:   Livewire calls component's update method
Time 184ms:   Server processes business logic
Time 185ms:   Server validates input
Time 186ms:   Server updates model/state
Time 187ms:   Server re-renders Blade template
Time 188ms:   Server serializes response (HTML morph)
Time 189ms:   Response sent to client
Time 190ms:   Response received by browser
Time 191ms:   Livewire parses response
Time 192ms:   Livewire applies DOM morph (diff + patch)
Time 193ms:   DOM changes applied
Time 194ms:   MutationObserver fires (value attribute changed by morph)
Time 195ms:   reconcileValue() runs — detects no-op (value matches)
Time 196ms:   Component idle — total round-trip: ~196ms
```

**Note:** This timeline is a simplified view. Actual timing depends on server load, network latency, and component complexity. The key insight is that the entire flow — from user input to DOM reconciliation — completes in under 200ms in typical conditions, providing a responsive feel without full page reloads.

## 32. Component Composition Patterns

### 32.1 Simple Composition (Component Inside Component)

```blade
{{-- Input with clear button --}}
<gsmui:input wire:model="search" placeholder="{{ __('Search...') }}">
    @if ($search)
        <gsmui:button
            as="div"
            size="xs"
            variant="ghost"
            wire:click="$set('search', '')"
            aria-label="{{ __('Clear search') }}"
        >
            <gsmui:icon name="x-mark" />
        </gsmui:button>
    @endif
</gsmui:input>
```

**Flow:**
1. Blade renders `<gsmui:input>` template
2. `@if ($search)` conditionally renders the clear button
3. `<gsmui:button>` renders its own template inside the input's slot
4. `gsmui.js` initializes both components independently
5. MutationObserver watches both for attribute changes
6. Click on clear button triggers Livewire `$set('search', '')`
7. Livewire updates, morphs DOM, input value clears

### 32.2 Complex Composition (State Root Pattern)

```blade
{{-- Color picker composes a hue slider --}}
<gsmui:color-picker wire:model="color">
    {{-- The hue slider is a sub-element that calls methods on the color picker root --}}
    <gsmui:slider
        min="0"
        max="360"
        value="{{ $hue }}"
        data-gsmui-parent="color-picker"
        data-gsmui-method="updateHue"
        aria-label="{{ __('Hue') }}"
    />

    {{-- Saturation/light area is a sub-element --}}
    <div
        class="gsmui-color-area"
        data-gsmui-parent="color-picker"
        data-gsmui-method="updateSatLight"
        role="application"
        aria-label="{{ __('Saturation and lightness') }}"
    />
</gsmui:color-picker>
```

**Flow:**
1. Color picker renders with slot content (hue slider, sat/light area)
2. `gsmui.js` initializes color picker as state root
3. Hue slider initializes as sub-element
4. Hue slider reads `data-gsmui-parent` to find state root
5. When hue changes, slider calls `stateRoot.updateHue(newHue)`
6. Color picker's `updateHue` method recalculates hex/rgb
7. Color picker updates `value` attribute via `setAttribute`
8. MutationObserver fires → reconcileValue → UI updates

### 32.3 Livewire Component Composition

```blade
{{-- Livewire parent with multiple GsmUi children --}}
<div wire:poll.5s="refreshData">
    {{-- Stats cards --}}
    <div class="grid grid-cols-3 gap-4">
        @foreach ($stats as $stat)
            <gsmui:card>
                <gsmui:card-header>
                    {{ __($stat->label) }}
                </gsmui:card-header>
                <gsmui:card-body>
                    <gsmui:text size="lg" weight="bold">
                        {{ $stat->value }}
                    </gsmui:text>
                </gsmui:card-body>
            </gsmui:card>
        @endforeach
    </div>

    {{-- Data table --}}
    <gsmui:table>
        <gsmui:table-header>
            <gsmui:table-row>
                <gsmui:table-head>{{ __('Name') }}</gsmui:table-head>
                <gsmui:table-head>{{ __('Value') }}</gsmui:table-head>
            </gsmui:table-row>
        </gsmui:table-header>
        <gsmui:table-body>
            @foreach ($data as $row)
                <gsmui:table-row>
                    <gsmui:table-cell>{{ $row->name }}</gsmui:table-cell>
                    <gsmui:table-cell>{{ $row->value }}</gsmui:table-cell>
                </gsmui:table-row>
            @endforeach
        </gsmui:table-body>
    </gsmui:table>
</div>
```

**Flow:**
1. Livewire renders the parent component
2. `wire:poll.5s="refreshData"` triggers a Livewire request every 5 seconds
3. Each poll re-renders the Blade template
4. Livewire morphs the DOM (updates stats cards and table rows)
5. GsmUi components inside the Livewire component re-initialize only if needed
6. MutationObserver detects attribute changes and reconciles

## 35. Final Synthesis

The GsmUi frontend architecture, as documented across Section 08, represents a deliberate choice to prioritize security, consistency, and verifiability over flashy client-side frameworks. Every architectural decision — from the inline bootstrap script that prevents FOUC, to the MutationObserver that bridges Livewire DOM morphs with component state, to the CSS variable cascade that enables instant theme switching — serves the core principle that the server is authoritative and the client is a thin, verifiable shell.

The complete page flow (this document) ties together 57 companion documents into a single, traceable lifecycle. A request enters the Laravel kernel, compiles Blade against the `gsmui:` namespace, emits localized HTML with `.dark` already resolved, delivers self-hosted `dist/` assets, initializes components through shared JS mixins, stays in lockstep with Livewire via signed payloads, and reconciles DOM changes through MutationObserver — all while maintaining a strict CSP that blocks external scripts, eval, and inline code.

This architecture is not the simplest possible approach, nor the most trendy. It is the most auditable. Every component can be inspected in Playwright, every CSP header can be validated in CI, every DOM state can be asserted in tests, and every architectural decision is documented in the 08.xx series. The result is a frontend that is secure by default, consistent by convention, and verifiable by automation — a system that can be maintained, extended, and trusted by the teams that build on it.

## 38. Appendix C — Common Pitfalls and Solutions

### Pitfall 1: FOUC (Flash of Unstyled Content)

**Symptom:** Page briefly shows light theme before switching to dark.

**Cause:** Bootstrap script not in `<head>`, or script is deferred/async.

**Solution:** Ensure the bootstrap script is inline, synchronous, and in `<head>`:

```html
<head>
    <script>
        var m = localStorage.getItem('gsmui-theme')
            || (matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
        if (m === 'dark') document.documentElement.classList.add('dark');
    </script>
</head>
```

### Pitfall 2: MutationObserver Not Firing

**Symptom:** Component doesn't update when Livewire morphs the DOM.

**Cause:** Using native `el.setAttribute()` instead of `setAttribute` from `utils.js`, or missing `attributeFilter`.

**Solution:** Always use `setAttribute` from `utils.js` and verify `attributeFilter` includes the changed attribute.

### Pitfall 3: Infinite Sync Loop

**Symptom:** Component keeps updating in a loop, browser freezes.

**Cause:** Missing `detangle()` at a Livewire sync point, causing the observer to re-trigger the same change.

**Solution:** Wrap Livewire-initiated changes in `detangle('livewire', ...)`:

```js
this.detangle('livewire', () => {
    this.el.value = newValue;
});
```

### Pitfall 4: CSP Violation in Production

**Symptom:** Scripts or styles blocked in production but not in development.

**Cause:** CSP enforcement is on in production (`CSP_ENABLED=true`) but off in development.

**Solution:** Test with `CSP_ENABLED=true` in staging. Check CSP headers in DevTools Network tab.

### Pitfall 5: Dark Mode Not Persisting

**Symptom:** Theme resets to light on page reload.

**Cause:** Bootstrap script not reading `localStorage`, or localStorage key mismatch.

**Solution:** Verify `localStorage.getItem('gsmui-theme')` returns the correct value. Check key spelling.

### Pitfall 6: Focus Not Restored After Modal Close

**Symptom:** After closing a modal, focus goes to `<body>` instead of the trigger button.

**Cause:** Missing focus restoration logic in the modal close handler.

**Solution:** Store `document.activeElement` before opening the modal, restore it on close:

```js
function openModal(trigger) {
    const previousFocus = document.activeElement;
    // ... open modal ...
    modal._previousFocus = previousFocus;
}

function closeModal(modal) {
    modal._previousFocus?.focus();
}
```

### Pitfall 7: Memory Leak from MutationObserver

**Symptom:** Page becomes slower over time, heap size grows.

**Cause:** MutationObserver not disconnected when component is removed from DOM.

**Solution:** Implement `destroy()` method and call it on `disconnectedCallback`:

```js
destroy() {
    this.observer.disconnect();
    this.el.removeEventListener('click', this.handleClick);
    // ... clean up all references
}
```
