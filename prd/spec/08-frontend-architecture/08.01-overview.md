## 6. Frontend Build Pipeline

The GsmUi frontend build pipeline is a multi-stage process that transforms source assets into production-ready bundles. Understanding this pipeline is critical for any developer working on the UI layer.

### 6.1 Pipeline Stages

```text
Source Assets                    Build Stage                     Output
─────────────────                ───────────                     ──────
Blade templates (*.blade.php) → Blade compiler           → HTML
Tailwind CSS (@theme)       → @tailwindcss/vite plugin  → CSS bundle
JavaScript (dist/*)          → Vite bundler              → JS bundle
SVG icons (inline)           → Blade components          → Embedded SVG
Design tokens (JSON/DB)      → Token engine              → CSS custom properties
```

Each stage has clear inputs, transformation rules, and outputs. The pipeline is designed to be deterministic — the same source always produces the same output.

### 6.2 Vite Configuration

The Vite configuration is minimal by design. Tailwind v4 replaces the PostCSS pipeline with its own Vite plugin:

```js
// Conceptual vite.config.js for GsmUi product UI
import { defineConfig } from "vite";
import laravel from "laravel-vite-plugin";
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({
  plugins: [
    laravel({
      input: ["resources/css/app.css", "resources/js/app.js"],
      refresh: true,
    }),
    tailwindcss(),
  ],
});
```

| Config Entry | Purpose |
| --- | --- |
| `laravel()` plugin | Routes Vite through Laravel's asset manifest for cache-busting |
| `tailwindcss()` plugin | Replaces PostCSS config; handles `@theme`/`@utility` processing |
| `refresh: true` | HMR for Blade changes during development |
| Source maps | Enabled in dev, stripped in prod builds |

### 6.3 Bundle Manifest

The Vite build produces a manifest that maps source paths to versioned output paths:

| Bundle | Source | Output | Contents |
| --- | --- | --- | --- |
| CSS | `resources/css/app.css` | `build/assets/app-[hash].css` | Tailwind utilities + GsmUi component styles |
| JS | `resources/js/app.js` | `build/assets/app-[hash].js` | App logic + Alpine.js |
| GsmUi JS | `dist/gsmui.js` | Served from package | Component behavior mixins |
| Editor JS | `dist/editor.js` | Served from package | Monaco editor integration |
| Editor CSS | `dist/editor.css` | Served from package | Editor-specific styles |

The manifest is consumed by `@vite` Blade directive to emit correct `<script>` and `<link>` tags with cache-busting hashes.

### 6.4 Asset Loading Order

The load order is defined to prevent FOUC and ensure correct cascade:

```html
{{-- 1. Theme bootstrap (inline, pre-paint) --}}
<script>
  (function() {
    const t = localStorage.getItem('gsmui-theme');
    if (t) document.documentElement.setAttribute('data-theme', t);
  })();
</script>

{{-- 2. CSS (Tailwind + GsmUi component styles) --}}
@vite(['resources/css/app.css'])

{{-- 3. GsmUi JS bundle --}}
<script src="{{ Vite::asset('dist/gsmui.js') }}"></script>

{{-- 4. App JS (Livewire, Alpine, app logic) --}}
@livewireScriptConfig
@vite(['resources/js/app.js'])
```

This order ensures:
1. Theme is applied before first paint (no FOUC)
2. CSS is parsed before JS executes
3. GsmUi component JS is available before Alpine/Livewire initialize
4. Livewire script config is loaded before component hydration

## 7. Component Communication Patterns

Components in GsmUi communicate through several well-defined channels. Understanding these patterns is essential for building consistent, maintainable UIs.

### 7.1 Top-Down (Props)

Data flows from parent to child through Blade component attributes:

```blade
{{-- Parent --}}
<gsmui:select
    wire:model="status"
    :options="$statuses"
    placeholder="Select status"
    size="sm"
    searchable
/>
```

Props are the primary communication channel. They are immutable within the child — a component never modifies its own props.

### 7.2 Bottom-Up (Events)

Child components emit events to notify parents of state changes:

```blade
{{-- Child emits --}}
x-on:change="$dispatch('status-changed', { value: $event.detail })"

{{-- Parent listens --}}
<div x-on:status-changed="handleStatusChange($event.detail)">
```

Events are the only sanctioned way for a child to communicate upward. Components never directly call parent methods.

### 7.3 Cross-Component (Livewire)

For server-side coordination, components use Livewire's reactive properties:

```php
class OrderForm extends Component
{
    public $status;
    public $items = [];

    // Livewire handles the sync; components read wire:model values
}
```

Livewire acts as the orchestration layer between components that need shared server state.

### 7.4 Global State (Theme)

Theme state is global and read through CSS custom properties. Components never store theme values in JavaScript — they always reference `--gsmui-*` variables.

### 7.5 Communication Pattern Summary

| Pattern | Direction | Mechanism | Use Case |
| --- | --- | --- | --- |
| Props | Parent → Child | Blade attributes | Configuration, data |
| Events | Child → Parent | `$dispatch` / Alpine | User actions, state changes |
| Livewire | Cross-component | `wire:model` / reactive props | Shared server state |
| CSS Variables | Global | `--gsmui-*` on `:root` | Theme, tokens |
| JS State | Internal | GsmUi JS mixins | Ephemeral UI state (focus, open/close) |

## 8. Responsive Design Architecture

GsmUi's responsive design is built on Tailwind's breakpoint system with GsmUi-specific conventions.

### 8.1 Breakpoint Scale

| Breakpoint | Prefix | Min Width | Typical Target |
| --- | --- | --- | --- |
| Mobile | (none) | 0px | Phone portrait |
| Small | `sm:` | 640px | Phone landscape |
| Medium | `md:` | 768px | Tablet portrait |
| Large | `lg:` | 1024px | Tablet landscape / small desktop |
| Extra large | `xl:` | 1280px | Desktop |
| 2XL | `2xl:` | 1536px | Large desktop |

### 8.2 Responsive Patterns

**Container queries** are preferred over media queries for component-level responsiveness:

```css
@utility gsmui-responsive {
  container-type: inline-size;
}
```

**Mobile-first** is the default. Base styles target mobile; breakpoint prefixes add complexity for larger screens.

**Touch targets** follow the 44px minimum on mobile, 32px on desktop:

```blade
{{-- Mobile: full-width button, desktop: auto --}}
<gsmui:button class="w-full sm:w-auto">Submit</gsmui:button>
```

### 8.3 Responsive Component Patterns

| Component | Mobile Behavior | Desktop Behavior |
| --- | --- | --- |
| `gsmui:date-picker` | `max-sm:fixed! max-sm:inset-0!` fullscreen popover | Positioned dropdown |
| `gsmui:select` | Full-width sheet | Positioned dropdown |
| `gsmui:modal` | Full-screen with drag handle | Centered dialog |
| `gsmui:sidebar` | Overlay with backdrop | Persistent sidebar |
| `gsmui:table` | Card layout or horizontal scroll | Full table |
| `gsmui:command` | Full-screen search | Dropdown palette |

### 8.4 Responsive Spacing

Spacing scales adapt to viewport. The token engine provides responsive spacing:

```css
:root {
  --gsmui-space-section: 3rem;    /* mobile */
}
@container (min-width: 768px) {
  --gsmui-space-section: 5rem;    /* tablet+ */
}
```

### 8.5 Typography Responsive

Font sizes use Tailwind's responsive prefixes to maintain readability:

```blade
<h1 class="text-2xl sm:text-3xl lg:text-4xl font-bold">
    Page Title
</h1>
<p class="text-sm sm:text-base leading-relaxed">
    Body text that scales appropriately.
</p>
```

## 9. Animation & Motion Architecture

The GsmUi motion system provides consistent, accessible animations across all components.

### 9.1 Motion Principles

| Principle | Rule |
| --- | --- |
| Purposeful | Every animation communicates a state change |
| Performant | Use `transform` and `opacity` only; never animate `width`/`height`/`top`/`left` |
| Respectful | Honor `prefers-reduced-motion` |
| Brief | Most animations 150-300ms; never exceed 500ms |
| Consistent | Same animation pattern for same interaction type |

### 9.2 Animation Categories

| Category | Duration | Easing | Use |
| --- | --- | --- | --- |
| Micro-interactions | 100-150ms | ease-out | Button press, toggle, hover state |
| State transitions | 200-300ms | ease-in-out | Dropdown open, modal enter, tab switch |
| Page transitions | 300-500ms | ease-in-out | Route changes, major layout shifts |
| Loading states | 1000-2000ms | linear | Spinners, skeleton shimmer |

### 9.3 CSS Animation Implementation

```css
/* Entry animation */
@keyframes gsmui-enter {
  from { opacity: 0; transform: translateY(-4px) scale(0.98); }
  to { opacity: 1; transform: translateY(0) scale(1); }
}

/* Exit animation */
@keyframes gsmui-exit {
  from { opacity: 1; transform: translateY(0) scale(1); }
  to { opacity: 0; transform: translateY(-4px) scale(0.98); }
}

/* Popover enter/exit */
.gsmui-popover[data-entering] {
  animation: gsmui-enter 200ms ease-out;
}
.gsmui-popover[data-exiting] {
  animation: gsmui-exit 150ms ease-in forwards;
}
```

### 9.4 Reduced Motion Support

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

Components respect `prefers-reduced-motion` by default. No component should require motion to convey information.

### 9.5 JavaScript Animation Hooks

GsmUi JS provides animation lifecycle hooks for components:

```js
// Conceptual animation lifecycle
el.addEventListener('gsmui:enter', () => {
  el.setAttribute('data-entering', '');
  el.addEventListener('animationend', () => {
    el.removeAttribute('data-entering');
  }, { once: true });
});
```

## 10. Accessibility Architecture

Accessibility is a first-class concern in GsmUi, not an afterthought. Every component follows WCAG 2.2 AA compliance.

### 10.1 ARIA Implementation Rules

| Rule | Implementation |
| --- | --- |
| Follow closest pattern | Input trigger = `role="combobox"`; button trigger = native `<button>` |
| No invented roles | Check ARIA APG and React Aria before introducing new patterns |
| Dynamic labels | `__()` from Blade; JS uses Blade-set value as primary |
| Live regions | Feedback components use `aria-live="polite"` or `aria-live="assertive"` |
| Focus management | Trapped in modals; restored on close; visible in dialogs |

### 10.2 Keyboard Navigation

| Component | Keyboard Behavior |
| --- | --- |
| `gsmui:button` | Enter/Space to activate |
| `gsmui:input` | Standard input keyboard |
| `gsmui:select` | Arrow keys to navigate options; Enter to select; Escape to close |
| `gsmui:slider` | Arrow keys for step; Home/End for min/max; PageUp/PageDown for larger steps |
| `gsmui:date-picker` | Arrow keys for day navigation; Enter to select; Escape to close popover |
| `gsmui:accordion` | Enter/Space to toggle; Arrow keys between headers |
| `gsmui:modal` | Tab trap; Escape to close; focus restored to trigger on close |
| `gsmui:command` | Type to search; Arrow keys to navigate results; Enter to select |

### 10.3 Color Contrast

All text and interactive elements meet WCAG 2.2 AA contrast ratios:
- Normal text: 4.5:1 minimum
- Large text: 3:1 minimum
- Interactive elements: 3:1 minimum
- Focus indicators: 3:1 minimum

### 10.4 Screen Reader Support

Components provide appropriate screen reader announcements:

```blade
{{-- Status announcement --}}
<div role="status" aria-live="polite" class="sr-only">
    {{ $statusMessage }}
</div>

{{-- Error announcement --}}
<div role="alert" aria-live="assertive" class="sr-only">
    {{ $errorMessage }}
</div>
```

## 11. Error Handling & Edge Cases

The frontend handles errors gracefully without breaking the user experience.

### 11.1 Component Error States

| Error Type | Handling |
| --- | --- |
| Invalid input | Layer `data-invalid:` styles; no shake animation |
| Network failure | Silent retry; show cached state if available |
| Hydration mismatch | Log warning; re-render component |
| Theme load failure | Fall back to default theme tokens |
| JS bundle failure | Degrade to server-rendered content |

### 11.2 Edge Case Patterns

**Empty states:** Components render meaningful empty states, not blank screens:

```blade
<gsmui:card>
    <x-slot:empty>
        <div class="text-center py-8">
            <x-heroicon-o-inbox class="w-12 h-12 mx-auto text-zinc-400" />
            <p class="mt-2 text-sm text-zinc-500">No items yet</p>
        </div>
    </x-slot:empty>
</gsmui:card>
```

**Loading states:** Components show appropriate loading indicators:

```blade
<gsmui:button loading>
    <x-gsmui:spinner class="w-4 h-4" />
    <span class="sr-only">Loading...</span>
</gsmui:button>
```

**Overflow handling:** Long content is truncated or scrolled, never breaking layout:

```blade
<div class="truncate max-w-xs" title="{{ $longText }}">
    {{ $longText }}
</div>
```

## 13. Testing Strategy

The frontend testing strategy covers multiple levels of verification.

### 13.1 Test Levels

| Level | Tool | Scope | Speed |
| --- | --- | --- | --- |
| Unit | PHPUnit | Component PHP logic | Fast |
| Integration | Livewire testing | Component hydration + rendering | Medium |
| Browser | Playwright | Full UI interaction | Slow |
| Visual | Playwright screenshots | Visual regression | Slow |
| Accessibility | Playwright + axe | WCAG compliance | Medium |

### 13.2 Playwright Testing

Playwright is the primary browser testing tool. Tests run against a running Laravel server:

```js
// tests/Browser/example.spec.js
const { test, expect } = require("@playwright/test");

test("select opens dropdown on click", async ({ page }) => {
  await page.goto("/test/select");
  await page.click("[data-gsmui-select-trigger]");
  await expect(page.locator("[data-gsmui-select-dropdown]")).toBeVisible();
});
```

### 13.3 Visual Regression

Screenshots are taken at each component state:
- Base state
- Hover state
- Focus state
- Active state
- Disabled state
- Invalid state
- Size variants (sm, default, xs)
- Dark mode variants

### 13.4 Accessibility Testing

Every interactive component is tested with axe-core:

```js
test("select is accessible", async ({ page }) => {
  await page.goto("/test/select");
  const results = await page.evaluate(() => axe.run());
  expect(results.violations).toEqual([]);
});
```

## 14. Security Considerations

Frontend security is enforced through CSP and input sanitization.

### 14.1 Content Security Policy

| Directive | Value | Rationale |
| --- | --- | --- |
| `script-src` | `'self'` | No CDN scripts; self-hosted bundles only |
| `style-src` | `'self' 'unsafe-inline'` | `adoptedStyleSheets` + minimal inline |
| `img-src` | `'self' data:` | Inline SVG only |
| `font-src` | (none) | System fonts only |
| `connect-src` | `'self'` | No external network requests |
| `frame-src` | `'none'` | No iframes |
| `object-src` | `'none'` | No plugins |

### 14.2 XSS Prevention

- All Blade output is escaped by default
- `@html` directive used only for trusted HTML (SVG icons)
- No `eval()`, `Function()`, or `innerHTML` in GsmUi JS
- `setAttribute`/`removeAttribute` utility functions handle attribute setting safely

### 14.3 CSRF Protection

- All Livewire requests include CSRF tokens automatically
- Form submissions use `@csrf` directive
- API routes use Sanctum tokens

## 24. Frontend State Management Deep Dive

GsmUi manages state across multiple layers: server-side Livewire state, client-side JavaScript ephemeral state, and CSS-driven visual state. Understanding how these layers interact is critical for building correct, performant UIs.

### 24.1 State Layer Architecture

```text
┌─────────────────────────────────────────────────────────────┐
│                    State Layer Stack                         │
├─────────────────────────────────────────────────────────────┤
│  Layer 4: CSS Visual State                                  │
│  data-invalid, data-disabled, data-open, :focus-visible     │
│  Driven by: Attributes + CSS selectors                      │
│  Lifetime: As long as attribute exists                       │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: JavaScript Ephemeral State                         │
│  focusedIndex, isOpen, hoverTimeout, animationFrame          │
│  Driven by: GsmUi JS mixins                                 │
│  Lifetime: Component DOM lifetime                            │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: Livewire Wire State                               │
│  wire:model bound properties                                 │
│  Driven by: Server round-trips                               │
│  Lifetime: Server session                                    │
├─────────────────────────────────────────────────────────────┤
│  Layer 1: Server Persistent State                           │
│  Database records, user preferences, theme definitions       │
│  Driven by: Eloquent/QueryBuilder                           │
│  Lifetime: Permanent                                         │
└─────────────────────────────────────────────────────────────┘
```

### 24.2 State Interaction Rules

| Interaction | Direction | Mechanism | Rule |
| --- | --- | --- | --- |
| Layer 1 → Layer 2 | Server → Livewire | Hydration | Server is source of truth |
| Layer 2 → Layer 3 | Livewire → JS | MutationObserver | JS reacts to attribute changes |
| Layer 3 → Layer 4 | JS → CSS | setAttribute/removeAttribute | CSS selectors drive visuals |
| Layer 4 → Layer 3 | CSS → JS | :focus-visible, :hover | CSS pseudo-classes inform JS |
| Layer 3 → Layer 2 | JS → Livewire | wire:model sync | Debounced, not every keystroke |
| Layer 2 → Layer 1 | Livewire → Server | Eloquent save | Explicit save action only |

### 24.3 State Ownership Matrix

| State Type | Owner | Sync Direction | Conflict Resolution |
| --- | --- | --- | --- |
| Theme preference | Server DB + localStorage | Bidirectional | DB wins on conflict |
| Form input value | Livewire (server) | Server → Client | Server is authoritative |
| Popover open/close | GsmUi JS | Client only | No server sync |
| Focused element | GsmUi JS | Client only | No server sync |
| Animation state | CSS + GsmUi JS | Client only | No server sync |
| Validation errors | Livewire (server) | Server → Client | Server determines errors |
| Loading state | Livewire | Server → Client | Server controls loading |
| Selected options | Livewire (server) | Bidirectional | Server is authoritative |

### 24.4 State Synchronization Patterns

**Pattern 1: Server-Authoritative (wire:model)**
```text
User types in input
       │
       ▼
GsmUi JS captures input event
       │
       ▼
Debounce timer (150ms default)
       │
       ▼
wire:model dispatches to server
       │
       ▼
Server validates and stores
       │
       ▼
Hydration diff returns to client
       │
       ▼
DOM updated via morph
       │
       ▼
MutationObserver triggers UI sync
```

**Pattern 2: Client-Only (ephemeral UI state)**
```text
User clicks trigger button
       │
       ▼
GsmUi JS sets isOpen = true
       │
       ▼
setAttribute('data-open', '')
       │
       ▼
CSS selector [data-open] applies popover styles
       │
       ▼
Popover visible
```

**Pattern 3: Optimistic Update**
```text
User toggles switch
       │
       ▼
GsmUi JS immediately updates visual state
       │
       ▼
wire:model dispatches to server
       │
       ▼
If server rejects: revert visual state
       │
       ▼
If server accepts: no change needed
```

### 24.5 State Debugging

GsmUi provides debugging utilities for development:

```js
// Enable state debugging in development
window.GsmuiDebug = {
    logState(component) {
        const el = document.querySelector(`[data-gsmui-${component}]`);
        if (!el) return;
        console.group(`GsmUi State: ${component}`);
        console.log('Attributes:', Object.fromEntries(
            [...el.attributes]
                .filter(a => a.name.startsWith('data-gsmui'))
                .map(a => [a.name, a.value])
        ));
        console.groupEnd();
    },

    logAllStates() {
        document.querySelectorAll('[data-gsmui-]').forEach(el => {
            const component = el.dataset.gsmuiComponent || 'unknown';
            this.logState(component);
        });
    },
};
```

## 25. Frontend Error Boundary Architecture

GsmUi implements a multi-layered error boundary system that ensures graceful degradation when components fail.

### 25.1 Error Boundary Layers

```text
Layer 1: Component-Level Try/Catch
  └─ Catches PHP rendering errors in Blade
  └─ Renders fallback markup
  └─ Logs error to Sentry

Layer 2: JavaScript Error Boundary
  └─ Catches JS runtime errors in GsmUi mixins
  └─ Logs error to console + Sentry
  └─ Component remains server-rendered

Layer 3: Livewire Error Boundary
  └─ Catches hydration errors
  └─ Re-renders component from server
  └─ Preserves page state

Layer 4: Global Error Handler
  └─ Catches unhandled errors
  └─ Shows error toast (if available)
  └─ Logs to Sentry
```

### 25.2 Error Handling Implementation

```blade
{{-- Component-level error boundary --}}
@php
try {
    $resolvedValue = $this->resolveValue($value);
} catch (\Exception $e) {
    report($e);
    $hasError = true;
    $resolvedValue = null;
}
@endphp

@if($hasError)
    <div role="alert" class="text-sm text-red-600 dark:text-red-400">
        {{ __('gsmui.component.error') }}
    </div>
@else
    {{-- Normal component render --}}
@endif
```

### 25.3 Error State Visual Treatment

| Error Level | Visual | User Action |
| --- | --- | --- |
| Warning | Yellow badge | None required |
| Error | Red border + message | Correct input |
| Critical | Full component fallback | Refresh page |
| Fatal | Error page | Contact support |

### 25.4 Error Recovery Strategies

| Scenario | Strategy | Implementation |
| --- | --- | --- |
| Network failure | Silent retry | Retry up to 3 times with exponential backoff |
| Validation error | Inline error display | `data-invalid` attribute + error message |
| Hydration error | Server re-render | Livewire re-fetches component state |
| Theme error | Fallback to default | Use Tailwind default values |
| JS bundle error | Server-rendered content | Components degrade to static HTML |
| CSP violation | Block and log | `securitypolicyviolation` event handler |

## 26. Frontend Performance Monitoring

### 26.1 Core Web Vitals Tracking

```js
// Performance monitoring (conceptual, in app.js)
function observeWebVitals() {
    // Largest Contentful Paint
    new PerformanceObserver((list) => {
        for (const entry of list.getEntries()) {
            if (entry.startTime > 2500) {
                console.warn('LCP exceeded threshold:', entry.startTime);
            }
        }
    }).observe({ type: 'largest-contentful-paint', buffered: true });

    // Cumulative Layout Shift
    let clsValue = 0;
    new PerformanceObserver((list) => {
        for (const entry of list.getEntries()) {
            if (!entry.hadRecentInput) {
                clsValue += entry.value;
                if (clsValue > 0.1) {
                    console.warn('CLS exceeded threshold:', clsValue);
                }
            }
        }
    }).observe({ type: 'layout-shift', buffered: true });

    // First Input Delay
    new PerformanceObserver((list) => {
        for (const entry of list.getEntries()) {
            if (entry.processingStart - entry.startTime > 100) {
                console.warn('FID exceeded threshold:', entry.processingStart - entry.startTime);
            }
        }
    }).observe({ type: 'first-input', buffered: true });
}
```

| Metric | Target | Measurement Method |
| --- | --- | --- |
| Component render time | < 5ms | `performance.mark()` in JS |
| Hydration time per component | < 50ms | Livewire debug bar |
| wire:model sync latency | < 100ms | Network tab round-trip |
| DOM diff time | < 16ms | Chrome DevTools performance |
| Memory per component | < 10KB | Chrome DevTools memory |
| CSS calculation time | < 2ms | Chrome DevTools rendering |

### 26.3 Performance Budget Enforcement

```js
// Performance budget checker (conceptual)
const PERFORMANCE_BUDGETS = {
    css: { max: 75 * 1024, current: 0 },      // 75KB
    js: { max: 150 * 1024, current: 0 },      // 150KB
    total: { max: 150 * 1024, current: 0 },   // 150KB gzipped
    lcp: { max: 2500, current: 0 },           // 2.5s
    fid: { max: 100, current: 0 },            // 100ms
    cls: { max: 0.1, current: 0 },            // 0.1
    tbt: { max: 200, current: 0 },            // 200ms
};

function checkBudget(metric, value) {
    const budget = PERFORMANCE_BUDGETS[metric];
    if (budget && value > budget.max) {
        console.warn(`Performance budget exceeded: ${metric} = ${value} (max: ${budget.max})`);
        return false;
    }
    return true;
}
```

## 29. Frontend Security Architecture

### 29.1 Security Layer Model

```text
Layer 1: Content Security Policy
  └─ script-src 'self'
  └─ style-src 'self' 'unsafe-inline'
  └─ img-src 'self' data:
  └─ connect-src 'self'
  └─ No CDN, no external resources

Layer 2: Input Sanitization
  └─ Blade {{ }} escapes all output
  └─ No {!! !!} except trusted HTML
  └─ No eval(), Function(), innerHTML
  └─ setAttribute/removeAttribute utils

Layer 3: CSRF Protection
  └─ Livewire auto-includes CSRF token
  └─ Form @csrf directive
  └─ API Sanctum tokens

Layer 4: XSS Prevention
  └─ All dynamic content escaped
  └─ No DOM manipulation with user input
  └─ CSP blocks inline scripts

Layer 5: Authentication
  └─ Livewire session-based auth
  └─ API token-based auth (Sanctum)
  └─ Middleware protection on routes
```

### 29.2 CSP Policy Matrix

| Directive | Value | Rationale |
| --- | --- | --- |
| `script-src` | `'self'` | No CDN scripts; self-hosted bundles only |
| `style-src` | `'self' 'unsafe-inline'` | `adoptedStyleSheets` + minimal inline |
| `img-src` | `'self' data:` | Inline SVG only |
| `font-src` | (none) | System fonts only |
| `connect-src` | `'self'` | No external network requests |
| `frame-src` | `'none'` | No iframes |
| `object-src` | `'none'` | No plugins |
| `base-uri` | `'self'` | No base tag injection |
| `form-action` | `'self'` | Forms submit to self only |

## 31. Frontend Build & Distribution Architecture

### 31.1 Build Pipeline Stages

```text
Source Assets                    Build Stage                     Output
─────────────────                ───────────                     ──────
Blade templates (*.blade.php) → Blade compiler           → HTML
Tailwind CSS (@theme)       → @tailwindcss/vite plugin  → CSS bundle
JavaScript (dist/*)          → Vite bundler              → JS bundle
SVG icons (inline)           → Blade components          → Embedded SVG
Design tokens (JSON/DB)      → Token engine              → CSS custom properties
```

### 31.2 Bundle Manifest

| Bundle | Source | Output | Contents | Target Size |
| --- | --- | --- | --- | --- |
| CSS | `resources/css/app.css` | `build/assets/app-[hash].css` | Tailwind utilities + GsmUi styles | < 50KB |
| JS | `resources/js/app.js` | `build/assets/app-[hash].js` | App logic + Alpine.js | < 100KB |
| GsmUi JS | `dist/gsmui.js` | Served from package | Component behavior mixins | < 80KB |
| Editor JS | `dist/editor.js` | Served from package | Monaco editor integration | < 50KB |
| Editor CSS | `dist/editor.css` | Served from package | Editor-specific styles | < 20KB |

### 31.3 Asset Loading Order

The load order is defined to prevent FOUC and ensure correct cascade:

```html
{{-- 1. Theme bootstrap (inline, pre-paint) --}}
<script>
  (function() {
    const t = localStorage.getItem('gsmui-theme');
    if (t) document.documentElement.setAttribute('data-theme', t);
  })();
</script>

{{-- 2. CSS (Tailwind + GsmUi component styles) --}}
@vite(['resources/css/app.css'])

{{-- 3. GsmUi JS bundle --}}
<script src="{{ Vite::asset('dist/gsmui.js') }}"></script>

{{-- 4. App JS (Livewire, Alpine, app logic) --}}
@livewireScriptConfig
@vite(['resources/js/app.js'])
```

### 31.4 Cache Strategy

| Asset Type | Cache Duration | Header |
| --- | --- | --- |
| Versioned assets | 1 year | `Cache-Control: max-age=31536000, immutable` |
| HTML | No cache | `Cache-Control: no-cache` |
| API responses | Short | `Cache-Control: private, max-age=300` |
