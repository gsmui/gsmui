# 07.50 - Scheduler

**Project:** GsmUi
**Architecture:** Task Scheduling (Console Kernel)
**Framework:** Laravel 13 + Livewire 4
**Version:** 1.0.0

---

> See also: `05.37-cli-architecture.md` for the command taxonomy. `07.51-cli-commands.md` is the Artisan command implementation contract. This document is the *scheduling implementation contract*: where recurring tasks are registered, how the environment timezone is pinned, how overlaps are prevented, and how output is logged.

# Purpose

The scheduler runs recurring maintenance and aggregation work â€” cache refresh, analytics rollups, search reindex, session purge, backups â€” outside any user request. It is the time-driven counterpart to the queue system (see `07.49-queues.md`): the scheduler *dispatches* jobs or runs lightweight closures, while Horizon *executes* them. Tasks are registered in one place so the single `php artisan schedule:run` entry point (driven by the OS cron) has a complete, auditable view of recurring work.

Goals:

- **One registration site** â€” all recurring tasks live in `routes/console.php` (or a dedicated `ScheduleServiceProvider`), never scattered across commands.
- **Deterministic timezone** â€” every task pins an explicit timezone; the app `timezone` config is authoritative.
- **No overlap** â€” long-running tasks use `withoutOverlapping()` so a slow run never stacks on a new one.
- **Observable output** â€” `appendOutputTo` / `emailOutputTo` send failures to the structured log (see `07.54-logging.md`).

# 1. Registration Site

Recurring tasks are declared with `Schedule::command(...)` in `routes/console.php`. Closure schedules use `Schedule::call(...)`.

```php
// routes/console.php
use Illuminate\Support\Facades\Schedule;

Schedule::command('gsmui:cache:clear --tag=search')
    ->dailyAt('03:00')
    ->timezone(config('app.timezone'))
    ->withoutOverlapping(10)
    ->appendOutputTo(storage_path('logs/schedule.log'))
    ->onFailure(fn () => report(new \RuntimeException('search cache clear failed')));

Schedule::command('analytics:aggregate --day=yesterday')
    ->dailyAt('02:00')
    ->timezone(config('app.timezone'))
    ->withoutOverlapping(30)
    ->onQueue('low');

Schedule::call(function () {
    \App\Domains\Shared\Jobs\PurgeExpiredSessions::dispatch()->onQueue('low');
})->hourly()->timezone(config('app.timezone'));
```

For larger task sets, prefer a dedicated provider so `routes/console.php` stays readable:

```php
// app/Providers/ScheduleServiceProvider.php
declare(strict_types=1);

namespace App\Providers;

use Illuminate\Console\Scheduling\Schedule;
use Illuminate\Support\ServiceProvider;

final class ScheduleServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        $this->app->booted(function (): void {
            $schedule = $this->app->make(Schedule::class);

            $schedule->command('backup:run')->daily()->at('01:00')
                ->timezone(config('app.timezone'))->withoutOverlapping();
        });
    }
}
```

Register the provider in `bootstrap/providers.php` (Laravel 13 style).

# 2. Timezone

The app timezone is the single source of truth. Pin it explicitly on every task so Daylight Saving transitions never shift a maintenance window.

```php
// config/app.php (excerpt)
'timezone' => 'UTC',
```

Laravel 11+ also exposes `schedule:timezone` config; keep it aligned with `app.timezone`:

```php
// config/scheduling.php (optional)
return [
    'timezone' => config('app.timezone'),
];
```

Never use `->daily()` without an explicit `->timezone(...)` in a multi-region deployment â€” server-local TZ will drift the window.

# 3. Preventing Overlaps

`withoutOverlapping($minutes)` acquires a Redis/cache lock so a new run cannot start until the lock expires. Use it for any task that can outlive its interval.

| Task | Interval | `withoutOverlapping` |
| --- | --- | --- |
| `analytics:aggregate` | daily | 30 min |
| `backup:run` | daily | 60 min |
| `gsmui:cache:clear` | daily | 10 min |
| `search:reindex --delta` | hourly | 15 min |

```php
Schedule::command('search:reindex --delta')
    ->hourly()
    ->timezone(config('app.timezone'))
    ->withoutOverlapping(15)
    ->onQueue('search');
```

For tasks that must not run on multiple servers simultaneously in a multi-node deployment, the overlap lock defaults to the cache store (`redis`); it is cluster-safe.

# 4. Logging & Failure Notification

Capture output and surface failures into the logging pipeline (see `07.54-logging.md`):

```php
Schedule::command('analytics:aggregate')
    ->dailyAt('02:00')
    ->timezone(config('app.timezone'))
    ->withoutOverlapping(30)
    ->appendOutputTo(storage_path('logs/schedule.log'))
    ->emailOutputTo(['ops@gsmui.dev'])      // only on failure by default
    ->onFailure(fn () => report(new \App\Domains\Shared\Exceptions\ScheduledTaskFailed(
        'analytics:aggregate'
    )));
```

Output files should be rotated by the OS logrotate to avoid unbounded growth; the `*OutputTo` paths live under `storage/logs`.

# 6. Operational Rules

1. Register every recurring task in exactly one place (no hidden `Console\Kernel` `$commands` scheduling elsewhere).
2. Always pin `->timezone(config('app.timezone'))`.
3. Always `->withoutOverlapping()` for tasks longer than their interval.
4. Long tasks dispatch jobs to a dedicated queue rather than running inline.
5. Failures must `report()` so they reach the log + monitoring (see `07.54-logging.md`, `07.52-health-checks.md`).

# 8. Task Registration Patterns

### 8.1 Inline Registration

For small projects, register tasks directly in `routes/console.php`:

```php
// routes/console.php
use Illuminate\Support\Facades\Schedule;

Schedule::command('gsmui:cache:clear --tag=search')
    ->dailyAt('03:00')
    ->timezone(config('app.timezone'))
    ->withoutOverlapping(10)
    ->appendOutputTo(storage_path('logs/schedule.log'))
    ->onFailure(fn () => report(new \RuntimeException('search cache clear failed')));

Schedule::command('analytics:aggregate --day=yesterday')
    ->dailyAt('02:00')
    ->timezone(config('app.timezone'))
    ->withoutOverlapping(30)
    ->onQueue('low');
```

### 8.2 Provider-Based Registration

For larger task sets, use a dedicated service provider:

```php
namespace App\Providers;

use Illuminate\Console\Scheduling\Schedule;
use Illuminate\Support\ServiceProvider;

final class ScheduleServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        $this->app->booted(function (): void {
            $schedule = $this->app->make(Schedule::class);

            $this->registerCoreTasks($schedule);
            $this->registerMediaTasks($schedule);
            $this->registerSearchTasks($schedule);
            $this->registerSecurityTasks($schedule);
        });
    }

    private function registerCoreTasks(Schedule $schedule): void
    {
        $schedule->command('analytics:aggregate --day=yesterday')
            ->dailyAt('02:00')
            ->timezone(config('app.timezone'))
            ->withoutOverlapping(30)
            ->onQueue('low')
            ->appendOutputTo(storage_path('logs/schedule.log'));

        $schedule->command('backup:run')
            ->dailyAt('01:00')
            ->timezone(config('app.timezone'))
            ->withoutOverlapping(60)
            ->appendOutputTo(storage_path('logs/backup.log'))
            ->onFailure(fn () => report(new \RuntimeException('backup failed')));
    }

    private function registerMediaTasks(Schedule $schedule): void
    {
        $schedule->command('media:optimize-pending')
            ->everyFifteenMinutes()
            ->timezone(config('app.timezone'))
            ->withoutOverlapping(15)
            ->onQueue('media');

        $schedule->command('media:cleanup-temp')
            ->hourly()
            ->timezone(config('app.timezone'))
            ->withoutOverlapping(10)
            ->onQueue('low');
    }
}
```

# 9. Overlap Prevention Deep Dive

### 9.1 Lock Mechanism

`withoutOverlapping()` uses a cache lock (Redis) to prevent concurrent execution:

```php
Schedule::command('analytics:aggregate')
    ->dailyAt('02:00')
    ->withoutOverlapping(30); // Lock held for 30 minutes

// How it works internally:
// 1. Acquire lock: "schedule:analytics:aggregate"
// 2. If lock acquired â†’ run command
// 3. If lock not acquired â†’ skip this run
// 4. Release lock after command completes (or after 30 min timeout)
```

### 9.2 Lock Timeout Selection

| Task duration | Recommended lock timeout | Notes |
| --- | --- | --- |
| < 5 min | 10 min | Generous buffer |
| 5-15 min | 20 min | Moderate buffer |
| 15-30 min | 45 min | Large buffer |
| 30-60 min | 90 min | Very large buffer |
| > 60 min | 120 min | Or split into smaller tasks |

### 9.3 Multi-Node Lock Behavior

In a multi-server deployment, the Redis lock is cluster-safe:

```text
Server A acquires lock â†’ runs task
Server B tries to acquire lock â†’ skipped (lock held by A)
Server C tries to acquire lock â†’ skipped (lock held by A)

After task completes:
Server A releases lock
Next scheduled run: any server can acquire lock
```

### 9.4 Without Overlapping vs Exclusive

| Method | Behavior | Use case |
| --- | --- | --- |
| `withoutOverlapping()` | Skip if running, wait for lock | Most tasks |
| `withoutOverlapping()->evenInMaintenanceMode()` | Run even during maintenance | Critical tasks |
| `onOneServer()` | Only run on one server in fleet | Singleton tasks |
| `runInBackground()` | Non-blocking schedule run | Long-running tasks |

# 10. Timezone Handling

### 10.1 Global Timezone

```php
// config/app.php
'timezone' => 'UTC',

// All schedules use UTC by default
Schedule::command('analytics:aggregate')
    ->dailyAt('02:00') // 02:00 UTC
    ->timezone(config('app.timezone')); // Explicit UTC
```

### 10.2 Per-Task Timezone

Override timezone for specific tasks:

```php
// For a user-facing task in a specific timezone
Schedule::command('notifications:send-daily-digest')
    ->dailyAt('09:00')
    ->timezone('America/New_York'); // 09:00 ET

// For a global maintenance task
Schedule::command('backup:run')
    ->dailyAt('01:00')
    ->timezone('UTC'); // Always UTC
```

### 10.3 DST Transition Handling

Laravel's scheduler handles DST transitions automatically:

```text
Spring forward (UTC-4 â†’ UTC-3):
  Task at 02:00 UTC â†’ still 02:00 UTC (no change)
  Task at 02:00 ET â†’ 03:00 ET (skipped hour)

Fall back (UTC-3 â†’ UTC-4):
  Task at 02:00 UTC â†’ still 02:00 UTC (no change)
  Task at 02:00 ET â†’ runs twice (2:00 ET and 3:00 ET)
```

### 10.4 Timezone Validation

```php
// In schedule registration:
assert(
    in_array(config('app.timezone'), DateTimeZone::listIdentifiers()),
    'Invalid app timezone: ' . config('app.timezone')
);
```

# 12. Scheduler Performance

### 12.1 Scheduler Execution Time

The `schedule:run` command should complete quickly:

| Metric | Target | Notes |
| --- | --- | --- |
| `schedule:run` duration | < 5s | Should not block cron |
| Task dispatch latency | < 50ms | Per task |
| Lock acquisition | < 100ms | Per task |
| Total tasks per run | < 50 | Keep cron fast |

### 12.2 Optimization Tips

```text
1. Use onQueue() to dispatch long tasks to workers
2. Avoid expensive operations in schedule:run itself
3. Use withoutOverlapping() to prevent stacking
4. Keep task count manageable (combine related tasks)
5. Use config arrays for task definitions (faster than provider)
```

# 14. Operational Rules

1. Register every recurring task in exactly one place (no hidden `Console\Kernel` `$commands` scheduling elsewhere).
2. Always pin `->timezone(config('app.timezone'))`.
3. Always `->withoutOverlapping()` for tasks longer than their interval.

# 17. Scheduler Security

### 17.1 Task Authorization

Scheduled tasks run as the system user, not an authenticated user. Ensure tasks don't assume auth context:

```php
// âŒ Bad: assumes authenticated user
Schedule::command('analytics:aggregate')
    ->dailyAt('02:00');

// Inside the command:
$user = auth()->user(); // null â€” fails!

// âœ… Good: use system user
Schedule::command('analytics:aggregate --user=system')
    ->dailyAt('02:00');

// Or handle missing auth:
public function handle(): int
{
    // Run as system user if no auth
    if (!auth()->check()) {
        Auth::login(User::system());
    }

    // ... rest of command
}
```

### 17.2 Task Output Security

```php
// Don't log sensitive data in scheduled task output
Schedule::command('export:user-data --format=csv')
    ->dailyAt('03:00')
    ->appendOutputTo(storage_path('logs/exports.log')); // Might contain PII!

// Better: log to a secure location with restricted permissions
Schedule::command('export:user-data --format=csv')
    ->dailyAt('03:00')
    ->appendOutputTo(storage_path('logs/secure/exports-' . date('Y-m-d') . '.log'));

// Or avoid logging output entirely for sensitive tasks
Schedule::command('export:user-data --format=csv')
    ->dailyAt('03:00')
    ->emailOutputTo(['security@gsmui.dev']);
```

# 18. Scheduler Deployment

### 18.1 Cron Setup

```bash
# /etc/crontab or crontab -e
* * * * * cd /var/www/gsmui && php artisan schedule:run >> /dev/null 2>&1
```

### 18.2 Single Server vs Multi-Server

| Deployment | Strategy | Notes |
| --- | --- | --- |
| Single server | Cron on one server | Simple, default |
| Multi-server | Cron on one server + Redis locks | Lock prevents duplicates |
| Container | Single container runs cron | Use `onOneServer()` |

### 18.3 Container Deployment

```dockerfile
# Dockerfile
FROM php:8.3-cli

# Install cron
RUN apt-get update && apt-get install -y cron

# Add cron job
RUN echo "* * * * * cd /var/www/gsmui && php artisan schedule:run >> /dev/null 2>&1" > /etc/cron.d/gsmui

# Start cron + app
CMD ["cron", "-f"]
```

# 20. Operational Rules

1. Register every recurring task in exactly one place.
2. Always pin `->timezone(config('app.timezone'))`.
3. Always `->withoutOverlapping()` for tasks longer than their interval.
4. Long tasks dispatch jobs to a dedicated queue.
5. Failures must `report()` so they reach the log + monitoring.
6. Use `onQueue()` for tasks that take > 5s.
7. Lock timeout should be 2x expected task duration.
8. Output logs should be rotated by OS logrotate.
9. Monitor schedule:run duration â€” keep under 5 seconds.
10. Test schedule registration in CI.

# 21. Scheduler Integration with Queues

### 21.1 Dispatching Jobs from Scheduler

The scheduler dispatches jobs to queues for execution by Horizon workers:

```php
// Schedule dispatches job to queue
Schedule::command('analytics:aggregate --day=yesterday')
    ->dailyAt('02:00')
    ->onQueue('low'); // Job runs on low queue worker

// Or dispatch a job directly from a scheduled closure
Schedule::call(function () {
    \App\Domains\Shared\Jobs\PurgeExpiredSessions::dispatch()->onQueue('low');
})->hourly();
```

### 21.2 Queue-Aware Scheduling

| Task | Schedule | Queue | Worker timeout |
| --- | --- | --- | --- |
| `analytics:aggregate` | Daily 02:00 | `low` | 300s |
| `backup:run` | Daily 01:00 | â€” (inline) | 3600s |
| `search:reindex --delta` | Hourly | `search` | 60s |
| `media:optimize-pending` | Every 15 min | `media` | 120s |
| `notifications:send-digest` | Daily 09:00 | `mail` | 60s |
| `flag:analytics:prune` | Daily | `low` | 120s |

### 21.3 Inline vs Queued Execution

```php
// Inline execution (blocks schedule:run)
Schedule::command('gsmui:cache:clear --tag=search')
    ->dailyAt('03:00')
    ->withoutOverlapping(10); // Lock prevents stacking

// Queued execution (non-blocking)
Schedule::command('analytics:aggregate')
    ->dailyAt('02:00')
    ->onQueue('low'); // Dispatched to queue, runs async

// Hybrid: schedule runs a thin command that dispatches a job
Schedule::call(function () {
    \App\Domains\Analytics\Jobs\AggregateDaily::dispatch()
        ->onQueue('low');
})->dailyAt('02:00');
```

### 28.2 Task Lifecycle

```text
1. Cron triggers schedule:run every minute
2. Scheduler loads all registered events
3. For each event, check if it's due:
   - Parse cron expression
   - Compare with current time
   - Check timezone
4. If due:
   - Check overlap lock (Redis)
   - If lock available â†’ execute
   - If lock held â†’ skip this run
5. Execute task:
   - Inline: run artisan command directly
   - Queued: dispatch job to queue
6. Log output (if configured)
7. Release lock
8. Move to next task
```

### 28.3 Lock Mechanism

```text
Without overlapping:
  schedule:run starts
    Task A acquires lock "schedule:task-a"
    Task A executes (takes 5 minutes)
    schedule:run starts again (new cron tick)
    Task A lock still held â†’ SKIP Task A
    Task A completes â†’ releases lock
    Next schedule:run â†’ Task A can execute again
```

        return 'failed';

# 41. Scheduler Backup and Recovery

### 41.1 Backing Up Schedule Configuration

Export the current schedule to a JSON file for documentation and disaster recovery. Iterate over all registered events, capture command, expression, timezone, overlap settings, server settings, and queue. Write to storage/app/schedule-config.json with pretty print.

### 41.2 Recovery Procedures

| Scenario | Steps |
| --- | --- |
| Redis lock stuck | Run redis-cli DEL schedule:* to clear all locks |
| Schedule not running | Check crontab -l, check storage/logs/schedule.log, run php artisan schedule:run manually |
| Task corrupted | Export schedule, compare to expected config, re-register |
| Cron service down | Restart cron: service cron restart (Linux) or systemctl restart cron |
| Multiple servers running same task | Verify onOneServer() is set, check Redis connectivity |

### 41.3 Disaster Recovery Runbook

`	ext
1. Assess: Which tasks are affected?
2. Contain: Stop cron on all servers
3. Fix: Clear stuck locks, fix corrupted configs
4. Verify: Run schedule:run --verbose on one server
5. Resume: Restart cron on all servers
6. Monitor: Watch for 30 minutes
7. Post-mortem: Document root cause and prevention
`

# 42. Scheduler Integration Patterns

### 42.1 Integration with Feature Flags

Conditionally schedule tasks based on feature flags. Check the FeatureFlagService in the schedule callback to determine whether to run. This allows enabling/disabling scheduled tasks without code deployment.

### 42.2 Integration with Observers

Scheduled tasks often trigger observer events. When a scheduled task updates a model, the model observer fires. Ensure observers are idempotent since scheduled tasks may retry.

### 42.3 Integration with Multi-Tenancy

For multi-tenant deployments, schedule tasks per-tenant or globally:

- Global tasks: backup, analytics aggregation, cache warming
- Per-tenant tasks: tenant-specific cleanup, per-tenant analytics
- Use tenant context switching in task execution

### 42.4 Integration with Settings

Read task configuration from the settings system rather than hardcoding. The scheduler reads settings once at registration time. For dynamic settings, use runtime callbacks.

# 43. Scheduler Security

### 43.1 Command Authorization

Scheduled commands should validate they are running in the correct context:

- Check APP_ENV matches expected environment
- Verify the command is registered and authorized
- Log the command execution with user context where applicable
- Rate-limit commands that modify data

### 43.2 Output Security

Scheduled command output should never contain:

- Database credentials or connection strings
- API keys or tokens
- User PII (emails, names, addresses)
- Internal IP addresses or hostnames
- Stack traces in production logs

### 43.3 Lock Security

Redis locks used for schedule coordination should:

- Use unique lock namespacing per application instance
- Set reasonable TTLs to prevent permanent locks
- Be cleared only by authorized processes
- Be monitored for unexpected acquisition patterns

# 44. Scheduler Checklist for New Commands

When adding a new scheduled command, verify these items before merging:

| Item | Check |
| --- | --- |
| Command registered in Kernel | Verify in schedule() method |
| Timezone pinned | ->timezone(config('app.timezone')) set |
| Overlap prevention | ->withoutOverlapping() if duration > 1 minute |
| Queue specified | ->onQueue() if dispatching jobs |
| Failure reporting | ->onFailure() callback with report() |
| Idempotency | Command can run twice without side effects |
| Timeout set | ->withoutOverlapping(N) with reasonable timeout |
| Output rotation | ->appendOutputTo() with rotation if verbose |
| CI test | Schedule registration test passes |
| Documentation | Command purpose and frequency documented |

### 44.1 Code Review Checklist

Reviewers should verify:

- Task is necessary (not duplicating an existing task)
- Cron expression is correct and documented
- Overlap prevention is configured
- Queue is appropriate (low for background, default for medium, high for urgent)
- Failure handling reports to bugsnag
- Command is idempotent
- No secrets or PII in command arguments or output

### 44.2 Pre-Deployment Verification

`ash
# Verify all tasks are registered
php artisan schedule:list

# Run a dry-run of critical tasks
php artisan analytics:aggregate --dry-run

# Check schedule output
php artisan schedule:run --verbose 2>&1 | head -50
`

### 44.3 Post-Deployment Monitoring

Monitor the first few runs of new scheduled tasks:

1. Check that the task appears in schedule:list
2. Verify it runs at the expected time
3. Confirm no errors in storage/logs/scheduler.log
4. Validate the output matches expectations
5. Monitor queue depth for any buildup

# 45. Scheduler Summary

The scheduler is the heartbeat of the Gsmui backend. It orchestrates recurring work across analytics, backups, cache management, search indexing, monitoring, and maintenance. The scheduler integrates tightly with the queue system for heavy work, the lock system for coordination, and the monitoring system for observability. Every scheduled task must be idempotent, timezone-aware, overlap-protected, and failure-reported. The schedule should be treated as production infrastructure: documented, tested, monitored, and backed up.
