# 07.12 - Events

**Project:** GsmUi
**Architecture:** Event-Driven Architecture (EDA)
**Framework:** Laravel 13 + Livewire 4
**Version:** 1.0.0

---

# Purpose

> See also: `05.10-events.md` for the conceptual event architecture, lifecycle, and listener matrix. This document specifies the **implementation contract** — the concrete event class shape, payload rules, `ShouldBroadcast` usage for real-time listeners, past-tense naming, and the exact dispatch pattern that Actions (see `07.08-action-layer.md`) use after commit.

Events are the decoupling mechanism between GsmUi bounded contexts. Instead of an Action or Service calling another domain directly, it publishes an immutable event describing something that has **already happened**. Listeners (see `07.13-listeners.md`) subscribe and perform follow-up work — search indexing, notifications, cache invalidation, external sync. This keeps domains independent, supports async processing via queues, and paves the way for future extraction of domains into services.

Every event is a `final` class with `public readonly` constructor properties carrying only the data listeners need — never an HTTP request, a model instance, or a service. Events are dispatched **after** the surrounding database transaction commits (encoded by `Action::dispatchAfterCommit()`).

│                                                                         │
│  WITH EVENTS (decoupled):                                               │
│  ┌─────────────────────────────────────────────────────────┐            │

│  │  {                                                      │            │
│  │      $component = $this->create($data);                 │            │

│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘

# 1E. Event Decision Tree

```text
Should I create an Event?
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  Did something happen? (past tense)                             │
│  ├─ NO  → It's an Action, not an Event                         │
│  └─ YES → Do other domains need to react?                      │
│            ├─ NO  → No event needed                             │
│            └─ YES → Create an Event                             │
│                                                                 │
│  Should the listener be queued?                                 │
│  ├─ NO  → Sync listener (cache invalidation, audit)            │
│  └─ YES → Queued listener (search, email, external API)        │
│                                                                 │
│  Should the event broadcast to browsers?                        │
│  ├─ NO  → Standard event                                       │
│  └─ YES → Event with ShouldBroadcast                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

# 2A. Extended Event Class Contract

Events are plain payload carriers with strict rules:

| Rule | Implementation | Rationale |
| --- | --- | --- |
| `final` class | `final class ComponentCreated` | Prevents inheritance |
| `readonly` properties | `public readonly int $componentId` | Immutable payload |
| Past-tense name | `ComponentCreated` not `CreateComponent` | Encodes "already happened" |
| Scalar values | `int $componentId` not `Component $component` | Serializable across queues |
| No services | No DB, Cache, Event facades | Pure data carrier |
| Minimal data | Only what listeners need | Avoid payload bloat |

---

# 2B. Event Property Naming

| Convention | Example | Rationale |
| --- | --- | --- |
| Entity ID as `{entity}Id` | `$componentId`, `$userId` | Clear what the ID refers to |
| Scalar types | `int`, `string`, `float` | Serializable |
| Nullable for optional | `?string $reason = null` | Explicit optional data |
| No collections | `array $tags` not `Collection $tags` | Serializable |
| No dates as objects | `string $publishedAt` not `Carbon $publishedAt` | Serializable |

```php

{

        public readonly int $userId,
        public readonly string $version,
        public readonly array $tags = [],
        public readonly ?string $changelog = null,
    ) {}
}
```

# 2D. Event Anti-Patterns

| Anti-pattern | Why it's bad | Correct approach |
| --- | --- | --- |
| Imperative name (`CreateComponent`) | Confuses with Action | Use past tense (`ComponentCreated`) |
| Eloquent model in payload | Serialization issues, stale data | Pass scalar IDs |
| Request object in payload | Ties event to HTTP | Pass scalar values |
| Service in payload | Hidden coupling | Listener constructs services |
| Large payload | Queue performance | Pass IDs, re-query in listener |
| Mutable properties | Listeners may mutate | Use `readonly` |
| Business logic in event | Violates single responsibility | Move to Service |

# 3. Event Class Contract

Events are plain payload carriers. They use past-tense names and `public readonly` typed properties. For real-time (Livewire/browser) consumption they implement `ShouldBroadcast`.

```php
namespace App\Domains\Components\Events;

use Illuminate\Foundation\Events\Dispatchable;
use Illuminate\Queue\SerializesModels;

final class ComponentPublished
{
    use Dispatchable, SerializesModels;

    public function __construct(
        public readonly int $componentId,
        public readonly int $userId,
        public readonly string $version,
    ) {}
}
```

---

# 3A. Event with SerializesModels

The `SerializesModels` trait ensures Eloquent models in the payload are serialized by ID and re-fetched on deserialization:

```php
final class ComponentPublished
{
    use Dispatchable, SerializesModels;

    public function __construct(
        public readonly int $componentId,
        public readonly int $userId,
        public readonly string $version,
    ) {}
}

// Usage:
event(new ComponentPublished(
    componentId: $component->id,
    userId: $user->id,
    version: '1.0.0',
));
```

# 3B. Event Serialization Matrix

| Data Type | Serialization | Deserialization |
| --- | --- | --- |
| `int` | Direct | Direct |
| `string` | Direct | Direct |
| `float` | Direct | Direct |
| `array` | Direct | Direct |
| `?string` | Nullable | Nullable |
| Eloquent Model | ID (via SerializesModels) | Re-fetched from DB |
| Value Object | `toArray()` (via cast) | Reconstructed from array |
| Enum | `->value` (string) | `::from($value)` |

# 3C. Event with Metadata Array

For events that carry variable metadata, use an `array` property:

```php
final class ComponentPublished
{

    public function __construct(
        public readonly int $componentId,

        public readonly string $version,

// Dispatch with metadata:

    userId: $user->id,
    version: '1.0.0',
    metadata: [
        'tags' => ['ui', 'form'],
        'changelog' => 'Added new variants',
        'breaking' => false,
    ],
));
```

# 4. Payload Shape Rules

| Rule                          | Reason                                              |
| ----------------------------- | --------------------------------------------------- |
| Pass IDs, not models          | Models may be detached from a rolled-back transaction |
| Pass scalars / small VOs      | Serializable across queue workers                  |
| No request or service objects | Avoids hidden coupling and memory leaks             |
| Immutable (`readonly`)        | Listeners must not mutate the payload               |
| Minimal data                 | Listeners re-query if they need more                |

---

# 4A. Payload Shape Deep Dive

| Rule | Reason | Example |
| --- | --- | --- |
| Pass IDs, not models | Models may be detached from rolled-back transaction | `$componentId` not `$component` |
| Pass scalars / small VOs | Serializable across queue workers | `int`, `string`, `Money` |
| No request or service objects | Avoids hidden coupling and memory leaks | Never `Request` or `DB` |
| Immutable (`readonly`) | Listeners must not mutate the payload | `public readonly int $id` |
| Minimal data | Listeners re-query if they need more | Only IDs, not full models |

# 4B. Payload Size Guidelines

| Payload Size | Acceptable? | Example |
| --- | --- | --- |
| < 1KB | Yes | IDs + scalars |
| 1-5KB | Acceptable | IDs + metadata array |
| 5-10KB | Review carefully | Consider splitting |
| > 10KB | No | Pass IDs, re-query in listener |

# 4C. Payload Versioning

When event payloads change over time, use optional properties with defaults:

```php
// Version 1:
final class ComponentPublished
{
    public function __construct(
        public readonly int $componentId,
        public readonly int $userId,
    ) {}
}

// Version 2 (backward compatible):
final class ComponentPublished
{
    public function __construct(
        public readonly int $componentId,
        public readonly int $userId,
        public readonly string $version = '1.0.0', // NEW — optional
        public readonly array $tags = [],          // NEW — optional
    ) {}
}
```

Existing listeners continue to work. New listeners can access the new properties.

# 5. Real-Time Events (`ShouldBroadcast`)

Events that must reach the browser (Livewire echo, websockets) implement `ShouldBroadcast` and declare a channel. They still carry only IDs.

```php
namespace App\Domains\Components\Events;

use Illuminate\Broadcasting\Channel;
use Illuminate\Broadcasting\InteractsWithSockets;
use Illuminate\Contracts\Broadcasting\ShouldBroadcast;

final class ComponentPublished implements ShouldBroadcast
{
    use Dispatchable, InteractsWithSockets, SerializesModels;

    public function __construct(
        public readonly int $componentId,
        public readonly int $userId,
        public readonly string $version,
    ) {}

    public function broadcastOn(): array
    {
        return [new Channel("user.{$this->userId}")];
    }

    public function broadcastAs(): string
    {
        return 'component.published';
    }
}
```

# 7. Dispatch Pattern (After Commit)

Actions must dispatch via `Action::dispatchAfterCommit()` so listeners never observe rolled-back data (see `05.10-events.md` §"Transaction Rules"). Direct `event()` calls inside an Action are forbidden.

```php
// Inside CreateComponentAction::handle():
$this->dispatchAfterCommit(new ComponentCreated(
    componentId: $component->id,
    userId: $data->userId,
));

// Equivalent manual form (only outside Actions):
DB::afterCommit(fn () => event(new ComponentCreated(
    componentId: $component->id,
    userId: $data->userId,
)));
```

# 7A. Dispatch After Commit Deep Dive

Actions must dispatch via `Action::dispatchAfterCommit()` so listeners never observe rolled-back data:

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                    DISPATCH AFTER COMMIT PATTERN                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  WITHOUT dispatchAfterCommit (dangerous):                               │
│  ┌─────────────────────────────────────────────────────────┐            │
│  │  DB::transaction(function () {                          │            │
│  │      $component = $this->create($data);                 │            │
│  │      event(new ComponentCreated($component->id)); // ❌  │            │
│  │      // Listener runs BEFORE commit                     │            │
│  │      // If transaction rolls back, listener has stale   │            │
│  │      // data in its queue job                           │            │
│  │  });                                                    │            │
│  └─────────────────────────────────────────────────────────┘            │
│                                                                         │
│  WITH dispatchAfterCommit (safe):                                       │
│  ┌─────────────────────────────────────────────────────────┐            │
│  │  DB::transaction(function () {                          │            │
│  │      $component = $this->create($data);                 │            │
│  │      $this->dispatchAfterCommit(                        │            │
│  │          new ComponentCreated($component->id) // ✅     │            │
│  │      );                                                 │            │
│  │      // Event queued ONLY after commit succeeds         │            │
│  │  });                                                    │            │
│  └─────────────────────────────────────────────────────────┘            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

# 7B. Dispatch After Commit in Actions

```php
class CreateComponentAction extends Action
{
    public function run(CreateComponentData $data): Component
    {
        $component = $this->components->create($data->toArray());

        $this->dispatchAfterCommit(new ComponentCreated(
            componentId: $component->id,
            userId: $data->userId,
        ));

        return $component;
    }
}
```

# 7C. Dispatch After Commit in Services

Outside Actions, use `DB::afterCommit()`:

```php
class SubscriptionService
{
    public function cancel(int $subscriptionId): void
    {
        DB::transaction(function () use ($subscriptionId) {
            $subscription = Subscription::find($subscriptionId);
            $subscription->update(['status' => SubscriptionStatus::Canceled]);

            DB::afterCommit(fn () => event(new SubscriptionCanceled(
                subscriptionId: $subscriptionId,
                userId: $subscription->user_id,
            )));
        });
    }
}
```

# 8. Event Registration & Discovery

Laravel's automatic event discovery registers listeners declared in each domain's `Listeners/` folder. No manual mapping is required when the listener's `handle()` type-hints the event.

```php
// app/Domains/Components/Listeners/UpdateSearchIndex.php
namespace App\Domains\Components\Listeners;

use App\Domains\Components\Events\ComponentPublished;
use Illuminate\Contracts\Queue\ShouldQueue;

final class UpdateSearchIndex implements ShouldQueue
{
    public function handle(ComponentPublished $event): void
    {
        // re-query by $event->componentId, push to Meilisearch
    }
}
```

Expensive listeners implement `ShouldQueue` (see `07.14-jobs.md`). Sync listeners are reserved for lightweight work (cache invalidation, audit logging).

# 12. Event Security Considerations

| Risk | Mitigation |
| --- | --- |
| Payload contains secrets | Only IDs and scalars in payload |
| Event listener performs unauthorized action | Listeners check authorization independently |
| Broadcast leaks data to unauthorized users | Private/presence channels with auth |
| Event replay attacks | Idempotency keys, unique constraints |
| Stale data from serialized models | `SerializesModels` re-fetches on deserialize |
| Memory leak from large payloads | Strict payload size limits |

| Broadcast event | Browser exposure | Private channels with auth middleware |

# 13. Event Error Handling

```php
// In a listener:
class UpdateSearchIndex implements ShouldQueue
{
    public int $tries = 3;

    public array $backoff = [10, 30, 60];

    public function handle(ComponentPublished $event): void
    {
        try {
            $this->search->upsert('components', $event->componentId);
        } catch (\Exception $e) {
            logger()->error('search_index.update_failed', [
                'component_id' => $event->componentId,
                'error' => $e->getMessage(),

            throw $e; // Re-throw to trigger retry
        }
    }

    public function failed(ComponentPublished $event, \Throwable $exception): void
    {
        report($exception);

        // Optionally notify admin
        Notification::send(
            User::where('is_admin', true)->get(),
            new SearchIndexFailedNotification($event, $exception)
        );
    }
}
```

# 20. Event Best Practices Summary

| Practice | Description |
| --- | --- |
| Past-tense naming | `ComponentCreated` not `CreateComponent` |
| Scalar payloads | IDs and strings, not models |
| Dispatch after commit | Never dispatch inside uncommitted transactions |
| Idempotent listeners | Safe to run multiple times |
| One responsibility | One listener per follow-up action |
| Queue expensive work | I/O, external services, media |
| Test with Event::fake | Assert dispatch and payload |
| Monitor with Horizon | Dashboard, alerts, dead letters |

---

# 21. Event Anti-Patterns Complete List

| Anti-pattern | Why it's bad | Correct approach |
| --- | --- | --- |
| Imperative name | Confuses with Action | Use past tense |
| Eloquent model in payload | Serialization issues | Pass scalar IDs |
| Request object in payload | Ties event to HTTP | Pass scalar values |
| Service in payload | Hidden coupling | Listener constructs services |
| Large payload (> 10KB) | Queue performance | Pass IDs, re-query |
| Mutable properties | Listeners may mutate | Use `readonly` |
| Business logic in event | Violates SRP | Move to Service |
| Direct event dispatch in Action | May fire before commit | Use `dispatchAfterCommit()` |
| Sync listeners for expensive work | Blocks HTTP request | Use `ShouldQueue` |
| No failure handling | Silent failures | Implement `failed()` method |
| No idempotency | Duplicate side effects | Use unique constraints |
| Broadcast without auth | Data leakage | Use private channels |
| Event without listener | Dead code | Remove or add listener |

| Check | What to verify |
| --- | --- |
| Class is `final` | Prevents inheritance |

        foreach ($followers as $follower) {
            Notification::send($follower, new ComponentPublishedNotification(
                component: $component,
                author: $author,
            ));
        }
    }
}

// Notification class:
class ComponentPublishedNotification extends Notification
{
    public function __construct(
        private Component $component,
        private User $author,
    ) {}

    public function via(object $notifiable): array
    {
        return ['database', 'mail'];
    }

    public function toArray(object $notifiable): array
    {
        return [
            'type' => 'component_published',
            'component_id' => $this->component->id,
            'component_name' => $this->component->name,
            'author_name' => $this->author->name,
        ];
    }
}

# 31. Event and Webhook Integration

Events can trigger external webhooks:

```php
class DispatchWebhooksListener implements ShouldQueue
{
    public string $queue = 'webhooks';

    public int $tries = 3;

    public array $backoff = [30, 60, 120];

    public function handle(object $event): void
    {
        $webhooks = Webhook::where('event', get_class($event))
            ->where('active', true)
            ->get();

        foreach ($webhooks as $webhook) {
            $payload = [
                'event' => class_basename($event),
                'data' => $this->serializeEvent($event),
                'timestamp' => now()->toIso8601String(),
            ];

            $signature = hash_hmac('sha256', json_encode($payload), $webhook->secret);

            Http::withHeaders([
                'X-Webhook-Signature' => $signature,
                'X-Webhook-Event' => class_basename($event),
            ])->timeout(10)->post($webhook->url, $payload);
        }
    }

    private function serializeEvent(object $event): array
    {
        return array_filter((array) $event, fn ($v) => $v !== null);
    }
}
```

# 34. Event Performance Optimization

| Optimization | When to Use | Implementation |
| --- | --- | --- |
| Batch listeners | High-volume events | Process in chunks of 100 |
| Lazy loading | Multiple listeners | Load services only when needed |
| Queue prioritization | Mixed urgency | High/low queue separation |
| Event throttling | Burst traffic | Rate limit per event type |
| Deferred events | Non-urgent work | Delay 60s before processing |
