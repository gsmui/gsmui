# 07.49 - Queues

**Project:** GsmUi
**Architecture:** Background Processing & Queue System
**Framework:** Laravel 13 + Livewire 4 + Horizon
**Version:** 1.0.0

---

> See also: `05.11-jobs.md` for the conceptual queue topology, priorities, and worker scaling. `07.14-jobs.md` is the job implementation contract. This document is the *infrastructure implementation contract*: the `config/queue.php` connection, the `config/horizon.php` supervisor mapping, prioritization rules, failed-job handling, and the dead-letter strategy that actually runs the jobs.

# Purpose

Queues move long-running, resource-intensive, or asynchronous work off the HTTP request lifecycle so controllers and Livewire components stay responsive. GsmUi uses Redis as the queue backend and Laravel Horizon for worker supervision, scaling, and failure visibility. `Actions` (see `07.08-action-layer.md`) and `Listeners` (see `07.13-listeners.md`) dispatch jobs (see `07.14-jobs.md`); this document defines how those jobs are connected, prioritized, retried, and triaged when they fail.

Goals:

- **One connection** — every environment uses the `redis` queue connection; no `sync` in production.
- **Independent scaling** — each logical queue maps to a named Horizon supervisor with its own `maxProcesses`.
- **Priority is structural** — the `queue` string on a job determines processing order, not in-Job logic.
- **Failures are observable and retriable** — failed jobs land in `failed_jobs` and, after exhausting the retry budget, escalate to a dead-letter queue for human triage.

# 1. Queue Connection (`config/queue.php`)

The default connection is `redis`. Horizon owns the workers, so `QUEUE_CONNECTION` must be `redis` and `REDIS_QUEUE` names the default logical queue.

```php
// config/queue.php (excerpt)
'default' => env('QUEUE_CONNECTION', 'redis'),

'connections' => [
    'redis' => [
        'driver'     => 'redis',
        'connection' => 'default',
        'queue'      => env('REDIS_QUEUE', 'default'),
        'retry_after' => 120,   // must exceed the longest job timeout
        'block_for'   => 5,
    ],
],

'failed' => [
    'driver'     => env('QUEUE_FAILED_DRIVER', 'database-uuids'),
    'database'   => env('DB_CONNECTION', 'mysql'),
    'table'      => 'failed_jobs',
],
```

Sensitive queued payloads are encrypted at rest. Enable queue encryption so `{encrypted}` wrapping is honored for jobs that carry PII:

```php
// config/queue.php (excerpt)
'redis' => [
    // ...
    'encrypt' => true,
],
```

# 2. Horizon Configuration (`config/horizon.php`)

Each logical queue gets a dedicated supervisor. `queue` lists queues in priority order left-to-right; Horizon drains `high` before `default` within a single supervisor, but separate supervisors let you scale `high` independently of `low`.

```php
// config/horizon.php (excerpt)
'environments' => [
    'production' => [
        'supervisors' => [
            'high' => [
                'connection'  => 'redis',
                'queue'       => 'high',
                'maxProcesses' => 6,
                'balance'      => 'simple',
                'tries'        => 3,
            ],
            'default' => [
                'connection'  => 'redis',
                'queue'       => 'default,mail',
                'maxProcesses' => 4,
                'balance'      => 'simple',
                'tries'        => 3,
            ],
            'media' => [
                'connection'  => 'redis',
                'queue'       => 'media',
                'maxProcesses' => 4,
                'tries'        => 3,
            ],
            'search' => [
                'connection'  => 'redis',
                'queue'       => 'search',
                'maxProcesses' => 2,
                'tries'        => 3,
            ],
            'exports' => [
                'connection'  => 'redis',
                'queue'       => 'exports,imports',
                'maxProcesses' => 2,
                'tries'        => 3,
            ],
            'low' => [
                'connection'  => 'redis',
                'queue'       => 'low,backups',
                'maxProcesses' => 1,
                'tries'        => 1,
            ],
        ],
    ],
],
```

Override `balance` to `auto` only for supervisors whose job runtime is highly variable (e.g. `media`). Keep `retry_after` (in `queue.php`) strictly greater than the largest `$timeout` assigned to any job on that supervisor.

# 3. Job Prioritization

Priority is determined entirely by the `queue` property on the job (see `07.14-jobs.md` §8). The canonical priority ladder is:

| Rank | Queue(s) | Examples |
| --- | --- | --- |
| 1 | `high` | Payments, license generation, webhook reconciliation |
| 2 | `default` | Notifications, indexing, audit fan-out |
| 3 | `mail` | Transactional email |
| 4 | `media` | Image optimization, variant generation |
| 5 | `search` | Meilisearch indexing (see `07.24-search.md`) |
| 6 | `exports`, `imports` | Theme/package export, bulk import |
| 7 | `low`, `backups` | Analytics aggregation, cache refresh, backups |

Dispatch onto the matching queue explicitly so the right supervisor picks it up:

```php
GenerateThemeAssets::dispatch($themeId)->onQueue('exports');
```

Never rely on `default` for user-facing critical work — those jobs must sit on `high`.

# 4. Failed-Job Handling

When a job exhausts `$tries`, Laravel writes a row to `failed_jobs` (driver `database-uuids`). The `failed()` hook on the job runs before that write, so report-and-continue logic belongs there.

```php
// app/Domains/Billing/Jobs/GenerateInvoicePdf.php (excerpt)
public int $tries = 5;
public array $backoff = [5, 15, 60, 120, 300];

public function failed(\Throwable $exception): void
{
    report($exception);

    // Non-fatal side effects only (e.g. notify billing admin).
    // Do NOT re-dispatch here — that risks an infinite loop.
}
```

Admins triage `failed_jobs` via the Horizon dashboard or `php artisan queue:failed`. Retry with `php artisan queue:retry <id>`; forget with `php artisan queue:forget <id>`.

# 5. Dead-Letter Queue (DLQ)

Jobs that are expected to fail permanently, or whose payload should never be auto-retried, escalate to a `dead_letter` queue instead of being retried to exhaustion. A thin forwarding listener pulls from the conventional failure path and re-queues a minimal DLQ record carrying the original `uuid`, `queue`, `exception`, and a human note.

```php
// app/Domains/Shared/Jobs/ForwardToDeadLetter.php
final class ForwardToDeadLetter extends AbstractJob
{
    public string $queue = 'dead_letter';

    public function __construct(
        public readonly string $originalUuid,
        public readonly string $originalQueue,
        public readonly string $exception,
        public readonly string $note,
    ) {}

    public function handle(): void
    {
        // Persist to dead_letter_jobs (or emit to monitoring). The row is
        // immutable and is the hand-off point for on-call triage.
        \DB::table('dead_letter_jobs')->insert([
            'uuid'           => $this->originalUuid,
            'original_queue' => $this->originalQueue,
            'exception'      => $this->exception,
            'note'           => $this->note,
            'created_at'     => now(),
        ]);
    }
}
```

A dedicated `dead_letter` supervisor (low `maxProcesses`, `tries => 1`) ensures DLQ writes never compete with production traffic:

```php
// config/horizon.php (excerpt, production supervisors)
'dead_letter' => [
    'connection'   => 'redis',
    'queue'        => 'dead_letter',
    'maxProcesses' => 1,
    'tries'        => 1,
],
```

# 6. Supervisor Mapping (Process Manager)

Horizon itself is supervised by the OS process manager. For a typical deployment, `supervisorctl` runs `horizon:listen` under a single `gsmui-horizon` program; Horizon then multiplexes its own supervisors internally.

```ini
; /etc/supervisor/conf.d/gsmui-horizon.conf
[program:gsmui-horizon]
process_name=%(program_name)s
command=php /var/www/gsmui/artisan horizon
autostart=true
autorestart=true
user=www-data
redirect_stderr=true
stdout_logfile=/var/www/gsmui/storage/logs/horizon.log
stopwaitsecs=60
```

On ephemeral/container platforms, run `php artisan horizon` as the long-lived container command (one replica runs the Horizon master; additional replicas scale workers). Never run `queue:work` alongside Horizon — pick one supervisor strategy.

# 7. Operational Rules

1. `retry_after` > every job `$timeout` on that connection (prevents duplicate execution from premature release).
2. Jobs pass IDs, not models (see `07.14-jobs.md` §1).
3. Sensitive payloads use `encrypted` connection config; do not hand-encrypt inside the job.
4. DLQ escalation must be idempotent — re-forwarding the same `uuid` updates, not duplicates.
5. Failed-job triage is a human process; do not auto-loop retries beyond `$tries`.

# 8. Job Design Patterns

### 8.1 Payload Design

Jobs carry IDs, not models. This prevents stale data and serialization issues.

```php
namespace App\Domains\Components\Jobs;

use App\Domains\Components\Models\Component;
use Illuminate\Bus\Queueable;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Bus\Dispatchable;
use Illuminate\Queue\InteractsWithQueue;
use Illuminate\Queue\SerializesModels;

final class GenerateComponentAssets implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    /** Queue name — determines which supervisor picks it up. */
    public string $queue = 'exports';

    /** Maximum attempts before failure. */
    public int $tries = 3;

    /** Backoff in seconds between retries. */
    public array $backoff = [10, 30, 60];

    /** Job timeout in seconds. */
    public int $timeout = 120;

    /**
     * @param int $componentId  Pass IDs, not models.
     * @param array $options    Optional configuration overrides.
     */
    public function __construct(
        public readonly int $componentId,
        public readonly array $options = [],
    ) {}

    public function handle(): void
    {
        $component = Component::findOrFail($this->componentId);

        // Process asset generation...
    }

    public function failed(\Throwable $exception): void
    {
        report($exception);

        // Non-fatal side effects only (e.g., notify admin).
        // Do NOT re-dispatch — that risks an infinite loop.
    }
}
```

### 8.2 Job Chaining

Chain multiple jobs for sequential processing:

```php
use Illuminate\Support\Facades\Bus;

Bus::chain([
    new PrepareExportData($exportId),
    new GenerateExportFile($exportId),
    new NotifyExportReady($exportId),
])->onConnection('redis')->onQueue('exports')->dispatch();
```

### 8.3 Job Batching

Batch jobs for parallel processing with a callback on completion:

```php
use Illuminate\Support\Facades\Bus;

$batch = Bus::batch([
    new ProcessComponentVersion($versionId, 1),
    new ProcessComponentVersion($versionId, 2),
    new ProcessComponentVersion($versionId, 3),
])->then(function (Batch $batch) {
    // All jobs completed successfully
    MarkVersionComplete::dispatch($versionId);
})->catch(function (Batch $batch, \Throwable $e) {
    // One job failed
    report($e);
})->finally(function (Batch $batch) {
    // Always runs, regardless of success/failure
    $batch->allModels()->each->delete();
})->onQueue('exports')->dispatch();
```

### 8.4 Job Middleware

Apply middleware to jobs for cross-cutting concerns:

```php
namespace App\Domains\Shared\Jobs\Middleware;

use Closure;

final class EnsureModelExists
{
    public function handle(object $job, Closure $next): void
    {
        $modelClass = $job->modelClass ?? null;
        $modelId = $job->modelId ?? null;

        if ($modelClass && $modelId && !$modelClass::exists($modelId)) {
            // Model was deleted before job ran — skip gracefully
            $job->delete();
            return;
        }

        $next($job);
    }
}

// Usage in job:
public $middleware = [
    new EnsureModelExists,
];
```

### 8.5 Unique Jobs

Prevent duplicate job dispatch:

```php
final class SyncSearchIndex implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public string $uniqueFor = 300; // 5 minutes
    public string $uniqueId;

    public function __construct(
        public readonly string $modelClass,
        public readonly int $modelId,
    ) {
        $this->uniqueId = "{$modelClass}:{$modelId}";
    }

    public function uniqueId(): string
    {
        return $this->uniqueId;
    }

    public function handle(): void
    {
        $model = $this->modelClass::find($this->modelId);
        if ($model) {
            $model->searchable();
        }
    }
}
```

# 9. Job Error Handling

### 9.1 Error Handling Matrix

| Error type | Handler | Retry? | Escalation |
| --- | --- | --- | --- |
| Network timeout | `failed()` → report | Yes (backoff) | After $tries exhausted |
| Model not found | `failed()` → log, skip | No | Log and continue |
| Validation error | `failed()` → report | No | Log and continue |
| External API error | `failed()` → report | Yes (backoff) | After $tries exhausted |
| Memory limit | `failed()` → report | No | Alert ops team |
| Unknown error | `failed()` → report | Yes (backoff) | After $tries exhausted |

### 9.2 Graceful Failure

```php
final class ProcessMediaJob implements ShouldQueue
{
    public function failed(\Throwable $exception): void
    {
        report($exception);

        // Attempt partial cleanup
        try {
            Storage::disk('temp')->delete($this->tempPath);
        } catch (\Throwable $cleanupError) {
            report($cleanupError);
        }

        // Notify stakeholders
        $this->notifyFailure($exception);
    }

    private function notifyFailure(\Throwable $exception): void
    {
        $user = User::find($this->userId);
        if ($user) {
            $user->notify(new MediaProcessingFailed(
                mediaId: $this->mediaId,
                error: $exception->getMessage(),
            ));
        }
    }
}
```

# 13. Dead-Letter Queue Deep Dive

### 13.1 DLQ Record Schema

```php
Schema::create('dead_letter_jobs', function (Blueprint $table) {
    $table->uuid('uuid')->primary();
    $table->string('original_queue', 50);
    $table->string('original_job', 255);
    $table->text('exception');
    $table->text('note')->nullable();
    $table->json('payload')->nullable();
    $table->timestamp('created_at');
    $table->timestamp('resolved_at')->nullable();
    $table->string('resolved_by')->nullable();
    $table->index('original_queue');
    $table->index('created_at');
});
```

### 13.2 DLQ Triage Process

```text
1. Job fails all retries → forwarded to dead_letter queue
2. ForwardToDeadLetter job persists to dead_letter_jobs table
3. Admin receives notification (Slack, email)
4. Admin reviews in Horizon dashboard or admin UI
5. Admin decides: retry, fix, or archive
6. Admin resolves: php artisan queue:dlq:resolve {uuid}
```

### 13.3 DLQ Resolution

```php
namespace App\Console\Commands;

use Illuminate\Console\Command;

final class ResolveDeadLetter extends Command
{
    protected $signature = 'queue:dlq:resolve
        {uuid : The dead letter job UUID}
        {--action=retry : retry|archive}
        {--note= : Resolution note}';

    protected $description = 'Resolve a dead-lettered job';

    public function handle(): int
    {
        $uuid = $this->argument('uuid');
        $action = $this->option('action');
        $note = $this->option('note');

        $dlq = DB::table('dead_letter_jobs')->where('uuid', $uuid)->firstOrFail();

        if ($action === 'retry') {
            // Re-dispatch the original job
            $jobClass = $dlq->original_job;
            $payload = json_decode($dlq->payload, true);

            (new $jobClass(...$payload))->dispatch();

            $this->info("Retried job: {$uuid}");
        }

        // Mark as resolved
        DB::table('dead_letter_jobs')
            ->where('uuid', $uuid)
            ->update([
                'resolved_at' => now(),
                'resolved_by' => auth()->id(),
                'note' => $note,
            ]);

        $this->info("Resolved: {$uuid}");

        return self::SUCCESS;
    }
}
```

# 14. Queue Performance Optimization

### 14.1 Batch Dispatching

Dispatch multiple jobs in a single Redis call:

```php
namespace App\Domains\Shared\Jobs;

final class BatchDispatch
{
    public static function dispatch(array $jobs, string $queue = 'default'): void
    {
        Redis::pipeline(function ($pipe) use ($jobs, $queue) {
            foreach ($jobs as $job) {
                $job->onQueue($queue);
                $pipe->lpush("queues:{$queue}", serialize($job));
            }
        });
    }
}

// Usage:
BatchDispatch::dispatch([
    new UpdateAnalyticsCounter('page_views', 1),
    new UpdateAnalyticsCounter('unique_visitors', 1),
    new SyncSearchIndex(User::class, $userId),
], 'low');
```

### 14.2 Job Chunking

Process large datasets in chunks:

```php
final class ProcessLargeExport implements ShouldQueue
{
    public int $timeout = 600;

    public function handle(): void
    {
        Component::query()
            ->where('status', ComponentStatus::Published)
            ->chunkById(100, function ($components) {
                foreach ($components as $component) {
                    ProcessSingleComponent::dispatch($component->id)
                        ->onQueue('exports');
                }
            });
    }
}
```

# 15. Operational Rules

1. `retry_after` > every job `$timeout` on that connection (prevents duplicate execution from premature release).
2. Jobs pass IDs, not models (see `07.14-jobs.md` §1).
3. Sensitive payloads use `encrypted` connection config; do not hand-encrypt inside the job.
4. DLQ escalation must be idempotent — re-forwarding the same `uuid` updates, not duplicates.
5. Failed-job triage is a human process; do not auto-loop retries beyond `$tries`.
6. Long tasks dispatch to dedicated queues, not `default`.
7. Job backoff follows exponential pattern: [10, 30, 60, 120, 300].
8. Unique job IDs prevent duplicate processing within 5 minutes.
9. Batch operations use Bus::batch for completion callbacks.
10. Job middleware handles cross-cutting concerns (model existence, rate limiting).
11. Horizon dashboard is the primary monitoring tool for queue health.
12. Dead-letter queue is for human triage only — no auto-retry.

# 17. Queue Encryption Deep Dive

### 17.1 How Queue Encryption Works

When `encrypt => true` is set on the Redis connection, Laravel wraps the serialized job payload with AES-256-CBC encryption before pushing to Redis.

```text
Without encryption:
  Redis LPUSH queues:default O:30:"App\Domains\Billing\Jobs\ProcessPayment":2:{...}

With encryption:
  Redis LPUSH queues:default eyJpdiI6Ii4uLiIsInRhZyI6Ii4uLiJ9
```

### 17.2 Encrypted Payload Structure

```json
{
    "iv": "base64-encoded-initialization-vector",
    "value": "base64-encoded-ciphertext",
    "mac": "hmac-sha256-integrity-check",
    "tag": "optional-auth-tag"
}
```

### 17.3 When to Use Encryption

| Scenario | Encrypt? | Reason |
| --- | --- | --- |
| User PII in payload | Yes | GDPR/CCPA compliance |
| Payment data | Yes | PCI-DSS compliance |
| API keys/tokens | Yes | Secret protection |
| Public data (IDs, slugs) | No | No sensitivity |
| Analytics counters | No | No sensitivity |
| Internal IDs only | No | No sensitivity |

# 21. Queue Operational Runbook

### 21.1 High Queue Depth

```text
Symptom: Queue depth > 100 for any queue
Impact: Job processing delay, user-facing slowness
Investigation:
  1. Check Horizon dashboard for worker status
  2. Check worker logs for errors
  3. Check if external APIs are slow
Resolution:
  1. Scale workers: php artisan horizon:terminate (Horizon auto-scales)
  2. Check for stuck jobs: Horizon dashboard → Pause
  3. If external API: increase timeout or add circuit breaker
```

### 21.2 Failed Jobs Spike

```text
Symptom: Failed jobs > 10/hour
Impact: Async work not completing
Investigation:
  1. php artisan queue:failed — review recent failures
  2. Check exception messages for patterns
  3. Check if dependency is down (DB, Redis, external API)
Resolution:
  1. Fix root cause
  2. php artisan queue:retry all — retry transient failures
  3. php artisan queue:forget {id} — discard permanent failures
  4. Forward to DLQ for human triage if uncertain
```

### 21.3 Worker Stuck

```text
Symptom: Horizon shows workers but throughput is 0
Impact: No jobs being processed
Investigation:
  1. Check worker process status: ps aux | grep horizon
  2. Check memory usage: workers might be OOM
  3. Check for deadlock in database
Resolution:
  1. php artisan horizon:terminate — restart workers
  2. If OOM: reduce --max-memory or increase server RAM
  3. If deadlock: kill stuck DB queries
```

### 21.4 Dead-Letter Queue Triage

```text
Symptom: DLQ has > 10 unresolved jobs
Impact: Important work not being retried
Investigation:
  1. Review DLQ records in admin UI
  2. Categorize: transient vs permanent failures
  3. Check if payload data is still valid
Resolution:
  1. Transient: php artisan queue:dlq:resolve {uuid} --action=retry
  2. Permanent: php artisan queue:dlq:resolve {uuid} --action=archive
  3. If data invalid: recreate job with corrected payload
```

# 22. Operational Rules

1. `retry_after` > every job `$timeout` on that connection.
2. Jobs pass IDs, not models.
3. Sensitive payloads use `encrypted` connection config.
4. DLQ escalation must be idempotent.
5. Failed-job triage is a human process.
6. Long tasks dispatch to dedicated queues.
7. Job backoff follows exponential pattern: [10, 30, 60, 120, 300].
8. Unique job IDs prevent duplicate processing within 5 minutes.
9. Batch operations use Bus::batch for completion callbacks.
10. Job middleware handles cross-cutting concerns.
11. Horizon dashboard is the primary monitoring tool.
12. Dead-letter queue is for human triage only.
13. Monitor queue depth — investigate if > 100 per queue.
14. Monitor failure rate — investigate if > 5% per queue.
15. Workers should be restarted daily to prevent memory leaks.

### 26.3 Rate Limiting Middleware

```php
namespace App\Domains\Shared\Jobs\Middleware;

use Closure;
use Illuminate\Support\Facades\RateLimiter;

final class RateLimitedForModel
{
    public function __construct(
        private readonly string $key,
        private readonly int $maxAttempts = 10,
        private readonly int $decayMinutes = 1,
    ) {}

    public function handle(object $job, Closure $next): void
    {
        $key = "rate-limit:{$this->key}:" . ($job->modelId ?? 'global');

        if (RateLimiter::tooManyAttempts($key, $this->maxAttempts)) {
            $job->release(60); // Wait 60 seconds
            return;
        }

        RateLimiter::hit($key, $this->decayMinutes * 60);

        $next($job);
    }
}
```

# 33. Queue Performance Optimization

### 33.1 Batch Dispatch

Dispatch multiple jobs in a single Redis call:

```php
namespace App\Domains\Shared\Jobs;

final class BatchDispatch
{
    public static function dispatch(array $jobs, string $queue = 'default'): void
    {
        Redis::pipeline(function ($pipe) use ($jobs, $queue) {
            foreach ($jobs as $job) {
                $job->onQueue($queue);
                $pipe->lpush("queues:{$queue}", serialize($job));
            }
        });
    }
}

// Usage:
BatchDispatch::dispatch([
    new UpdateAnalyticsCounter('page_views', 1),
    new UpdateAnalyticsCounter('unique_visitors', 1),
    new SyncSearchIndex(User::class, $userId),
], 'low');
```

### 33.2 Job Chunking

Process large datasets in chunks to control memory:

```php
final class ProcessLargeExport implements ShouldQueue
{
    public int $timeout = 600;

    public function handle(): void
    {
        Component::query()
            ->where('status', ComponentStatus::Published)
            ->chunkById(100, function ($components) {
                foreach ($components as $component) {
                    ProcessSingleComponent::dispatch($component->id)
                        ->onQueue('exports');
                }
            });
    }
}
```

# 34. Queue Architecture Patterns

### 34.1 Priority Queue Pattern

Implement priority through separate queues:

```text
Priority 1: high       → Payments, licenses, webhooks
Priority 2: default    → General async work
Priority 3: mail       → Transactional email
Priority 4: media      → Image processing
Priority 5: search     → Search indexing
Priority 6: exports    → Data exports
Priority 7: low        → Analytics, cache refresh
Priority 8: dead_letter → Failed job triage
```

### 34.2 Fan-Out Pattern

Dispatch multiple jobs from a single event:

```php
final class OrderPaidListener
{
    public function handle(OrderPaid $event): void
    {
        // Fan out to multiple queues
        SendPaymentConfirmation::dispatch($event->orderId)->onQueue('mail');
        GenerateInvoicePdf::dispatch($event->orderId)->onQueue('high');
        UpdateAnalyticsCounter::dispatch('orders_paid', 1)->onQueue('low');
        SyncSearchIndex::dispatch(Order::class, $event->orderId)->onQueue('search');
    }
}
```

### 34.3 Chain Pattern

Execute jobs sequentially:

```php
Bus::chain([
    new PrepareExportData($exportId),
    new GenerateExportFile($exportId),
    new NotifyExportReady($exportId),
])->onConnection('redis')->onQueue('exports')->dispatch();
```

### 34.4 Batch Pattern

Execute jobs in parallel with completion callback:

```php
$batch = Bus::batch([
    new ProcessComponentVersion($versionId, 1),
    new ProcessComponentVersion($versionId, 2),
    new ProcessComponentVersion($versionId, 3),
])->then(function (Batch $batch) {
    MarkVersionComplete::dispatch($versionId);
})->catch(function (Batch $batch, \Throwable $e) {
    report($e);
})->finally(function (Batch $batch) {
    $batch->allModels()->each->delete();
})->onQueue('exports')->dispatch();
```

### 34.5 Circuit Breaker Pattern

Stop retrying when external services are down:

```php
final class ExternalApiJob implements ShouldQueue
{
    public function handle(): void
    {
        $key = 'circuit:external-api';

        if (Cache::get("{$key}:open", false)) {
            // Circuit is open — skip this job
            $this->release(300); // Try again in 5 minutes
            return;
        }

        try {
            $this->callExternalApi();
        } catch (\ConnectionException $e) {
            $failures = Cache::increment("{$key}:failures") ?? 1;
            Cache::put("{$key}:failures", $failures, 300);

            if ($failures >= 5) {
                Cache::put("{$key}:open", true, 60); // Open circuit for 60s
                Log::warning('Circuit breaker opened for external API');
            }

            throw $e;
        }
    }
}
```

# 35. Queue Failure Analysis

### 35.1 Common Failure Patterns

| Pattern | Cause | Resolution |
| --- | --- | --- |
| Timeout failures | Job takes too long | Increase timeout or optimize |
| Connection failures | DB/Redis unavailable | Check dependency health |
| Memory failures | Job uses too much RAM | Chunk processing, reduce memory |
| Validation failures | Invalid payload data | Fix dispatch code |
| Logic failures | Business logic error | Fix job handle() method |
| Rate limit failures | External API throttled | Add backoff, reduce frequency |

### 35.2 Failure Diagnosis

```php
// Analyze failed jobs
$failures = DB::table('failed_jobs')
    ->selectRaw('queue, exception, COUNT(*) as count')
    ->groupBy('queue', 'exception')
    ->orderByDesc('count')
    ->get();

// Common exception patterns
$commonErrors = DB::table('failed_jobs')
    ->selectRaw('
        CASE
            WHEN exception LIKE "%timeout%" THEN "timeout"
            WHEN exception LIKE "%Connection%" THEN "connection"
            WHEN exception LIKE "%Memory%" THEN "memory"
            WHEN exception LIKE "%422%" THEN "validation"
            ELSE "other"
        END as error_type,
        COUNT(*) as count
    ')
    ->groupBy('error_type')
    ->orderByDesc('count')
    ->get();
```

# 36. Queue Conventions Summary

1. Jobs carry IDs, not models.
2. Sensitive payloads use `encrypted` connection.
3. DLQ escalation is idempotent.
4. Failed-job triage is human-driven.
5. Long tasks dispatch to dedicated queues.
6. Backoff follows exponential pattern.
7. Unique IDs prevent duplicate processing.
8. Batch operations use Bus::batch.
9. Middleware handles cross-cutting concerns.
10. Horizon dashboard is primary monitoring.
11. DLQ is for human triage only.
12. Monitor queue depth (alert > 100).
13. Monitor failure rate (alert > 5%).
14. Restart workers daily.
15. Use priority queues for ordering.
