# Purpose

This document defines the mandatory coding standards for GsmUi so that contributions stay consistent, type-safe, and statically analyzable. It covers PSR-12 formatting with `strict_types`, naming conventions, docblocks, typed properties, the static-analysis stack (Laravel Pint for formatting, PHPStan/Larastan for types), pre-commit hooks, and a reviewer checklist. It is the enforcement layer for every contract in this section (error handling, logging, testing, performance, security).

> See also: 07.53-error-handling.md (exception typing), 07.54-logging.md (log call hygiene), 07.55-testing.md (test style), 07.56-performance.md (query discipline), 07.57-security.md (secret/SSRF guards verified by analyzers).

# 1. PSR-12 + strict_types

Every PHP file opens with `declare(strict_types=1);` immediately after the `<?php` tag, before namespace.

```php
<?php

declare(strict_types=1);

namespace App\Domains\Components\Actions;

use App\Models\Component;

final class PublishComponentAction
{
    public function execute(Component $component): void
    {
        // ...
    }
}
```

Rules:

- `final` on classes unless explicitly designed for extension (then `abstract` or documented).
- One class/interface/enum per file.
- 4-space indent, no tabs, Unix line endings, UTF-8, trailing newline.
- Opening braces for classes/methods on the next line; control structures on the same line.
- `else`/`catch`/`finally` on the same line as the closing brace.

# 2. Naming Conventions

| Element | Convention | Example |
| --- | --- | --- |
| Class | PascalCase, noun | `ComponentRepository` |
| Interface | PascalCase, `*Interface` or adjective | `SearchClientInterface` |
| Trait | PascalCase | `RefreshDatabaseOnce` |
| Method | camelCase, verb phrase | `paginateWithAuthor()` |
| Property | camelCase | `$perPage` |
| Constant | SCREAMING_SNAKE | `DEFAULT_LIMIT` |
| Enum case | PascalCase | `case Published` |
| Variable | camelCase, descriptive | `$componentCount` |
| Config key | snake_case | `services.stripe.secret` |
| DB column | snake_case | `published_at` |
| Route param | kebab-case | `{component-slug}` |
| Event/Listener | PastTense + suffix | `ComponentPublished` / `SendNotification` |

- Acronyms are treated as words: `MeiliSearchClient`, not `MeiliSearchClient`/`MEILISearch`.
- Boolean methods/props use `is*`, `has*`, `can*`, `should*`.
- Actions are `*Action` (single verb), Services are `*Service`, Jobs are `*Job`, Listeners are noun/verb phrases.

# 3. Typed Properties & Return Types

All properties, method params, and return types are explicit. Use `mixed` only where genuinely unknown; prefer templates/`@template`.

```php
final class ComponentQueryService
{
    /** @var array<int, string> */
    private array $allowedSorts = ['downloads', 'created_at'];

    public function __construct(
        private ComponentRepository $repository,
    ) {}

    /** @return \Illuminate\Contracts\Pagination\LengthAwarePaginator */
    public function paginate(int $perPage = 15): LengthAwarePaginator
    {
        return $this->repository->paginateWithAuthor($perPage);
    }
}
```

- Never use nullable return to signal failure — throw (`07.53-error-handling.md`) or return a `Result` object.
- Constructor promotion is preferred for dependencies.
- `never` return type for methods that always throw/exit.

# 4. Docblocks

PHPDoc required on public APIs; use typed arrays with `@param`/`@return`. Internal private methods may omit when the signature is self-evident.

```php
/**
 * Index a batch of components into Meilisearch.
 *
 * @param  iterable<Component>  $components
 * @throws \App\Exceptions\Infrastructure\SearchEngineException
 */
public function indexComponents(iterable $components): void
{
    // ...
}
```

- `@throws` documents every exception type the caller must handle.
- Do not duplicate type info already in the signature; add *why*, not *what*.
- No docblocks that merely restate the method name.

# 5. Formatting with Laravel Pint

`pint.json` at repo root pins the ruleset:

```json
{
    "preset": "laravel",
    "rules": {
        "declare_strict_types": true,
        "ordered_imports": { "sort_algorithm": "alpha" },
        "no_unused_imports": true,
        "array_syntax": { "syntax": "short" },
        "trailing_comma_in_multiline": true,
        "single_quote": true,
        "strict_comparison": true
    }
}
```

Run:

```bash
vendor/bin/pint --test      # CI: fail on diff
vendor/bin/pint            # local: auto-fix
```

Pint is the single source of truth for style; do not hand-tune formatting.

# 6. Static Analysis with Larastan (PHPStan)

`phpstan.neon` targets level 9 for app code, with paths excluded where third-party limitations exist.

```neon
includes:
    - ./vendor/larastan/larastan/extension.neon

parameters:
    level: 9
    paths:
        - app
    excludePaths:
        - app/Providers/*
    ignoreErrors:
        - '#Unsafe usage of new static#'
    checkMissingIterableValueType: true
    checkGenericClassInNonGenericObjectType: true
```

Run:

```bash
vendor/bin/phpstan analyse --memory-limit=1G
```

- Level 9 is the floor; raise on new code.
- `missingType.iterableValue` must be resolved, not ignored.
- Suppress only with a scoped `// @phpstan-ignore-next-line` and a one-line reason.

# 7. Pre-Commit & CI Hooks

Local pre-commit (`.husky`/`lefthook` or git hooks) runs fast checks; CI runs the full gate.

```yaml
# .github/workflows/quality.yml
quality:
  script:
    - vendor/bin/pint --test
    - vendor/bin/phpstan analyse --memory-limit=1G
    - composer test -- --coverage --min=85
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

Lefthook config (local):

```yaml
pre-commit:
  parallel: true
  commands:
    pint:
      glob: "*.php"
      run: vendor/bin/pint --test {staged_files}
    phpstan:
      glob: "*.php"
      run: vendor/bin/phpstan analyse --no-progress
```

Gate fails the merge on any error. Lint must pass before review.

# 8. Reviewer Checklist

Before approving a PR, verify:

- [ ] `declare(strict_types=1);` present in every new PHP file.
- [ ] PSR-12 passes (`pint --test`), no manual formatting.
- [ ] PHPStan level 9 clean on touched files.
- [ ] All properties/methods typed; no untyped `iterable`/`array`.
- [ ] Naming matches the conventions table.
- [ ] Public methods have docblocks with `@throws` where relevant.
- [ ] No `env()` outside `config/`.
- [ ] No committed secrets; `.env.example` only.
- [ ] No `sleep()`/raw SQL concatenation; bound params only.
- [ ] Tests added; coverage gate passes for the module (`07.55-testing.md`).
- [ ] Exceptions thrown (not returned) for failures (`07.53-error-handling.md`).
- [ ] Logs use context arrays; PII redacted (`07.54-logging.md`).
- [ ] Security-sensitive code adds CSP/rate-limit/SSRF guards (`07.57-security.md`).

---

# 9. Architectural Discipline

- Services/actions are thin and single-responsibility (`07.06`, `07.08`).
- Repositories own query logic; controllers never write SQL (`07.07`).
- DTOs validate at the boundary (`07.09`); value objects are immutable (`07.10`).
- No business logic in Blade/Livewire views beyond presentation (`07.19`, `07.20`).
- Cross-cutting concerns (logging, security) live in middleware/services, not scattered inline.

---

# 10. Anti-Patterns (Banned)

- `extract()` / variable variables.
- `@` error suppression operator.
- `eval()`, `create_function()`.
- Public properties on entities used as DTOs.
- `dd()` / `dump()` left in committed code (use tests/`Log::debug`).
- Trailing `?>` closing tag.
- `env()` calls outside `config/`.

# 12. Import Ordering

Imports follow a strict ordering enforced by Pint:

```php
<?php

declare(strict_types=1);

namespace App\Domains\Components\Actions;

// 1. PHP built-in classes
use ArrayAccess;
use Countable;

// 2. Third-party packages
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Str;

// 3. Application classes (alphabetical)
use App\Domains\Components\Exceptions\ComponentAlreadyExistsException;
use App\Domains\Components\Repositories\ComponentRepository;
use App\Domains\Components\Services\ComponentService;
use App\DTOs\ComponentData;
use App\Models\Component;

final class CreateComponentAction
{
    // ...
}
```

Rules:
- Imports are grouped: PHP built-ins → third-party → application classes.
- Each group is separated by a blank line.
- Within each group, imports are sorted alphabetically by namespace.
- No unused imports — enforced by Pint's `no_unused_imports` rule.
- Single imports only — no `use function` or `use const` unless absolutely necessary.

# 13. Enum Conventions

Enums follow strict conventions for readability and consistency:

```php
<?php

declare(strict_types=1);

namespace App\Enums;

enum ComponentStatus: string
{
    case Draft = 'draft';
    case Review = 'review';
    case Published = 'published';
    case Archived = 'archived';

    public function label(): string
    {
        return match ($this) {
            self::Draft => 'Draft',
            self::Review => 'In Review',
            self::Published => 'Published',
            self::Archived => 'Archived',
        };
    }

    public function color(): string
    {
        return match ($this) {
            self::Draft => 'gray',
            self::Review => 'yellow',
            self::Published => 'green',
            self::Archived => 'red',
        };
    }

    public function isEditable(): bool
    {
        return $this === self::Draft || $this === self::Review;
    }
}
```

Rules:
- Enum cases use PascalCase.
- Enum values are snake_case strings (stored in the database).
- Every enum has a `label()` method for human-readable display.
- Enums may have `color()` methods for UI rendering.
- Boolean helper methods use `is*` / `has*` / `can*` naming.
- Enums are stored as VARCHAR in MySQL (see `06.01-design-principles.md` §6).

# 14. DTO Conventions

DTOs are immutable, typed value carriers. They follow these conventions:

```php
<?php

declare(strict_types=1);

namespace App\DTOs;

use App\Enums\PurchaseChannel;
use App\ValueObjects\IdempotencyKey;
use App\ValueObjects\Money;
use Illuminate\Support\Str;

final readonly class PurchaseTemplateData
{
    public function __construct(
        public string $templateSlug,
        public Money $amount,
        public string $paymentMethodId,
        public IdempotencyKey $idempotencyKey,
        public PurchaseChannel $channel,
        public bool $acceptedTerms = false,
    ) {}

    public static function from(array $data): self
    {
        return new self(
            templateSlug: $data['template_slug'],
            amount: new Money(
                cents: $data['amount_cents'],
                currency: $data['currency'] ?? 'USD',
            ),
            paymentMethodId: $data['payment_method_id'],
            idempotencyKey: new IdempotencyKey($data['idempotency_key']),
            channel: PurchaseChannel::from($data['channel'] ?? 'web'),
            acceptedTerms: $data['accepted_terms'] ?? false,
        );
    }

    public function toArray(): array
    {
        return [
            'template_slug' => $this->templateSlug,
            'amount_cents' => $this->amount->cents(),
            'currency' => $this->amount->currency(),
            'payment_method_id' => $this->paymentMethodId,
            'idempotency_key' => $this->idempotencyKey->value(),
            'channel' => $this->channel->value,
            'accepted_terms' => $this->acceptedTerms,
        ];
    }
}
```

Rules:
- DTOs use `final readonly class` (PHP 8.2+).
- Constructor promotion for all properties.
- `static from(array $data)` factory method for construction from request data.
- `toArray()` method for serialization.
- No mutable state — once created, a DTO never changes.
- Property names use camelCase; array keys use snake_case.

# 15. Value Object Conventions

Value objects are immutable types that encapsulate domain logic:

```php
<?php

declare(strict_types=1);

namespace App\ValueObjects;

use InvalidArgumentException;

final readonly class Money
{
    public function __construct(
        public int $cents,
        public string $currency = 'USD',
    ) {
        if ($cents < 0) {
            throw new InvalidArgumentException('Money amount cannot be negative.');
        }

        if (strlen($currency) !== 3) {
            throw new InvalidArgumentException('Currency must be a 3-letter ISO code.');
        }
    }

    public static function fromCents(int $cents, string $currency = 'USD'): self
    {
        return new self($cents, $currency);
    }

    public static function fromDecimal(float $amount, string $currency = 'USD'): self
    {
        return new self((int) round($amount * 100), $currency);
    }

    public function add(self $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new InvalidArgumentException('Cannot add different currencies.');
        }

        return new self($this->cents + $other->cents, $this->currency);
    }

    public function subtract(self $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new InvalidArgumentException('Cannot subtract different currencies.');
        }

        return new self($this->cents - $other->cents, $this->currency);
    }

    public function format(): string
    {
        return number_format($this->cents / 100, 2) . ' ' . $this->currency;
    }

    public function equals(self $other): bool
    {
        return $this->cents === $other->cents
            && $this->currency === $other->currency;
    }
}
```

Rules:
- Value objects use `final readonly class`.
- Validation happens in the constructor.
- No setter methods — immutability is absolute.
- Factory methods use `static from*()` naming.
- Equality is defined by value, not identity.
- Value objects are serializable for cache and queue storage.

# 16. Service Class Conventions

Services contain business logic. They follow these conventions:

```php
<?php

declare(strict_types=1);

namespace App\Domains\Components\Services;

use App\Domains\Components\Repositories\ComponentRepository;
use App\Domains\Search\Services\SearchIndexService;
use App\DTOs\ComponentData;
use App\Models\Component;
use Illuminate\Support\Facades\Log;

final class ComponentService
{
    public function __construct(
        private readonly ComponentRepository $repository,
        private readonly SearchIndexService $searchIndex,
    ) {}

    public function create(ComponentData $data): Component
    {
        Log::info('service.component.create', [
            'slug' => $data->slug,
            'category' => $data->category,
        ]);

        $component = $this->repository->create($data->toArray());

        $this->searchIndex->indexComponent($component);

        return $component;
    }

    public function publish(Component $component): Component
    {
        if ($component->status->isPublished()) {
            throw new ComponentAlreadyPublishedException($component->slug);
        }

        $published = $this->repository->updateStatus($component, 'published');

        $this->searchIndex->indexComponent($published);

        Log::info('service.component.published', [
            'component_id' => $component->id,
            'slug' => $component->slug,
        ]);

        return $published;
    }

    public function findBySlug(string $slug): ?Component
    {
        return $this->repository->findBySlug($slug);
    }
}
```

Rules:
- Services use `final class` (no inheritance).
- Dependencies injected via constructor.
- Services are thin — they orchestrate, not implement persistence.
- Services use repositories for database access.
- Services use actions for write operations.
- Logging happens at the service level with structured context.
- Services never throw HTTP exceptions — they throw domain exceptions.

# 17. Repository Conventions

Repositories own all database access. They follow these conventions:

```php
<?php

declare(strict_types=1);

namespace App\Domains\Components\Repositories;

use App\Models\Component;
use Illuminate\Contracts\Pagination\LengthAwarePaginator;
use Illuminate\Database\Eloquent\Builder;
use Illuminate\Support\Facades\DB;

final class ComponentRepository
{
    public function __construct(
        private readonly Component $model,
    ) {}

    public function create(array $data): Component
    {
        return $this->model->create($data);
    }

    public function findBySlug(string $slug): ?Component
    {
        return $this->model->where('slug', $slug)->first();
    }

    public function paginateWithAuthor(int $perPage = 15): LengthAwarePaginator
    {
        return $this->model
            ->with('author')
            ->orderByDesc('created_at')
            ->paginate($perPage);
    }

    public function updateStatus(Component $component, string $status): Component
    {
        $component->update(['status' => $status]);

        return $component->fresh();
    }

    public function search(string $query, int $limit = 20): \Illuminate\Support\Collection
    {
        return $this->model
            ->where('title', 'LIKE', "%{$query}%")
            ->orWhere('description', 'LIKE', "%{$query}%")
            ->limit($limit)
            ->get();
    }
}
```

Rules:
- Repositories use `final class`.
- The model is injected via constructor (not resolved inside methods).
- Repositories own all query logic — no raw SQL in controllers or services.
- Repositories return Eloquent models, not arrays.
- Pagination uses `LengthAwarePaginator`.
- Search methods return `Collection`.
- Repositories never throw exceptions — they return `null` for not-found cases.

# 18. Action Conventions

Actions are the single entry point for write operations. They follow these conventions:

```php
<?php

declare(strict_types=1);

namespace App\Domains\Components\Actions;

use App\Domains\Components\Services\ComponentService;
use App\DTOs\ComponentData;
use App\Models\Component;
use Illuminate\Support\Facades\DB;

final class CreateComponentAction
{
    public function __construct(
        private readonly ComponentService $service,
    ) {}

    public function run(ComponentData $data): Component
    {
        return DB::transaction(function () use ($data) {
            $component = $this->service->create($data);

            return $component;
        });
    }
}
```

Rules:
- Actions use `final class`.
- The `run()` method is the single entry point.
- Actions open transactions for write operations.
- Actions orchestrate services — they do not contain business logic.
- Actions throw domain exceptions on failure.
- Actions return the result of the operation (model, collection, etc.).

# 19. Event Conventions

Events are dispatched after commits for async work:

```php
<?php

declare(strict_types=1);

namespace App\Events;

use App\Models\Order;
use Illuminate\Broadcasting\InteractsWithSockets;
use Illuminate\Foundation\Events\Dispatchable;
use Illuminate\Queue\SerializesModels;

final class OrderPlaced
{
    use Dispatchable, InteractsWithSockets, SerializesModels;

    public function __construct(
        public readonly Order $order,
    ) {}
}
```

Rules:
- Events use `final class`.
- Event properties are `public readonly`.
- Events use `Dispatchable`, `InteractsWithSockets`, and `SerializesModels` traits.
- Events are dispatched via `dispatchAfterCommit()` in actions.
- Events contain only the data needed by listeners — no extra context.
- Event class names use past tense (`OrderPlaced`, not `PlaceOrder`).

# 20. Listener Conventions

Listeners handle events and dispatch jobs:

```php
<?php

declare(strict_types=1);

namespace App\Listeners;

use App\Events\OrderPlaced;
use App\Jobs\SendPurchaseReceiptJob;
use App\Jobs\ProvisionLicenseJob;
use Illuminate\Contracts\Queue\ShouldQueue;

final class SendPurchaseReceiptListener implements ShouldQueue
{
    public function __construct(
        public int $retryAfter = 60,
    ) {}

    public function handle(OrderPlaced $event): void
    {
        SendPurchaseReceiptJob::dispatch(
            orderId: $event->order->id,
        );
    }
}
```

Rules:
- Listeners use `final class`.
- Listeners implement `ShouldQueue` for async work.
- Listeners dispatch jobs — they do not contain heavy logic.
- Listeners are thin — one event, one action.
- Listeners do not catch exceptions — let the queue handle retries.

# 21. Job Conventions

Jobs encapsulate long-running or async work:

```php
<?php

declare(strict_types=1);

namespace App\Jobs;

use App\Domains\Billing\Services\BillingService;
use App\Models\Order;
use Illuminate\Bus\Queueable;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Bus\Dispatchable;
use Illuminate\Queue\InteractsWithQueue;
use Illuminate\Queue\SerializesModels;
use Illuminate\Support\Facades\Log;

final class SendPurchaseReceiptJob implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 3;
    public int $backoff = 60;
    public int $timeout = 120;

    public function __construct(
        public readonly int $orderId,
        private readonly string $correlationId = 'unknown',
    ) {}

    public function handle(BillingService $billing): void
    {
        Log::shareContext([
            'correlation_id' => $this->correlationId,
            'job_id' => $this->job->getJobId(),
        ]);

        $order = Order::findOrFail($this->orderId);

        $billing->sendReceipt($order);

        Log::info('job.send_receipt.completed', [
            'order_id' => $this->orderId,
        ]);
    }

    public function failed(\Throwable $exception): void
    {
        Log::channel('queue')->error('job.send_receipt.failed', [
            'order_id' => $this->orderId,
            'exception' => get_class($exception) . ': ' . $exception->getMessage(),
            'attempt' => $this->attempts(),
        ]);
    }
}
```

Rules:
- Jobs use `final class`.
- Jobs use `Dispatchable`, `InteractsWithQueue`, `Queueable`, and `SerializesModels` traits.
- Jobs define `$tries`, `$backoff`, and `$timeout`.
- Jobs log lifecycle events on the `queue` channel.
- Jobs implement `failed()` for error logging.
- Jobs receive correlation IDs from dispatchers.

# 22. Policy Conventions

Policies centralize authorization logic:

```php
<?php

declare(strict_types=1);

namespace App\Policies;

use App\Models\Component;
use App\Models\User;

final class ComponentPolicy
{
    public function viewAny(User $user): bool
    {
        return true; // Components are public
    }

    public function view(User $user, Component $component): bool
    {
        return true; // Components are public
    }

    public function create(User $user): bool
    {
        return $user->hasRole('developer');
    }

    public function update(User $user, Component $component): bool
    {
        return $user->id === $component->author_id
            || $user->hasRole('admin');
    }

    public function delete(User $user, Component $component): bool
    {
        return $user->id === $component->author_id
            || $user->hasRole('admin');
    }

    public function publish(User $user, Component $component): bool
    {
        return $user->id === $component->author_id
            && $component->status->isEditable();
    }
}
```

Rules:
- Policies use `final class`.
- Methods are named after the action (`view`, `create`, `update`, `delete`, `publish`).
- Policies return boolean — never throw exceptions.
- Policies check ownership and roles.
- Policies are registered in `AuthServiceProvider`.

# 23. Form Request Conventions

Form Requests encapsulate validation and authorization:

```php
<?php

declare(strict_types=1);

namespace App\Http\Requests;

use Illuminate\Foundation\Http\FormRequest;

final class PurchaseTemplateRequest extends FormRequest
{
    public function authorize(): bool
    {
        return $this->user()->hasVerifiedEmail();
    }

    public function rules(): array
    {
        return [
            'template_slug' => ['required', 'string', 'exists:templates,slug'],
            'payment_method_id' => ['required', 'string'],
            'idempotency_key' => ['required', 'uuid', 'unique:orders,idempotency_key'],
            'accepted_terms' => ['required', 'accepted'],
        ];
    }

    public function messages(): array
    {
        return [
            'template_slug.exists' => 'The selected template does not exist.',
            'idempotency_key.unique' => 'This purchase has already been processed.',
            'accepted_terms.accepted' => 'You must accept the terms of service.',
        ];
    }
}
```

Rules:
- Form Requests use `final class`.
- `authorize()` returns boolean — never throws.
- `rules()` returns an array of validation rules.
- `messages()` provides human-readable error messages.
- Form Requests are used in controllers, not in services or actions.

# 24. Controller Conventions

Controllers are thin — they delegate to actions and services:

```php
<?php

declare(strict_types=1);

namespace App\Http\Controllers;

use App\Domains\Components\Actions\CreateComponentAction;
use App\DTOs\ComponentData;
use App\Http\Requests\CreateComponentRequest;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;
use Illuminate\View\View;

final class ComponentController extends Controller
{
    public function index(Request $request): View
    {
        $components = $this->service->paginateWithAuthor(
            perPage: $request->integer('per_page', 15),
        );

        return view('components.index', compact('components'));
    }

    public function store(
        CreateComponentRequest $request,
        CreateComponentAction $action,
    ): RedirectResponse {
        $data = ComponentData::from($request->validated());

        $component = $action->run($data);

        return redirect()
            ->route('components.show', $component->slug)
            ->with('success', 'Component created successfully.');
    }
}
```

Rules:
- Controllers use `final class`.
- Controllers are thin — they delegate to actions and services.
- Controllers never write SQL — they use repositories via services.
- Controllers return views or redirects, never data directly.
- Controllers use Form Requests for validation.
- Controllers use Actions for write operations.

# 32. Refactoring Guidelines

## 32.1 When to Refactor

Refactor when:

1. Code duplication exceeds 3 instances.
2. A method exceeds 20 lines.
3. A class exceeds 200 lines.
4. Cyclomatic complexity exceeds 10.
5. A method has more than 4 parameters.
6. Code is harder to understand than necessary.

## 32.2 Refactoring Process

```
1. Write tests for current behavior
2. Get tests green
3. Refactor in small steps
4. Run tests after each step
5. Get tests green again
6. Remove dead code
7. Update documentation
8. Submit PR
```

## 32.3 Refactoring Rules

- Never refactor and add features in the same PR.
- Never refactor without test coverage.
- Never refactor in a production incident — fix first, refactor later.
- Always refactor toward the established patterns (§1–§30).

## 32.4 Common Refactoring Patterns

| Pattern | When to Use | Example |
| --- | --- | --- |
| Extract Method | Long method | Split 30-line method into 3 methods |
| Extract Class | God class | Split into focused services |
| Replace Temp with Query | Complex expression | Extract to a method |
| Introduce Parameter Object | Many parameters | Create a DTO |
| Replace Conditional with Polymorphism | Complex switch | Use enums with methods |
| Extract Interface | Tight coupling | Define contract |

# 33. Security Coding Standards

## 33.1 Input Validation

All user input is validated at the boundary (Form Requests):

```php
public function rules(): array
{
    return [
        'email' => ['required', 'email', 'max:255'],
        'name' => ['required', 'string', 'max:255', 'regex:/^[a-zA-Z\s]+$/'],
        'url' => ['nullable', 'url', 'max:2048'],
    ];
}
```

## 33.2 SQL Injection Prevention

Never use string concatenation in SQL:

```php
// BAD — SQL injection risk
DB::select("SELECT * FROM users WHERE email = '{$email}'");

// GOOD — parameterized query
DB::select('SELECT * FROM users WHERE email = ?', [$email]);

// GOOD — Eloquent
User::where('email', $email)->first();
```

## 33.3 XSS Prevention

Always escape output in Blade:

```blade
{{-- GOOD — Blade auto-escapes --}}
<p>{{ $user->name }}</p>

{{-- BAD — Raw output (XSS risk) --}}
<p>{!! $user->name !!}</p>

{{-- GOOD — Only for trusted HTML --}}
{!! nl2br(e($user->bio)) !!}
```

## 33.4 CSRF Protection

All state-changing routes require CSRF tokens:

```blade
<form method="POST" action="{{ route('components.store') }}">
    @csrf
    {{-- ... --}}
</form>
```

## 33.5 Authentication Checks

Every protected route uses middleware:

```php
Route::middleware('auth')->group(function () {
    Route::post('/components', [ComponentController::class, 'store']);
    Route::put('/components/{component}', [ComponentController::class, 'update']);
    Route::delete('/components/{component}', [ComponentController::class, 'destroy']);
});
```

## 33.6 Authorization Checks

Every write operation uses policies:

```php
public function update(UpdateComponentRequest $request, Component $component): RedirectResponse
{
    $this->authorize('update', $component);

    // ... update logic
}
```

## 33.7 Rate Limiting

API endpoints use rate limiting:

```php
Route::middleware('throttle:api')->group(function () {
    Route::post('/login', [AuthController::class, 'login']);
    Route::post('/register', [AuthController::class, 'register']);
});
```

## 33.8 Secret Management

Never commit secrets:

```php
// BAD — hardcoded secret
$stripe = new \Stripe\StripeClient('sk_live_abc123');

// GOOD — environment variable
$stripe = new \Stripe\StripeClient(config('services.stripe.secret'));
```

# 34. Performance Coding Standards

## 34.1 N+1 Query Prevention

Always eager-load relationships:

```php
// BAD — N+1 queries
$components = Component::all();
foreach ($components as $component) {
    echo $component->author->name; // Each author is a separate query
}

// GOOD — eager loading
$components = Component::with('author')->get();
foreach ($components as $component) {
    echo $component->author->name; // Single query for all authors
}
```

## 34.2 Query Optimization

Use indexed columns for filtering:

```php
// BAD — full table scan
Component::where('title', 'LIKE', '%button%')->get();

// GOOD — use indexed column
Component::where('slug', 'button')->first();

// GOOD — use search engine for full-text
Component::search('button')->get();
```

## 34.3 Caching

Cache expensive queries:

```php
$components = Cache::remember('components.published', 3600, function () {
    return Component::where('status', 'published')->get();
});
```

## 34.4 Memory Management

Process large datasets in chunks:

```php
// BAD — loads all records into memory
$users = User::all();
foreach ($users as $user) {
    // process
}

// GOOD — processes in chunks
User::chunk(100, function ($users) {
    foreach ($users as $user) {
        // process
    }
});
```

## 34.5 Lazy Collections

Use lazy collections for large datasets:

```php
// BAD — loads all records into memory
$users = User::all()->filter(fn ($user) => $user->isActive());

// GOOD — processes lazily
$users = User::cursor()->filter(fn ($user) => $user->isActive());
```

## 42.1 Metrics Collection

Every service method should emit metrics:

```php
namespace App\Metrics;

final class ComponentMetrics
{
    public static function recordCreation(float $durationMs): void
    {
        \Metrics::histogram('component.creation.duration_ms', $durationMs);
        \Metrics::increment('component.creation.count');
    }

    public static function recordSearch(float $durationMs, int $hits): void
    {
        \Metrics::histogram('component.search.duration_ms', $durationMs);
        \Metrics::histogram('component.search.hits', $hits);
    }
}
```

## 42.2 Distributed Tracing

Every request should be traced:

```php
// In middleware
$span = $tracer->startSpan('request.handle');
$span->setAttribute('http.method', $request->method());
$span->setAttribute('http.url', $request->url());

// In service
$childSpan = $tracer->startChildSpan('component.create');
$childSpan->setAttribute('component.slug', $data->slug);
$childSpan->end();

$span->end();
```

## 42.3 Health Checks

Every service should have a health check:

```php
namespace App\Health;

final class ComponentServiceHealth
{
    public function check(): bool
    {
        try {
            DB::select('SELECT 1');
            return true;
        } catch (\Exception $e) {
            return false;
        }
    }
}
```

# 43. Operational Rules (Complete Final Extended)

1. Every PHP file opens with `declare(strict_types=1);`.
2. PSR-12 formatting is enforced by Pint — no manual formatting.
3. PHPStan level 9 is the floor — raise on new code.
4. All properties, method params, and return types are explicit.
5. Naming follows the conventions table (§2).
6. Public methods have docblocks with `@throws` where relevant.
7. No `env()` outside `config/`.
8. No committed secrets — `.env.example` only.
9. No `sleep()` or raw SQL concatenation — bound params only.
10. Tests are added for every change; coverage gate passes.
11. Exceptions are thrown (not returned) for failures.
12. Logs use context arrays; PII is redacted.
13. Security-sensitive code adds CSP/rate-limit/SSRF guards.
14. Enums have `label()` and `color()` methods.
15. DTOs have `from()` and `toArray()` methods.
16. Value objects are immutable — no setters.
17. Services are thin — orchestrate, not implement.
18. Repositories own all query logic.
19. Actions are the single entry point for writes.
20. Events use past tense naming.
21. Listeners dispatch jobs, not contain heavy logic.
22. Jobs log lifecycle events on the queue channel.
23. Policies return boolean, never throw.
24. Form Requests use `authorize()` and `rules()`.
25. Controllers are thin — delegate to actions/services.
26. Blade components use `@props` for declaration.
27. Tests use Pest/PHPUnit with descriptive names.
28. Imports are ordered: built-ins → third-party → app classes.
29. No unused imports — enforced by Pint.
30. Single class/interface/enum per file.
31. Code review follows structured workflow and SLA.
32. Refactoring follows established patterns and process.
33. Security standards prevent SQL injection, XSS, CSRF.
34. Performance standards prevent N+1 queries and memory issues.
35. Documentation standards cover code, README, and API docs.
36. Git conventions cover branches, commits, and PRs.
37. IDE configuration integrates PHPStan, Pint, and EditorConfig.
38. Anti-patterns are banned (§28).
39. Tooling versions are pinned (§11).
40. Performance benchmarks are defined and tested.
41. Accessibility standards meet WCAG 2.1 AA.
42. Internationalization uses translation functions for all strings.
43. Monitoring and observability standards ensure traceability.
44. The coding standards contract is the single source of truth.
