# 10.01 — Permissions Overview

**Project:** GsmUi
**Domain:** Authorization & RBAC
**Version:** 1.0.0

---

## Purpose

This document defines the **complete Authorization & Role-Based Access Control (RBAC)** architecture for GsmUi. Authorization is not a feature — it is the gatekeeper of every interaction on the platform. Every request, every API call, every marketplace transaction, and every admin action flows through this system.

GsmUi's authorization system is built on Role-Based Access Control (RBAC) using Spatie Laravel-Permission. It governs what authenticated users, creators, admins, and API consumers can do across all platform domains: Marketplace, Themes, Components, Templates, Documentation, Blog, Playground, Billing, AI, MCP, Admin, and User Dashboard.

## Scope

GsmUi's authorization system must serve:

* Public visitors (read-only access to public content)
* Registered users (dashboard, purchases, profile management)
* Pro Users (premium features, priority support)
* Creators (theme/component publishing, revenue tracking)
* Moderators (content review, community moderation)
* Support staff (order management, refund processing)
* Editors (documentation, blog, CMS content)
* Admins (full platform administration)
* Super Admins (system-level configuration)
* API consumers (Sanctum token-based access)
* MCP clients (tool execution authorization)
* Enterprise users (team-scoped permissions — future)

## Authorization Flow

```text
Authenticated User
    ↓
Resolve Roles (Spatie Permission)
    ↓
Resolve Permissions (role_permissions + direct)
    ↓
Policy Evaluation (Laravel Policy class)
    ↓
Business Service Rules
    ↓
Repository / Database
```

Every authorization check follows this chain. Controllers never contain complex authorization logic — they delegate to policies, which delegate to services where business rules live.

## Permission Architecture

```text
User
  ↓
Roles (model_has_roles)
  ↓
Permissions (role_permissions + model_has_permissions)
  ↓
Policies (per-model authorization classes)
  ↓
Services (business rule enforcement)
  ↓
Repositories (data access layer)
  ↓
Business Rules (domain constraints)
```

This layered architecture ensures that authorization logic is:
- **Composable:** Roles compose permissions, policies compose role checks
- **Testable:** Each layer can be tested in isolation
- **Cacheable:** Permission sets are cached per user
- **Auditable:** Every permission change is logged

## Design Principles

1. **Controllers never contain complex authorization logic.** Authorization lives in policies and services. Controllers call `$this->authorize()` or rely on policy auto-discovery.

2. **Permissions use `resource.action` naming.** Examples: `themes.publish`, `marketplace.purchase`, `admin.access`. Avoid vague names like `manage_everything`, `edit`, or `access`.

3. **Policies enforce ownership, role checks, and business constraints.** A policy method combines permission checks with ownership verification and domain rules.

4. **Cache resolved permission sets per model.** Spatie Permission handles this via the cache store. Clear cache on role/permission assignment changes.

5. **All authorization checks are testable in isolation.** Each policy, gate, and role check has corresponding unit and feature tests.

6. **Least privilege by default.** New roles start with zero permissions. Permissions are explicitly granted, never implicitly inherited from unrelated roles.

7. **Ownership overrides role where appropriate.** A creator managing their own theme does not need `themes.admin` — they need `themes.update` plus ownership.

## Default Roles Hierarchy

```text
Guest           (unauthenticated visitor)
    ↓
User            (registered, email verified)
    ↓
Pro User        (active paid subscription)
    ↓
Creator         (published themes/components/templates)
    ↓
Moderator       (content moderation, review management)
    ↓
Support         (customer support, order management)
    ↓
Editor          (documentation, blog, CMS management)
    ↓
Admin           (full platform administration)
    ↓
Super Admin     (system-level administration, admin management)
```

Roles inherit permissions downward. A higher role includes all permissions of lower roles. This means an Admin automatically has all permissions of Editor, Support, Moderator, Creator, Pro User, and User.

## Authorization Patterns

### Pattern 1: Role-Based Gate

The simplest pattern. A gate checks whether the authenticated user holds a specific role. This pattern is used for top-level section access (admin panel, system health, debug tools) where the operation does not tie to a specific model instance.

```php
Gate::define('view-admin-panel', function (User $user) {
    return $user->hasRole(['admin', 'super_admin']);
});
```

Use this when:
- The check is for a section of the application, not a specific resource.
- The logic is simple role membership.
- No ownership or resource state is involved.

### Pattern 2: Permission-Based Gate

A gate checks whether the user holds a specific permission string. This is more granular than role-based gates because direct permission assignments can override role defaults.

```php
Gate::define('publish-content', function (User $user) {
    return $user->hasPermissionTo('themes.publish')
        || $user->hasRole(['admin', 'super_admin']);
});
```

Use this when:
- You need to support direct permission overrides.
- The same action might be allowed by different roles in different contexts.
- You want to decouple the gate from specific role names.

### Pattern 3: Policy with Ownership

The most common pattern for resource operations. The policy method checks both a permission and ownership of the resource.

```php
public function update(User $user, Theme $theme): bool
{
    return $user->id === $theme->user_id
        || $user->hasPermissionTo('themes.update');
}
```

Use this when:
- The operation targets a specific model instance.
- Owners should be able to manage their own resources without elevated roles.
- Admins should be able to manage any resource.

### Pattern 4: Policy with Status

Combines permission checks with resource state transitions. Used for publishing workflows where the current status determines whether the action is valid.

```php
public function publish(User $user, Theme $theme): bool
{
    if ($theme->status !== 'pending_review') {
        return false;
    }

    return $user->hasRole(['admin', 'moderator', 'super_admin']);
}
```

Use this when:
- Resources have a lifecycle (draft → pending → published → archived).
- The action is only valid from certain states.
- Different roles can perform different transitions.

### Pattern 5: Quota-Based Gate

Combines permission checks with usage quotas. Used for features with tiered limits (playground executions, AI generation, API calls).

```php
Gate::define('access-ai', function (User $user) {
    if (! $user->hasVerifiedEmail()) {
        return false;
    }

    $quotaService = app(AiQuotaService::class);
    return ! $quotaService->isExhausted($user);
});
```

Use this when:
- Access depends on remaining quota, not just role.
- Different subscription tiers have different limits.
- The check requires a database or cache query.

### Pattern 6: Environment-Aware Gate

Combines permission checks with application environment. Used for debug tools, development features, and staging-only functionality.

```php
Gate::define('access-debug', function (User $user) {
    return $user->hasRole('super_admin')
        && app()->environment(['local', 'staging', 'development']);
});
```

Use this when:
- The feature should only be available in non-production environments.
- Even authorized users should not access certain tools in production.
- The check combines role, environment, and optionally feature flags.

## Permission Resolution Flow (Detailed)

When `$user->can('themes.update', $theme)` is called, the following resolution chain executes:

```text
1. Gate::before callbacks
   ├── Super admin bypass → return true
   └── Null → continue

2. Gate::after callbacks (if any)
   └── Typically empty

3. Policy resolution (because second argument is a Theme model)
   ├── ThemePolicy@update invoked
   ├── Ownership check: $user->id === $theme->user_id
   ├── Permission check: $user->hasPermissionTo('themes.update')
   ├── Role check: $user->hasRole(['admin', 'super_admin'])
   └── Combine results (typically OR logic)

4. Cache lookup (Spatie Permission)
   ├── In-memory collection check
   ├── Redis cache check
   └── Database query fallback

5. Return boolean to caller
```

### Resolution Priority

The `Gate::before` callback is evaluated first. If it returns `true`, the gate is authorized immediately without checking the policy. If it returns `null`, the system proceeds to the gate or policy definition.

```php
// This runs BEFORE any gate or policy
Gate::before(function (User $user, string $ability) {
    if ($user->hasRole('super_admin')) {
        return true; // Short-circuit: super admin can do everything
    }
    return null; // Defer to gate/policy
});
```

### Policy Method Signatures

Each policy method receives the authenticated user as the first argument and the model instance (where applicable) as the second:

```php
// List-level check (no model)
public function viewAny(User $user): bool;

// Single resource check
public function view(User $user, Theme $theme): bool;

// Create check (no model)
public function create(User $user): bool;

// Update check
public function update(User $user, Theme $theme): bool;

// Delete check
public function delete(User $user, Theme $theme): bool;

// Custom action check
public function publish(User $user, Theme $theme): bool;
```

### Combining Policy and Gate

In controllers and Livewire components, you can combine policy checks with gate checks:

```php
// In a controller
public function update(Request $request, Theme $theme)
{
    // Policy check (ownership + permission)
    $this->authorize('update', $theme);

    // Gate check (additional business rule)
    if (! Gate::allows('publish-content')) {
        abort(403, 'Creator profile not approved.');
    }

    // Proceed with update
    $theme->update($request->validated());
}
```

## Role Hierarchy Mechanics

### How Inheritance Works

Spatie Permission stores role hierarchy via the `role_has_roles` pivot table. When checking if a user has a permission, Spatie resolves all roles the user holds, then checks the permissions of each role and its ancestors.

```text
User holds: [creator]
Creator has permissions: [themes.create, themes.update, themes.publish]
Creator parent: [pro_user]
Pro User has permissions: [playground.save, ai.view]
Pro User parent: [user]
User has permissions: [marketplace.view, orders.view]

Effective permissions: [themes.create, themes.update, themes.publish,
                        playground.save, ai.view,
                        marketplace.view, orders.view]
```

### Permission Union

When a user holds multiple roles, the effective permissions are the union of all permissions from all roles:

```text
User holds: [creator, moderator]
Creator permissions: [themes.create, themes.update]
Moderator permissions: [themes.feature, components.feature]

Effective permissions: [themes.create, themes.update,
                        themes.feature, components.feature]
```

### Direct Permission Override

Direct permission assignments (via `model_has_permissions`) take precedence over role-based permissions. This allows granting or revoking specific permissions without changing roles:

```php
// Grant a specific permission directly
$user->givePermissionTo('system.maintenance');

// Revoke a specific permission directly
$user->revokePermissionTo('themes.create');
```

### Hierarchy Enforcement Rules

1. A role cannot be its own parent (no circular references).
2. A role cannot be both a parent and child of the same role.
3. Hierarchy depth is limited to 10 levels (prevents abuse).
4. Changing hierarchy triggers cache invalidation for all affected users.
5. Hierarchy changes are audit-logged with before/after state.

```php
// Preventing circular references
public function addChildRole(Role $child): void
{
    if ($this->id === $child->id) {
        throw new InvalidArgumentException('A role cannot be its own child.');
    }

    if ($child->descendants()->pluck('id')->contains($this->id)) {
        throw new InvalidArgumentException('Cannot create circular hierarchy.');
    }

    $this->children()->attach($child);
}
```

## Cache Strategy (Detailed)

### Cache Key Structure

Spatie Permission uses the following cache key structure:

```text
spatie_permission.cache.{guard_name}
```

The cache stores:
- All roles for the guard
- All permissions for the guard
- Role-permission mappings
- Role-hierarchy mappings
- User-role assignments (per user)

### Cache Layers

```text
Request
    ↓
In-Memory Collection (Eloquent models already loaded)
    ↓ (if not loaded)
Redis Cache (TTL: configurable)
    ↓ (if cache miss)
Database Query
    ↓
Store in Redis
    ↓
Store in Memory for rest of request
```

### Cache Invalidation Triggers

| Event | Cache Action |
|---|---|
| Role assigned to user | Clear user's cached permissions |
| Role revoked from user | Clear user's cached permissions |
| Permission added to role | Clear all users with that role |
| Permission removed from role | Clear all users with that role |
| Role hierarchy changed | Clear all users with affected roles |
| Direct permission granted | Clear that user's cached permissions |
| Direct permission revoked | Clear that user's cached permissions |
| New role created | Clear role cache |
| Role deleted | Clear role cache and affected users |
| New permission created | Clear permission cache |

### Cache Configuration

```php
// config/permission.php
'cache' => [
    'store' => env('CACHE_DRIVER', 'redis'),
    'prefix' => 'gsmui_permission',
    'ttl' => 3600, // 1 hour
],
```

### Cache Warming

On application boot, the permission cache is warmed by loading all roles and permissions into memory:

```php
// In PermissionServiceProvider
public function boot(): void
{
    // Warm cache on first request
    if (Cache::get('permission_cache_warmed') === null) {
        Permission::all();
        Role::all();
        Cache::put('permission_cache_warmed', true, now()->addHour());
    }
}
```

## Security Considerations (Detailed)

### Principle of Least Privilege

Every role starts with zero permissions. Permissions are explicitly granted, never inherited from unrelated roles. When in doubt, the default is deny.

### Defense in Depth

Authorization is checked at multiple layers:

1. **Route middleware** — prevents unauthorized access to controller actions.
2. **Policy checks** — prevent unauthorized resource operations.
3. **Gate checks** — prevent unauthorized ad-hoc operations.
4. **Service layer** — enforces business rules and constraints.
5. **Database constraints** — prevent data corruption from race conditions.

### Audit Trail

Every permission change, role assignment, and authorization failure is logged:

```php
activity()
    ->causedBy($user)
    ->performedOn($target)
    ->withProperties([
        'action' => 'role_assigned',
        'role' => 'admin',
        'ip' => request()->ip(),
        'user_agent' => request()->userAgent(),
    ])
    ->log('admin.role_assigned');
```

### Rate Limiting

Authorization endpoints are rate-limited to prevent brute-force permission enumeration:

```php
Route::middleware('throttle:10,1')->group(function () {
    Route::post('/admin/roles/assign', [RoleController::class, 'assign']);
});
```

### API Token Scoping

API tokens are scoped to specific permissions and cannot exceed the user's own permissions:

```php
// Token creation validates requested permissions against user's permissions
$validPermissions = $user->getAllPermissions()->pluck('name')->toArray();
$requestedPermissions = array_intersect($requested, $validPermissions);
$token = $user->createToken('api-token', $requestedPermissions);
```

### CSRF Protection

All state-changing operations require CSRF tokens. Authorization checks are independent of CSRF — a valid CSRF token does not grant authorization.

### Session Security

- Sessions are invalidated on role changes.
- Concurrent session limits are enforced.
- Session tokens are rotated on privilege escalation.

## Migration Guide

### From Simple Role Checks

If your existing code uses `$user->isAdmin()` or similar boolean checks, migrate to the RBAC system:

```php
// Before
if ($user->isAdmin()) {
    // admin logic
}

// After
if ($user->hasRole('admin')) {
    // admin logic
}
```

### From Inline Authorization

If your controllers contain authorization logic, extract it to policies:

```php
// Before (in controller)
public function update(Request $request, Theme $theme)
{
    if ($request->user()->id !== $theme->user_id && ! $request->user()->isAdmin()) {
        abort(403);
    }
    // ...
}

// After (using policy)
public function update(Request $request, Theme $theme)
{
    $this->authorize('update', $theme);
    // ...
}
```

### From Hardcoded Permission Strings

If your code uses hardcoded permission strings, extract them to constants:

```php
// Before
$user->hasPermissionTo('themes.create');

// After
class Permissions
{
    const THEMES_CREATE = 'themes.create';
    const THEMES_UPDATE = 'themes.update';
    // ...
}

$user->hasPermissionTo(Permissions:: THEMES_CREATE);
```

## Appendix: Common Authorization Mistakes

### Mistake 1: Checking Roles in Controllers

```php
// BAD: Controller contains authorization logic
if (! auth()->user()->hasRole('admin')) {
    abort(403);
}

// GOOD: Use policy or gate
$this->authorize('view-admin-panel');
```

### Mistake 2: Hardcoding Permission Strings

```php
// BAD: String typo causes silent failure
$user->hasPermissionTo('theme.craete'); // typo!

// GOOD: Use constants
$user->hasPermissionTo(Permissions::THEMES_CREATE);
```

### Mistake 3: Forgetting Cache Invalidation

```php
// BAD: Cache not cleared after role change
$user->assignRole('admin');
// Cached permissions still reflect old state

// GOOD: Clear cache after role change
$user->assignRole('admin');
Permission::forgetCache();
```

### Mistake 4: Client-Side Authorization

```blade
{{-- BAD: Client-side check can be bypassed --}}
@if ($user->role === 'admin')
    <a href="/admin">Admin</a>
@endif

{{-- GOOD: Server-side check via gate --}}
@can('view-admin-panel')
    <a href="/admin">Admin</a>
@endcan
```

### Mistake 5: Not Testing Authorization

```php
// BAD: No authorization test
public function test_update_theme(): void
{
    $theme = Theme::factory()->create();
    $this->put("/themes/{$theme->id}", ['name' => 'Updated']);
    // No assertion about authorization
}

// GOOD: Test authorization separately
public function test_non_owner_cannot_update_theme(): void
{
    $user = User::factory()->create();
    $theme = Theme::factory()->create();

    $this->actingAs($user)
        ->put("/themes/{$theme->id}", ['name' => 'Updated'])
        ->assertForbidden();
}
```

## Frequently Asked Questions

### Q: Can a user have multiple roles?

**A:** Yes. A user can hold multiple roles simultaneously. The effective permissions are the union of all permissions from all assigned roles.

### Q: What happens when a user's subscription expires?

**A:** The `pro_user` role is automatically removed via a billing webhook. The user retains the `user` role and its associated permissions.

### Q: Can an admin assign the `super_admin` role?

**A:** No. Only existing Super Admins can assign the `super_admin` role. This prevents privilege escalation.

### Q: How are permissions cached?

**A:** Spatie Permission caches permission data in the application's cache store (Redis). Cache is cleared whenever permissions or role assignments change.

### Q: Can permissions be assigned directly to users?

**A:** Yes, but it's not recommended. Direct permission assignments bypass the role system and can make permission management complex.

### Q: How does the role hierarchy work?

**A:** Each role can have parent roles. A child role inherits all permissions from its parents. For example, `admin` inherits from `editor`, which inherits from `support`, etc.

### Q: What happens if I delete a role?

**A:** Deleting a role revokes it from all users who hold it. The role's permissions are also deleted. Use caution when deleting roles.

### Q: How do I test authorization logic?

**A:** Use Laravel's built-in testing helpers: `$this->assertTrue($user->can('permission'))` for unit tests, and `$this->actingAs($user)->get('/route')->assertForbidden()` for feature tests.

### Q: Can I customize the permission naming convention?

**A:** The `resource.action` convention is recommended but not enforced. You can use any naming scheme, but consistency is important.

### Q: How do I handle team-based permissions?

**A:** Enable teams in `config/permission.php` and use the `SetTeamContext` middleware. Roles and permissions can then be scoped to specific teams.

## Troubleshooting

### Permission not working

1. Check that the permission exists in the database
2. Check that the role has the permission assigned
3. Check that the user has the role assigned
4. Clear the permission cache: `Permission::forgetCache()`
5. Check the guard name matches

### Role hierarchy not working

1. Check the `role_has_roles` pivot table
2. Verify parent-child relationships
3. Clear the cache
4. Check for circular references

### Cache not clearing

1. Verify cache driver is configured correctly
2. Check that `Permission::forgetCache()` is called after changes
3. Check Redis connection
4. Verify cache prefix matches config

### Policy not being called

1. Check that the policy is registered in `AuthServiceProvider`
2. Check that the model type hint matches
3. Check that the method name matches the ability
4. Verify the policy class extends `Illuminate\Auth\Access\HandlesAuthorization`

### Gate not working

1. Check that the gate is registered in `AuthServiceProvider::boot()`
2. Check that the gate name matches the ability
3. Check for `Gate::before()` callbacks that might override
4. Verify the user is authenticated

## Detailed Permission Flow Diagrams

### Request Authorization Flow

When a user makes a request to a protected route, the following flow executes:

```text
HTTP Request
    ↓
Route Matching
    ↓
Middleware Stack
    ↓
auth middleware → Verify authenticated user
    ↓
verified middleware → Verify email confirmed
    ↓
role middleware → Check required role
    ↓
permission middleware → Check required permission
    ↓
can middleware → Check gate/policy
    ↓
Controller Action
    ↓
Policy Check (if model involved)
    ↓
Service Layer Business Rules
    ↓
Repository / Database
    ↓
Response
```

### Role Resolution Flow

When checking if a user has a role, the system resolves through this chain:

```text
User::hasRole('admin')
    ↓
Load user's roles from cache or database
    ↓
Check direct role assignment (model_has_roles)
    ↓
Check role hierarchy (role_has_roles)
    ↓
Resolve parent roles recursively
    ↓
Return true/false
```

### Permission Resolution Flow

When checking if a user has a permission:

```text
User::hasPermissionTo('themes.create')
    ↓
Check direct permissions (model_has_permissions)
    ↓ (if not found)
Check role-based permissions (model_has_roles → role_permissions)
    ↓ (if not found)
Check parent role permissions (role_has_roles → role_permissions)
    ↓ (if not found)
Default: return false (deny)
```

## Common RBAC Patterns

### Pattern 1: Simple Role Check

The simplest pattern. Check if the user holds a specific role.

```php
// Check single role
if ($user->hasRole('admin')) {
    // User is admin
}

// Check multiple roles
if ($user->hasAnyRole(['admin', 'moderator'])) {
    // User is admin or moderator
}
```

### Pattern 2: Permission Check

Check if the user has a specific permission.

```php
// Check single permission
if ($user->hasPermissionTo('themes.create')) {
    // User can create themes
}

// Check multiple permissions
if ($user->hasAllPermissions(['themes.create', 'themes.update'])) {
    // User can both create and update themes
}

if ($user->hasAnyPermission(['themes.create', 'components.create'])) {
    // User can create themes or components
}
```

### Pattern 3: Ownership Check

Check if the user owns the resource.

```php
// Check ownership
if ($theme->user_id === $user->id) {
    // User owns the theme
}
```

### Pattern 4: Combined Check

Combine role, permission, and ownership checks.

```php
// Combined check
if ($user->hasRole('admin') || ($user->hasPermissionTo('themes.update') && $theme->user_id === $user->id)) {
    // User can update theme (admin or owner with permission)
}
```

## RBAC Security Considerations

### Principle of Least Privilege

Every role starts with zero permissions. Permissions are explicitly granted, never inherited from unrelated roles. When in doubt, the default is deny.

### Defense in Depth

Authorization is checked at multiple layers:

1. **Route middleware** — prevents unauthorized access to controller actions.
2. **Policy checks** — prevent unauthorized resource operations.
3. **Gate checks** — prevent unauthorized ad-hoc operations.
4. **Service layer** — enforces business rules and constraints.
5. **Database constraints** — prevent data corruption from race conditions.

### Audit Trail

Every permission change, role assignment, and authorization failure is logged.

### Rate Limiting

Authorization endpoints are rate-limited to prevent brute-force permission enumeration.

### API Token Scoping

API tokens are scoped to specific permissions and cannot exceed the user's own permissions.

### CSRF Protection

All state-changing operations require CSRF tokens. Authorization checks are independent of CSRF.

### Session Security

- Sessions are invalidated on role changes.
- Concurrent session limits are enforced.
- Session tokens are rotated on privilege escalation.

## RBAC Performance Optimization

### Cache Strategy

- Permission data is cached per user in Redis.
- Cache is cleared on role/permission changes.
- Cache is warmed on application boot.

### Query Optimization

- Use eager loading for role/permission relationships.
- Add database indexes for common queries.
- Use query caching for repeated permission checks.

### Permission Check Optimization

- Check direct permissions first (fastest).
- Check role-based permissions second.
- Check parent role permissions last (slowest).

### Permission Change Monitoring

Monitor all permission changes for security:

```php
Event::listen(RoleAssigned::class, function ($event) {
    if (in_array($event->role->name, ['admin', 'super_admin'])) {
        Log::warning("Elevated role assigned", [
            'user_id' => $event->user->id,
            'role' => $event->role->name,
            'assigned_by' => auth()->id(),
        ]);
    }
});
```

### Permission Health Checks

Run regular health checks:

```php
Schedule::call(function () {
    $healthCheck = new PermissionHealthCheck();
    $issues = $healthCheck->check();
    
    if (! empty($issues)) {
        Notification::send(
            User::role('super_admin')->get(),
            new PermissionHealthAlert($issues)
        );
    }
})->daily();
```

## RBAC Migration Guide

### From Boolean Flags

Migrate from boolean flags (`is_admin`, `is_moderator`) to roles:

```php
// Create roles
Role::create(['name' => 'admin', 'level' => 7]);
Role::create(['name' => 'moderator', 'level' => 4]);
Role::create(['name' => 'creator', 'level' => 3]);

// Assign roles based on flags
User::where('is_admin', true)->each(fn($user) => $user->assignRole('admin'));
User::where('is_moderator', true)->each(fn($user) => $user->assignRole('moderator'));
User::where('is_creator', true)->each(fn($user) => $user->assignRole('creator'));

// Drop boolean columns
Schema::table('users', function (Blueprint $table) {
    $table->dropColumn(['is_admin', 'is_moderator', 'is_creator']);
});
```

### From String-Based Roles

Migrate from a `role` string column:

```php
$roleMap = [
    'admin' => 'admin',
    'moderator' => 'moderator',
    'creator' => 'creator',
    'user' => 'user',
];

User::all()->each(function ($user) use ($roleMap) {
    $roleName = $roleMap[$user->role] ?? 'user';
    $user->assignRole($roleName);
});

Schema::table('users', function (Blueprint $table) {
    $table->dropColumn('role');
});
```

## RBAC Best Practices Summary

### Do's

- Use descriptive permission names: `themes.publish` not `tp`
- Group related permissions: all theme actions under `themes.*`
- Document each permission's purpose
- Test permissions in isolation
- Audit permission changes
- Use the principle of least privilege
- Review permissions quarterly
- Use permission constants for type safety
- Cache permission lookups
- Log permission checks in debug mode

### Don'ts

- Don't create overly broad permissions: `manage_everything`
- Don't assign permissions directly to users (use roles)
- Don't skip permission tests
- Don't forget to clear cache after changes
- Don't hardcode permission strings in templates
- Don't ignore permission conflicts
- Don't create permissions without documentation
- Don't forget to update seeder when adding permissions
- Don't create circular role hierarchies
- Don't forget to test role inheritance
