# 13.02 Component Philosophy — GsmUi Design Decisions

## Core Philosophy

**Internal consistency > external best practices.** If `gsmui:button` does something one way, `gsmui:select` does it the same way. Consistency across the system beats "better" patterns that create fragmentation.

## Decision Framework

When facing a design decision, apply these filters in order:

| Priority | Filter | Action |
|----------|--------|--------|
| 1 | **Consistency** | Does this match existing GsmUi components? → Follow precedent |
| 2 | **Simplicity** | Does this add meaningful complexity? → Cut it; ship simpler |
| 3 | **Browser-native** | Can the browser do this natively? → Use native, remove polyfill |
| 4 | **Accessibility** | Does this meet WCAG 2.1 AA? → If no, redesign until yes |
| 5 | **Themeability** | Does this work with design tokens? → If no, use tokens |
| 6 | **External precedent** | What do Radix, Base UI, ARIA APG do? → Reference, don't copy |

## Key Principles

### Punt Aggressively
If a feature adds meaningful complexity without proportional value to most users, **cut it**. Ship the simpler version. Features can come in v2.

> "I'd keep it simple and ship" — default response to feature requests.

### Inline = Separate Component
If a feature changes the component's fundamental shape (e.g., inline mode = no trigger, no popover), it's a **separate component**, not a prop.

### Most Useful Variant = Default
Don't make users opt-in to the better experience. The default should be the most useful variant.

### Push Back on Feature Creep
Say "I'd keep it simple and ship" and wait for confirmation. Don't build every casual mention.

### Accept Pragmatic Imperfections
- Color precision loss in round-trips? Accept and move on.
- Invalid input? Silent revert, no shake animations.
- Don't over-engineer edge cases.

### Research External, Decide Internal
Research Base UI, React Aria, Radix, ShadCN, Mantine, Tailwind UI. Use their decisions as **reference points**, not templates. **Check GsmUi's own patterns first.**

### Outside-In Development
Start from the docs page and user experience. Browse with Playwright. Then work inward to code review and architecture. Not the reverse.

### Dead Code is a Liability
Actively remove unused methods, lookup tables, parsers. If the browser can do it natively, delete the polyfill.

## Anti-Patterns to Avoid

| Anti-Pattern | Why | Alternative |
|--------------|-----|-------------|
| Boolean props for variants (`:input="true"`) | Explodes combinatorially | Single `type` prop: `type="input" \| "button"` |
| Inventing new ARIA patterns | Breaks accessibility | Follow ARIA APG / React Aria patterns |
| Custom color parsing | Browser does it natively | `<canvas>` context for color parsing |
| Alpine for complex state | Hard to test, debug | Vanilla JS classes (Controllable, etc.) |
| Ternary class blocks for states | Unmaintainable | Layer `data-invalid:` / `data-disabled:` classes |
| CDN dependencies | Breaks CSP, offline | Bundle everything in `dist/` |

## Composability Rules

1. **Sub-elements call methods on the state root** — don't duplicate state
2. **Use `detangle()`** — prevents sync loops between Controllable and internal subscriptions
3. **Copy sibling structure before styling** — if a trigger is conceptually an input, copy the input pattern first
4. **Compose, don't inherit** — Color picker uses `ui-slider` for hue, doesn't reimplement slider

## Naming Conventions

| Pattern | Example | Rationale |
|---------|---------|-----------|
| Short, natural prop names | `dropper` not `eye-dropper` | Discoverable |
| `-able` suffix for boolean opt-in | `clearable`, `copyable`, `searchable` | Consistent |
| `type` for trigger variants | `type="input" \| "button"` | Not boolean explosion |
| `gsmui:` prefix for all components | `<x-gsm-button>` | Namespace isolation |
| `--gsmui-*` CSS variables | `--gsmui-color-primary` | No collision with app |

## Styling Conventions

### Cursors
- `cursor-pointer` **only** on elements that perform navigation
- Buttons and clickable widgets keep default cursor

### Focus Rings
- **Native focusable elements** (`<button>`, `<input>`): **no focus classes** — use browser native outline
- **Custom elements** (`tabindex="0"`, wrapper around `<input type="range">`): use slider thumb pattern:
  ```css
  has-focus-visible:outline-2 has-focus-visible:outline-[-webkit-focus-ring-color]
  ```
- **Never** use `focus:outline-none focus:ring-2 focus:ring-(--color-accent)`

### Dialog/Popover
Copy verbatim from date-picker:
```css
max-sm:max-h-full! rounded-xl shadow-xl sm:shadow-2xs
max-sm:fixed! max-sm:inset-0! sm:backdrop:bg-transparent
bg-white dark:bg-zinc-700 sm:border border-zinc-200 dark:border-white/10 p-3
```

### Trigger Buttons (default/sm/xs)
Copy from `date-picker/button.blade.php`:
- Height: `h-10` / `h-8` / `h-6`
- Text: `text-base sm:text-sm` / `text-sm` / `text-xs`
- Radius: `rounded-lg` / `rounded-md` / `rounded-md`

### Inputs
Copy from `gsmui/stubs/resources/views/gsmui/input/index.blade.php` outline variant:
- `bg-white dark:bg-white/10`
- `border-zinc-200 border-b-zinc-300/80 dark:border-white/10`
- `shadow-xs`
- `rounded-lg`
- **Native focus = no class**

### Disabled on Custom Elements
CSS `:disabled` only works on native form elements. Custom elements need:
```css
[&[disabled]]:shadow-none!
```

### Invalid Styling
Layer `data-invalid:` classes on top of base styles. **Never ternary-swap entire class block.** Match `gsmui:input` pattern.

### Numeric Display
`tabular-nums` when value changes rapidly (prevents width jitter).

### Whole Trigger = One Input
Clicking whitespace in trigger container focuses the text input. `cursor: text` across container, except over action buttons.

### Pixel-Level Parity
Measure with Playwright. Don't guess. If exact Tailwind value doesn't exist, use magic numbers (`pe-[9px]`). But strive for round values.

### Critical States Need Explicit Checks
Empty states, white-on-white, disabled, focus-visible — inspect on real docs page before considering done.

### Text Sizes Must Match
Across trigger variants and sibling components.

### Lock Scroll When Popover Open
Copy date-picker pattern.

## JavaScript Conventions

### Use Utility Functions
`setAttribute`/`removeAttribute` from `utils.js` — not native DOM methods (MutationObserver implications).

### Move Logic from Alpine to JS When
- Needs disabled-state awareness
- Needs component coordination
- Alpine should be RARE in GsmUi

### Fire Both `input` AND `change`
- Keyboard changes: fire both (matches native `<input type="range">`)
- `change` fires on mouse release (pointer commit), **not** on popover close

### MutationObserver Watches `value` Attribute
In addition to config attributes.

### Lean on the Browser
- `<canvas>` context parses any CSS color — no lookup tables/parsers
- Native form validation, native date parsing, native color parsing

### 2D Area Keyboard Navigation
- Arrow keys: move in grid
- Home/End: horizontal edges
- PageUp/PageDown: vertical edges

## Blade/PHP Conventions

### Aria-Labels Use `__()`
Set from Blade where `__()` runs. JS uses Blade-set value as primary, hardcoded English only as safety-net fallback.

### Real `<x-gsmui:button>` for Action Buttons
Clear, copy, dropper inside input triggers. Only use `<x-gsmui:button as="div">` when nested inside `<button>` (HTML constraint).

### ARIA Follows Closest Pattern
- Input trigger = `role="combobox"` on `<input>`
- Button trigger = native `<button>` with `aria-haspopup="dialog"`
- Don't invent — check ARIA APG and React Aria

## Documentation Conventions

### Labels Only When Contextually Meaningful
- ✅ `label="hex"` for format demo
- ❌ `label="Clearable"` (echoes section title)
- ❌ `label="Brand"` (random filler)
- When in doubt: **no label**

### Previews Dressed Up, Code Blocks Minimal
- Previews: `value="#0ea5e9"` for visual context
- Code blocks: `wire:model="color"` — clean copy-paste
- They don't need to match

### Remove Scaffolding/Testing Sections Before Shipping
Launch blocker.

### Reference Section Structure
Use `<x-docs.variant level="3">` for sub-components. Match date-picker/select pattern. Container components listed before children.

### Reference Prop Order
1. `wire:model`, `value`, `name`, `format`, `type`, `placeholder`, `size`
2. Behavioral: `swatches`, `dropper`, `clearable`, `copyable`
3. `label`, `description`, `disabled`, `invalid`
**Never alphabetical.**

### Document Limitations Honestly
If `copyable` doesn't work with `type="button"`, say so explicitly.

## Decision Framework Deep Dive

### Filter 1: Consistency Check

Before making any design decision, check if existing GsmUi components already handle this pattern. The system must feel cohesive.

```php
// BAD: Inventing a new pattern
class Alert {
    public string $style = 'filled'; // New word
}

// GOOD: Following existing pattern
class Alert {
    public string $variant = 'solid'; // Matches feedback variants
}
```

**Consistency checklist:**
- Does the prop name match similar components?
- Does the variant name match the variant system?
- Does the sizing match the size scale?
- Does the color usage match the color system?
- Does the keyboard interaction match ARIA patterns?

### Filter 2: Simplicity Assessment

For every feature request, ask: "Does this add meaningful complexity without proportional value to most users?"

**Complexity indicators:**
- More than 3 new props required
- New CSS architecture needed
- New JavaScript behavior required
- New ARIA pattern needed
- New test category required
- Documentation grows significantly

**Value indicators:**
- Used by > 80% of users
- Solves a common pain point
- Improves accessibility
- Reduces code duplication
- Enables new use cases

**Decision matrix:**

| Complexity | Value | Decision |
|-----------|-------|----------|
| Low | High | Ship immediately |
| Low | Low | Ship (minimal cost) |
| High | High | Evaluate carefully, may ship |
| High | Low | Cut. Ship simpler version. |

### Filter 3: Browser-Native Check

The browser is the most optimized, accessible, and performant UI toolkit available. Use it.

**Native features to prefer:**
- `<details>` / `<summary>` for accordion
- `<dialog>` for modals
- `<select>` for simple dropdowns
- `<input type="date">` for date input
- `<input type="color">` for color input
- `<input type="range">` for sliders
- `<progress>` for progress bars
- `<meter>` for gauges
- `:has()` for conditional styling
- `:focus-visible` for focus management
- `popover` attribute for popovers
- `inert` for inert regions
- CSS `scroll-snap` for carousels
- CSS `aspect-ratio` for responsive media
- CSS `clamp()` for fluid typography
- `ResizeObserver` for size tracking
- `IntersectionObserver` for lazy loading
- `MutationObserver` for DOM changes

**When to build custom:**
- Native doesn't support the use case (e.g., multi-select with search)
- Native has poor accessibility (e.g., custom select with complex options)
- Native styling is insufficient (e.g., animated progress)
- Native behavior doesn't match requirements (e.g., virtual scrolling)

### Filter 4: Accessibility Design

Accessibility is not a feature — it's a requirement. Design for accessibility first.

**Accessibility-first design process:**
1. Define the keyboard interaction pattern
2. Define the ARIA roles and properties
3. Define the screen reader announcements
4. Build the visual UI on top

**Example: Select component**

```
1. Keyboard: Arrow keys navigate, Enter selects, Escape closes
2. ARIA: role="combobox", aria-expanded, aria-activedescendant
3. Screen reader: "Option 1 of 5, selected"
4. Visual: Dropdown, highlight, checkmark
```

### Filter 5: Themeability Check

Every component must work with design tokens. No hardcoded values.

```css
/* BAD: Hardcoded values */
.gsmui-button {
    background-color: #3b82f6;
    padding: 8px 16px;
    border-radius: 6px;
}

/* GOOD: Token-based values */
.gsmui-button {
    background-color: var(--gsmui-color-primary);
    padding: var(--gsmui-space-2) var(--gsmui-space-4);
    border-radius: var(--gsmui-radius-lg);
}
```

### Filter 6: External Precedent

Research how established libraries solve the same problem, then decide independently.

**Research sources (in order of priority):**
1. ARIA Authoring Practices Guide (APG) — accessibility patterns
2. React Aria — interaction logic, accessibility
3. Radix UI — component API design
4. Base UI — unstyled component patterns
5. ShadCN — Tailwind-based styling
6. Mantine — comprehensive component library
7. Headless UI — unstyled components
8. Tailwind UI — visual design reference

**Research process:**
1. Read the ARIA APG pattern for this component
2. Check React Aria's implementation notes
3. Review Radix's API design
4. Look at ShadCN's Tailwind classes
5. Check Mantine's prop names
6. Synthesize into GsmUi's approach

## Principle Deep Dives

### Punt Aggressively

**The cost of a feature is not just the initial implementation.** It's:
- Documentation
- Testing (unit, feature, browser, visual)
- Maintenance burden
- API surface area
- Cognitive load for users
- Combinatorial explosion with other features

**Decision rule:** If a feature doesn't clearly improve the experience for > 80% of users, cut it.

**Examples of punting:**
- Loading skeleton variants → Ship with one variant
- Custom animation durations → Use design tokens
- Programmatic API for every action → Keep it minimal
- Every possible ARIA attribute → Only the required ones

### Inline = Separate Component

**Rationale:** A component's fundamental shape determines its API, rendering, and interaction model. Changing the shape changes everything.

**Examples:**
- Date picker vs inline date picker → Different components
- Select vs combobox → Different components
- Modal vs drawer → Different components
- Tooltip vs popover → Different components

**Why not a prop?**
- Different ARIA patterns
- Different keyboard interactions
- Different slot structures
- Different positioning logic
- Different test requirements

### Most Useful Variant = Default

**The default should be the best experience.** Users shouldn't need to opt-in to the better version.

**Examples:**
- Button: `variant="primary"` (most common action)
- Input: `size="md"` (comfortable size)
- Select: `searchable` when > 10 options
- Date picker: with time picker when time is relevant

### Push Back on Feature Creep

**The conversation:**

```
User: Can we add a loading skeleton variant?
AI: I'd keep it simple and ship with the default skeleton.
User: But we need different skeleton shapes for different content.
AI: I'd keep it simple and ship with the default skeleton.
    The shape adapts to the content container naturally.
User: Ok, ship it simple.
```

**When to push back:**
- Feature adds > 3 props
- Feature requires new ARIA pattern
- Feature needs new test category
- Feature increases bundle size significantly
- Feature only benefits edge cases

### Accept Pragmatic Imperfections

**Examples of acceptable imperfections:**
- Color precision loss in round-trips (hex → RGB → HSL → hex)
- Invalid input silently reverts (no shake animation)
- Minor layout shift during loading
- Browser-native focus ring instead of custom

**Examples of unacceptable imperfections:**
- Missing ARIA attributes
- Broken keyboard navigation
- WCAG contrast failures
- Missing error states
- Broken responsive behavior

### Research External, Decide Internal

**Process:**
1. Research how 3+ external libraries solve this
2. Identify common patterns
3. Identify unique approaches
4. Decide what works for GsmUi
5. Document the decision

**Example: Date picker research**

| Library | Approach | Pros | Cons |
|---------|----------|------|------|
| React Aria | Headless, accessible | Excellent a11y | Complex API |
| Radix | Unstyled, composable | Clean API | Limited styling |
| Mantine | Full-featured | Many features | Large bundle |
| Flatpickr | Vanilla JS | Lightweight | Limited i18n |

**GsmUi decision:** Follow React Aria's accessibility model with Mantine's feature set and Tailwind styling.

### Outside-In Development

**Traditional (wrong) approach:**
1. Build PHP class
2. Build Blade template
3. Add JS behavior
4. Write tests
5. Write docs
6. Check if it works

**Outside-In (correct) approach:**
1. Write docs page with examples
2. Browse the docs page in Playwright
3. Verify visual states (base, hover, focus, disabled, invalid)
4. Verify interactions (click, keyboard, screen reader)
5. Build PHP class to match docs
6. Build Blade template to match docs
7. Add JS behavior to match docs
8. Write tests to match docs

### Dead Code is a Liability

**Why remove dead code:**
- Increases bundle size
- Confuses developers
- May have security implications
- Makes testing harder
- Slows down builds

**What to remove:**
- Unused methods
- Unused props
- Unused CSS classes
- Unused JavaScript functions
- Unused dependencies
- Polyfills for browsers no longer supported

## Anti-Pattern Deep Dives

### Boolean Props for Variants

**Why it's bad:**
- Explodes combinatorially (n boolean props = 2^n combinations)
- Hard to document
- Hard to test
- Hard to maintain
- Confusing API

**Example:**

```blade
<!-- BAD: 5 boolean props = 32 combinations -->
<x-gsmui:button 
    :primary="true"
    :outline="false"
    :ghost="false"
    :success="false"
    :danger="false"
/>

<!-- GOOD: 1 variant prop = 5 options -->
<x-gsmui:button variant="primary" />
```

### Inventing New ARIA Patterns

**Why it's bad:**
- Screen readers won't understand it
- Keyboard users won't know how to use it
- Testing tools won't validate it
- Users will be confused

**Example:**

```blade
<!-- BAD: Custom pattern -->
<div role="super-button" aria-custom="true">

<!-- GOOD: Standard pattern -->
<button type="button">
```

### Custom Color Parsing

**Why it's bad:**
- The browser already does this
- Native parsing is more accurate
- Native parsing handles more formats
- Custom parsing adds bundle size

**Example:**

```javascript
// BAD: Custom color parser
function parseColor(color) {
    // 200 lines of parsing code
}

// GOOD: Use canvas context
function parseColor(color) {
    const ctx = document.createElement('canvas').getContext('2d');
    ctx.fillStyle = color;
    return ctx.fillStyle; // Normalized hex
}
```

### Alpine for Complex State

**Why it's bad:**
- Hard to test
- Hard to debug
- Hard to share state
- No type safety
- No dev tools

**Example:**

```blade
<!-- BAD: Complex Alpine state -->
<div x-data="{ open: false, selected: null, search: '', filtered: [] }">

<!-- GOOD: Vanilla JS class -->
<gsmui-select></gsmui-select>
```

### Ternary Class Blocks

**Why it's bad:**
- Unmaintainable
- Hard to read
- Hard to override
- Breaks Tailwind's utility model

**Example:**

```blade
<!-- BAD: Ternary class block -->
<div class="{{ $disabled ? 'opacity-50 cursor-not-allowed' : '' }} 
            {{ $invalid ? 'border-red-500' : 'border-zinc-200' }} 
            {{ $size === 'sm' ? 'h-8 text-sm' : 'h-10 text-base' }}">

<!-- GOOD: Data attributes + layered classes -->
<div data-disabled="{{ $disabled }}" data-invalid="{{ $invalid }}">
```

```css
/* GOOD: Layered state classes */
.component { /* base */ }
.component[data-disabled="true"] { opacity: 0.5; pointer-events: none; }
.component[data-invalid="true"] { border-color: var(--gsmui-color-danger); }
```

### CDN Dependencies

**Why it's bad:**
- Breaks CSP
- Breaks offline mode
- Adds network request
- No version control
- Security risk

**Example:**

```blade
<!-- BAD: CDN dependency -->
<script src="https://cdn.example.com/library.js"></script>

<!-- GOOD: Bundled dependency -->
<script src="{{ Vite::asset('resources/js/app.js') }}"></script>
```

## Composability Deep Dive

### Sub-Elements Call Methods on State Root

**Rationale:** State should live in one place. Sub-elements are just UI, not state containers.

**Example:**

```javascript
// BAD: Sub-element has its own state
class SelectOption extends HTMLElement {
    constructor() {
        super();
        this.selected = false; // Duplicate state
    }
}

// GOOD: Sub-element calls parent method
class SelectOption extends HTMLElement {
    constructor() {
        super();
        this.select = () => {
            this.closest('gsmui-select').selectOption(this.value);
        };
    }
}
```

### Use detangle()

**Problem:** When Controllable syncs with internal state, it can create infinite loops.

**Solution:** `detangle()` breaks the loop by temporarily disabling sync.

```javascript
// Without detangle: infinite loop
controllable.setValue(newValue); // Triggers internal update
internalState.update(newValue); // Triggers controllable update
controllable.setValue(newValue); // Loop!

// With detangle: one-way sync
controllable.setValue(newValue); // Triggers internal update
detangle(); // Temporarily disable sync
internalState.update(newValue); // No loop
```

### Copy Sibling Structure Before Styling

**Rationale:** If two components serve similar purposes, they should look similar.

**Example:**
- Select trigger = Input-like → Copy input styles first
- Date picker trigger = Input-like → Copy input styles first
- Combobox trigger = Input-like → Copy input styles first

### Compose, Don't Inherit

**Rationale:** Composition is more flexible than inheritance.

**Example:**

```javascript
// BAD: Inheritance
class ColorPicker extends Slider { }

// GOOD: Composition
class ColorPicker extends HTMLElement {
    constructor() {
        super();
        this.hueSlider = document.createElement('gsmui-slider');
        this.saturationSlider = document.createElement('gsmui-slider');
    }
}
```

## Naming Deep Dives

### Short, Natural Prop Names

**Good:** `dropper`, `clearable`, `searchable`, `copyable`
**Bad:** `eye-dropper`, `is-clearable`, `is-searchable`, `allow-copy`

### -able Suffix for Boolean Opt-In

**Pattern:** `{behavior}-able`

**Examples:**
- `clearable` — can be cleared
- `copyable` — can be copied
- `searchable` — can be searched
- `expandable` — can be expanded
- `collapsible` — can be collapsed
- `draggable` — can be dragged
- `resizable` — can be resized
- `selectable` — can be selected

### Type for Trigger Variants

**Pattern:** `type="{trigger-type}"`

**Examples:**
- `type="input"` — trigger is an input
- `type="button"` — trigger is a button
- `type="native"` — uses native element

**Why not boolean props:**
- `:input="true"` vs `type="input"` —后者更清晰
- Single prop, single source of truth
- Extensible (can add new types)

### gsmui: Prefix for All Components

**Pattern:** `<x-gsmui:{component-name}>`

**Examples:**
- `<x-gsmui:button>`
- `<x-gsmui:input>`
- `<x-gsmui:select>`
- `<x-gsmui:date-picker>`

### --gsmui-* CSS Variables

**Pattern:** `--gsmui-{category}-{name}`

**Examples:**
- `--gsmui-color-primary`
- `--gsmui-spacing-4`
- `--gsmui-radius-lg`
- `--gsmui-text-sm`

## Styling Deep Dives

### Cursor Rules

```css
/* Navigation elements: pointer cursor */
a, [role="link"], [role="tab"] { cursor: pointer; }

/* Action elements: default cursor */
button, [role="button"], input[type="submit"] { cursor: default; }

/* Form elements: default cursor */
input, select, textarea { cursor: default; }

/* Disabled elements: not-allowed cursor */
[disabled], [aria-disabled="true"] { cursor: not-allowed; }
```

### Focus Ring Rules

```css
/* Native focusable elements: no custom focus ring */
button:focus-visible,
input:focus-visible,
select:focus-visible,
textarea:focus-visible {
    outline: none; /* Browser default is sufficient */
}

/* Custom focusable elements: slider thumb pattern */
[tabindex="0"]:focus-visible {
    outline: 2px solid -webkit-focus-ring-color;
    outline-offset: 2px;
}

/* Never use: focus:outline-none focus:ring-2 focus:ring-accent */
```

## JavaScript Deep Dives

### Use Utility Functions

```javascript
// BAD: Native DOM methods
element.setAttribute('disabled', '');
element.removeAttribute('disabled');

// GOOD: Gsmui utilities (MutationObserver implications)

```

### Move Logic from Alpine to JS When

**Move to JS when:**
- Disabled state affects behavior
- Multiple components need coordination
- Complex state management needed
- Testing required
- Performance critical

**Keep in Alpine when:**
- Simple show/hide
- Basic form binding
- One-way data flow
- No disabled state

### Fire Both input AND change

**Why:**
- `input` fires on every keystroke (live feedback)
- `change` fires on commitment (blur, Enter, mouse release)
- Matches native `<input type="range">` behavior

**When to fire each:**
- `input`: On every value change
- `change`: On blur, on Enter, on mouse release (for sliders)

## Component Design Patterns

### Compound Component Pattern

Compound components share state through a parent provider:

```blade
<x-gsmui:select>
    <x-gsmui:select.trigger>
        <x-gsmui:select.value />
    </x-gsmui:select.trigger>
    <x-gsmui:select.content>
        <x-gsmui:select.option value="1">Option 1</x-gsmui:select.option>
        <x-gsmui:select.option value="2">Option 2</x-gsmui:select.option>
    </x-gsmui:select.content>
</x-gsmui:select>
```

**Why compound components:**
- Each piece is independently composable
- Users can rearrange the structure
- State is shared automatically
- Accessibility is handled by the parent

### Renderless Component Pattern

Components that provide logic without markup:

```blade

```

### Polymorphic Component Pattern

Components that render different HTML elements:


```markdown
### Context
The select component needs a trigger element. Options are:
1. Native `<select>` element
2. Custom `<button>` trigger
3. Custom `<input>` trigger

### Decision

- Select (uses button trigger)
```

## API Design Principles

### Principle 1: Consistent Naming

| Pattern | Example | Anti-Example |
|---------|---------|--------------|
| Short names | `size` | `componentSize` |
| Natural names | `disabled` | `isDisabled` |
| -able suffix | `clearable` | `canBeCleared` |
| type prop | `type="button"` | `:button="true"` |

Ship with the fewest props possible. Add props only when users need them.

Every prop has a default that works for 80% of use cases.

### Focus Management

```
Component opens
    ↓
Focus moves to:
    - First focusable element in component
    - Or: Element specified by initialFocus prop
    ↓
Component closes
    ↓
Focus returns to:
    - Element that triggered the component
    - Or: Element specified by finalFocus prop
    - Or: Element that had focus before component opened
```

### Focus Trap Pattern

```javascript
// Modal focus trap
function trapFocus(modal) {
    const focusableElements = modal.querySelectorAll(
        'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
    );
    
    const firstElement = focusableElements[0];
    const lastElement = focusableElements[focusableElements.length - 1];
    
    modal.addEventListener('keydown', (e) => {
        if (e.key !== 'Tab') return;
        
        if (e.shiftKey) {
            if (document.activeElement === firstElement) {
                lastElement.focus();
                e.preventDefault();
            }
        } else {
            if (document.activeElement === lastElement) {
                firstElement.focus();
                e.preventDefault();
            }
        }
    });
}
```

- `<input>` trigger: Wrong ARIA pattern

### Example 2: Modal Component

**Context:** Need a modal dialog for confirmations and forms.

**Decision:** Use `<dialog>` element with progressive enhancement.

**Rationale:**
- Filter 3 (Browser-native): `<dialog>` has built-in modal behavior
- Filter 4 (Accessibility): `<dialog>` has built-in focus trapping
- Filter 6 (External precedent): Base UI uses `<dialog>`

**Alternatives Considered:**
- Custom overlay: More work, less accessible
- Alpine.js modal: Harder to test

### Example 3: Tooltip Component

**Context:** Need a tooltip for hover information.

**Decision:** Use CSS `popover` attribute with JS fallback.

**Rationale:**
- Filter 3 (Browser-native): `popover` attribute handles positioning
- Filter 4 (Accessibility): Native tooltip semantics
- Filter 6 (External precedent): Radix uses `popover`

**Alternatives Considered:**
- Alpine.js tooltip: More JavaScript
- Custom positioning: More complex

## Component Design Summary

### Key Takeaways

1. **Consistency over cleverness** — Follow existing patterns
2. **Simplicity over completeness** — Ship with less, add later
3. **Browser-native over custom** — Use what the browser provides
4. **Accessible by default** — Design for accessibility first
5. **Themeable via tokens** — Use CSS custom properties
6. **Composable via slots** — Use slots for complex content
7. **Outside-in development** — Start from docs, work inward
8. **Dead code is a liability** — Remove unused code

## Component Design Best Practices

### Do's

- Follow existing patterns
- Use design tokens
- Include ARIA attributes
- Support keyboard navigation
- Test all states
- Document all props
- Use slots for complex content
- Support dark mode

### Don'ts

- Invent new ARIA patterns
- Use hardcoded colors
- Skip accessibility
- Ignore keyboard users
- Leave edge cases untested
- Forget documentation
- Use props for complex content
- Forget dark mode
